# Release notes: a dead Tick is noticed

The notes for the minor release that ships the daily Tick check ([#461](https://github.com/jrey8343/fabrik/issues/461), ADR-0009's addendum). Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- **A Product repo whose hourly Tick has stopped gets a Dead-tick issue.** Every morning at 07:00 in the Operator's time zone, a new job on the `fabrik-runs` store's caller, the Tick check, reads each Product repo the Fabrik App's installation lists. A repo's Tick is dead when no Tick has started its jobs in the last 25 hours (no `tick / …` check run on a recent `main` commit) and `fabrik.yml` has been on `main` at least that long. A Tick that GitHub refuses at startup, as when a caller job grants too little after a bump (#422), or that never fires, because GitHub disabled the workflow after 60 days without activity or the caller lost its schedule, counts as dead. A Tick that starts and then fails a job doesn't.
- **The Dead-tick issue** is titled "The hourly Tick hasn't run since <time>", labelled `fabrik:dead-tick` and `ready-for-human`, and assigned to the Operator, so it's a push. It gives the last started Tick's time, a link to its run and the release it ran on, and leads with "The Tick stopped after the bump from vX to vY" when the pin has changed since. Its steps: read the newest run's error on the Actions tab for `fabrik.yml`, check the workflow is enabled, and compare the caller's job permissions with the release's notes, or re-run Setup. There's never more than one open per repo. The check creates the label in a repo that lacks it.
- **It closes itself.** The first Tick to run in the repo comments when it started and on which release, and closes the issue as completed. The daily check does the same once it sees a started Tick, which covers a Product repo still pinned to a release from before this one. Closing it by hand while the Tick is still dead has the next morning's check open a fresh one.
- **A Product repo the Fabrik App can't reach gets an issue in `fabrik-runs` instead**, titled "The Fabrik App can't reach owner/name", with the same labels and assignee, saying to reinstall the App on it. That's a repo the installation lists that refuses the App's reads, or one with Run records in the store from the last 30 days that the installation no longer lists. The check closes it once it reads the repo again.
- The store's caller now runs on two schedules: Mondays at 07:00 for the Weekly summary, as before (and by hand from the Actions tab), and every day at 07:00 for the Tick check. The check mints its own Fabrik App token, with Checks read, Contents read and Issues write on every installed repo. The App already has all three, so its permissions don't change, and the Weekly summary's tokens are unchanged.
- `fabrik:dead-tick` joins Setup's labels, and the caller template names the run a Dead-tick issue's opening starts `Opened #<n>`. A caller set up before still names it `Triage #<n>`, which is only its name on the Actions tab.
- **Why a minor:** the check is opt-in ([#139](https://github.com/jrey8343/fabrik/issues/139)). Until the store's caller is rewritten, nothing runs and nothing breaks: an old caller has no daily schedule and no Tick check job, and files the Weekly summary as before. There's no Product-repo shim change, no new secret and no new App permission, and no Kit config field. A Product repo only merges the bump PR.

## To turn it on

The check runs from `fabrik-runs`, so it's turned on once, for every Product repo, by rewriting the store's caller. Until then nothing runs.

1. **Bump the Pilot first.** Merge this release's bump PR in the Pilot, so its Tick closes its own Dead-tick issue.
2. **Bump the store's caller to this release.** In `fabrik-runs`, merge Dependabot's bump PR for `.github/workflows/weekly-summary.yml` (or use "Check for updates" on its Dependabot page). Do this before step 3: Setup rewrites the store's caller at the release it already pins, and a caller whose Tick check job pins a release from before this one names a workflow that doesn't exist there, which fails every run of it at startup, the Weekly summary's included.
3. **Re-run Setup in the Pilot at this release**, giving the same time zone as before. Its plan rewrites `fabrik-runs`' `.github/workflows/weekly-summary.yml` with the daily schedule and the `tick-check` job, and creates the `fabrik:dead-tick` label in the Pilot.
4. **Check it the next morning.** The store's Actions tab has a run of the caller at 07:00 with a green Tick check job, whose step summary has a Tick check section naming each Product repo's last started Tick. The Tick check runs only on its schedule, not by hand. To see the issue, disable the Pilot's `fabrik.yml` workflow for a little over a day: the next check opens a Dead-tick issue, and the first Tick after you enable it again closes it.
5. **Then the other Product repos.** The check already covers them. Merge the bump PR in each, so its own Tick closes its Dead-tick issue too, and re-run Setup there when you next do, for the label.
