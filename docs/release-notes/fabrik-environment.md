# Release notes: the Kit's tokens in the `fabrik` environment

These are the notes of this part of the major that carries the Kit's Operator sessions ([Spec: The Kit's tokens in the `fabrik` environment, which only the default branch may use](https://github.com/jrey8343/fabrik/issues/915)): the Kit's three service-account tokens stop being repo-level Actions secrets, which GitHub gives to a workflow run on any ref, a workflow pushed on a branch included, and become the secrets of one GitHub environment that only the default branch may use. Each of the major's five parts has its own notes, and this is this part's. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## Release-note line

The Kit's three service-account tokens are the secrets of the `fabrik` environment, a GitHub environment in each Product repo, and one in `fabrik-runs`, which only the default branch may use, so a workflow run on any other ref is given none of them, a workflow pushed on a branch included. A pull request review's run, the one run of the Loop's that GitHub doesn't start as the default branch, reads no token and hands off to a run on the default branch. A major: the caller workflow gains a trigger, and each Product repo moves its tokens over two runs of Setup.

## What changed

- **Each Kit job that reads a token names the `fabrik` environment** ([#928](https://github.com/jrey8343/fabrik/issues/928)). Every job of the Kit's four reusable workflows, `loop.yml`, `schedule.yml`, `weekly-summary.yml` and `tick-check.yml`, that reads a service-account token names the caller repo's `fabrik` environment, with `deployment: false`, so GitHub records no Deployment for a Kit job (ADR-0021). GitHub gives such a job the environment's secrets only on a ref the environment's rules let through, and fails it before its first step on any other. A job that reads no token names none: `loop.yml`'s `review-checks`, `rerun-checks`, `rerun-wait` and `review-hand-off`, and the `kit` job of each of the other three. The name is one constant, `KIT_ENVIRONMENT`, `fabrik`, in `src/kit/environment.ts`. The tokens keep their names, and the caller workflow's three `secrets:` lines don't change: a secret the caller passes by name reaches the job from the environment.
- **A pull request review's run reads no token and hands off** ([#927](https://github.com/jrey8343/fabrik/issues/927), [#926](https://github.com/jrey8343/fabrik/issues/926)). GitHub runs a review as the pull request's merge ref, never as the default branch, so the `fabrik` environment refuses it. On a `pull_request_review` event the Kit job is skipped, and with it every job that needs it, and the run runs one job alone, `review-hand-off`. It holds `actions: write` and nothing else, names no environment, reads no secret and checks nothing out: it starts the caller workflow on the default branch by `workflow_dispatch`. The caller workflow gains that trigger, with two required string inputs, `pull_request`, the pull request's number, and `review`, the review's id, and the run it starts is named `Review on PR #<number>, handed off` on the Actions tab. That run believes neither input, since whoever can start a workflow can start it with any. Each input must be a positive whole number with no leading zero, or the run does nothing. The Kit job, the claim job and the push job then each read the review from GitHub, with their own client, and act only on a review that is there, on that pull request, submitted and not dismissed, and written by the Operator (Kit config's `operator`, or the repo's owner), whatever the case of the login. For such a review the run plans what the review's own event planned before, from GitHub's copy of the review, a Comment or Approve review as well as a Request changes. For any other it plans nothing, and the Kit job's log says so.
- **A Request-changes run uses the default branch's caller workflow and Kit config** ([#927](https://github.com/jrey8343/fabrik/issues/927)), where it used the pull request's own copy of both. It starts one run after the review's own, and if the hand-off fails, the check for an undelivered Request changes (ADR-0015) finds the review. A Request changes from anyone but the Operator now gets no line at all: a person's used to get one line on the agent PR, saying only the Operator's reviews start runs, and the run a review hands off to plans nothing for it. That line is the one behaviour the move loses.
- **Setup makes the `fabrik` environment and holds it to the default branch** ([#929](https://github.com/jrey8343/fabrik/issues/929)). On every run Setup reads the Product repo's `fabrik` environment, and whenever it isn't held it plans one step, first among the plan's steps, so a refusal stops Setup before it applies any other. An environment is held when it is set to "Selected branches and tags" and its rules are exactly one, a branch rule naming the default branch. Its being there, or its setting, is never taken for its being held: GitHub makes an environment a workflow names when the repo lacks it, with no rule, and one with no rule gives its secrets to every ref. The step's calls go in this order: a PUT of the environment that sends only its branch policy; the rule naming the default branch added, if it isn't there; only then every other rule deleted; and the rules read back. Unless they read back as exactly the one rule, Setup stops and stores no token. The plan names the change from what to what, so a rule that was deleted, an environment GitHub made and a renamed default branch are each put right and said. There is no fallback to repo-level secrets: when GitHub refuses the PUT, as it should on a private repo whose GitHub plan has no environments, Setup stops, giving GitHub's answer and the plans that have them, GitHub Pro for a personal account's repo, or GitHub Team for an organization's. A read of the environment that GitHub refuses with anything but a 404 stops Setup too, with GitHub's answer in what it says.
- **The three tokens are in the environment, under new service accounts** ([#930](https://github.com/jrey8343/fabrik/issues/930)). A token is missing when the `fabrik` environment lacks it, wherever else it sits, so a repo-level secret of its name doesn't count. Setup makes a missing one with a new read-only service account, `fabrik-<owner>-<repo>-agent-env`, `-implement-env` or `-push-env`, reading the vaults its role read before, and stores it straight into the environment as `FABRIK_OP_AGENT_TOKEN`, `FABRIK_OP_IMPLEMENT_TOKEN` or `FABRIK_OP_PUSH_TOKEN`, with `gh secret set --env`, on its stdin, and never as a repo-level secret. Before it makes an account, the step reads the environment's rules itself, whether or not this run changed the environment, and stops with no account made unless they are the one rule. 1Password shows a token once and GitHub never gives a secret back, so a repo already on the Kit gets three new accounts: the ones it had are named the same with no `-env`.
- **The repo-level tokens are deleted once the default branch's Kit names the environment** ([#931](https://github.com/jrey8343/fabrik/issues/931)). Setup reads the caller workflow that the default branch's tip on `origin` holds, never the checkout's own copy. Once it pins one release of Setup's own major or a later one, nothing reads the repo-level tokens, and Setup plans, after every new account, a step for each repo-level secret that carries one of the three names, which deletes it by `gh secret delete`, and never a repo-level secret of any other name. It names the old service accounts, `fabrik-<owner>-<repo>-agent`, `-implement` and `-push`, for the Operator to delete on 1Password's site, under the plan and again in the run's last lines: `op` has no command that deletes one, and their tokens still work until then, though they sit nowhere on GitHub. Setup says it on that run alone, since on a later one it can't tell that the accounts are still there. On any other run where one sits at repo level, Setup deletes nothing and says they stay until the setup PR is merged and Setup runs again.
- **`fabrik-runs`'s token moves the same way** ([#932](https://github.com/jrey8343/fabrik/issues/932)). On a run where the Operator's time zone is answered, as the store's other steps are planned, Setup reads the store's own `fabrik` environment and plans it held to the store's own default branch, right after the Product repo's own and ahead of every other step, or, for a store the run makes, after the store's files, whose first commit makes that branch. The store's one token, the push account's, goes into it under a new account, `fabrik-<owner>-fabrik-runs-push-env`. Setup commits the store's caller workflow straight to its default branch, so the store's repo-level `FABRIK_OP_PUSH_TOKEN` is deleted only on a run that found the store's caller workflow already pinning Setup's major or a later one, never on the run that writes that caller, and that run names the old `fabrik-<owner>-fabrik-runs-push` account. Until then Setup says the secret stays. With `--no-time-zone` nothing of the store is planned, and nothing is said of it.
- **Setup's report** ([#933](https://github.com/jrey8343/fabrik/issues/933)). A new part of Setup's output, headed `Setup's report:`, said on every run under the plan, after its notes, and again in the run's last lines, and never in the setup PR, where a public repo would show a secret's name. It has a line for each repo-level Actions secret that isn't one of the Kit's three, by name, saying a workflow run on any branch can read it, and then the Kit's rule for a Product repo's own credentials: a credential that can reach production belongs in an environment held to the default branch alone, or in a role taken by OIDC whose trust names that environment and not the whole repo, and only test and preview credentials sit at repo level. A repo with none of its own gets one line saying so. When Kit config's `production` block names an environment, a last line says whether it is held to the default branch alone, by the test above, with its rules when it isn't, or that the repo has no environment of that name. Setup reports and never blocks: no line changes a step or a note of the plan, and Setup makes and changes none of the repo's own environments or secrets, judges no secret by its name, and doesn't look inside a cloud account's trust policy.
- **ADR-0004 and the README** ([#934](https://github.com/jrey8343/fabrik/issues/934)). ADR-0004 says where the tokens are and why, the options it weighed and what the move costs. The README's list of what Setup does, its paragraph on a repo's move and its Merge gate section say the same.
