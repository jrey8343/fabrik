# Release notes: Visual evidence

The notes for the minor release that ships Visual evidence on UI pull requests ([#153](https://github.com/jrey8343/fabrik/issues/153)). Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- The Kit config gains two optional blocks, both off by default. The starter Kit config now spells them out as `"ui": null` and `"preview": { "url": null }`.
  - `ui`: `paths`, at least one glob of the files whose change makes a pull request UI; `serve`, the command run in the background after `sandbox.build` to serve the branch; `url`, the local `http://` or `https://` base URL it serves on, which capture waits for and captures routes under; and optionally `before_url`, the production site's base URL, and `default_routes`, each a path starting with one `/`.
  - `preview`: `url`, a template that may use only `{pr}`, `{branch_slug}` and `{sha}`, and must fill in to an `http://` or `https://` URL.
- **A repo without a `ui` block never captures.** The capture step still runs once the Implementer's agent has ended well, but captures nothing, passes out no result, uploads nothing and adds no step-summary line of its own. The Kit job's step summary for each Implement run says in one quiet line that Visual evidence is off and that `/fabrik-setup` turns it on. An invalid `ui` or `preview` block is reported with every problem at the start of the run, like any other Kit config error. `.fabrik/config.json` is already a Trust-root file, so no agent can turn Visual evidence off or narrow its paths.
- **Whether a pull request is UI is the Kit's call, never an agent's.** The agent runs on the same runner before capture, so the push job, which the agent can't touch, decides. A PR is UI when the run's changes match `ui.paths` in the Kit config the push job reads from the default branch, or when the Fabrik App already wrote an evidence marker in the PR's body, since a Retry's changes hold only its own commits. A PR that isn't UI gets no evidence section, no images and no extra text in the Reviewer's prompt, whatever capture passed out. The Implement job decides only whether capture is worth its time, from the branch's diff against the default branch.
- **On a UI pull request, the Implement Sandbox job captures UI evidence** once the Implementer's agent has ended well, on first, Retry and Request-changes runs alike. It installs Chromium, runs `sandbox.build`, stops anything already answering on `ui.url`'s port (such as a server the agent left running), starts `ui.serve`, and waits up to 3 minutes for `ui.url` to answer at all. A Kit script then drives headless Playwright through each route, giving each page up to a minute to load, for the After screenshots: PNGs one screen high from the top of the page, not the whole page, at a mobile width (390 by 844) and a desktop width (1440 by 900). With `before_url` set it then takes Before screenshots of the same routes from the production site, and without one it skips Before quietly. Capture uses no model turns, no Playwright MCP and no video, so it costs no Subscription usage.
- **Build and server get `sandbox.env`, but not `sandbox.secrets`.** They run with the runner's env and `sandbox.env` over it, never the 1Password step's outputs: neither the Claude token, nor any test secret `sandbox.secrets` lists, nor a GitHub or Actions token reaches them. A build or server that needs one of those secrets fails capture.
- **The timeout budget.** The capture step has its own 20-minute timeout, and capture stops itself 2 minutes short of it, so it still writes what it took. The agent step now stops at the Implement role's own timeout, and the Implement job's timeout is that, plus capture's 20 minutes, plus 10 for its other steps: 90 minutes by default. So a slow capture never cancels the job before the Implementer's result uploads, and an agent that runs out of time still reads as a timeout, as before. A capture step that hits its own timeout passes out no result, which the PR's section names as `no-result`.
- **The routes:** every route the Ticket names, as the path alone in backticks such as `/book` (in a code span, not a fenced code block), is always captured. The routes the Implementer names in its output, a new optional `routes` list, come next, and `ui.default_routes` is used only when neither names one. Each route is captured once, and the list stops at 4 routes so capture stays fast. The Implementer's routes and the defaults only fill the places left under 4, but every route the Ticket names is kept past it: a Ticket naming 5 routes gets all 5 captured, and none of the Implementer's.
- **The pull request links a gallery.** It's one self-contained HTML page with every screenshot inlined, Before and After side by side for each route and viewport, with no image cap. It's uploaded as an unzipped artifact, so it opens in one click, and its link is built from the push job's own run, never from an address the agent's runner passed out. It's kept 30 days, as is the zipped artifact of the screenshots and the capture result. A capture that took no screenshot keeps no gallery. The PR body gets an evidence section between the summary and `Closes #n`, ending in a hidden marker, `<!-- fabrik:ui-evidence {"run":…,"artifact":…,"failure":…} -->`, that records which Implement run holds its images, and why its capture failed (`null` when it captured), so a Reviewer with no screenshots to read still hears the reason. The section holds:
  - the gallery link;
  - each captured route, with why it was chosen: named by the Ticket, named by the Implementer, or a default route;
  - any screenshot whose page answered with a server error (5xx), flagged as an error page rather than the design;
  - the preview link, or why there isn't one;
  - when capture failed, why, with any screenshots it took first. The reasons are:
    - `build-failed`: `sandbox.build` failed, so there was no build to serve;
    - `server-did-not-start`: nothing answered at `ui.url` once `ui.serve` ran;
    - `timeout`: capture ran out of time;
    - `no-routes`: neither the Ticket nor the Implementer named a route, and `ui.default_routes` is empty;
    - `error`: anything else capture caught, such as the browser failing to install or `ui.url`'s port not freeing, which the Implement job's log shows;
    - `no-result`: the push job found the PR is UI but got no capture result it could read, as when the capture step hit its own timeout or crashed.
- **The Kit's section is the only one.** Any evidence section or marker in the Implementer's own summary is stripped before the body is built, so no agent can forge where evidence is kept, and a Retry's agent never sees the old section. Routes are agent text, so they show as code and mention nobody.
- **Capture never blocks a pull request and never uses up a Retry.** Every failure is caught and named in the evidence section, and is never an Infrastructure failure. The PR still opens.
- **Every Retry and Request-changes run on a UI pull request captures again** and replaces the evidence section, so the evidence always matches the PR's head.
- **The Reviewer sees the screenshots.** On a UI pull request the Review job, which gains read access to Actions artifacts, downloads the screenshots and capture result the PR's marker names. A download that fails, such as after the 30 days, never fails the Review. The Reviewer's runner copies at most 8 of them into `fabrik-ui-evidence/` in its working directory, in this order: After before Before, mobile before desktop, then the Ticket's routes, the Implementer's and the defaults. So with 4 routes the 8 are all After, and the Reviewer sees no Before. With more than 4 it gets every route's mobile After first. With 1 or 2 routes and `before_url` set, it gets every screenshot. The review prompt gets a UI evidence block naming each image's route, viewport and side, and flagging any server error. The Reviewer judges three things: whether the screenshots show what the Ticket asked for, plain breakage (a blank or error page, content spilling over at mobile width, overlapping or cut-off content), and regressions against Before on parts the Ticket didn't touch. Taste stays the Operator's. A visual failure is an ordinary Execution flaw that names the route and the screenshot, so the Verdict means what it always has. When the PR's head has moved on since capture, as after the Operator's own push or a Retry's rebase, the block says the screenshots were captured at that earlier commit, so later commits may change what they show. When capture failed or left nothing to read, the block says why, and the Reviewer reviews the code as usual.
- **The preview link.** With `preview.url` set, the push job fills in the template once it has pushed a UI pull request. `{pr}` is the PR's number, the one it has just opened on a first run, and `{sha}` the full head commit the push left the branch at. `{branch_slug}` is the PR's branch in lower case, with each run of characters other than `a` to `z` and `0` to `9` made one `-`, and no `-` at either end, so `fabrik/ticket-12` is `fabrik-ticket-12`. The Kit never shortens it, though a host may shorten a long one. Until the preview answers, the section says it's linked once it does.
  - The push job then polls the URL: at once, then every 15 seconds, for 4 minutes at most, giving each request 10 seconds. The preview **answers** when it returns a 2xx status once redirects are followed. A 404 from a host still building, a server error, a 401 or 403, or no answer at all counts as not yet.
  - When it answers, the section links it, and when it doesn't, the section says it never answered. The step edits the PR's body as it stands once polling is done, changing only that line of the section its own run wrote, so the Operator's edits stay, and a section a later run has replaced is left alone.
  - The step has its own 5-minute timeout inside the push job's 10 minutes, never fails the job, and runs before the Run record step. Its Fabrik App token can edit pull requests and nothing else. The Kit never calls a hosting provider's API and needs no new secret.
- To ask for a visual change, the Operator uses Request changes and cites a screenshot. There's no thumbs-down or reaction trigger for rework (ADR-0007).
- `/fabrik-setup` gains an opt-in step, Visual evidence. It asks for `ui.paths`, `serve`, `url`, `before_url`, `default_routes` and `preview.url`, and writes them into `.fabrik/config.json` in its setup PR, keeping every other setting. Its wizard gains a stage, "Visual evidence", that checks the Kit config has a `ui` block. Without the step's answers, setup leaves the Kit config alone.
- The release pins Playwright (`playwright-core`) at one exact version beside Sandcastle and the Claude Code CLI, and Dependabot bumps it. Capture installs its Chromium when it runs.
- **Why a minor:** `ui` and `preview` are new Kit config blocks that default to off, and turning Visual evidence on is an opt-in Operator setup step ([#139](https://github.com/jrey8343/fabrik/issues/139)). Until a repo takes that step, no PR is captured, and runs note quietly that Visual evidence is off. There are no shim changes: the caller workflow already grants the `actions: read` the Review job now uses. No Kit config field is renamed or removed. So a Product repo only merges the bump PR.

## To turn it on

The setup step is Visual evidence: `/fabrik-setup` with its answers, whose wizard stage "Visual evidence" checks it's on. Turn it on for the Pilot now, with no preview. The other Product repos can take the step whenever they want it.

1. **The Pilot now.** Merge this release's bump PR in the Pilot only. Then re-run `/fabrik-setup` at this release there, saying yes to Visual evidence, and answer:
   - `ui.paths`: the files that make up its pages, such as its page, layout, component and style files;
   - `ui.serve` and `ui.url`: the command that serves its built site, and the local URL it serves on;
   - `ui.before_url`: its production site, so Before comes from the live site without a second build;
   - `ui.default_routes`: at least `/`;
   - `preview.url`: none. Setup writes `"preview": { "url": null }`, which the Kit reads as `preview: null`, so no preview is linked. The Pilot has no preview host, and setting one up is a separate Operator decision.

   Before merging, check that the Pilot's `sandbox.build` and `ui.serve` work without its `sandbox.secrets`, which they don't get. If either needs a value, give it a non-secret stand-in in `sandbox.env`, or capture will fail with `build-failed` or `server-did-not-start`. Then merge the setup PR: the push job reads the `ui` block from the default branch. Re-running setup with the same answers then plans nothing for it, and the wizard's "Visual evidence" stage says it's on.
2. **Check it on a real UI issue** in the Pilot before the release goes anywhere else. Open an issue that changes a page and names its route in backticks, and let it run to its draft PR's Review:
   - the Implement job's step summary says, under **UI evidence**, how many screenshots it captured of how many routes;
   - the PR's evidence section links a gallery that opens in one click, with Before and After at mobile and desktop widths for each route, and says Kit config declares no preview;
   - the routes it lists include every one the Ticket named, each with why it was chosen;
   - the Review job's "Download the UI evidence" step succeeded, and the Review run's transcript shows the Reviewer opening the screenshots in `fabrik-ui-evidence/`; a visual problem comes back as an Execution flaw that names the route and the screenshot;
   - a Retry or Request-changes run replaces the evidence section with its own;
   - a PR that touches no file in `ui.paths` gets no evidence section.
3. **Then the other Product repos, when they want it.** In each, merge the bump PR: the repo runs as before, with one quiet line in each Implement run's Kit job step summary saying Visual evidence is off. To turn it on, re-run `/fabrik-setup` and answer its Visual evidence step, after the same check that `sandbox.build` and `ui.serve` work without `sandbox.secrets`. A repo with a preview host gives `preview.url`, checking first that the host names a branch's preview as `{branch_slug}` does. A repo with no public production site leaves `before_url` out and still gets After evidence. A repo with no UI never takes the step.
