# Release notes: UI evidence from Evidence shots

The notes for the minor release that lets a Product repo's UI evidence come from the Evidence shots its own Journeys take, which one of its Required checks uploads, and makes an Implementer that shows nothing of its change an Evidence miss ([#813](https://github.com/jrey8343/fabrik/issues/813), ADR-0032, ADR-0033). Every Ticket of #813 has its part here. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- **A second source of UI evidence.** Route capture visits routes, one page load each, so it can't reach a step of a multi-step form, a box shown only after a choice, or a list that is empty until records exist. A Product repo whose Journeys, its end-to-end tests, already reach those states can now have them take the pictures. A Journey marks a moment with one line and a name, such as `composer: draft ready`, and a helper of the Product's own takes an Evidence shot there at the Kit's two sizes. The Required check that runs the Journeys uploads the shots and a `manifest.json` as an artifact, named `fabrik-evidence-shots` by default, and the Kit reads it at the pull request's head, so the pictures follow the head through the Operator's pushes and the Kit's rebases. A Product repo uses one source or the other.
- **What a Product repo builds.** The README's [Evidence shots](../../README.md#evidence-shots) section is the contract: the artifact, the manifest, the two sizes, the rules the Kit reads them by, an upload step that runs whether the Journeys passed or failed, and a reference helper for Playwright to copy. The helper, the shots and the upload step are the Product repo's own code: nothing the Kit versions runs inside its tests.
- **The artifact is untrusted.** The pull request's own code writes it, so the Kit reads only `manifest.json` and the images it lists, and runs none of it. An image's file name is flat and ends `.png`, the file starts as a PNG does, and it is at most 1 MB. A name is at most 80 characters on one line, of letters, digits, spaces and `: - _ / . ,`. A run has at most 100 shots, and the section counts those dropped past them. An entry that breaks a rule is dropped with its reason, two entries with one name make that name ambiguous, and a manifest that is missing, isn't JSON or has another `version` can't be read at all.
- **The `ui.shots` block in Kit config**, such as `{ "check": "e2e", "artifact": "fabrik-evidence-shots" }`. `check` is required and must be one of `sandbox.checks`; `artifact` defaults to `fabrik-evidence-shots`. With it set, the Implement job captures no routes: no browser is installed and nothing is built or served for capture, and the Kit job's step summary says in one line which check UI evidence comes from. `paths` still says which pull requests are UI, and `serve`, `url` and the sign-in fields stay, since a prototype turn still captures with them.
- **Kit config refuses route capture's fields beside `shots`.** `default_routes`, `before_url` and `resolve_route` are each refused by name beside `shots`, even set to `null` or `[]`, so a `ui` block can't say both. `/fabrik-visual-evidence` wrote `"before_url": null` and `"default_routes": []` into every `ui` block it wrote until now, so a hand edit that adds `shots` must delete those fields, not empty them. Running `/fabrik-visual-evidence` takes them out for the Operator.
- **The Implementer names the shots that show its change, or says nothing visible changes.** On a Product repo with `ui.shots`, its prompt tells it to find names by reading the Journeys, never to name a shot that isn't in a Journey's code, to add a shot to the Journey that reaches a changed state with none, and, when nothing a person sees changes, to say so and why. Its output gains two optional fields: `shots`, at most four Evidence shots by name, a fifth dropped and said so, and `nothingVisible`, one sentence. `routes`, and routes a Ticket names in backticks, are ignored there. The latest run that says anything wins: names replace the pull request's, a sentence clears them, and a run that gives neither keeps what the pull request had, so a Retry never wipes a right picture.
- **The section waits for the check.** From the Implement run's push until the Review's jobs have read the artifact, the pull request's evidence section names the check it is waiting for. Once the Required checks have been waited for, the review job finds the newest attempt of the named check at the head, downloads its artifact with the token it already holds, and builds an Evidence page of every shot of the run at both sizes, the named ones first, kept unzipped in the Review's own run for 30 days. The section then lists the named shots, each with its Journey and path, says which head they are from, and gives each miss and failure in the Kit's own sentence. The Reviewer sees the named shots alone, at most 8 images, mobile before desktop, and checks a `nothingVisible` sentence against the diff: a diff that plainly changes what a person sees is an Execution flaw.
- **An Evidence miss uses a Retry.** A UI pull request whose Implementer named no shot and gave no sentence, or named a shot the green check didn't produce (`not-produced`, `ambiguous-name` or `refused`), gets the Kit's own Execution flaw at that head, with source `evidence-miss`, before the Reviewer runs. Naming nothing is judged at once, in the Implement run's push job; a shot not produced, once the named check has finished green. Its comment names what was missed and, once the check has run, the shots it did produce. It calls for a Retry, never a Touch-up, and counts in the Ticket's two Retries, beside the Reviewer's findings.
- **With no Retry left, nothing is sent back.** The pull request goes on to Review with the miss shown, reaches the Merge gate on a pass, and its Digest marks the changed screen as not proven. The Operator can ask for the shot with Request changes. Nothing is sent back either at a head the Operator pushed or the Kit's plain rebase made, when the named check is still red after the Kit's re-run (the Reviewer's judgment of the check decides the Retry), or for a shot with one of its two sizes, which counts as produced with the missing size listed.
- **A failure of the wiring blocks nothing.** A green check that uploaded no artifact of that name (`no-artifact`), or a manifest that can't be read (`bad-manifest`), is shown in the section as the Product's wiring, the Operator's to fix, and never sends back or uses a Retry.
- **A Digest item's picture may be a named shot.** On a pull request whose UI evidence is Evidence shots, an item's `picture` is one of its named shots that was produced, by name, compared exactly, in place of a captured route. The Digest writer is told those names, or that there are none, and a changed screen with no such shot is an item that is not proven.
- **`/fabrik-visual-evidence` asks where UI evidence comes from.** It suggests Evidence shots when the repo has Journeys run by one of `sandbox.checks`, asks which check runs them and the artifact's name, offering the default, and tells the Operator what the Product repo's side needs first and that the workflow change is theirs to make. It names each of `default_routes`, `before_url` and `resolve_route` the `ui` block holds and takes them out only once the Operator confirms, and going back to captured routes takes `shots` out. The writer checks a `shots.check` against the Kit config's own `sandbox.checks`, and the answers gain `remove`, the `ui` fields the Operator confirmed taking out.
- **For readers of the read library:** it exports the manifest's reader and the artifact's rules (`readShotsManifest`, `namedShots`, `isShotName`, `droppedShotSentence`, `SHOT_LIMIT`, `SHOT_IMAGE_MAX_BYTES`, `SHOT_NAME_MAX_LENGTH`, `DEFAULT_SHOTS_ARTIFACT` and the rest), the shots marker's reader `shotsMarkerIn`, `producedNamedShots`, and the Kit's sentences for a miss and a failure, so a reader reads a head's shots from the check's artifact, with its own credential, as the Kit does. This is how a Plain pull request, a Pairing session's, or a head the Operator pushed at the Merge gate gets its pictures: the Kit writes no section where no Review runs. A row gains `shots`, its named shots with their Journey, path, whether each was produced, and links in the preview and in production built from the path; `evidence` is null on such a row. `Facts` gains `shotsMarkers`, which every gather fills in. It is required: a reader that builds `Facts` itself must give it (`homeFactsOf` defaults it to `[]`), or it fails to compile. `Facts` cached as JSON by an earlier release, which has none, still reads in `rowsOf`, with no row carrying shots until it is gathered again.
- **The Run record.** Its schema is unchanged. A Review whose Reviewer an Evidence miss stopped ran no agent, so it records no run.
- **Unchanged:** route capture, which still never blocks a pull request or uses a Retry; Prototypes, captured as before in a Product repo that uses Evidence shots; a `ui` block with no `shots`, and a Product repo with no `ui` block, which behave exactly as before; and the permissions and secrets. The Fabrik App gains no permission, no job is given a new one, and there is no new secret: the review job already reads Actions and already downloads a pull request's evidence.
- **Why a minor:** the new behaviour waits behind one Kit config block that is off by default, which `/fabrik-visual-evidence` writes when the Operator chooses it. Merging the bump changes nothing for a Product repo, and markers an earlier release wrote still read. The read library gains exports and a row field; the one break, `Facts.shotsMarkers`, falls on a reader that builds `Facts` itself, and only when it compiles.

## To turn it on

Merging the bump changes nothing. Turn it on for the Pilot first, and then in each Product repo whose Journeys run in one of its Required checks.

1. Merge this release's bump PR.
2. Build the Product repo's side to the contract in the README's [Evidence shots](../../README.md#evidence-shots) section: the helper, shots in the Journeys that reach the states the Operator wants to see, and an upload step in the check's workflow job that runs whether the Journeys passed or failed. A Ticket can build the helper and the shots. The workflow is a Trust-root file, so the upload step is the Operator's own change. Make sure the check that runs the Journeys is listed in `sandbox.checks`.
3. Once that is merged and the check uploads the artifact, run `/fabrik-visual-evidence`, choose Evidence shots, confirm the check, the artifact's name and each route capture field it will take out, and merge the PR it opens.
4. Check it on a real UI issue: the PR's evidence section waits for the named check, then lists the shots the Implementer named, and the Evidence page holds every shot of the run, the named ones first.
