# Release notes: Full Reviews and Touch-ups

The notes for the minor release that makes a pull request's first Review a Full Review, settles the code a Reviewer Verdict judged, and fixes small findings with Touch-ups instead of Retries ([#745](https://github.com/jrey8343/fabrik/issues/745), [ADR-0026](../adr/0026-a-later-review-judges-what-changed-since-the-head-the-reviewer-last-judged.md), [ADR-0027](../adr/0027-an-execution-flaw-of-only-small-or-missed-earlier-findings-calls-for-a-touch-up-not-a-retry.md)). Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## Release-note line

A pull request's first Review is a Full Review that names everything at once. Later Reviews judge only what changed since, and a flaw of only small or missed-earlier findings is fixed by a Touch-up, which uses none of the Ticket's Retries.

## What changed

- **Why:** the Reviewer judged the whole pull request fresh on every push. In the week of 9 Nov, 71 of the 95 findings on Retry pushes were in code an earlier Verdict had already judged ([#711](https://github.com/jrey8343/fabrik/issues/711)), and 10 Execution flaws held only stale comments, docs or a body that didn't match the branch. Each spent a Retry, often a Step-up, and two sent their Tickets back to design.
- **Full Review** ([#747](https://github.com/jrey8343/fabrik/issues/747)). A pull request's first Review is a Full Review: the Kit works out the kind from the Verdict markers when it starts the Review, and a pull request whose Reviewer Verdicts carry no change line (from before #643) gets one too. Only a Full Review's prompt has the Full Review section: it is the only full Review the pull request gets, so it reads the whole diff and every changed file without cutting its own output, follows every name the change renames or removes, names every flaw at once, and says when a check it tried couldn't run. A Replay arm's Review is always a Full Review.
- **Later Review and Settled code** ([#748](https://github.com/jrey8343/fabrik/issues/748)). Every other Review is given every earlier Reviewer Verdict with its head, each Implement run's `fix` comment named by its run (`Retry n`, `Touch-up n`, `Touch-up n, body only`, `Request-changes run` or `conflict-only run`), the kind of run that pushed the head, and the pull request's own change since the last judged head, worked out with git so that what `main` brought in is no part of it. It judges whether each finding of the Verdict before was fixed, what the change gained since in full, every acceptance criterion and the body across the whole pull request, and, in Settled code, only a behaviour bug, tagged `[missed earlier]`. A Design flaw stays open to it. A conflict-only run's push is judged only on how it changed the pull request's own diff, plus the criteria and body. When a rebase dropped the last judged head, the Review gets the pull request's own files whose hashes changed and reads their whole change.
- **Finding tags** ([#749](https://github.com/jrey8343/fabrik/issues/749)). Each finding of an Execution flaw is a `- ` item, which may open with `[small: body]`, `[small: comment]` or `[missed earlier]`. The Kit reads the tags and checks nothing in code. A Reviewer's Execution-flaw marker counts them as `"tags":{"small":…,"missedEarlier":…,"counted":…,"smallBody":…}`, where a `[missed earlier]` on a Full Review counts as untagged, and the posted Verdict shows the tags as written.
- **Touch-ups and their pool** ([#750](https://github.com/jrey8343/fabrik/issues/750)). A Reviewer's Execution flaw with at least one item, every one tagged, calls for a Touch-up instead of a Retry while the pull request has one left: an Implement run on the same branch, on the same model as the run whose push the flaw judged, which uses none of the Ticket's two Retries. A pull request gets two Touch-ups, counted from its Verdict markers (`"touchUp":n`); a third such flaw counts like any other. An unbuilt Request changes and a Ticket no longer `ready-for-agent` come first, and a Verdict from red checks, an empty diff or a Broken run never calls for one. A Touch-up is in flight, held, restarted and refused as a Retry is, and its push note opens `<!-- fabrik:touch-up-push n -->`. Every run's push note now records its Step-up reason ([#746](https://github.com/jrey8343/fabrik/issues/746)), so a Touch-up's model, and the model of a Retry after it, is read from the pull request alone; taking `fabrik:step-up` off drops back to the model the Retry rules give that run without the label. The Digest's facts count Touch-ups apart from Retries, with the Touch-ups left.
- **Body-only Touch-ups** ([#751](https://github.com/jrey8343/fabrik/issues/751)). A Touch-up whose findings are all `[small: body]` is told so and may commit nothing. The Kit then replaces the body with its `summary`, posts its `fix` under a `<!-- fabrik:touch-up-body-only n <sha> -->` note, which ends it but is no push, and starts the Review of the same head, which may give that head a second Verdict: the one exception to one Verdict per head. Its Run record has `pushed: null` and no empty diff, and the Digest shows it as a round of its own.
- **Two Weekly summary rows** ([#753](https://github.com/jrey8343/fabrik/issues/753), [#754](https://github.com/jrey8343/fabrik/issues/754)), straight after Retries per merged PR: **Touch-ups per merged PR**, the Touch-ups on each merged agent PR's Ticket's whole path, each counted once for its Ticket, PR and number, and **Missed earlier per merged PR**, the `[missed earlier]` findings of the Review records whose Verdict landed. Touch-ups are in no Yield and in neither Retries row.
- **Run records move to schema 11**, adding three fields: `fullReview` on a Review (true, false, or null for every other role), `findingTags: { small, missedEarlier, counted }` on a Review's Execution flaw (null otherwise), and `touchUp` on an Implement run (its number, 0 for any other run; a Touch-up's `retry` is 0). Records of schema 1 to 10 read as `fullReview: null`, `findingTags: null` and `touchUp: 0`, so the first week on this release reads the two new rows low.
- **The Review's default effort is `high`** ([#759](https://github.com/jrey8343/fabrik/issues/759)). In [#755](https://github.com/jrey8343/fabrik/issues/755)'s reruns of the Reviewer with the new prompt on 10 known-miss heads, `high` named 22 of the 27 known first-Review misses and `medium` 15, and the longest run at `high` took 438 s, inside the Review's 30-minute limit. A repo's own `roles.review.effort` still wins, and a `null` one still takes the default. The Digest writer keeps its own `medium`: it follows a Review effort the repo sets itself, never the Kit's default. Every other role, and the Step-up, stays at `medium`. The starter Kit config names `high` for `roles.review` and `medium` for `roles.digest`.
- The Glossary gains **Settled code**, **Full Review**, **Small finding** and **Touch-up**, and **Retry** says what calls for a Touch-up instead.
- **Why a minor:** new behaviour with no Kit config field, shim change, secret or App permission, so a Product repo only merges the bump PR. `RunRecord` gains fields, which the read library's rule counts as a minor.

## Before the bump: the Operator's check

Done on [#755](https://github.com/jrey8343/fabrik/issues/755): `high` named 22 of the 27 known misses and `medium` 15, so the Review's default goes to `high` in this release ([#759](https://github.com/jrey8343/fabrik/issues/759)).

## Upgrading

**Bump the store's pin** in `fabrik-runs` to this release, with the Pilot, so its Weekly summary reads schema 11 records. Until then it leaves them out, and says how many. A Product repo merges the bump PR, the Pilot first. A Product repo whose `.fabrik/config.json` was written from an earlier starter names `"effort": "medium"` for `roles.review` outright, so its Review stays at `medium`: to take `high`, delete the field, and the Digest writer keeps `medium`. Changing it to `"high"` instead takes the Digest writer to `high` too, unless `roles.digest` names `"effort": "medium"`, as the new starter does.
