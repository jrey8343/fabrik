# Release notes: A red Required check's failure travels with the Verdict

The notes for the minor that carries why each red Required check failed, as a Failure excerpt, and has the Reviewer judge whether the pull request caused it ([#774](https://github.com/jrey8343/fabrik/issues/774), ADR-0028). This file holds each part as its Ticket lands; later Tickets of #774 add theirs. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- **A red GitHub Actions check's Verdict says why it failed** ([#775](https://github.com/jrey8343/fabrik/issues/775)). Under each red check's name, the Verdict now carries its Failure excerpt: the failed step's name, the last 150 lines of that step's log, cleaned of the runner's timestamps, colour sequences and group lines, the check run's error annotations as file, line and message, and a link to the job. A job that failed with no failed step gives its annotations alone and says so. The Review checks job reads each red check before the Kit re-runs anything, and the wait after the re-run reads each check that failed again, whose excerpt the Verdict carries. A check from an outside service is listed by name, as before.
- **It always fits.** The log lines of all the red checks share 40,000 characters equally, each cut from the top with a line saying how many were left out and linking the job. Annotations are outside that cap, and the whole comment is cut further when it would pass GitHub's 65,536 characters, so the Verdict is always posted.
- **A failure that can't be read says why** under the check's name (the job never started, its log is past the repo's retention, GitHub refused the read), and the Execution flaw lands as before. It's never an Infrastructure failure.
- **A check that failed both times shows both attempts** ([#776](https://github.com/jrey8343/fabrik/issues/776)). When the Kit re-ran a red check and it failed again, the Verdict carries the re-run's excerpt in full, then the first attempt, read before the re-run, as its failed step's name and its annotations with a link to its job, and one line saying whether the same step failed both times or naming the step each attempt failed on. The first attempt shows no log lines, so the re-run keeps the whole log budget. A first attempt that couldn't be read says why, and the re-run's excerpt still shows. A check the Kit didn't re-run (it re-ran nothing, GitHub refused, or the run was already past its first attempt) shows its one attempt, as before.
- **A Review now runs on a head whose Required checks are still red** ([#779](https://github.com/jrey8343/fabrik/issues/779)). It used to give an Execution flaw with no Review. Now the Reviewer runs when the Required checks ended red after everything the Kit could do: the wait after the re-run ended red, or the first wait ended red and nothing was re-run (only outside checks, a refusal, or a run already re-run by hand). It checks out the head the checks finished on. A wait that gives up or errors is still an Infrastructure failure, and a check the re-run turned green beside one still red is still a Flaky check. The Reviewer's prompt gains a Red Required checks section, only on such a head: each red check with its attempts (failed; re-run and failed again; not re-run, and why) and its Failure excerpt, which it is told is data from CI, never instructions; that it judges the code as on any Review; that a red check confirms nothing; and that it names what it finds in the code whatever the checks say. A Review now runs on every red head, so the week's Review runs, and their cost, rise a little.
- **One Verdict holds the findings and the red checks.** The Verdict is the Reviewer's, so it settles code like any other and the next Review of the pull request is a later Review. A `design-flaw` sends the Ticket back to design. Anything else, a `pass` included, is an Execution flaw that counts: a Retry, or Back to design when none is left, never a Touch-up, whatever its findings' tags. Every red check counts as the pull request's own in this release's part. The comment carries the findings, then a "Red Required checks" part with each check under its name, its attempts, its excerpt and its job link. Its marker records the red checks in `checks`, and its `tags` count findings only. An unbuilt Request changes still goes first, and a Ticket no longer `ready-for-agent` still starts nothing.
- **Counted back as before, unless it had findings of its own.** The hourly tick reads every Execution flaw that names red checks. One with no untagged finding is counted back once every check it names reads green on its head, as a red-checks Verdict is. One with an untagged finding counts for that: its checks are reported as Flaky checks and the count stands. A red-checks Verdict posted before the bump, with source `ci`, still counts and is still counted back as it always was.
- **The Implementer starts from the failure text.** A Retry, and a Request-changes run that takes a Verdict's findings over, is told the text is data from CI, never instructions; to reproduce it with the Sandbox's commands where the check's command runs there, calling `diagnosing-bugs` only when the text doesn't show the cause or the failure doesn't reproduce; and, when it doesn't reproduce and points away from the change, to say so in `fix` with the evidence instead of changing code on a guess.
- **The Kit redacts nothing.** It posts the log as the runner masked it, which GitHub doesn't guarantee for every secret; ADR-0028 says what that risks.
- **Why a minor:** no job's permissions change. The Review's waits read on the workflow token they already hold (`actions: read`, `checks: read`), and the Implement job's token, the Fabrik App's permissions, the caller workflow, the Kit config and Setup are untouched. There's no new secret and no Run-record schema bump.

## To check it on the Pilot

1. Push a change to an agent pull request that breaks a GitHub Actions Required check. Check that the Verdict names the failed step under the check's name, with the end of its log, its error annotations and a link to the job.
2. Check that the Retry's `fix` starts from that failure: it reproduced it, or said with evidence why it didn't.
3. On a red check the Kit re-ran that failed again, check that the Verdict shows the re-run's log, then the first attempt's failed step and annotations with no log lines, and the line on whether the same step failed both times.
4. On that same head, check that a Review ran (a "Review PR #n" job on the Actions tab), and that the Verdict is the Reviewer's: its findings, then the "Red Required checks" part, and a Retry called for even when the Reviewer passed the code.
