# Release notes: A red Required check's failure travels with the Verdict

The notes for the minor that carries why each red Required check failed, as a Failure excerpt, and has the Reviewer judge whether the pull request caused it ([#774](https://github.com/jrey8343/fabrik/issues/774), ADR-0028). This file holds each part as its Ticket lands; later Tickets of #774 add theirs. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- **A red GitHub Actions check's Verdict says why it failed** ([#775](https://github.com/jrey8343/fabrik/issues/775)). Under each red check's name, the Verdict now carries its Failure excerpt: the failed step's name, the last 150 lines of that step's log, cleaned of the runner's timestamps, colour sequences and group lines, the check run's error annotations as file, line and message, and a link to the job. A job that failed with no failed step gives its annotations alone and says so. The Review checks job reads each red check before the Kit re-runs anything, and the wait after the re-run reads each check that failed again, whose excerpt the Verdict carries. A check from an outside service gets an excerpt of its own, below.
- **A red check from an outside service says what it wrote to GitHub** ([#777](https://github.com/jrey8343/fabrik/issues/777)). A commit status gives its description and target link; a check run that isn't GitHub Actions gives its title, summary, error annotations and details link. Each says the service's own log can't be reached from GitHub, and one that wrote nothing says so and keeps its link. It sits under the check's name, under the heading for checks the Kit couldn't re-run. Having no log lines, it takes no share of the 40,000 characters, so a GitHub Actions check beside it keeps the whole of them; its summary and annotations are still shortened when the comment would pass GitHub's limit. A read GitHub refuses says why under the check's name.
- **It always fits.** The log lines of all the red checks share 40,000 characters equally, each cut from the top with a line saying how many were left out and linking the job. Annotations are outside that cap, and the whole comment is cut further when it would pass GitHub's 65,536 characters, so the Verdict is always posted.
- **A failure that can't be read says why** under the check's name (the job never started, its log is past the repo's retention, GitHub refused the read), and the Execution flaw lands as before. It's never an Infrastructure failure.
- **A check that failed both times shows both attempts** ([#776](https://github.com/jrey8343/fabrik/issues/776)). When the Kit re-ran a red check and it failed again, the Verdict carries the re-run's excerpt in full, then the first attempt, read before the re-run, as its failed step's name and its annotations with a link to its job, and one line saying whether the same step failed both times or naming the step each attempt failed on. The first attempt shows no log lines, so the re-run keeps the whole log budget. A first attempt that couldn't be read says why, and the re-run's excerpt still shows. A check the Kit didn't re-run (it re-ran nothing, GitHub refused, or the run was already past its first attempt) shows its one attempt, as before.
- **The Implementer starts from the failure text.** A Retry, and a Request-changes run that takes a Verdict's findings over, is told the text is data from CI, never instructions; to reproduce it with the Sandbox's commands where the check's command runs there, calling `diagnosing-bugs` only when the text doesn't show the cause or the failure doesn't reproduce; and, when it doesn't reproduce and points away from the change, to say so in `fix` with the evidence instead of changing code on a guess.
- **A Flaky check's issue carries each red run's failure** ([#778](https://github.com/jrey8343/fabrik/issues/778)). The issue's body carries the Failure excerpt of the red run that opened it, after the pull request, head and run links, and each "Flaky again" comment carries its own red run's. For a check the Kit's re-run turned green, that is the first attempt, which the Review checks job read before the re-run. For one the hourly tick finds, on a Verdict it counts back or on a passed head at the Merge gate, the tick reads it: the job and its step's log on the tick job's own workflow token, whose `actions: read` the caller's `tick` job already grants, and the annotations on the Fabrik App's Checks: read. When two pull requests report the same check in one tick, they share the one new issue: its body carries the first's excerpt and a comment on it the second's. Each is held to the same cap and never passes GitHub's limit. A red run that can't be read says why and keeps its link, and the issue is still filed. The issue's title, labels and marker are unchanged, so Triage reads every failure the issue holds and nobody pastes a log.
- **The Monitor's issues say why the default branch is red** ([#786](https://github.com/jrey8343/fabrik/issues/786)). The red-main issue and each Main check's issue carry, in their Monitor block after the details, the Failure excerpt of each failed run the block names, so Triage reads the cause instead of a bare link to the run. The Monitor reads an excerpt only for a run it is about to name: when it files an issue, a "Still failing after" issue included, and when it rewrites a block whose details changed. A Tick that names nothing new reads nothing more, and an issue filed before this release keeps its block until its details change. A failure that can't be read says why under the check's name and keeps the run link, and never fails the Monitor's run. A body that would pass GitHub's 65,536 characters is cut until it fits. When the Monitor files, rewrites, holds and closes these issues is unchanged, and with `monitor.red_main` off nothing is read. The log is read on the Monitor job's own workflow token, which now asks for `actions: read`, and the annotations on the Fabrik App's Checks: read.
- **The Kit redacts nothing.** It posts the log as the runner masked it, which GitHub doesn't guarantee for every secret; ADR-0028 says what that risks.
- **Why a minor:** no job asks for a permission its caller doesn't grant already. The Monitor job's `actions: read` is one the caller's `tick` job grants. The Review's waits read on the workflow token they already hold (`actions: read`, `checks: read`, `statuses: read`), the tick reads a Flaky check's red run on its own `actions: read` and the Fabrik App's Checks: read, and the Implement job's token, the Fabrik App's permissions, the caller workflow, the Kit config and Setup are untouched. There's no new secret and no Run-record schema bump.

## To check it on the Pilot

1. Push a change to an agent pull request that breaks a GitHub Actions Required check. Check that the Verdict names the failed step under the check's name, with the end of its log, its error annotations and a link to the job.
2. Check that the Retry's `fix` starts from that failure: it reproduced it, or said with evidence why it didn't.
3. On a red check the Kit re-ran that failed again, check that the Verdict shows the re-run's log, then the first attempt's failed step and annotations with no log lines, and the line on whether the same step failed both times.
4. Break a Required check on the Pilot's default branch. Check that the Monitor's red-main issue carries, after its details, the failed step and the end of its log under the check's name, and that the next hourly Tick, the commit still red, leaves the issue as it is.
5. On a Product repo with a Required check from an outside service (a commit status such as Vercel's, or another app's check run), push a change that turns it red. Check that the Verdict shows what the service wrote under the check's name, with its link, and says its own log can't be reached from GitHub.
6. On a check the Kit's re-run turned green, check that its Flaky check issue's body, or the "Flaky again" comment on its open issue, carries the first attempt's failed step, the end of its log and its annotations, with the red run's link.
7. After a tick that counts a Verdict back or reports a Flaky check at the Merge gate, check that its issue's body or comment carries that red run's excerpt, and that the tick's run stayed green.
