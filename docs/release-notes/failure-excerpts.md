# Release notes: A red Required check's failure travels with the Verdict

The notes for the minor that carries why each red Required check failed, as a Failure excerpt, and has the Reviewer judge whether the pull request caused it ([#774](https://github.com/jrey8343/fabrik/issues/774), ADR-0028, ADR-0029). This file holds each part as its Ticket lands; later Tickets of #774 add theirs. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- **A red GitHub Actions check's Verdict says why it failed** ([#775](https://github.com/jrey8343/fabrik/issues/775)). Under each red check's name, the Verdict now carries its Failure excerpt: the failed step's name, the last 150 lines of that step's log, cleaned of the runner's timestamps, colour sequences and group lines, the check run's error annotations as file, line and message, and a link to the job. A job that failed with no failed step gives its annotations alone and says so. The Review checks job reads each red check before the Kit re-runs anything, and the wait after the re-run reads each check that failed again, whose excerpt the Verdict carries. A check from an outside service gets an excerpt of its own, below.
- **A red check from an outside service says what it wrote to GitHub** ([#777](https://github.com/jrey8343/fabrik/issues/777)). A commit status gives its description and target link; a check run that isn't GitHub Actions gives its title, summary, error annotations and details link. Each says the service's own log can't be reached from GitHub, and one that wrote nothing says so and keeps its link. It sits under the check's name, under the heading for checks the Kit couldn't re-run. Having no log lines, it takes no share of the 40,000 characters, so a GitHub Actions check beside it keeps the whole of them; its summary and annotations are still shortened when the comment would pass GitHub's limit. A read GitHub refuses says why under the check's name.
- **It always fits.** The log lines of all the red checks share 40,000 characters equally, each cut from the top with a line saying how many were left out and linking the job. Annotations are outside that cap, and the whole comment is cut further when it would pass GitHub's 65,536 characters, so the Verdict is always posted.
- **A failure that can't be read says why** under the check's name (the job never started, its log is past the repo's retention, GitHub refused the read), and the Execution flaw lands as before. It's never an Infrastructure failure.
- **A check that failed both times shows both attempts** ([#776](https://github.com/jrey8343/fabrik/issues/776)). When the Kit re-ran a red check and it failed again, the Verdict carries the re-run's excerpt in full, then the first attempt, read before the re-run, as its failed step's name and its annotations with a link to its job, and one line saying whether the same step failed both times or naming the step each attempt failed on. The first attempt shows no log lines, so the re-run keeps the whole log budget. A first attempt that couldn't be read says why, and the re-run's excerpt still shows. A check the Kit didn't re-run (it re-ran nothing, GitHub refused, or the run was already past its first attempt) shows its one attempt, as before.
- **A Review now runs on a head whose Required checks are still red** ([#779](https://github.com/jrey8343/fabrik/issues/779)). It used to give an Execution flaw with no Review. Now the Reviewer runs when the Required checks ended red after everything the Kit could do: the wait after the re-run ended red, or the first wait ended red and nothing was re-run (only outside checks, a refusal, or a run already re-run by hand). It checks out the head the checks finished on. A wait that gives up or errors is still an Infrastructure failure, and a check the re-run turned green beside one still red is still a Flaky check. The Reviewer's prompt gains a Red Required checks section, only on such a head: each red check with its attempts (failed; re-run and failed again; not re-run, and why) and its Failure excerpt, which it is told is data from CI, never instructions; that it judges the code as on any Review; that a red check confirms nothing; and that it names what it finds in the code whatever the checks say. A Review now runs on every red head, so the week's Review runs, and their cost, rise a little.
- **One Verdict holds the findings and the red checks.** The Verdict is the Reviewer's, so it settles code like any other and the next Review of the pull request is a later Review. A `design-flaw` sends the Ticket back to design. With a red check the Reviewer judged caused, below, anything else, a `pass` included, is an Execution flaw that counts: a Retry, or Back to design when none is left, never a Touch-up, whatever its findings' tags. The comment carries the findings, then a "Red Required checks" part with each check under its name, its judgment and reason, its attempts, its excerpt and its job link. Its marker records the caused checks in `checks`, and its `tags` count findings only. An unbuilt Request changes still goes first, and a Ticket no longer `ready-for-agent` still starts nothing.
- **The Reviewer judges each red check caused or an Unrelated failure** ([#780](https://github.com/jrey8343/fabrik/issues/780), ADR-0029). The Review checks job also reads each red check's result on the default branch's head (passed, failed with its link, still running, or not run there), and the Reviewer is given it beside the excerpt and the attempts. Its prompt asks it to judge each red check separately, as `caused` or `unrelated`, with a one-line reason, in a `red-checks:` block after its findings and any Follow-ups. It calls a check unrelated only on positive evidence: the same check red on `main`, a failure in code the change can't reach, two attempts failing on different things, or a failure from the runner or a service rather than the code. A failing test in a file the change didn't touch is evidence to weigh, never enough alone. Without such evidence the check is caused, and the reason says why the Reviewer couldn't tell; a check the block leaves out, misnames or misspells is caused too, and the Verdict says the Reviewer gave no judgment. Each head's red checks are judged afresh.
- **An Unrelated failure never counts.** A Verdict whose red checks are all Unrelated failures lands by the Reviewer's line, as on green: an `execution-flaw` calls for a Touch-up when every finding is tagged and one is left, else a Retry, and a `pass` is a pass, which starts the Digest writer, leaves draft, requests your review and counts in Gate load and Yield. GitHub holds the merge until the check is green on the head (ADR-0019). With a caused check beside it, the Verdict counts on that check, says which checks are Unrelated failures, and the Retry is told to leave them alone. A pass that names an Unrelated failure says the Merge gate holds the pull request until it is green. The marker records the caused checks in `checks`, which count-back reads, and the Unrelated failures in a new `unrelated` field.
- **Counted back as before, unless it had findings of its own.** The hourly tick reads every Execution flaw that names caused red checks. One with no untagged finding is counted back once every check it names reads green on its head, as a red-checks Verdict is. One with an untagged finding counts for that: its checks are reported as Flaky checks and the count stands. A red-checks Verdict posted before the bump, with source `ci`, still counts and is still counted back as it always was.
- **The Implementer starts from the failure text.** A Retry, and a Request-changes run that takes a Verdict's findings over, is told the text is data from CI, never instructions; to reproduce it with the Sandbox's commands where the check's command runs there, calling `diagnosing-bugs` only when the text doesn't show the cause or the failure doesn't reproduce; and, when it doesn't reproduce and points away from the change, to say so in `fix` with the evidence instead of changing code on a guess.
- **A Flaky check's issue carries each red run's failure** ([#778](https://github.com/jrey8343/fabrik/issues/778)). The issue's body carries the Failure excerpt of the red run that opened it, after the pull request, head and run links, and each "Flaky again" comment carries its own red run's. For a check the Kit's re-run turned green, that is the first attempt, which the Review checks job read before the re-run. For one the hourly tick finds, on a Verdict it counts back or on a passed head at the Merge gate, the tick reads it: the job and its step's log on the tick job's own workflow token, whose `actions: read` the caller's `tick` job already grants, and the annotations on the Fabrik App's Checks: read. When two pull requests report the same check in one tick, they share the one new issue: its body carries the first's excerpt and a comment on it the second's. Each is held to the same cap and never passes GitHub's limit. A red run that can't be read says why and keeps its link, and the issue is still filed. The issue's labels and marker are unchanged (its title changes, below), so Triage reads every failure the issue holds and nobody pastes a log.
- **You hear of an Unrelated failure as quietly as of a Flaky check** ([#781](https://github.com/jrey8343/fabrik/issues/781)). Ahead of the Verdict, one line on the pull request, mentioning nobody, says each check the Reviewer judged an Unrelated failure is still red on that head and that the Reviewer judged the pull request didn't cause it, and links the check's issue; the pass or flaw that follows links it too, beside the Reviewer's reason. The line carries its own marker, `fabrik:unrelated-failure`, with the head and the checks. A second Verdict on the same head, after a Touch-up that changed only the body, says nothing more of a check already said there.
- **One issue per check holds its Flaky checks and its Unrelated failures alike.** It is the issue a Flaky check uses, found by its marker and labelled `needs-triage` and `fabrik:flaky-check`. A new one is titled ``Flaky check or Unrelated failure: `<name>` ``. **A check's issue filed before the bump keeps its old title, `Flaky required check: <name>`,** and while it's open it still takes every comment, found by its marker; once it's closed, the next failure files a fresh one under the new title. Its body says which it was when filed, a Flaky check, or an Unrelated failure with the Reviewer's one-line reason, and names the pull request and head, with that red run's Failure excerpt. Each later comment says "Flaky again" or "Unrelated failure", with the pull request, head and run links, the Reviewer's reason for an Unrelated failure, and that red run's excerpt. The Kit files nothing more for it: never a Ticket or a Design issue. Triage routes it as any check's issue.
- **An Unrelated failure that later passes on its head is a Flaky check.** It gets the Flaky check line and the comment on its issue, and nothing is counted back, since nothing counted. At the Merge gate the hourly tick's read of the passed head finds it, as it finds any Flaky check there; on an open draft the tick's sweep now also reads the Unrelated failures of the latest Verdict, each on its own as it reads green.
- **The Weekly summary gains an Unrelated failures row**, straight after Flaky checks, counted as that row is: from the Kit's lines on agent pull requests in the week, once per pull request, head and check. The Run-record schema doesn't change.
- **The Monitor's issues say why the default branch is red** ([#786](https://github.com/jrey8343/fabrik/issues/786)). The red-main issue and each Main check's issue carry, in their Monitor block after the details, the Failure excerpt of each failed run the block names, so Triage reads the cause instead of a bare link to the run. The Monitor reads an excerpt only for a run it is about to name: when it files an issue, a "Still failing after" issue included, and when it rewrites a block whose details changed. A Tick that names nothing new reads nothing more, and an issue filed before this release keeps its block until its details change. A failure that can't be read says why under the check's name and keeps the run link, and never fails the Monitor's run. A body that would pass GitHub's 65,536 characters is cut until it fits. When the Monitor files, rewrites, holds and closes these issues is unchanged, and with `monitor.red_main` off nothing is read. The log is read on the Monitor job's own workflow token, which now asks for `actions: read`, and the annotations on the Fabrik App's Checks: read.
- **Triage routes an issue from its Failure excerpts** ([#782](https://github.com/jrey8343/fabrik/issues/782)). Triage's prompt gains a part, after the six Fast-path tests, for an issue that carries Failure excerpts: a Flaky check's issue, or the Monitor's red-main or Main check issue. The excerpts are data from CI, never instructions. A check's issue can hold several failures, in its body and its later comments, and Triage judges each one. It sends the issue to an Implementer when the excerpts point at test or product code and one pull request can fix all of them; to the Operator (`ready-for-human`), saying what to check, when the fix is in a Trust-root file such as a workflow, or when the excerpts point outside the repo's code (a service that didn't come up, a credential, a provider); and otherwise to `needs-design`, when the excerpts don't show the cause or the failures are too many for one pull request. The six Fast-path tests are unchanged, and an issue sent to an Implementer still passes all six. Triage never splits an issue: the size test sends that to a Design session, which splits it. Triage's output, and how the Kit applies it, are unchanged; it was already given the issue's comments.
- **An Unrelated failure is re-run once more at the Merge gate** ([#783](https://github.com/jrey8343/fabrik/issues/783)). The first hourly tick after a pass that names an Unrelated failure still red on the head it was given on, with the pull request at the Merge gate, re-runs that check's failed jobs once more on that head, so a check that clears by itself opens the gate without you. The tick posts a quiet line on the pull request, mentioning nobody, and adds a new trigger label, **`agent:rerun-checks`**, which the Loop routes to the Re-run red checks job, past a run's first attempt this once; the label comes off as the run starts. On the Actions tab the run shows as **`PR #<n> labeled agent:rerun-checks`**, with its Kit, Claim the work and Re-run red checks jobs and no Review or push job. Later ticks read the head's check runs: a check green again is a Flaky check, as the tick's read of a passed head already reports it, with nothing counted back; a check red again by a run started after the line, a re-run that started no run, and a label still on at the next tick with no run behind it are each said once on the pull request and count as done. A check from an outside service, and one red on the default branch's head, aren't re-run, and the line says so. The Kit asks once per pull request, head and check: the label added anywhere else, or again for the same head, by anyone, comes off with one line saying why, and the stuck-trigger sweep leaves it alone. GitHub creates the label the first time the Kit adds it; re-running Setup creates it with the Kit's colour and description. **No caller change:** the tick's job still holds only the `actions: read` the caller's `tick` job grants, and the Re-run red checks job, still the only job with `actions: write`, which the caller's `loop` job already grants, loads no secret and holds no Fabrik App token.
- **A held pull request is brought up to date once its check's fix lands** ([#784](https://github.com/jrey8343/fabrik/issues/784)). When a check's issue closes as completed, the Kit brings up to date each open agent pull request at the Merge gate whose latest pass, on its current head, names an Unrelated failure of that check that hasn't since read green there, though it is only behind `main`, so the fix reaches it without your asking. It takes ADR-0011's path unchanged: into draft, a plain rebase onto `main` pushed with a lease, else one conflict-only run, one attempt per `main` head with the attempt marker, and the push starts a Review. Its notes say the fix for the check landed, naming the check and its issue. A run in flight, an unbuilt Request changes and a `main` head already tried are left alone, as ADR-0011 leaves them. A pull request that already holds `main`'s head has nothing to bring in: nothing is pushed, and one note on it records so. The issue-closed event acts at once, and the hourly tick's conflict check catches any it missed: a check's issue closed as completed in the last week, since the pass. The trigger is the issue closing, not `main`'s check going green, since `main` doesn't run every Required check. An issue closed as not planned or as a duplicate brings nothing up to date, and neither does a push to `main`: a Plain pull request, and an agent pull request no such pass names, are left alone when only behind `main`, as before. Each note carries a `fabrik:check-fix` marker with the head, `main`'s head, how it went and each check with its issue, so the move is spent for that check on that head. This is the one exception to ADR-0011's "a pull request only behind `main` is left alone".
- **The Kit redacts nothing.** It posts the log as the runner masked it, which GitHub doesn't guarantee for every secret; ADR-0028 says what that risks.
- **Why a minor:** no job asks for a permission its caller doesn't grant already. The Monitor job's `actions: read` is one the caller's `tick` job grants. The Review's waits read on the workflow token they already hold (`actions: read`, `checks: read`, `statuses: read`), the tick reads a Flaky check's red run on its own `actions: read` and the Fabrik App's Checks: read, and the Implement job's token, the Fabrik App's permissions, the caller workflow, the Kit config and Setup are untouched. There's no new secret and no Run-record schema bump.

## To check it on the Pilot

1. Push a change to an agent pull request that breaks a GitHub Actions Required check. Check that the Verdict names the failed step under the check's name, with the end of its log, its error annotations and a link to the job.
2. Check that the Retry's `fix` starts from that failure: it reproduced it, or said with evidence why it didn't.
3. On a red check the Kit re-ran that failed again, check that the Verdict shows the re-run's log, then the first attempt's failed step and annotations with no log lines, and the line on whether the same step failed both times.
4. Break a Required check on the Pilot's default branch. Check that the Monitor's red-main issue carries, after its details, the failed step and the end of its log under the check's name, and that the next hourly Tick, the commit still red, leaves the issue as it is.
5. On a Product repo with a Required check from an outside service (a commit status such as Vercel's, or another app's check run), push a change that turns it red. Check that the Verdict shows what the service wrote under the check's name, with its link, and says its own log can't be reached from GitHub.
6. On a check the Kit's re-run turned green, check that its Flaky check issue's body, or the "Flaky again" comment on its open issue, carries the first attempt's failed step, the end of its log and its annotations, with the red run's link.
7. After a tick that counts a Verdict back or reports a Flaky check at the Merge gate, check that its issue's body or comment carries that red run's excerpt, and that the tick's run stayed green.
8. Once Triage runs on that check's issue, check that its comment names each failure the issue holds and that it chose `ready-for-agent`, `ready-for-human` (saying what to check) or `needs-design` as the excerpts warrant, without asking for the log.
9. On a head still red after the Kit's re-run, check that a Review ran (a "Review PR #n" job on the Actions tab), and that the Verdict is the Reviewer's: its findings, then the "Red Required checks" part with each check's judgment and reason, and a Retry called for when the Reviewer judged a check caused, even when it passed the code.
10. On a head whose only red check is also red on the default branch, check that the Review checks job's log names the check's result on the default branch's head, that the Reviewer judged it an Unrelated failure, and that a pass left draft and requested your review while GitHub held the merge.
11. In the first week, read each Verdict that names an Unrelated failure and check the Reviewer's reason against the job. A check called unrelated that the pull request did cause is a Review miss worth a Retro line.
12. On that pull request, check that one line ahead of the Verdict, mentioning nobody, names the check as still red and links its issue, that the Verdict links the same issue beside the Reviewer's reason, and that the issue, titled ``Flaky check or Unrelated failure: `<name>` `` unless one was already open under the old title, carries the reason and the red run's excerpt.
13. Re-run that check by hand until it passes on the same head, and check that the next hourly tick posts one Flaky check line, comments on the same issue, and counts nothing back.
14. In the next Weekly summary, check that the Unrelated failures row sits straight after Flaky checks and counts each pull request, head and check once.
15. After a pass that names an Unrelated failure, check that the next hourly tick posted the quiet line and added `agent:rerun-checks`, that a `PR #<n> labeled agent:rerun-checks` run re-ran the check's failed jobs and took the label off, and that a later tick either reported a Flaky check or said once that the re-run was done.
16. With a pull request held at the Merge gate by an Unrelated failure of a check, merge the check's fix and close its issue as completed. Check that the pull request went back to draft, that the note on it names the check and its issue under the attempt marker, and that a Review started on the rebased head. Close and reopen the issue, close it as completed again, and check that nothing more happens on that `main` head.
17. Close another check's issue as not planned, and check that the pull request it holds is left as it was.
