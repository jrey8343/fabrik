# Release notes: Staging trials

The notes for the minor release that ships Staging trials ([#814](https://github.com/jrey8343/fabrik/issues/814), [ADR-0038](../adr/0038-a-staging-trials-result-is-a-label-the-operator-puts-on-the-merged-pull-request.md)): a `staging` block in Kit config, by which a reader of the Kit follows a merged agent pull request onto a Product repo's staging environment; the Operator's Staging trial of it there, whose result is a label they put on the merged pull request; and the Promote list, which says what a production deployment would take. Every Ticket of #814 has its part here. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changes with no action

One thing, in the Loop's Design session. In every repo, with the block or without it, a Design session's rewrite of an issue's body now keeps a Trial problem's line, `From Staging trial of PR #50` on a line of its own outside code, as it keeps the other lines that mark an issue for something that reads it later. A session the Kit runs carries it, and a session taken live is told to by its skill. Without it a Trial problem a Design session rewrote would stop naming its pull request. An issue with no such line is rewritten as it was. That is the only change to the Loop.

Nothing else changes. A Product repo whose Kit config has no `staging` block reads exactly as it did: the same Standings, the same rows, and a gather that asks GitHub what it ever asked.

## What is new in Kit config

- **The `staging` block**, such as `{ "url": "https://staging.shop.example", "environment": "staging" }`: `url`, the staging site's base address, an `http://` or `https://` URL that staging links are built from; and `environment`, the name the repo's staging deploys carry in GitHub's Deployments. A block must have both, since a staging link that can't say whether anything is deployed is no use. An `environment` that `production.environment` names too is refused: a deploy to staging could not be told from a deploy to production. Each of those, and a field the block doesn't have, is a Kit config error naming the field.
- **`production.workflow`**, such as `"deploy.yml"`: the file name of the workflow the Operator dispatches to deploy production, ending in `.yml` or `.yaml`, never a path. It is read only to build the address of that workflow's page on GitHub, which the Promote list carries. Nothing dispatches it, and nothing checks that the repo has it.
- **Both are `null` by default.** Left out or `null`, each declares nothing. Kit config is a Trust-root file, so no agent can change where a staging link points.

## What it turns on

Only a reader of the Kit, such as the Console, works any of this out and shows it. In a Product repo whose Kit config declares `staging`:

- **A merged agent pull request stands at Staging.** Its Standing gains a place, Staging, between the Merge gate and Production, from its merge until a production deployment that contains it has started. There it reads:
  - **Merged** before any staging deploy has started, and whenever staging's Deployments could not be read, which it says.
  - **Deploying** while a staging deploy at the merge commit or later runs, and after one succeeds while a Main check has not passed on the deployed commit yet.
  - **Deploy failed** when the deploy failed, with its log's address, or when a Main check is red on the deployed commit, with the check's page.
  - **No deploy seen** when no staging deploy started within an hour of the merge.
  - **On staging** once it is on staging, until its Staging trial has a result.
  - **Accepted** or **Problem found** once its Staging trial has a result, whether or not it is on staging.
- **On staging means deployed and checked.** A pull request is on staging when GitHub shows a successful Deployment in `staging.environment` of its merge commit, or of a later commit that contains it, and every Main check `monitor.main_checks` names is green on the commit of the newest such Deployment. A Main check is judged by the one rule the Monitor reads it by, so the two never disagree. A repo that names no Main checks, or has `monitor.red_main` off, is on staging on the Deployment alone. So the Operator is never sent to try a change on a staging site its own checks call broken. Production's Live is as it was: deployed, not checked.
- **Which pull requests ask for a Staging trial.** One the Kit treated as a UI pull request, a failed capture and an Evidence miss included, unless its Implementer said nothing visible changes; and one that closes a Trial problem, UI evidence or not. Every other merged agent pull request changes no screen: on staging it says it needs no Staging trial, and it waits on nobody.
- **An untried pull request on staging is the Operator's move.** It is never marked as stopping work and is never Stuck: it is in the Operator's queue, and nothing treats it as holding the Loop up. Every other Standing at Staging is nobody's move.
- **Where to try it, and what to try.** A captured route that is not a Dynamic route links to that route on the staging site. A Dynamic route, and every Evidence shot, links to the staging site itself: the Kit cannot tell whether staging holds the record a capture or a Journey visited in the Sandbox, so a staging link never opens a record. Beside the links is what to try: the route patterns, then the Evidence shot names.
- **The result is the Operator's own label.** The Operator ends a Staging trial by putting `fabrik:trial-accepted` or `fabrik:trial-problem` on the merged pull request. Only a label the Operator put on counts, the Operator being Kit config's `operator`, or the repo's owner when that is `null`. Anyone else's labelling is ignored, the Fabrik App's included, so no agent and no App can accept a change for them. The Operator's latest labelling of either decides, and removing that label makes the pull request untried again, whatever the other label says. GitHub holds the record: no Kit job adds, removes or reads either label.
- **A problem becomes a Trial problem.** The Operator files an issue for it whose body carries, on a line of its own, `From Staging trial of PR #50`, with the pull request's own number. It is an ordinary issue otherwise: it gets no label of its own, Intake and Triage treat it like any other, and a Design session's rewrite keeps the line. The pull request reads Problem found, naming its Trial problems, until its fix is accepted: every one of its Trial problems closed as completed, each with at least one merged pull request GitHub records as closing it, and each of those accepted by this same rule. It then reads Accepted through its fix, so the Operator accepts the fix once. A pull request that closes a Trial problem always asks for a Staging trial, so a fix with no UI evidence never accepts the original with nobody looking. A Trial problem that ends any other way, closed as not planned, as a duplicate or with no pull request, leaves the pull request at Problem found until the Operator labels it accepted.
- **How long each Standing lasts.** A pull request that needs a Staging trial and has no result keeps its Standing, whatever its name and its place, until it has a result or production takes it, however long that is. Production takes it when a production deployment that contains it has succeeded: one that failed, or is still running, has not. One with a result keeps its Standing for 24 hours from the labelling that gave it, or from its fix's acceptance. One that changes no screen keeps it for 24 hours from its merge.
- **Production counts from the deployment.** Once a production deployment that contains it has started, the pull request is at Production, with production's names. It is Live for 24 hours from the Deployment that took it, not from its merge, so a change promoted days after its merge is still Live for a day. While that deployment runs, and after it failed, a pull request that waits on nobody stands for 24 hours from that Deployment too, and one that still needs a Staging trial and has no result keeps its Standing, as above. Merged and No deploy seen are only ever said at Staging, so a production the Operator promotes by hand is never reported as missing.
- **The Promote list** says what a production deployment would take: every pull request merged to the default branch since the newest successful production Deployment, agent or Plain, newest first. Where no production Deployment has ever succeeded, or Kit config names no production environment, it starts at the first successful Deployment in `staging.environment`.
  - **An agent pull request** has its evidence, its staging links, what to try and its trial result: untried, accepted, problem found with its Trial problems, changes no screen, or not yet on staging with the name that says why.
  - **A Plain pull request** has its kind and nothing more: no evidence, no staging links and no claim about screens. It asks for no Staging trial, is never counted, and has no Standing at Staging.
  - **The count** is of the entries not yet accepted: each that needs a Staging trial and is not accepted.
  - **The dispatch page** is GitHub's page for the workflow `production.workflow` names, or none when Kit config names no workflow.
  - **The cap** is the 100 most recent merges, agent and Plain together, with a count of those left out. It is the gather's one cap, so the pull requests production has not taken that have a row are the agent ones among the same 100.

## What it never does

- **It never deploys production, dispatches a workflow or refuses a deploy.** The dispatch page is an address and no more. The Operator's own dispatch of their production workflow is the approval, and the Promote list only tells them what that deploy holds.
- **The Loop still ends at the merge.** No Loop rule, job or prompt reads `staging`, and nothing waits on it. The line a Design session's rewrite keeps is the Loop's one change, and it reads nothing of staging. The Weekly summary says nothing past the merge.
- **Nothing is written on GitHub for it:** no comment and no mention, and the Kit puts neither label on anything. The Fabrik App's permissions are as they were.
- **A failed staging deploy is still the Monitor's to file**, when `monitor.red_main` is on, as a failed production deploy is.

## What is new for a reader of the Kit

All of it is exported through the read library's entry, `src/read/index.ts`. Nothing the entry exported is removed or changes meaning.

- **The rows.** `rowsOf` takes a sixth argument, a `StagingRead`: `deployments`, the Deployments read of `staging.environment`, and `mainChecks`, the Main checks read of the commits on staging. Left out or `null`, every staging deploy is unread, and a merged pull request with no trial result reads Merged at Staging. The fourth argument is still the read of production's environment. In a repo that declares `staging`, every merged agent pull request's `Row`, at Staging and at Production, has a new optional key, `staging`: the `site`, the staging `pages` of its captured routes, its named `shots`, and what `toTry`. No other row has the key.
- **The staging reads.** `readDeployments` takes a sixth argument, `{ newest: true }`, with which each success in its `DeployOf` also carries `newest`: the newest successful Deployment that contains the merge, whose commit the Main checks are read on. A read of `staging.environment` is made with it, and a read without it is as it ever was. `readMainChecks` says how each Main check asked about stands on each commit asked about, `green`, `red` or `undecided`, over REST with the reader's credential. It gives a `MainChecksRead`, of a `MainCheckOf` for each check of each `CommitToCheck`, and never throws: a commit GitHub refuses or fails is `unread`.
- **The join with staging.** `joinStaging` settles kept rows against a fresh `StagingRead` with no gather, agreeing with the rule as `joinDeployments` does. `stagingMergesToRead` gives the merges that want a staging Deployments read, and `commitsToCheck`, given that read, the commits that want a Main checks read. `mergesToRead` now gives every row at Staging too, where Kit config names production's environment: production's read is how a production deployment starting is seen.
- **The order of the joins.** Join production's read first, with `joinDeployments`, then staging's, with `joinStaging`. `joinDeployments` moves a row from Staging to Production once a production deployment that contains it has started, and puts one back at Staging, its staging deploys unread, when production's read holds no such Deployment any more; `joinStaging` then settles it. The joins agree with the rule only in that order.
- **The Standing.** A Standing's `place` can be `staging`. `STANDING_NAMES` gains `on-staging`, `trial-accepted` and `trial-problem`, and `merged`, `deploying`, `deploy-failed` and `no-deploy-seen` are said at Staging too. In a repo that declares `staging`, every merged agent pull request's Standing, at Staging and at Production, carries `detail.staging`: `environment`, `productionEnvironment`, `trial`, `result`, `standsUntil`, `mainChecks`, `check` and `checksUnread`. `trial` is `needed` and `why`, one of `ui-evidence`, `closes-trial-problem` and `no-screen`. `standsUntil` is null while the pull request waits on the Operator. `wordStanding` words every one of them.
- **The Staging trial.** `TRIAL_ACCEPTED_LABEL` and `TRIAL_PROBLEM_LABEL` are the two labels' names. `trialProblemLine` writes the line a Trial problem's body carries and `trialProblemIn` reads it, so a reader holds no format. A label counts only when the Operator put it on, so a reader that records a result must put the label on with the Operator's own credential: one put on by an App, the reader's own included, is ignored.
- **The Promote list.** `promoteListOf` works it out from a gather's facts and the `StagingRead` a reader made for its rows, with no request of its own, and gives `null` for a repo that declares no `staging`. A `PromoteList` has `repo`, `start`, `entries`, `notAccepted`, `leftOut` and `dispatchPage`. A `PromoteEntry` is an agent pull request's or a Plain one's, told apart by `is`. An agent entry's `result` is `untried`, `accepted`, `problem`, `no-screen` or `not-on-staging`, the last with the Standing's `name` and whether that is for want of a read, `unread`. An agent entry also carries `standing`, its Standing at Staging for the same facts, whether or not its row still stands: `wordStanding` words it, so a reader words no result itself.
- **The fact builders.** `aStagingFacts` builds what a gather reads past the last day, `aStagingRead` a staging read and `aMainChecksRead` a Main checks read, beside `homeFactsOf`, `aDeploymentsRead` and `aDeployOf`, so a reader's fake data for Staging is the Kit's own facts.
- **The gather.** In a repo that declares `staging`, `gatherRepo` reads past the last day: the pull requests merged since the Promote list's start, agent and Plain together, the 100 most recent at most, with the label events and the Trial problems a result is read from. They are under a new optional key of `Facts`, `staging`. It makes more queries there, the repo's Deployments among them, and when GitHub refuses or fails that read it gives no facts and says why, as when any query of the facts fails. In any other repo it asks what it ever asked.
- **The reader's credential** needs Deployments read on the Product repo, as for production, and Checks read for the Main checks read. With a credential that cannot read check runs, in a repo that names Main checks, a merge whose staging deploy succeeded reads Deploying, saying the Main checks on its commit could not be read, and never On staging.
- **What a reader's own code meets.** `KitConfig` gains a required field, `staging`, so a reader that builds one by hand, and not from `DEFAULT_KIT_CONFIG`, must add it. A reader that switches over every `place` or every Standing name has one more place and three more names. An `on-staging` Standing that needs a Staging trial is `yours` and does not stop work, as `yours-to-read` and `parked` are, so a reader that files rows by `yours` and `stopsWork` needs no change for it. Every other addition is an optional field, `StandingFacts`' among them. This line is a guess until the release is checked against the Console (step 4 of [releasing.md](../releasing.md)), and that run's answer replaces it.
- **What a reader kept.** `STANDING_SCHEMA` stays 2: a new place and new names do not move it. A Standing or a row kept before this release reads back through `readStanding` or `readRow` as it was kept, and a row kept before it has no `staging` key and needs none. `joinStaging`, `stagingMergesToRead` and `commitsToCheck` refuse a Standing of another schema, as every export that takes kept rows does, so a reader that keeps rows across a move of its pin reads them back through `readRow` first.

## Why a minor

It adds behaviour, so not a patch. It adds two Kit config fields, `staging` and `production.workflow`, each `null` by default, so a Product repo merges the bump and edits nothing. It changes no caller or shim, asks for no new secret and no new permission for the Fabrik App, and leaves the Run-record schema and the Standing schema as they were. For the read library it adds exports, fields, a place and Standing names, and by the releasing guide a new export, a new field or a new Standing name is not a major, and a new place is counted as a new name is. So is a name said at the new place with a meaning of its own there: `deploying` at Staging also says a deploy that succeeded and whose Main checks have not passed, and at Production it means what it meant. It removes nothing the read library exports and changes what none of it means. Staging trials are opt-in: the feature stays dormant until the Operator's step is done, which the **To turn it on** section names. No run reads `staging`, so none can fail for want of the step. If the release that ships this is a higher kind for another Spec's sake, this part needs nothing beyond the bump.

## To turn it on

The steps are the Operator's, in each Product repo that deploys every merge to a staging environment. Take them on the Pilot first, after merging this release's bump PR there, then on the other Product repos that want it.

1. **Declare `staging` in Kit config**, with the site's address as `url` and the name its deploys carry in GitHub's Deployments as `environment`, such as `"staging": { "url": "https://staging.shop.example", "environment": "staging" }`. Kit config is a Trust-root file, so this is the Operator's own pull request: write the block by hand, or answer Setup's staging question in the next step, which writes it in its setup PR.
2. **Run Setup again** at the release, which creates `fabrik:trial-accepted` and `fabrik:trial-problem`. While Kit config declares no `staging` it also asks where staging is, beside production's question: it offers the environment named `staging` from the repo's Deployments, else a choice among the others it has, never production's, and then the address on that environment's newest successful Deployment.
3. **Optionally, declare `production.workflow`**, the file name of the workflow the Operator dispatches to deploy production, such as `"workflow": "deploy.yml"` in the `production` block. It only gives the Promote list its dispatch page.

Then merge a UI pull request on the Pilot and check that a reader of the Kit shows it Deploying, then On staging as the Operator's move, that its links open the staging site, and that putting `fabrik:trial-accepted` on it as the Operator turns it Accepted.

## Upgrading

- **A Product repo merges the bump**, as for any minor, and does nothing else. Until it declares `staging` it reads exactly as before.
- **The store needs nothing.** Its Run records, its caller and its schema are as they were.
- **A reader of the Kit moves its pin**, and meets what the section for a reader lists. The rows and Standings it kept read back as they were kept.

## What it does not cover

- **A host that reports no Deployments to GitHub.** Staging is read from GitHub's Deployments, as production is (ADR-0021), and unlike `production` the `staging` block has no form without an `environment`. Where the staging host reports none, a merged pull request reads Merged, then No deploy seen, and is never on staging, until the staging deploy runs from an Actions job that names an environment, since GitHub then records the Deployment itself.
- **A staging site whose data differs from the Sandbox's.** The Kit seeds nothing on a deployed environment, and a Product repo's staging data is its own business. That is why a staging link never opens a record.
- **A rollback.** Nothing says production went back to an earlier commit. A production deployment of an earlier commit moves the Promote list's start back to that commit, so the pull requests merged after it are on the list again.

## Things to know

- **Turning it on can put many pull requests in the Operator's queue at once.** The gather reaches back to the newest successful production Deployment, and to the first successful staging Deployment in a repo that names no production environment or has never deployed one. Every UI pull request among the 100 most recent merges since is untried, and once on staging it is the Operator's move. In a repo that names no production environment nothing ever takes one, so each stands until the Operator gives it a result: putting `fabrik:trial-accepted` on one settles it.
- **A later deploy can move an untried pull request back.** The Main checks are read on the newest successful staging Deployment that contains the merge, so a pull request on staging goes back to Deploy failed when a later deploy's Main check goes red. One with a result is never moved by a later deploy.
- **The Kit doesn't check when a label was put on, or that a Trial problem exists.** A label put on before the change reached staging counts, and `fabrik:trial-problem` with no Trial problem reads as a problem with no issue named.
- **A join cannot make a row.** A pull request whose Standing at Staging has ended has no row for `joinDeployments` to move to Production, so it gets its Live row at the first gather after the production deployment succeeds.
- **The Promote list can say unread of a pull request production has begun to take.** Once a production deployment has started on an untried pull request its row is at Production, and `stagingMergesToRead` asks no more about it. Where the `StagingRead` given to `promoteListOf` then holds nothing of its merge, its entry reads `not-on-staging`, with `unread` true.
- **Which merges production has taken is told by time.** The gather keeps the pull requests merged after the commit production last deployed was committed, and the Deployments read of production says of each whether a deployment contains it.
- **A Deployment that shows inactive alone is read by its age.** GitHub keeps what a Deployment reported for 90 days, all but its latest report, and marks a success inactive once a later deploy succeeds. So where the gather looks for the Promote list's start, a Deployment created more than 90 days ago that shows inactive and no success is taken for one that succeeded, its success since deleted. A younger one would still show a success it had, so it never succeeded and is passed over, as the Deployments read passes it over.
- **Production's links are as they were.** A merged row's production link to an Evidence shot still opens the path its Journey visited in the Sandbox, which production may not hold. A staging link avoids that, and production's stays, since changing what an export means is a major.
