# Release notes: Replay

The notes for the minor release that ships Replay ([#156](https://github.com/jrey8343/fabrik/issues/156)). Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- **The Operator can test one change before making it.** File an issue labelled `fabrik:replay` whose body holds one ` ```replay ` block naming one variable: `implement.model`, `implement.effort`, `review.model` or `review.effort` set to a value, or `kit` set to a full Fabrik commit sha whose prompts and Base skills to try, such as a Retro proposal's. `tickets:` optionally lists up to 10 Tickets. A model must be a full Claude model name, such as `claude-opus-5-5`: CLI aliases are refused, and so are Fable and `best`, as Kit config refuses them. Only the Operator's replay issues run, and Intake leaves them alone. The README's Replay section has the whole of it.
- **The tick accepts or rejects it.** On the next hourly tick the Kit reads the request. A bad one gets one comment saying why, and an edit to the body fixes it. A valid one is accepted once: the Kit picks its Tickets and lists them in the body below the Operator's text, with their flags. It picks 5 by default, the most recent merged Tickets spread across thirds of their original cost, or the listed ones. A picked Ticket must be merged and never reverted, its first Implement run must have left a Run record with a `baseSha`, and its merged PR must have changed no Trust-root file.
- **Each Ticket runs twice from its `baseSha`.** The baseline runs with the models and efforts Kit config held at `baseSha`. The variant changes only the variable. Each arm's Implement and Review jobs fetch that one commit alone, with no branch or tag, so neither agent can read the merged result from its checkout. Each arm is one Implement run and one Review on the pinned release, with no Retry and no Step-up. Each arm's gates run `sandbox.setup`, `sandbox.build` and `sandbox.test` on its diff, then the merged PR's test files over it. The Scorers score every replay Implement run. Nothing changes in the Product repo: no branch, no PR, and no label or comment except on the replay issue.
- **Only on spare capacity.** The tick starts at most one Ticket per hour, both arms, by adding the new trigger label `agent:replay` to the replay issue, and the claim job takes it off. It starts one only while Dispatch has nothing to start, no Subscription has an open weekly-limit or usage-credits issue, and the last weekly-limit reading on the Subscription it would use is `allowed` and under 50%. One replay Ticket runs at a time across every replay issue, which the claim checks again across all of the Operator's replay issues. `agent:replay` added by hand starts the next Ticket at once, as `agent:implement` added by hand starts past Dispatch's cap: only a replay Ticket in progress or a used-up Subscription stops it. A replay run is never held and never re-run on another Subscription.
- **New jobs in the Loop workflow.** The claim job claims a replay Ticket too. Then each arm runs as a matrix leg of four jobs: **Replay implement** and **Replay gates**, which hold no write credential, **Replay review**, with only the agent service account, and **Replay score**. None is named `Implement`, so Dispatch never counts them. The **Replay record** job, the Replay's own push job, writes both arms to `fabrik-runs` and lands the run on the replay issue. ADR-0009 has an addendum for it, and ADR-0003 one for the candidate Kit sha, which lays only the role prompts and the Base skills lock over the pinned release. The push job never runs on a replay. A run the Replay record job can't land at all, as when 1Password is down, the tick releases once its Ticket has been in progress longer than a run can last at Kit config's timeouts, plus an hour (210 minutes at the defaults), as an Infrastructure failure: it runs once more, then fails, so no Ticket stays in progress for good.
- **The results.** The body grows a results table as each Ticket finishes, with a row per arm: gates, Verdict, hidden tests, the three scores, cost, turns, duration, the arm's patch in `fabrik-runs`, and the Ticket's flags. Under it are the totals per arm beside the original runs, the baseline's gap from the original, and a headline the Kit computes from the totals. No model judges the results. When the last Ticket is in, one comment mentions the Operator, and the issue stays under Waiting on you in the Weekly summary until it's closed. Closing a replay issue cancels it.
- **Two deliberate refinements of the Spec.** A weekly-limit reading whose limit has reset since counts as spare capacity, whatever it said, so a quiet repo, whose newest reading may come from before the reset, never waits on it for good; the Spec counts only no reading as spare. And a Ticket whose Kit config at `baseSha` doesn't resolve under this release, or already runs the variable's value, is left out of the pick, the default pick taking another, since its two arms would be the same; the Spec's eligibility rules name neither.
- **Run records move to schema 4**, not the schema 3 the Spec planned, since UI prototypes already used 3. A record's new `replay` field names the replay issue, the arm, the Ticket and a `kit` variant's candidate sha, and is `null` for every live run. Score files move to schema 2 and carry the same field. The paths of a replay run's record, transcript, judge record and score file name its arm. The Weekly summary and the Retro leave replay records and score files out of every figure. The week's total gains a **Replay spend** line in a week that had any.
- **Bump the `fabrik-runs` caller with the Pilot.** A Weekly summary or Retro evidence job on an older Kit leaves schema 4 records and schema 2 score files out, the live runs' included, since every record this release writes is schema 4. So bump the `fabrik-runs` store's caller to this release when the Pilot takes it, or the next Weekly summary drops the Pilot's runs. The same goes for a Product repo you roll back from this release: its next Retro won't read the records it wrote meanwhile.
- No shim change, no Kit config field, no new secret and no new App permission. The Fabrik App already has Contents on `fabrik-runs`, and the tick only narrows it to read. The only setup step is re-running `/fabrik-setup` at this release, which creates the `fabrik:replay` and `agent:replay` labels. Without them nobody can file a replay, so nothing runs. A Product repo with no open replay issue reads nothing new and spends nothing on Replay. Without `fabrik-runs`, a valid replay request is never accepted and nothing runs. Only a request that doesn't read still gets its one comment.

## It starts on taking the release

There's nothing to turn on beyond the labels. A Product repo gets Replay once it merges the bump PR and re-runs `/fabrik-setup`, and nothing runs until the Operator files a replay issue there.

1. **Take it in the Pilot first.** Merge this release's bump PR in the Pilot only, bump the `fabrik-runs` store's caller to the same release, and re-run `/fabrik-setup` at this release in the Pilot for the labels. Then check:
   - with no replay issue open, the hourly tick's "Check out the store for the replay step" step says no replay issue is open and checks nothing out, and the tick plans what it did before;
   - a 2-Ticket experiment, `review.effort` set to an effort the Pilot's Kit config doesn't already run at, with `tickets:` naming two merged Tickets: the next tick accepts it and lists both Tickets, then runs one Ticket per tick, and only while Dispatch is idle (no ready, unblocked Ticket waiting);
   - each Ticket's run: the claim job takes `agent:replay` off, both arms' Replay implement, gates, review and score jobs run, and the Replay record job lands it, with no branch, PR or label anywhere but the replay issue, and Dispatch's in-flight count unchanged while the arms run;
   - its records in `fabrik-runs` carry `replay`, with the arm in each path, beside each arm's patch and gates file under `replays/`, and the next Weekly summary leaves them out of its metrics and shows them only on its Replay spend line;
   - the results table and headline match the stored records: each row's gates, Verdict, hidden tests, scores, cost, turns and duration, and the totals;
   - one comment mentions you once both Tickets are in, and the issue sits under Waiting on you in the next Weekly summary;
   - `agent:replay` added by hand to a second experiment's issue while a Ticket of the first runs: its claim plans nothing, saying which Ticket is in progress;
   - a second experiment closed while its first Ticket runs: the run finishes and keeps its records in the store, but the body isn't rewritten, and no later tick starts its next Ticket;
   - a `kit` request naming a Fabrik commit on a branch is accepted, which checks the Fabrik App's token can read jrey8343/fabrik's commits, and its variant's Implement step summary shows the candidate's prompts laid over the Kit;
   - how long the tick's sparse checkout of the store takes, and the tick's total time, against its 10-minute timeout.
2. Once the Pilot is healthy, merge the bump PR in the other Product repos, and re-run `/fabrik-setup` in each for the labels.
