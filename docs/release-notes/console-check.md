# Release notes: the Console check

These are the notes of the Console check's part of the major that carries the Kit's Operator sessions ([Spec: The Console check: `console.app_id`, Setup's part, and the Kit's read leaving it out](https://github.com/jrey8343/fabrik/issues/914)): on a Product repo whose Kit config names the Console's own GitHub App, Setup requires a check only that App can make, and every merge there goes through the Console. Each of the major's five parts has its own notes, and this is the Console check's. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

This draft holds the part of each of the Spec's six Tickets: the Console check's name and `console.app_id` in Kit config ([#919](https://github.com/jrey8343/fabrik/issues/919)), the Required checks read leaving the Console check out ([#920](https://github.com/jrey8343/fabrik/issues/920)), the Review's wait skipping it ([#921](https://github.com/jrey8343/fabrik/issues/921)), Setup requiring it ([#922](https://github.com/jrey8343/fabrik/issues/922)), Setup's merge ask ([#923](https://github.com/jrey8343/fabrik/issues/923)), and ADR-0019, the Glossary and the README ([#924](https://github.com/jrey8343/fabrik/issues/924)).

## Release-note line

On a Product repo whose Kit config names the Console's App in `console.app_id`, Setup requires the Console check, `Merge from the Console`, from that App, and the repo merges only from the Console: GitHub refuses a merge at any head that App hasn't passed, from github.com, `gh` and an Operator session alike. The read library leaves the Console check out of the Required checks and hands it back as `consoleCheck`, whether the branch requires it and the App GitHub expects it from, so nothing waits on it, re-runs it or names it as in the way. Nothing changes on a repo without the key.

## Why

On a throwaway repo protected exactly as Setup protects a default branch, a cloud session acting as the Operator merged at green Required checks, by REST and through the GitHub MCP server ([Try a merge stop on GitHub that a cloud session can't pass](https://github.com/jrey8343/fabrik/issues/815)). Auto mode refused the merge sent through the shell and let the same merge through as an MCP tool call, and a session can turn its own Required checks green by pushing the workflow its branch runs. The one stop that held was a check run expected from the Console's App: GitHub refused every merge until that App had made it, one beside a check run of the same name from the branch's own workflow included.

## What changed

- **The Console check's name, and `console.app_id`** ([#919](https://github.com/jrey8343/fabrik/issues/919)). The name is one constant, `CONSOLE_CHECK`, `Merge from the Console`, in `src/kit/consoleCheck.ts`, which imports nothing. Kit config gains a `console` block with one field, `app_id`: the numeric id of the Console's own GitHub App, whose presence says the Console covers the repo, read as `console.appId`, null when the key or the block is left out. A value that isn't a whole number of at least 1, a `console` that isn't an object and a field the block doesn't know are each a Kit config error naming the field, and so is `sandbox.checks` naming `Merge from the Console`, by its index, since the Console check is never a Required check. The starter Kit config and the README's defaults block hold no `console` block.
- **The Required checks read leaves it out** ([#920](https://github.com/jrey8343/fabrik/issues/920)). `readRequiredChecks`, `readDefaultBranchRequiredChecks` and so every reader of the Required checks read the branch's list without the Console check, by its name alone, from its protection's list and from each active ruleset's. It is in neither `required` nor any head's list, and no head is read for it, so a branch that requires it and nothing else requires nothing. The read hands it back as `consoleCheck`: `required`, with `apps`, the id of the App GitHub expects it from in each place the branch requires it, the protection's first and then each active rule's, or null where one names no App; `not-required`; or `unknown` when the branch couldn't be read. Whether the branch holds admins is judged from the protection's whole list, the Console check in it, as before. The read library exports `CONSOLE_CHECK` and `ConsoleCheckRead`.
- **The Review's wait skips it** ([#921](https://github.com/jrey8343/fabrik/issues/921)). The wait reads what `gh pr checks` printed without the Console check, whatever it reported, so a failed or running one neither holds the wait nor is among the red checks it re-runs, and no Failure excerpt or failure report names it. A head on which only the Console check has reported has no checks. The first wait and a Re-run checks run's wait both end as though it weren't there.
- **Setup requires it from the key's App** ([#922](https://github.com/jrey8343/fabrik/issues/922)). Where the checkout's Kit config names the Console's App, Setup's protection step requires the Console check on the default branch at once, beside the checks it already requires, with the key's id as its `app_id`, and keeps the App it finds beside every other check. It leaves the branch alone only once it requires the Console check from that App, so a branch that requires it from another App, or from none, is put right. The step names the Console check with its App beside it, so a change of App alone is a named change. On a run that adds the check or changes its App, the plan gains a note: from this run on the default branch merges only from the Console, the setup pull request's included; Setup can't check the Console is ready, so look for the repo there first; and until the Console can pass a head there, the only way to merge is the Merge gate's by-hand way past. Without the key, Setup adds no Console check and gives no note, and keeps one the branch already requires as it finds it. Setup still never removes a check, the Console check included, and never writes one into a ruleset.
- **Setup's merge ask follows the key** ([#923](https://github.com/jrey8343/fabrik/issues/923)). Where the Kit config the setup pull request merges, the setup branch's, names the Console's App, the setup pull request's Merging section and Setup's closing lines say to merge it from the Console once its Required checks pass, after any tokens to store by hand, since GitHub refuses the merge from anywhere else, github.com and `gh` included. Where that Kit config doesn't name it, or is missing, unreadable or invalid, a first setup's included, they say what they said, word for word: merge it yourself.
- **ADR-0019, the Glossary and the README** ([#924](https://github.com/jrey8343/fabrik/issues/924)). ADR-0019 says that on a Product repo the Console covers, the Merge gate holds a merge to the Console, by the Console check, which is not a Required check; why, from the trial; the options it weighed; what it costs; and that the by-hand way past is also the only way to merge there while the Console is down. The Glossary has the Console check as a term of its own, and its Merge gate and Required check say where it stands. The README's Merge gate says the same, beside what the Tickets before added to its Kit config section, its Branch protection bullet and its section on reading the Kit from another program.

## For a reader of the read library

- **New exports.** `CONSOLE_CHECK`, the Console check's name, `Merge from the Console`, and the type `ConsoleCheckRead`, through the read library's entry, `src/read/index.ts`. A reader that makes the check makes it under `CONSOLE_CHECK`, the one name the read leaves out.
- **`RequiredChecksRead.consoleCheck`.** Every `RequiredChecksRead` carries `consoleCheck`, so a reader that builds a `RequiredChecksRead` itself must fill it. A reader that knows its own App's id can tell a covered repo whose branch doesn't require the check yet, and one that expects it from another App.
- **`required` and every head's list leave the Console check out** on a branch that requires it, wherever it requires it, by its name alone. Nothing a reader builds from them waits on it or names it as in the way, so a pull request on a covered repo reads as it did before the key.
- **`KitConfig.console.appId`.** `resolveKitConfig` gives a Kit config's `console.app_id` as `console.appId`, null where it is left out, and `DEFAULT_KIT_CONFIG` has `console: { appId: null, heldWorkflows: [], sessionEnvironment: null }`, the Held workflows' list and the Session environment's name beside the key being their parts of the same major, so a reader knows which repos the Console covers from the Kit config it already reads.

## What the Console needs

- **Its pin moved, `consoleCheck` filled wherever it builds a `RequiredChecksRead`, and its own part built from its Spec before any Product repo is given the key.** The Console's own part, making the check at the tap of Merge and the rest, is [Write the Console's Spec and cut it into slices](https://github.com/jrey8343/fabrik/issues/913). This line is a guess until the release is checked against the Console (step 4 of [releasing.md](../releasing.md)), and that run's answer replaces it.

## Why a major

The release is one major with the four other parts of the Kit's Operator sessions ([How are the Specs cut, and who builds them?](https://github.com/jrey8343/fabrik/issues/874)), so each Product repo takes all five by the same two runs of Setup. By the releasing guide's [Choosing the version](../releasing.md#choosing-the-version), this part's new Kit config field and new exports alone would be a minor: the field has a default, and a new export is not a major. `required` and every head's list leaving out a check the branch requires is a change in what an export gives, which the guide counts as a major, whatever it asks of a Product repo.

## Upgrading

- **A Product repo runs Setup at the major**, naming it, as the major asks, since Dependabot opens no pull request for a major; without the key nothing of this part changes, and a first setup is unchanged: the starter Kit config holds no key, so the setup pull request still merges on github.com.
- **The key comes later, repo by repo.** A repo's Kit config is given `console.app_id` only once the Console can pass a head there, and that repo's Setup run then requires the check. Each is that repo's own sitting, filed in that repo.
- **Kit bumps and Setup's own pull requests merge from the Console on a covered repo like any other.**

## What does not change

- **The Required checks a Review waits on, the Standing, the re-run and the hourly tick** read as they did on a repo without the key, and on one with it but for the Console check, which none of them sees.
- **The Merge gate ruleset**, `Fabrik Merge gate`, is as it was: only repo admins may update the default branch.
- **`fabrik` and `fabrik-console`** are outside the Merge gate: neither default branch is protected, and nothing here holds a merge into either.
- **No Loop rule, job, prompt or label reads the key.** Kit config is a Trust-root file, so no agent can change it.

## Known limits

- **Setup can't tell whether the Console is ready.** A repo given the key before the Console can pass a head there merges only by the Merge gate's by-hand way past, which is also the way to merge a covered repo while the Console is down: there is no second way past.
- **Setup never removes the check.** A Kit config that drops `console.app_id` leaves the Console check on the branch, so the repo still merges only from the Console, while Setup's merge ask goes back to saying to merge it yourself. The check comes off the branch only by hand.
- **Not tried on GitHub.** Setup's PUT with an App beside a check was not tried on GitHub before this release (the trial set it by hand), nor whether GitHub takes an App id there before that App is installed on the repo with Checks write.
