# Release notes: The Kit opens issues itself

The notes for the minor release in which the Kit opens issues itself ([#882](https://github.com/jrey8343/fabrik/issues/882), ADR-0039), so that work the Operator has already asked for becomes an issue without the Operator opening it by hand. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

This draft holds all three of the Spec's parts: a Design session's Spin-offs ([#883](https://github.com/jrey8343/fabrik/issues/883)), a Request changes that asks for a Spin-off ([#884](https://github.com/jrey8343/fabrik/issues/884)), and a Follow-up that is a fault ([#885](https://github.com/jrey8343/fabrik/issues/885)).

## Release-note line

A Design session now opens the issue for work you put off in an answer: a Spin-off, opened with `needs-triage` as the session finishes and named in its closing comment, so no Operator step and no Pairing session exists only to open an issue. A Request changes can now ask for a point to be its own issue: say so in words, and the run leaves that point unbuilt, the Kit opens it as a Spin-off that waits on the pull request's Ticket, and a Request changes that asks for nothing else returns the pull request to the Merge gate with no Review. A Follow-up is now a fault or an idea: the Kit opens each fault as an issue when the pull request merges, under a new cap, `caps.follow_up_issues`, and an idea stays a link.

## What changed

- **A Design session opens its Spin-offs.** A Spin-off is work the Operator's answers put outside the session's outcome, which the Kit opens as an issue of its own. Any finish but a Map can carry them, in `spinOffs`: an agent brief, an Operator brief, a Spec, a split, a Roll-in and not planned. A round and a Map take none, and an output that gives one there is refused.
- **Only on the Operator's word.** The session writes a Spin-off when an answer of the Operator's states or implies that some work is wanted but is not part of this outcome, such as "not now", "later" or "leave that out of this one". It writes none for work the Operator did not speak to, none for work an open Ticket already holds, which the closing comment names instead, and it asks no question only to confirm one. Work the session designed fully is still a Ticket of its Spec.
- **What the Kit opens each one with.** The Kit opens each Spin-off in the plan that finishes the session, as the Fabrik App, in the same repo, with `needs-triage` and no other label, as a Check's issue is opened, so a Triage run follows. Its body opens with one hidden line, `<!-- fabrik:spin-off {"from":"design","issue":<n>} -->`, which says it is a Spin-off and names the issue whose Design session it came from. There is no new label: Kit code reads that line only as the first line of an issue the Fabrik App opened. When the finish writes a Spec or a split, the body ends `Follows #<Spec> (its Tickets: …)`, naming the Spec and its Tickets by the numbers the Kit gave them, so a Design session on the Spin-off is given those Tickets.
- **It can wait on work not yet built.** Each Spin-off has a `blockedBy`, under the rules of a Ticket's, which the Kit writes as native blocked-by edges: the key of a Ticket or an Operator step of the same Spec or split, the number of an open Ticket in "The open Tickets", and, on an agent brief, the issue the brief rewrites. A number not in "The open Tickets" is refused by the agent job, as a Ticket's is. The edges hold Dispatch, not Triage, which runs at once.
- **The closing comment names each one.** It ends with a list of the Spin-offs the Kit opened: for each, its number, its title and its `restsOn` line, the one line of the session's output that names the Operator's answer it rests on, written as `Rests on: …` under the title. The session writes neither the list nor the links. A Spin-off mentions nobody and is assigned to nobody.
- **Triage never sets one aside on its own judgement.** Triage's input marks a Spin-off with `spinOff`, and its prompt says a Spin-off exists because the Operator asked for it: it goes to the Fast path, a Design session or `ready-for-human`. A `wontfix` on a Spin-off with no `duplicateOf` is refused, by the agent job, which asks Triage once to put it right, and again by the push job. One that names an original closes as a duplicate, as any issue does.
- **No Operator step opens an issue.** An Operator step's `newIssue` is refused, with a message that names `spinOffs`, and the Kit writes no Open as issue link on an Operator step. An Operator step already open keeps the link its body has.
- **A Request changes can ask for a Spin-off.** In a Request changes on an agent pull request, say in words that a point is to be its own issue: "open this separately", "as its own issue", "in a different ticket", or any words that say so, in the review's own text or in a comment on the code in it. The Request-changes run leaves that point unbuilt, returns it in `spinOffs` with a title, a body that stands alone and quotes your words, and the id of the review or comment that asked for it, and builds every other point. A point without such words is built, however large or unrelated: the run recognises your instruction and never decides for you what belongs apart, and where it can't tell, it builds. An Operator comment asks for none, as it asks for no work. No other Implement run's `spinOffs` is read.
- **What the Kit opens a Request changes' Spin-off with.** The Kit opens each in the plan that lands the run, whether it pushed or committed nothing, as the Fabrik App, in the same repo, with `needs-triage` and no other label. Its body opens with `<!-- fabrik:spin-off {"from":"request-changes","pullRequest":<n>,"review":<id>} -->`, naming the pull request and the review, and ends with a `From PR #<n>` line. It has a blocked-by edge to the pull request's Ticket, so Triage sorts it at once and Dispatch holds it until that Ticket closes as completed. A Spin-off whose `from` names anything but a Request changes of yours on the pull request, or a comment of yours on the code in one, is refused: by the agent job, which asks the run once to put it right, and again by the push job, which reads the reviews itself.
- **The run's comment lists each one.** The run's comment on the pull request, its push note or its note that it committed nothing, ends with the Spin-offs the Kit opened: for each, its number, its title and a link to your words. The same comment records each on a hidden line, `<!-- fabrik:spin-off-opened #<issue> {…} -->`, which is where later runs, Reviews and the Digest read them. It mentions nobody.
- **A Request changes of only Spin-offs costs no Review.** The run commits nothing, and the pull request goes back to the Merge gate at the same head, out of draft with your review requested: no Review runs, no retry is used and nothing is handed back. Kit code decides this, never the run. It can't read a point, so it goes by asks: the review's own words when it has any, and each of your comments on the code in it. The pull request goes back to the gate only when the run committed nothing, the head did not move, the latest Verdict is a pass on that head, and every ask of every review the run read is named by a Spin-off. Anything short of that is handed back, as a Request-changes run that committed nothing always was, or reviewed when the head moved, with its Spin-offs opened all the same. A Request changes that came while the pull request's Digest was still being written gets that Digest first, and then the gate opens.
- **Later runs and Reviews are given them.** Every later Implement run and Review on the pull request, and the Digest writer, is given "The points set aside as Spin-offs": each one's issue, and your words it came from. A later run builds none of them and returns none again. The Reviewer holds a point properly set aside to be no part of the Ticket as amended, and never a finding for being unbuilt; a point set aside that your words did not ask to separate is an unbuilt requested change, an Execution flaw. A point set aside neither amends the Ticket nor is a Review miss.
- **The Digest shows them under the ask.** Kit code's facts carry `spinOffs` on each ask the Kit opened one from, and the fourth fold shows them under it. The writer answers such an ask for what was to be built, and has a fourth answer, `set-aside`, for an ask none of which was, which needs no item under Needs your eyes. Kit code refuses `set-aside` on any other ask and on a criterion. The Digest already on a pull request that went back to the gate on its earlier pass stays as it is.
- **A Follow-up is a fault or an idea.** The Reviewer marks each Follow-up on a pass with its kind. A fault is something already wrong: a bug, a test that is missing or fails, a doc that is stale. Its body says where it is, by file and line, and what shows it is wrong. An idea is anything else, such as an improvement, a refactor or a feature, and so is a problem the Reviewer cannot show that way. In the Reviewer's reply an item is `- [fault] <title>` or `- [idea] <title>`, and one with neither mark is an idea.
- **The Verdict says which.** A pass's comment still lists its Follow-ups under `### Follow-ups`, the ideas first and then the faults. An idea has its Open as issue link, as every Follow-up had. A fault has, in place of a link, the line "The Kit opens this fault as an issue when the pull request merges." A Verdict posted before this release lists links alone, so every Follow-up on it is an idea.
- **A fault opens as an issue at the merge.** When an agent pull request merges, the Kit gathers every fault any pass on it named, in the order named, and drops one whose title, outer spaces aside, repeats an earlier one's. It leaves out one you already opened, by the rule that read a Follow-up as opened before: an issue of yours whose body has the `From PR #<n>` line and whose title is the fault's, open or closed. It opens each of the rest as the Fabrik App, in the same repo, with `needs-triage` and no other label, so a Triage run follows. The body opens with one hidden line, `<!-- fabrik:follow-up {"pullRequest":<n>} -->`, then holds the Reviewer's text, and ends `From PR #<n>`. There is no new label: Kit code reads that line only as the first line of an issue the Fabrik App opened. An idea is never opened. A Plain pull request has no Verdict, so nothing opens for one, and nothing opens for a pull request closed unmerged.
- **A cap on the Follow-up issues the Kit has open.** `caps.follow_up_issues` (default 5) is a new Kit config field, and like the other caps it can only be lowered: a value above 5 is a Kit config error. It counts the open issues in the repo that the Fabrik App opened and whose first line is the Follow-up marker, whichever pull request each came from. A merge opens its faults only up to the room under it, and each fault over it stays an Open as issue link. At `0` the Kit opens none, and every fault stays a link. The starter Kit config lists it at its default.
- **One comment, once.** After opening them the Kit posts one comment on the merged pull request, which mentions nobody: each issue it opened, each fault left over the cap with its Open as issue link, and each fault that was an issue already. Its first line is `<!-- fabrik:follow-ups-opened -->`, and with it on the pull request a second look at the same merge opens nothing more. Hidden lines under it record which issue each fault became and which stayed a link, which is where the Retro's evidence and the read library read them. Should the push job fail after opening an issue and before posting the comment, the next look leaves out each fault the Fabrik App already opened for that pull request.
- **Triage sorts it as any issue.** Triage's input marks such an issue with `followUp`, which names its pull request, and its prompt says nobody asked for it: Triage sends it to the Fast path, a Design session or `ready-for-human`, and may set it aside, as it may not a Spin-off. A Design session that rewrites one keeps its hidden line, so it counts toward the cap for as long as it is open.
- **The Digest shows every fault.** Kit code's facts give each Follow-up its `kind`. Under **Follow-ups** the Digest lists every fault first, each once by its title, with a line saying the Kit opens it when the pull request merges, whatever the writer chose. The writer chooses only among the ideas, and Kit code refuses a reply that names a fault's id. Its choice gates nothing. The Digest's data gains `faults`, each with its `title`, beside `followUps`, which still holds the ideas shown with their links; a Digest written before this release reads with no faults.
- **The Retro's evidence says what became of each.** "Follow-ups on passing Verdicts" gives each Follow-up its `kind`. A fault the Kit opened has `kitOpened`: the issue, and its state label while open, or how it closed and whether the Operator or Triage closed it. A fault left a link has `overCap`. `openedAs` is still the issue the Operator opened from a link. The Retro's prompt says how to weigh it: faults the Operator keeps closing as not planned point at the Reviewer's bar for a fault or at the cap.
- **The read library.** Each of a row's `followUps` gains `kind`. On the row of an agent pull request merged in the last 24 hours, the Follow-ups of its last pass are now carried too, and a fault's `filedAs` names the issue the Kit opened for it, read from the Kit's comment at the merge; any other's is the open issue you opened from its link, or null. On an open pull request's row `filedAs` means what it did. The gather makes one more query for it, by number, for the latest comments of the agent pull requests merged in the last 24 hours, and keeps what they say under the facts' `mergedFollowUps`. `readRow` reads a Follow-up kept before it had a `kind` as an idea, and `DEFAULT_KIT_CONFIG` holds the new cap. Nothing is removed and no field changes meaning.
- **Why a minor:** it's new behaviour that needs nothing from a Product repo beyond the bump. No new label, no Setup step and no new App permission is needed. The one new Kit config field, `caps.follow_up_issues`, has a default, so no Kit config needs an edit, and the read library removes nothing.

## Upgrading

- **Nothing beyond the bump.** The Fabrik App already opens a Spec's Tickets, so it needs no new permission to open a Spin-off or a fault's issue.
- **Faults open by default.** From the first agent pull request that passes and merges at this release, each fault its passes named opens as an issue. To keep every Follow-up a link, as it was, set `caps.follow_up_issues` to `0` in `.fabrik/config.json`.
- **A reader of the read library** that draws a row's Follow-ups can show a fault apart from an idea by its `kind`, and reads rows it kept through `readRow`, as before. One still pinned to an earlier release reads a new Verdict's ideas and none of its faults, which is why a Verdict lists its ideas first.
- **A Product repo's own `.fabrik/design.md`.** If it tells the session to write an Operator step that opens an issue, or names `newIssue`, reword it: such an output is now refused, and the turn fails after its one chance to put it right.
- **Operator steps already open** that carry an Open as issue link are worked as before: open the issue from the link.

## What does not change

- **An idea, an Audit candidate and a Retro proposal** are still links the Operator opens.
- **A pull request already passed at an earlier release** lists its Follow-ups as links, and nothing opens for them when it merges.
- **An Operator comment still triggers nothing** (ADR-0007), and a point of a Request changes with no such words is still built on the pull request (ADR-0010).
- **A Request-changes run that commits nothing with something left to build** is still handed back to the Operator, and one whose head moved is still reviewed.
- **A live Design session** files as the Operator, so nothing it opens is a Spin-off to the Kit, and Triage sorts it like any other issue.
- **A Map** carries no Spin-off: its open questions are its Decisions.

## Known limits

- **A Design session that later rewrites a Spin-off drops its hidden line.** Triage has sorted the issue by then, and nothing else reads the line. A Follow-up issue keeps its own, which the cap reads.
- **No veto before the merge.** A fault you don't want opens all the same. Close its issue, and nothing reopens it. Lower `caps.follow_up_issues` if too many open.
- **A fault has no link on its Verdict.** One named on a pull request that closes unmerged opens nothing and has no link: its text is on the Verdict, and you open it by hand if you want it.
- **Only the merge's own event opens them.** No Tick looks at merged pull requests, so a merge whose push job failed before it opened anything opens nothing later. The faults are on the pull request's Verdicts.
- **A fault you opened and then retitled is opened again.** The Kit knows an issue as the fault's by its `From PR` line and its exact title.
- **Two merges at the same moment can pass the cap.** Each reads the count of open Follow-up issues before the other's exist.
- **A merged row carries its Follow-ups for 24 hours.** The read library reads a merged pull request's comments only while its merge is within the last 24 hours, so a row that stands longer, as one waiting at Staging does, carries none after that.
- **A Follow-up issue is Kit-owned to the read library**, as a Spin-off is. One Triage sent to an Implementer is a Ticket to its outcomes only once an agent pull request names it.
- **Triage runs before the work a Spin-off waits on is built.** Its brief or its Design session is written against the code as it stands, and Dispatch holds the Ticket until its Blockers land.
- **A Spin-off blocked by a Ticket that is closed as not planned stays held**, as any work behind such a Blocker does, until the Operator removes the edge.
- **Kit code goes by asks, not by points.** One review, or one comment on the code, can hold a point to build and a point to set aside. Once a Spin-off names it, Kit code counts the whole of it as set aside. A run that then commits nothing sends the pull request back to the Merge gate with the other point unbuilt and no Review to find it. Read the run's comment before merging: it lists what was set aside. Putting each point to be set aside in a comment of its own avoids it.
- **A run that ends without landing opens no Spin-off.** A Request-changes run refused by the trust-root guard, or that could not bring `main` in, opens none. Its Request changes still stands, and the run that follows returns them.
- **A landing that fails part-way can open a Spin-off twice.** When the push job fails after opening a Spin-off and before posting the run's comment, the run stays in flight, and landing it again opens the Spin-off again. Triage sets the second aside as a duplicate when it names the first.
- **A dismissed Request changes takes its Spin-offs out of later runs' input**, as it takes itself out. Their issues stay open.
- **The next Verdict after a run of only Spin-offs is marked as from a Request-changes run**, as after any Request-changes run that committed nothing, whichever run pushed the head it judges.
