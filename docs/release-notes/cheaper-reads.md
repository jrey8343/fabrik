# Release notes: The read library asks GitHub for less

The notes for the minor release in which the read library asks GitHub for less ([#894](https://github.com/jrey8343/fabrik/issues/894)): each read gives the answer it gave and asks fewer REST requests for it: a GraphQL query where it asked a REST request apiece, or a request about only the runs that changed. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

This draft holds all four of the Spec's parts: the gather's files in one query ([#895](https://github.com/jrey8343/fabrik/issues/895)), the Spend read's Run records a batch to a query ([#896](https://github.com/jrey8343/fabrik/issues/896)), the Deployments read's Deployments and their reports a hundred to a query ([#897](https://github.com/jrey8343/fabrik/issues/897)), and a read of named workflow runs with its fold, beside a whole runs read whose listing holds still for an hour ([#898](https://github.com/jrey8343/fabrik/issues/898)).

## Release-note line

The read library asks GitHub for less, and gives the same answers. A gather reads a Product repo's caller workflow and Kit files in one GraphQL query, the Spend read fetches new Run records 50 to a query, and the Deployments read takes a hundred Deployments with their reports to a query, each in place of a REST request apiece. A reader that knows which workflow runs changed can ask `readNamedRuns` about those alone and fold the answer into the runs read it keeps with `foldNamedRuns`, and the whole runs read is asked at one address all hour, so a conditional ask of it can be answered from what the reader holds. A reader spends more of GraphQL's allowance and less of REST's.

## Why

On 23 November 2026 the Console, reading as the Operator, spent the Operator's 5,000 REST requests for the hour in the eight minutes after a reset, and GitHub refused the Operator's own moves until the next one. Through all of it GraphQL's allowance, which is separate, stood nearly whole: about 50 of its 5,000 points used in the hour. The counts below were made that day by running each read once against a busy Product repo through a client that counted each request, but for three: the staging figure, which says it is an estimate, and the gather's queries now and the whole runs read's cost now, which say they are worked out.

## What changed

Each read gives the answer it gave before. What each cost before, and what it costs now:

- **The gather's files, in one query** ([#895](https://github.com/jrey8343/fabrik/issues/895)). Before: 11 REST requests a gather, one for the caller workflow and one for each of the Kit's ten files (the Kit config, the skills lock and each role's instructions), beside its 20 GraphQL queries. Now: one GraphQL query for all eleven, at the default branch's head the gather's first query gave, as before, and no REST request: 21 queries and none, for a Product repo whose files are all text, worked out as the Spec's 20 and the files query, not counted. A file GitHub won't give whole in a query, a binary one or one it truncates, and a symbolic link are still read singly, a REST request each. A path with nothing at it, a directory and a submodule are no file, as before, and a refusal of the query fails the gather, as a refused read of the caller workflow did.
- **The Spend read's Run records, a batch to a query** ([#896](https://github.com/jrey8343/fabrik/issues/896)). Before: a REST request for each Run record the reader didn't hold, ten at a time. Now: one GraphQL query for each 50 of them, one after another, so a hundred new records cost two queries, and a read with nothing new asks for none. It still lists the store's trees by REST, a request for each tree, and reads the store's caller singly. It asks `held` once of each record's path before it fetches any, so a reader's cap on how many new records one read fetches holds as before, and a refused batch makes the whole read unread, with why, as a refused record's read did.
- **The Deployments read, a hundred Deployments to a query** ([#897](https://github.com/jrey8343/fabrik/issues/897)). Before: a REST request for each page of a hundred of the environment's Deployments, and at least one more for each Deployment's reports. A read of a staging environment with 30 Staging trials waiting, the oldest merged five days before, at about 50 deploys a day, asked some hundreds; that one is an estimate, read from the code and the size of the bursts seen, not counted. Now: one GraphQL query for each hundred Deployments, newest first, each with its first hundred reports, and one more for each further hundred reports of a Deployment that has more, which few have. 250 Deployments since the earliest merge cost three queries where they cost 253 requests. It still stops at the first page that reaches before the earliest merge, asks nothing when asked about no merges, and asks GitHub's comparison of two commits by REST, once in a read for each pair the answer turns on. A Deployment's state is judged from its reports by the rule it was, so succeeded, failed, running and passed over mean what they meant.
- **A read of named workflow runs, and its fold** ([#898](https://github.com/jrey8343/fabrik/issues/898)). Before: a reader that learned a workflow run had changed, from a job's delivery say, could only make the whole runs read again: 15 REST requests that day, nine of them pages of the day's listing of over 800 runs, read to find the five still unfinished. Now: `readNamedRuns` asks about the runs named alone, two requests at most for each, the run and, while it is unfinished and inside the 24 hours, its jobs, with no listing and nothing for the Tick. Each run comes back with the runs in flight it tells of, by the one rule the whole read tells them by: none once it has ended, when it routed no agent run, or when it is older than the 24 hours. A run GitHub refuses comes back `"unread"`, that run alone, and the read never throws. `foldNamedRuns` puts the answer into the runs read a reader keeps, by the Kit's rule: each run read has its entries replaced by the answer's, and an unread run, every run not named, the Tick and the kept read's `readAt` are left as kept. Runs kept unread stay unread.
- **The whole runs read's listing, bounded at the hour** ([#898](https://github.com/jrey8343/fabrik/issues/898)). Before: its listing's `created` bound was the time to the second, so its address changed every second and no conditional ask of it could match. Now: the bound is rounded down to the hour, so it is asked at the same address all hour, and a reader that asks conditionally is answered from what it holds whenever the listing hasn't changed. A run from before the 24 hours, to the second, is left out after the listing, so the answer is the one a bound to the second gave. Its listing reaches back up to an hour further. An ask costs the requests it did, 15 that day, or a page more where that hour's runs take the listing onto another: worked out from the bound, not counted. It reads the runs a bound to the second read, since GitHub lists them newest first and that hour's are older than every run in the 24 hours. The Weekly summary reads its runs in flight through this read, so its listing is bounded at the hour too.

## For a reader of the read library

- **New exports.** `readNamedRuns`, `foldNamedRuns`, `NamedRunsRead`, `NamedRun`, `readFiles` and `FilesRead`, through the read library's entry, `src/read/index.ts`. Nothing the entry exported is removed or changes meaning, and no read returns anything it did not return before.
- **The files read.** `readFiles` reads several paths of one repo at one commit in one GraphQL query and gives each as its text or as null for no file, as the client's own file read gives it, reading singly only a file GitHub won't give whole in a query and a symbolic link. It throws a refusal of the query or of a file read, and asks nothing for no path. Its ref may be a branch, or `HEAD` for the default branch, which GitHub works out again for each call, so a reader that needs its paths at one commit across calls passes the commit.
- **The client.** Every read takes a `ReadClient`, as before, and two ask more of it: `readDeployments` now calls `graphql` as well as REST, and `readSpend` as well as REST and `fileText`. A reader that hands each read a whole `ReadClient` changes nothing, and one that hands either of the two a client of fewer calls gives it `graphql` too. Every new query is made through the client's own `graphql`, so a reader that counts or paces its client's calls counts these too.
- **Folding named reads.** The answer folded in last wins, whenever it was read, so a reader folds its named reads in the order it made them: two reads of one run folded out of that order can put back a run that has ended.
- **The credential.** A reader's own App needs no new permission: Deployments, contents and Actions are read as before.

## What the Console needs

- **Its pin moved, with its mock answering the new queries and its points count pricing them.** From this release a gather's files, the Spend read's Run records and the Deployments read's listing are asked by GraphQL query, so a Console test that reaches GitHub through those reads, as its test of the Deployments read does, needs the mock to answer queries where it answered REST requests, and the points count prices the files query, a batch of Run records and a page of Deployments with their reports. Its rows are the rows they were. This line is a guess until the release is checked against the Console (step 4 of [releasing.md](../releasing.md)), and that run's answer replaces it. The Console's move to this release is [fabrik-console#115](https://github.com/jrey8343/fabrik-console/issues/115), which expects as much.

## Why a minor

It adds exports, a read of named workflow runs, its fold and a files read, with their types, and by the releasing guide a new export is not a major. It removes nothing the read library exports and changes what none of it means: every read gives the answer it gave, and a read that came back unread, or threw, still does. No Kit config field, label, shim, Standing or permission changes, and neither the Run-record schema nor the Standing schema moves. Nothing is dormant, so no step turns it on.

## Upgrading

- **A Product repo merges the bump**, as for any minor, and does nothing else. The Fabrik App needs no new permission.
- **A reader of the read library** moves its pin and gets the answers it got. A reader that hands `readDeployments` or `readSpend` a client of fewer calls than `ReadClient` adds `graphql` to it, the one change to a reader's code this release can ask. From this release a reader spends more GraphQL points and fewer REST requests.

## What does not change

- **The Required checks read and the Main checks read** ask what they asked, five REST requests a head for the Required checks.
- **The Loop's own reads.** Dispatch's count of runs in flight and the Loop's other reads of Actions bound their listing to the second, as before, and the Loop reads a Product repo's Kit files a REST request apiece. Only the reads of the read library change, the Weekly summary's runs read among them, whose listing is bounded at the hour.
- **What a read returns.** No Standing, row or Run record changes.

## Known limits

- **A named read finds no run nobody named.** A run that started without a delivery the reader saw is found only by the whole runs read, so a reader still makes it now and then.
- **The whole runs read lists up to an hour more.** Its listing reaches back up to an hour before the 24 hours, so it can ask a page more than a bound to the second did. It reads the same runs: the hour's more are older than every run in the 24 hours, and GitHub lists newest first, so in a repo past the 1,000 runs GitHub lists, the runs it leaves unread are the ones a bound to the second left unread.
- **The files query asks for each directory's whole listing.** To know a symbolic link it asks for every entry of each directory its paths are in, so its answer grows with those directories: each of the Spend read's batches carries the listing of each month its records are filed under.
