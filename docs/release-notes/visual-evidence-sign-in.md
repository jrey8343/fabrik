# Release notes: Visual evidence behind a sign-in

The notes for the minor release that lets Visual evidence capture pages behind a sign-in ([#312](https://github.com/jrey8343/fabrik/issues/312), ADR-0012). Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- **Capture can sign in.** Until now capture opened a plain browser, so on an app behind a sign-in every screenshot was the sign-in page, and it read as a clean page. The `ui` block gains three optional fields, all absent by default, which come together. A `ui` block that sets none captures as before.
  - `sign_in`: each Capture identity, a named kind of fake user such as `owner`, and the command that signs it in, such as `{ "owner": "npm run sign-in -- owner" }`. At least one, each name letters, digits, `-` and `_`, starting with a letter or digit, and no command blank.
  - `sign_in_path`: the route the app sends a signed-out visitor to, such as `/login`.
  - `signed_in_routes`: an ordered, non-empty list of rules, such as `{ "route": "/admin/**", "as": "owner" }`, saying which Capture identity views a route. The first rule whose `route` matches the route's path wins, its query left out. `as: null`, or no rule matching, views it signed out. In a `route`, `*` matches within one path segment and `**` across segments, and `/**` matches `/` too. Every `as` must be `null` or one of `sign_in`'s identities.
- **A sign-in only ever reaches the Sandbox's own server, with fake users.** Kit config is refused when `sign_in` is set and `ui.url`'s host isn't loopback (`localhost`, a name under `.localhost`, `127.0.0.1` or `[::1]`), or when `sign_in_path` or `signed_in_routes` is set without `sign_in`. Rules in Kit config, never a Ticket or an agent, say who views a page.
- **The storage state contract.** Once `ui.serve` answers, and before any screenshot, capture runs the sign-in command of each Capture identity its routes need, once each, and none for a capture of public routes alone, Implement and prototype capture alike. Each runs in the Product directory, for up to 3 minutes within capture's own budget, with the env `ui.serve` gets, never `sandbox.secrets`, plus `FABRIK_STORAGE_STATE`: the path of a temp file outside the evidence folder, so a session is never uploaded. The command writes a Playwright storage state there, a JSON object with `cookies` and `origins` lists, which a Product can also write by hand without Playwright. Each signed-in route's screenshots load that identity's state at both viewports, and every public shot loads none.
- **Its limit: cookies and localStorage only.** A storage state holds cookies and localStorage, so an app that keeps its session in sessionStorage or memory can't sign in this way, and needs its own way in.
- **A signed-in route has no Before.** `ui.before_url` is a deployed site, which these sessions can't reach and must not. Public routes keep their Before. The evidence section, both Evidence pages and the Reviewer's prompt name the Capture identity on each signed-in screenshot, and the Reviewer's prompt says why it has no Before.
- **A new capture failure, `sign-in-failed`.** A sign-in command that fails, runs past its 3 minutes, or leaves no storage state that reads stops capture before any screenshot. So does a signed-in page that lands on `sign_in_path`, whose image is thrown away, the screenshots before it kept. Like every capture failure, it's named in the evidence section, never blocks the PR and never uses up a Retry. A public route is never checked, so a public route can still show the sign-in page, and an app that shows its sign-in form without redirecting to `sign_in_path` isn't caught.
- **`/fabrik-visual-evidence` asks how the app signs in.** Before suggesting any answer, it asks whether the app's pages sit behind a sign-in, and there are three outcomes:
  - **Public:** it asks for the same answers as before.
  - **Behind a sign-in, with a sign-in command:** it also suggests `ui.sign_in`, `ui.sign_in_path` and `ui.signed_in_routes` from the repo, or from the `ui` block the repo already has, for the Operator to confirm or correct. The Visual evidence writer writes them with the rest of the block, under the same rules: it keeps every other byte, running it again with the same answers writes nothing, and if the Kit config would refuse an answer, such as a sign-in with a `ui.url` that isn't loopback, it writes nothing and names each problem.
  - **Behind a sign-in, with no command yet:** it says every signed-in route would screenshot the sign-in page, leaves Visual evidence off and writes nothing. It names what the repo needs first: a command that signs a fake user in to the Sandbox's own server and writes a storage state to `FABRIK_STORAGE_STATE`. It never writes that command, since it's the Product repo's own code.
- **Why a minor:** the three fields are new, optional and absent by default, and turning them on is an opt-in Operator step. No Kit config field is renamed or removed, and there are no shim changes. So a Product repo only merges the bump PR.

## To turn it on

The step is `/fabrik-visual-evidence`, run in a Claude session in the Product repo at this release. Only a repo whose pages sit behind a sign-in needs it.

1. **The Pilot first, if its pages sit behind a sign-in.** Merge this release's bump PR. If the Pilot has no sign-in command yet, file a Ticket for one: a command that signs a fake user in to the Sandbox's own server and writes a Playwright storage state to `FABRIK_STORAGE_STATE`, using no `sandbox.secrets`. Once it's merged, run `/fabrik-visual-evidence`, say its pages sit behind a sign-in, confirm the sign-in fields it suggests with a loopback `ui.url`, and merge the PR it opens.
2. **Check it on a real UI issue** in the Pilot before the release goes anywhere else. Open an issue that changes a signed-in page and names its route in backticks, and let it run to its draft PR's Review:
   - the PR's evidence section names the Capture identity on the signed-in route, and its Evidence page shows the signed-in page, not the sign-in page, with no Before;
   - a public route the issue also names keeps its Before;
   - breaking the sign-in command on a branch gives `sign-in-failed` in the evidence section, and the PR still opens.
3. **Then the other Product repos whose pages sit behind a sign-in**, when they want it, the same way. A repo whose pages are public merges the bump PR and needs nothing more.
