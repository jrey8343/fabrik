# Release notes: What the Implementer is given

The notes for the minor release that gives every Implement run the Product repo's Coding standards, holds a Ticket's acceptance criteria to what a run can meet, and runs Design sessions at `high` ([#761](https://github.com/jrey8343/fabrik/issues/761)). Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## Release-note line

Every Implement run is given the Product repo's Coding standards, and a criterion no run can meet costs a Ticket one Design flaw instead of its Retries: Design sessions write none, an Implementer builds the rest and names it, and the Reviewer sends it back to design the first time it finds one. Design sessions run at `high`.

## What changed

- **Every Implement run is given the Coding standards** ([#762](https://github.com/jrey8343/fabrik/issues/762)). The whole of a Product repo's `CODING_STANDARDS.md`, from the root of the checkout, now goes inline into the Implementer's prompt, under the same heading and in the same form as the Reviewer's, with nothing cut or summarised. That covers a first run, a Kept-branch start, a Retry (the Step-up included), a Touch-up, a Request-changes run, a conflict-only run and a Replay Arm's Implement run, which gets the file as the Ticket's base commit holds it. The Implement prompt tells the run to build to it in the code it writes or changes, says the Reviewer judges the pull request against the same text, and has it name older code that breaks a rule in its summary instead of fixing it. A repo with no such file gets nothing in its place, a prototype turn gets none, and `.fabrik/review.md` and the review prompt still go to the Reviewer alone. The file stays a Trust-root file that only the Operator changes.
- **A Design session holds every acceptance criterion to what a run can meet** ([#763](https://github.com/jrey8343/fabrik/issues/763)). A criterion is one check on a Ticket that a test the Required checks run, or the diff itself, shows is met, and it never asks for a Trust-root change, a GitHub write, a commit, branch or state the run isn't given, a suite or command no Required check runs, or anything only the Operator can do, and it is never a literal no output can meet. Those five kinds and the literal are what the prompts mean by a criterion no run can meet. The rule covers an agent brief's criteria, each Ticket's in a Spec or a split, and a Roll-in's. An async turn is now given the Required checks `sandbox.checks` lists, under "The Required checks", and a live session reads them from the Kit config in its checkout; both read `.github/workflows/` for what each runs. A test no Required check runs is moved where one does or dropped, and a workflow change to bring it in becomes an Operator step that blocks the Ticket. A Ticket back from a Design flaw for such a criterion takes the usual path, and when nothing is left to build it finishes as an Operator brief and the Operator reopens the pull request. The live Design skill holds the same rule, in the same words. The Glossary gains **Acceptance criterion**.
- **An Implementer builds the rest of a Ticket around a criterion no run can meet** ([#764](https://github.com/jrey8343/fabrik/issues/764)), where it used to commit nothing. `prompts/implement.md` names what makes one: a Trust-root change, a GitHub write, a commit, branch or state the run wasn't given, a suite or command no Required check runs, something only the Operator can do, or a literal no output can meet. The run builds the rest of the Ticket, commits it, and names each such criterion, quoted, with the reason, in its summary under **Criteria no run can meet**, so the pull request opens, its Required checks run, and it is Reviewed as any is. It never works around one: no Trust-root edit, no `gh` or API call, no result claimed for a command it didn't run. A Ticket with nothing buildable without one still ends in no commits, with the reason in the summary. The rule holds on a first run, a Kept-branch start, a Retry, a Touch-up and a Request-changes run, and on a run on a pull request the heading stays in its body while the criterion is unmet. "Questions for the Operator" stays the one heading for questions. The Kit does nothing with the new heading.
- **The Reviewer gives a Design flaw the first time it finds a criterion no run can meet** ([#765](https://github.com/jrey8343/fabrik/issues/765)). Until now a criterion the pull request said it skipped was always an Execution flaw, so the Implementer was sent back to try again at what it couldn't do, and the Ticket spent its Retries before a Design flaw named the cause. `prompts/review.md` gains a part under **Your Verdict** naming the kinds of criterion no run can meet, as the Implement prompt does, the Trust-root files the guard refuses, that an Implementer holds no GitHub credential, works only on the branch the Kit checked out and runs only what its Sandbox has, and that the Required checks and what they run are read from `sandbox.checks` and `.github/workflows/` in the checkout. An unmet criterion, as amended by any Request changes, that no run can meet is a Design flaw on the first Verdict that finds it, on a Full Review or a later one, whether the body names it under **Criteria no run can meet** or the Reviewer sees it for itself, and its findings name the criterion and why. A Reviewer that disagrees with the body's claim gives an Execution flaw whose untagged finding says how a run can meet the criterion, and a pull request with an unmet criterion never passes. A Request changes that asks for what no run can meet now grounds a Design flaw too. The Full Review section is unchanged, so a Full Review that gives this Design flaw still names every other flaw it found. No Verdict, marker field or tag is added: the Design flaw goes Back to design as any does, and the pull request's branch becomes the Kept branch.
- **Ticket compliance moves to version 3** ([#766](https://github.com/jrey8343/fabrik/issues/766)), so a run that does as its prompt now says isn't scored `missed-criteria`. Under `ticket-compliance@2`, a run that built the rest and named a criterion under **Criteria no run can meet** would have scored 0.5. `ticket-compliance@3` (`prompts/scorers/ticket-compliance.md`) says a criterion the run named in its summary under that heading, with the reason, while it built the rest, is not one it missed or skipped, and that whether the claim is right is the Reviewer's to judge, not the Scorer's. Where a Ticket couldn't be built as written, it asks the run to name what it couldn't build and build the rest, or to make no commits when nothing could be built, in place of "make no commits and say why". The labels, the scale and the pass line (0.8) are unchanged. `ticket-compliance@2` stays recorded, so score files written under it still read, and the Weekly summary and a Replay show the two versions apart, as `Ticket compliance v2` and `Ticket compliance v3`.
- **The Design session's default effort is `high`** ([#767](https://github.com/jrey8343/fabrik/issues/767)). A miss in a Design session costs a Back to design, the sessions are the cheapest runs in the factory ($41 of the $404 spent from 7 to 15 Nov), and the longest turn took 4.1 of its 30 minutes ([#722](https://github.com/jrey8343/fabrik/issues/722)). A Replay can't vary Design, so this goes in without one. A repo's own `roles.design.effort` still wins, and a `null` or missing one takes the default, now `high`. A prototype turn runs on the Design role's model and effort, so it runs at `high` too, within the Implement role's time limit. Every other default stays: `high` for the Review, `medium` for Triage, Implement, the Auditor, the Retro, the Researcher, the Digest writer and the Step-up, and the Design time limit stays 30 minutes. The starter Kit config names `high` for `roles.design`.
- **Why a minor:** new behaviour with no Kit config field, shim change, secret or App permission, so a Product repo only merges the bump PR. No Run-record schema changes. `DEFAULT_KIT_CONFIG` in the read library still holds the defaults the Kit fills in, now `high` for `roles.design`, and `ticket-compliance@2` stays recorded beside `ticket-compliance@3`, so nothing the read library exports is removed or changes what it means.

## Upgrading

**Design at `high`** ([#767](https://github.com/jrey8343/fabrik/issues/767)). A Product repo that names no `roles.design.effort`, or names `null`, as gradually-core and Penrith do, takes `high` with the bump alone. One that names `roles.design.effort` outright, as a `.fabrik/config.json` written from an earlier starter does with `"medium"`, keeps that level until its Operator deletes the field, to take the default, or changes it.
