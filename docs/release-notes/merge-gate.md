# Release notes: The Merge gate holds the Operator to the Required checks

The notes for the minor release that ships Setup holding admins to the default branch's rules ([#590](https://github.com/jrey8343/fabrik/issues/590), ADR-0019). Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- **Setup holds admins to the default branch's rules in every Product repo.** GitHub then refuses a merge at a head whose Required checks haven't all passed, whether one failed, is still running or never reported, and refuses any push straight to the branch, the Operator's included, from github.com, `gh` or anywhere else. Until now the Operator, who holds the repo's admin role, could merge past a Required check with a tick-box on github.com, or with nothing at all through GitHub's API, and could push straight to `main`. A pull request whose Required checks have passed merges as before, and the Fabrik App still can't merge: the Merge gate ruleset is untouched.
- **Setup's plan names the change.** Its line protecting the default branch gains "admins held to the rules: no → yes", after the changes the line already names and before "every other setting stays as it is", and the setup pull request and Setup's closing lines list it the same way. There is no flag, no question and no Kit config key: it is the Kit's rule, not a choice per repo. A later Setup run that finds it switched off names the change again and puts it back. A run on a repo that already holds admins to its rules says nothing about it.
- **A branch that asked for an approving review and had enforcement off has both changed in the one step**, and the plan names both: "approving reviews: 1 → 0; admins held to the rules: no → yes". The Operator can't approve their own pull request, so a branch that held admins to its rules and asked for a review is one nobody could merge into. A branch that already holds admins to its rules and asks for a review is left alone, as before.
- **Setup's two messages about a clone whose default branch isn't the same as origin's no longer offer a push.** The opening check and the closing line after a repair that wrote no file now say to pull, or to take the commits made here to origin through a pull request, then run Setup again. The message for an origin with no default branch at all still says to push it: nothing protects a branch that doesn't exist yet.
- **The way past is by hand, on github.com.** In the default branch's protection settings, switch off "Do not allow bypassing the above settings", or take a check that can no longer report off the required list; merge; then run Setup, which puts enforcement back. That's how to merge past a Required check on purpose, and the only way out when one can never report again, as after a CI job is renamed, where the pull request that corrects `sandbox.checks` can't itself go green while the old name is still required. Setup adds Required checks and never takes one off, so a check that has gone for good comes off the branch's required list by hand. See [the README's Merge gate](../../README.md#merge-gate).
- **The Kit's words say Required checks throughout**, as the glossary does: Setup's notes and its ask for the merge, the Review's notice for a check that never reported, the Monitor's red-main issue and the line in the Implementer's prompt naming its pull request's checks. Only the words changed. A red-main issue already open keeps its old opening and closing sentences until it closes; the Monitor finds it by its marker, not its prose.
- **The Loop is unchanged.** Nothing in the Kit merges or pushes to a Product repo's default branch: Setup's files, Kit bumps and Skills bumps all arrive as pull requests. `fabrik-runs`, which the Kit writes to directly, is not a Product repo, and Setup leaves it unprotected as before.
- **Why it matters:** the Console is to make the Operator's merges with a credential a Worker holds, and that credential is safe to hold only with this on. Switching enforcement off needs Administration write, which the Console's GitHub App is not granted, so a leaked credential can do nothing to a default branch but merge a pull request whose Required checks have passed ([#540](https://github.com/jrey8343/fabrik/issues/540), and ADR-0019 from [#599](https://github.com/jrey8343/fabrik/issues/599)).
- **Why a minor:** it adds behaviour, so not a patch. It adds no Kit config field, changes no shim and asks no caller job for a new permission, and the Loop runs the same whether or not enforcement is on, so a Product repo still only merges the Kit bump for the Loop to run as before. The new behaviour waits on one Operator step, running Setup again, below. No run notes that it's off. If the release holding this is a major for another reason, that covers it: every Product repo runs Setup again naming the release anyway, and that run switches enforcement on with the rest, in place of the steps below.

## To turn it on

A Kit bump never runs Setup, so merging the Kit bump changes nothing here. Until a repo's Setup run at this release, the Operator can still merge past its Required checks, and nothing fails. Running Setup is the step that turns it on, in every Product repo; it's the Kit's rule, not a choice per repo.

1. **Merge this release's Kit bump in the Pilot.**
2. **Run Setup again in the Pilot at this release** (see [Adopting the Kit](../../README.md#adopting-the-kit)). Its plan shows the line protecting the default branch with "admins held to the rules: no → yes". With nothing else missing it opens no setup pull request.
3. **Check it**, as below.
4. **Then in each other Product repo**, merge the Kit bump and run Setup again.

## To check it on the Pilot

1. In the Pilot's default branch protection settings on github.com, "Do not allow bypassing the above settings" is ticked, and running Setup once more plans nothing.
2. Open a throwaway pull request with a failing Required check, and check that its merge is refused, on github.com and by `gh pr merge`. Close it. The trial that found the gap ([#523](https://github.com/jrey8343/fabrik/issues/523)) used a commit status as its required check, so where the Pilot's Required checks are Actions jobs this is the first time enforcement is seen against one.
3. If one can be made cheaply, open a pull request whose Required check never reports, and check that its merge is refused too. The trial didn't try that with enforcement on. Close it.
4. Check that a pull request whose Required checks have passed merges as before. Watch the next Kit bump in particular: a Required check that doesn't report on every pull request, such as one behind a path filter, now holds the pull requests it skips, a Kit bump among them.
