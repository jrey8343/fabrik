# Release notes: the Operator session

These are the notes for the Operator session's part of the major that carries the Kit's Operator sessions ([Spec: The Operator session: the Kit's skills and facts reach a cloud session, and the session reports itself on its issue](https://github.com/jrey8343/fabrik/issues/918)): the Kit's skills and the facts a session needs reach a Claude Code cloud session, the Kit's text tells that session its rules, `/fabrik-pair` runs there as at the Operator's terminal, and a session reports itself on its issue, where the read library gives its address on the issue's row. Each of the major's five parts has its own notes, and this is the Operator session's. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

This draft holds the part of each of the Spec's build Tickets: the shallow fetch ([#948](https://github.com/jrey8343/fabrik/issues/948)), `fabrik`'s own hook entry ([#949](https://github.com/jrey8343/fabrik/issues/949)), the Session environment ([#950](https://github.com/jrey8343/fabrik/issues/950)), the marker and the row's field ([#951](https://github.com/jrey8343/fabrik/issues/951)), `fabrik-operator-session` ([#952](https://github.com/jrey8343/fabrik/issues/952)), the hook's cloud lines ([#953](https://github.com/jrey8343/fabrik/issues/953)), `/fabrik-pair` ([#954](https://github.com/jrey8343/fabrik/issues/954)), Setup's report lines ([#955](https://github.com/jrey8343/fabrik/issues/955)), the README's "Operator sessions" ([#956](https://github.com/jrey8343/fabrik/issues/956)), the two new ADRs ([#946](https://github.com/jrey8343/fabrik/issues/946), [#947](https://github.com/jrey8343/fabrik/issues/947)), and the Glossary and the changed ADRs ([#957](https://github.com/jrey8343/fabrik/issues/957)).

## What changed

- **The hook entry and the Skills fetch download by git's own shallow fetch from `github.com`** ([#948](https://github.com/jrey8343/fabrik/issues/948)), in a cloud session, at a terminal and in an AFK run alike. The `SessionStart` hook entry in `templates/claude-settings.json` fetches Fabrik at its release tag, and `src/skills/fetch.ts` fetches the Base skills and each Skills source at its pinned commit, each by `git init`, `git fetch --depth 1` and a checkout of what it fetched. Before, each downloaded a source archive from `codeload.github.com`, which a cloud session refused with a 403 for a public repo that isn't attached to it, so a cloud session got none of the Kit's skills. No fallback is built. Where the fetch fails, the hook says `Fabrik didn't install its skills: fetching Fabrik <release> from github.com failed`.
- **`fabrik` has a hook entry of its own** ([#949](https://github.com/jrey8343/fabrik/issues/949)), `.claude/settings.json`, which runs `src/session/start.ts --kit` on its own checkout, with no release to read and no download of Fabrik: it installs the Base skills the checkout's `skills.lock.json` pins and every skill under its own `skills/` into `.claude/skills/`, which `fabrik` now ignores. So the Operator's terminal sessions in `fabrik`, and a cloud session there, run the pinned skills under their plain names, with the `mattpocock-skills` plugin off at project scope, where they ran an unpinned plugin. A skill edited on a branch is the one the next session on that branch runs.
- **The hook's lines in a cloud session** ([#953](https://github.com/jrey8343/fabrik/issues/953)). Where `CLAUDE_CODE_REMOTE` is `true`, the hook's context gains its lines after its others: that this is a cloud session on the repo, where `gh issue` and `gh pr` are refused and every tracker operation goes over REST by the forms in `fabrik-operator-session`, which the session reads before any work; the Operator's login; whether the repo has a Researcher; whether the session is in the Session environment the repo expects, read from `FABRIK_SESSION_ENVIRONMENT`, and if not, to say so first and do no work; the session's address, from `CLAUDE_CODE_REMOTE_SESSION_ID`, with the marker to write; and whether the default branch has `.fabrik/operator-session.md`. Where the hook couldn't install the skills it gives that line alone. At a terminal its context is as it was.
- **`fabrik-operator-session`, the Kit's text for cloud sessions** ([#952](https://github.com/jrey8343/fabrik/issues/952)), `skills/fabrik-operator-session/SKILL.md`, which the hook installs beside the Kit's other skills, hidden from the Operator's slash commands, since it is read and never run. It holds what every Operator session keeps: the short list of eight acts that are never a session's, the checks before any work, the REST form of every tracker operation, the marker, the sort of each step to the session, the Operator's hands or a laptop, what a repo attaches, merges and Held workflows, the record, a Map's Decision, a second repo and messages.
- **`/fabrik-pair` in both places** ([#954](https://github.com/jrey8343/fabrik/issues/954)), at the Operator's terminal and in a cloud session, one skill that reads the rules it shares with every Operator session from `fabrik-operator-session` and keeps no copy. In a cloud session it writes to the tracker over REST, builds no wizard, sorts every step before the first and writes the marker. In both places it keeps one record comment on the issue, edited as it goes, never merges its own pull request, merges nothing on a repo whose Kit config holds `console.app_id`, where a merge is the Operator's from the Console, and asks for the Operator's tap in the Console before it starts a Held workflow. Its steps for the Weekly-limit issue follow the issue as the Kit writes it with rotation on too: it waits for the first reset and re-adds nothing, since the Kit resumes held runs itself. The README's "Pairing session" says the same.
- **The marker, and the row's `operatorSession`** ([#951](https://github.com/jrey8343/fabrik/issues/951)). A session reports itself on its issue with a comment whose first line is `<!-- fabrik:operator-session <address> -->`, above a visible line with the link. The Kit counts it only when the Operator wrote the comment and the address is exactly `https://claude.ai/code/session_` and an id, and the comment posted last wins. The row of every open issue a Standing names carries the address as `operatorSession`, or null, read from the last hundred comments the gather already reads, with no new query.
- **The Session environment** ([#950](https://github.com/jrey8343/fabrik/issues/950)): `console.session_environment` in Kit config, the name of a repo's own Session environment, absent by default and valid with or without `console.app_id`; `BARE_SESSION_ENVIRONMENT`, `operator-sessions`, the bare one's name; and `sessionEnvironmentOf`, which gives the name a repo's Operator sessions open in, the bare one's where the key is left out or the Kit config wasn't read or is invalid. The Console's link names it, and the hook checks a cloud session is in it.
- **`.fabrik/operator-session.md`, and Setup's two report lines** ([#955](https://github.com/jrey8343/fabrik/issues/955)). `.fabrik/operator-session.md` is where a Product repo says in prose what its Operator sessions can reach beyond GitHub. Only an Operator session reads it, no Kit code acts on it, and it is under `.fabrik/`, so it is a Trust-root file already. Setup's report, on every run, gains a line for each job that asks for `id-token: write` and names no environment, or one not held to the default branch alone, so a run on another branch can take a role, and a line where Kit config names a Session environment and the repo has no `.fabrik/operator-session.md`. The Kit's own caller workflow is left out by name. Setup blocks on neither, changes nothing of the repo's, and never looks inside a cloud account's trust policy.
- **The docs.** The README's "Operator sessions" ([#956](https://github.com/jrey8343/fabrik/issues/956)): what reaches a session and what it leaves, the Session environments, what a repo attaches in `.fabrik/operator-session.md` with its skeleton, the checklist run on each Subscription, and what is kept by hand. Two new ADRs: [ADR-0041](../adr/0041-an-operator-session-runs-in-a-claude-code-cloud-session-started-by-a-link-and-the-console-draws-no-chat.md), on where an Operator session runs ([#947](https://github.com/jrey8343/fabrik/issues/947)), and [ADR-0042](../adr/0042-an-operator-session-is-trusted-as-the-operator-up-to-a-short-list-of-acts-which-stop-at-a-pull-request-the-operator-merges-or-at-the-operators-own-hands.md), on its posture ([#946](https://github.com/jrey8343/fabrik/issues/946)). ADR-0003's addendum, on the fetch from `github.com` and `fabrik`'s own hook entry ([#949](https://github.com/jrey8343/fabrik/issues/949)). The changed sentences of ADR-0005, ADR-0008 and ADR-0009, on what a Pairing session and an Operator session count as, install and record: ADR-0008's, that an Operator session installs every pick ([#949](https://github.com/jrey8343/fabrik/issues/949)), and ADR-0005's and ADR-0009's, that a Pairing session counts as the Operator and writes no Run record in both places ([#957](https://github.com/jrey8343/fabrik/issues/957)). The Glossary's five entries, Spec, Pairing session, Operator session, the new Session environment, and Trust-root file ([#957](https://github.com/jrey8343/fabrik/issues/957)).

## Why a major

By the releasing guide's [Choosing the version](../releasing.md#choosing-the-version), this part alone makes the release a major: the hook entry in `.claude/settings.json` is a changed shim, so each Product repo takes this by running Setup again at the major, once for all five Specs, naming the release, as the releasing guide has a changed shim go. Dependabot opens no pull request for a major. Setup's merge replaces the Kit's old hook entry where it stands and keeps the repo's other hooks, and its setup PR carries the new entry. Until that PR is merged, a Product repo's sessions fetch Fabrik as the old entry does, and a cloud session there gets none of the Kit's skills. The major is the one that carries the Kit's five Operator sessions Specs ([How are the Specs cut, and who builds them?](https://github.com/jrey8343/fabrik/issues/874)).

## For a reader of the read library

- **New exports** ([#950](https://github.com/jrey8343/fabrik/issues/950)), through the read library's entry, `src/read/index.ts`, under a heading of their own: `BARE_SESSION_ENVIRONMENT`, `operator-sessions`, the bare Session environment's name, and `sessionEnvironmentOf`, which takes a repo's resolved `KitConfig`, or null, and gives the name of the Session environment its Operator sessions open in: its `console.session_environment`, or the bare one's where it names none, and for null, which a reader passes for a Kit config it didn't read, that is invalid or that isn't there. A reader works out no name from a repo's name.
- **`KitConfig.console.sessionEnvironment`** ([#950](https://github.com/jrey8343/fabrik/issues/950)), the name `console.session_environment` holds, or null where it is left out. `DEFAULT_KIT_CONFIG` has `console: { appId: null, heldWorkflows: [], sessionEnvironment: null }`. A reader that builds a `KitConfig` itself fills it.
- **The row's `operatorSession`** ([#951](https://github.com/jrey8343/fabrik/issues/951)), on `Row`: on a row whose Standing names an open issue, the address of the Operator session that last reported itself there, or null, and null on every other row and on every row of the store. A reader parses nothing: it draws the address. A row a reader kept before the field has none of it, so a row kept before it reads with `operatorSession: null` through `readRow`.
- **Nothing the entry exported is removed or changes meaning.**

## What the Console needs

- **Its pin moved, and its own part built from its Spec:** the row's `operatorSession` for the Session pill, which links the session that last reported itself on the issue, and `sessionEnvironmentOf` for the link's `environment=`, so a session opens in the Session environment the hook checks. That part is [Write the Console's Spec and cut it into slices](https://github.com/jrey8343/fabrik/issues/913). This line is a guess until the release is checked against the Console (step 4 of [releasing.md](../releasing.md)), and that run's answer replaces it.

## To turn it on

Nothing in a Product repo. The Operator's steps are account-wide, and the Console offers no session until each is done:

1. **[Operator step: cut the Claude GitHub App's list to `fabrik` and the Product repos](https://github.com/jrey8343/fabrik/issues/910).** The App's list is a session's whole reach on GitHub, so it holds only the repos each of which has a hold a session can't pass.
2. **[Operator step: run the README's checklist on both Subscriptions](https://github.com/jrey8343/fabrik/issues/960),** the README's [The checklist, on each Subscription](../../README.md#the-checklist-on-each-subscription): GitHub connected through the Claude GitHub App, the bare Session environment, each repo's own, and the connectors cut to what the repos' files name. Nothing in the Kit or the Console reads it back.

A Product repo that attaches a credential makes its own Session environment and `.fabrik/operator-session.md` as its own issue.

## What does not change

- **Nothing the Kit counts reads a session.** No Standing, no Human touch, no Run record and no Weekly summary line reads a session: only the row's `operatorSession` reads the marker. A Pairing session writes no Run record in either place, and counts as a Human touch, as before.
- **The AFK runs install their own role's picks** as before, the Base skills and their own role's Extra skills alone. Only a session the Operator is in, at the terminal or in the cloud, installs every pick.
- **A Pairing session at the terminal** on a repo with no `console.app_id` merges another pull request on the Operator's word, as before, and still runs on the Operator's own `gh` credentials and builds its wizard.
