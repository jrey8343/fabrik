# Release notes: Fable for a Product repo that opts in

The notes for the minor release that lets a Product repo opt in to Fable for its AFK roles, behind the overage stop and the Fable fallback ([#828](https://github.com/jrey8343/fabrik/issues/828), [ADR-0034](../adr/0034-a-product-repo-can-opt-in-to-fable-for-its-afk-roles-behind-the-overage-stop-and-the-fable-fallback.md)). Every Ticket of #828 has its part here. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## Release-note line

A Product repo can opt in to Fable for its AFK roles with `"allow_fable": true`, naming Fable by its full id. Every Fable run stops on its first overage message, and a run refused on its Subscription's Fable cap falls back to Opus 5.5 at the same effort until the cap resets, quietly. A repo that doesn't opt in runs exactly as before.

## What changed

- **Why:** the Kit refused Fable in every AFK role, because past Fable's included share a `-p` run bills usage credits without asking. The Operator's two Ultra Subscriptions carry a Fable allowance a weekly loop otherwise leaves unused, and Design, Review and the Step-up are where a stronger model pays for itself. Three guards make it safe: usage credits off, the overage stop, and the Fable fallback.
- **The opt-in** ([#829](https://github.com/jrey8343/fabrik/issues/829)). Kit config gains `allow_fable`, a top-level boolean, `false` by default. Anything but `true` or `false` is a Kit config error naming it. Without it, every role that reads a model (triage, design, implement, review, audit, retro, research, digest and step_up) still refuses one naming Fable, for today's reason, and the error now says to set `allow_fable` to `true` to opt in (ADR-0034). With it, a role may name Fable only by its full id, `claude-fable-<version>`, such as `claude-fable-5-2`: the bare `fable` alias is refused, since a Claude Code upgrade or `ANTHROPIC_DEFAULT_FABLE_MODEL` can change what it resolves to, unseen. `true` with no role naming Fable changes nothing. Setup, the starter Kit config and the Visual evidence writer never write it. The agent runner holds the model its Kit job's plan gave it to the same rule, so a Step-up on `claude-fable-5-2` starts in a repo that opted in and is refused in one that didn't.
- **`best` has its own error, opt-in or not.** It is refused in every repo, and the error no longer gives Fable's reason: "the CLI can resolve best to any model, Fable included, so the Kit never runs it in an AFK role". The opt-in wouldn't let it run, so the error doesn't point at it.
- **Every Fable run stops on its first overage message, rotation or not.** The stream watch stopped a run for spending usage credits only while rotation was on, so a one-Subscription repo had no stop. It now stops a run whose model names Fable too, so credits left on by mistake spend nothing. A run that isn't Fable, with rotation off, goes on as before, and the Scorers' judge, which runs Sonnet, is unchanged.
- **With rotation off, a run killed for usage credits now opens its Subscription's usage-credits issue.** Before, with rotation off, nothing was killed and nothing opened. Now a Fable run killed for overage opens the "Turn off usage credits on the `<name>` Subscription" issue, labelled `fabrik:usage-credits`, assigned to the Operator as the one notification, and the Kit keeps off that Subscription until it is closed. With no other Subscription to run on, that means holding runs, as rotation does once every Subscription is used up: the killed run is held on the issue, with no failure comment, only its quiet held line, and so is each run due while the issue is open, Opus runs included. Closing the issue resumes them, in the order they were held. A weekly-limit or token-rotation issue alone still holds nothing with rotation off, as before. This is the release's one push, and it is the Operator's move: credits are on.
- **A Fable cap is told apart from the weekly limit** ([#830](https://github.com/jrey8343/fabrik/issues/830)). On a run whose model names Fable, a rejected `rateLimitType` that starts `seven_day_` is that Subscription's **Fable cap**, a new Infrastructure failure, `fable-cap`, with its reset when the stream gives one. Plain `seven_day` stays the weekly limit, and on a run that isn't Fable any `seven_day*` refusal is still the weekly limit, as before. **The rule is unverified:** Claude Code documents neither the stream's `rate_limit_event` nor the Fable cap's `rateLimitType`. It fails safe. If a real Fable cap reports as plain `seven_day`, the Kit reads it as the weekly limit and holds the Subscription, Opus runs too, until its reset, opening the weekly-limit issue as today: it costs time, never money. Every refusal's raw `rateLimitType` and `resetsAt` now go in the Run record, so the first real Fable cap shows how the Kit read it.
- **A Fable cap holds no run; it falls back** ([#830](https://github.com/jrey8343/fabrik/issues/830), [#831](https://github.com/jrey8343/fabrik/issues/831)). A Fable run refused on its Fable cap uses none of the Ticket's Retries, posts no failure comment, opens no Kit-owned issue, mentions nobody and holds no run on that Subscription or any other. It is re-run once, quietly, through its trigger label, with one Subscription listed too. The re-run starts on the first listed free Subscription with Fable left, or, with none left, on `claude-opus-5-5` at the role's effort: a **Fable fallback**. The fallback is per run. It never changes Kit config, and ends on its own when the cap resets. Every role's agent job, Triage and Design included, runs the model its Kit job's plan chose, so a fallback runs Opus and its Run record says so. A re-run refused again on a cap its issue or PR already marks, still in force or with the same reset, isn't re-run on its own, so a cap the Kit can't steer around never re-adds the label endlessly: it fails as an Infrastructure failure, with the notice that mentions the Operator. A Digest, an Audit or a Retro refused on a Fable cap isn't re-run, as none is on any failure: a Digest leaves its no-Digest line and the gate opens all the same, and the next Audit or Retro falls back at its start, as any run due does.
- **The re-run is told about the cap by a hidden line.** The re-run's Kit job is another Loop run, started by the trigger label before the refused run's push job has written its Run record. So the push job first writes a hidden line, `<!-- fabrik:fable-cap <Subscription> until <reset> -->`, on the body of the issue or PR the label goes on, then re-adds the label. With no reset of the cap's own from the stream, the line counts until its Subscription's weekly-limit reset, from the last weekly-limit reading in the refused run's stream, which its failure report carries as `weeklyResetsAt`, while that is still ahead, or for 7 days when that isn't known either: the same rule as a Run record's reading, below, in one place. A body keeps one line for each Subscription whose cap is in force, and drops each once its time has passed. On a pull request, only a body the Fabrik App wrote is read. An issue's is read whoever opened it, since the App marks someone else's issue and GitHub keeps only a body's last editor: a forged line can only move a Fable run to another Subscription or to Opus, never make one bill. The edit notifies nobody.
- **Any run due starts where Fable is left, with no refusal first** ([#831](https://github.com/jrey8343/fabrik/issues/831), ADR-0009's addendum). In a repo that opted in, the Kit job reads the Fable cap readings in the `fabrik-runs` store's Run records: every Product repo's from the store's last two months, a Replay arm's included, since a Subscription's Fable cap is reached by whichever repo runs on it. A reading counts until its refusal's reset, or, with none, its Subscription's newest weekly-limit reset by then while that is still ahead, or for 7 days from the run's end. A run due on a role naming Fable while no listed Subscription has Fable left starts on `claude-opus-5-5` at the role's effort straight away. To read the store, the Kit job's new "Check out the store for the Fable cap readings" step first reads `allow_fable` from the Product's Kit config, with no secret, so a repo that didn't opt in loads nothing. In one that did, it loads the Fabrik App key through the push service account (the `OP_PUSH_TOKEN` the caller already passes), asks as the App whether it's on `fabrik-runs`, mints a token for that repo alone with Contents read, and checks out only those Run records: no score file, transcript or Replay patch. The Kit job still runs no agent and no Product code and holds no write credential. **If the store can't be read**, no step fails: every Subscription counts as having Fable left, the worst case being one more refusal and the same fallback, and on a run whose role names Fable the Kit job's step summary says "The fabrik-runs store couldn't be read, so every Subscription counted as having Fable left."
- **Run records move to schema 12** ([#830](https://github.com/jrey8343/fabrik/issues/830)), adding three fields. `model` stays the model the run was started on. `configuredModel` is the model Kit config named, and `fallback` is `fable-cap` when a Fable fallback ran Opus 5.5 in its place, else null. `refusal` keeps a refused run's `rateLimitType` and `resetsAt` raw, Fable cap or not, beside `rateLimit`, the last weekly-limit reading. A judge run and a Replay arm never fall back. Records of schema 1 to 11 read as given the model they ran on, with `fallback: null` and `refusal: null`.
- **The Weekly summary shows the fallbacks and each Fable reset** ([#832](https://github.com/jrey8343/fabrik/issues/832)). While some Product repo's Kit config sets `allow_fable`, the Metrics table gains a **Fable fallbacks** row: the week's Run records with `fallback` `fable-cap` in those repos, against last week's. Every such record counts, one that ended in an Infrastructure failure included, apart from the Infrastructure failures row: a fallback refused on the weekly limit and resumed counts twice, once for each run that fell back. A Fable run's own refusal on its cap ran on Fable, so it is never a fallback. While a Subscription's Fable cap is in force at the filing, its usage line, or the one line with one Subscription, says "Fable cap reached, resetting" and when, and a Subscription capped but run on nothing that week gets its line too. With no repo opted in, it shows neither.
- **A Replay follows the live repo's opt-in** ([#833](https://github.com/jrey8343/fabrik/issues/833)). A Replay variable may name Fable by its full id only in a repo whose Kit config opts in, and is refused with Kit config's reason in one that doesn't; the bare `fable` and `best` are refused in every repo. The baseline arm runs the roles as Kit config at the Ticket's `baseSha` names them, Fable included. Each arm holds its model to the repo's own `allow_fable` as it is now, never `baseSha`'s, so a variant can name Fable on a Ticket built before the repo opted in, and a Ticket whose baseline would run Fable in a repo that no longer opts in is left out of the pick, naming why. **An arm refused on a Fable cap ends the Ticket's run with a new `fable-cap` end kind:** the Ticket goes back to pending and keeps its retry, nothing opens, and no arm falls back to Opus, since another model would spoil the comparison. A Fable cap costs the Replay time, never the Ticket, and can end a Replay early. A weekly-limit refusal in the same run still comes first.
- **Docs.** [ADR-0034](../adr/0034-a-product-repo-can-opt-in-to-fable-for-its-afk-roles-behind-the-overage-stop-and-the-fable-fallback.md) records the decision, and [ADR-0009](../adr/0009-run-records-live-in-a-central-private-repo.md) gains schema 12 and an addendum for the Kit job's read of the store. The README's Kit config block names `"allow_fable": false`, its failure table gains the Fable cap row (Silent), and its usage-credits row and Replay section say what changed. The Glossary gains **Fable cap** and **Fable fallback**. `docs/research/max-plan-headless.md` §7 says the Kit runs Fable only on the opt-in.
- **For readers of the read library:** `KitConfig` gains a required `allowFable`, and `RunRecord` gains required `configuredModel`, `fallback` and `refusal`, which every read fills in, an older record's included. A reader that builds either itself must give them, or it fails to compile. `infrastructureFailure` can now be `fable-cap`, so a reader that switches over it exhaustively needs that case. Nothing is removed or changes meaning.
- **Unchanged:** a repo that doesn't opt in behaves exactly as before. No shim or caller change, no new secret and no new Fabrik App permission: the Kit job's store read uses the push service account the caller already passes and the Contents read the App already holds on `fabrik-runs`. Interactive and Pairing sessions are the Operator's own and unchanged.
- **Why a minor:** `allow_fable` is a new Kit config field with a default, and the opt-in is the Operator's own Kit config edit, with no setup step the Loop needs: merging the bump changes nothing until a repo sets it. The read library gains fields only.

## Upgrading

**Bump the store's pin** in `fabrik-runs`, its `.github/workflows/weekly-summary.yml`, to this release, with the Pilot, so its Weekly summary reads schema 12 records. Until then it leaves them out, and says how many. A Product repo merges the bump PR, the Pilot first, and needs nothing else unless it opts in (below).

## To turn it on

Merging the bump changes nothing: no Product repo runs Fable until its Kit config says so. Take the bump on the Pilot first, as for every release, and leave the Pilot as it is: it doesn't opt in. Then opt in only the repo that wants Fable, `gradually-core` first.

1. Merge this release's bump PR in the Pilot, then in the repo to opt in, and bump the store's pin with the Pilot (see Upgrading).
2. **Check usage credits off on every listed Subscription** of that repo (each account's Settings, Usage), every name in its `subscriptions`, the first one included. The Kit can't read that setting: the overage stop is the backstop, not the guard.
3. In that repo's `.fabrik/config.json`, set `"allow_fable": true` and name a Fable model by its full id, `claude-fable-5-2`, in each role that should run it. Design, Review and the Step-up are where it pays for itself. A Digest writer with no model of its own follows the Reviewer's, so name `roles.digest` outright to keep it off Fable:

   ```json
   "allow_fable": true,
   "roles": {
     "design": { "model": "claude-fable-5-2", "effort": "high" },
     "review": { "model": "claude-fable-5-2", "effort": "high" },
     "digest": { "model": "claude-opus-5-5", "effort": "medium" },
     "step_up": { "model": "claude-fable-5-2", "effort": "high" }
   }
   ```

   Merge it to the default branch. A role naming the bare `fable` or `best` is a Kit config error, which stops the Loop before any agent starts and says why.
4. Check it on a real issue: the next Design session's or Review's agent job step summary names `claude-fable-5-2`, and its Run record has `configuredModel` and `model` both `claude-fable-5-2` and `fallback` null.
5. Over the first weeks, read the Weekly summary's **Fable fallbacks** row and each Subscription's line for a Fable reset. Fallbacks two weeks in a row, or a weekly-limit issue opening on the opted-in repo, say Fable is burning too fast: move `implement` back to Sonnet 5.5 at `medium` first, and turn Fable off second.

## To turn it off

In the repo's `.fabrik/config.json`, remove `allow_fable` and name non-Fable models, such as `claude-opus-5-5`, in every role that named Fable, in one change. Removing `allow_fable` alone, with a role still naming Fable, is a Kit config error, which stops the Loop before any agent starts until the role is changed too. Nothing else to undo: the fallback never changed Kit config, and no Kit-owned issue was opened for a Fable cap.
