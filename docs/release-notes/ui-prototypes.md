# Release notes: UI prototypes

The notes for the minor release that ships UI prototypes ([#155](https://github.com/jrey8343/fabrik/issues/155)). Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- **A Design session can offer a Prototype.** On a Product repo with Visual evidence's `ui` block, when a session's open question is how a page should look, the Design agent may offer one as an ordinary round question with a recommendation, naming the route and how many variants it will build: "Prototype the booking page as 3 variants first?" Nothing is built until the Operator says yes, and the reply can change the offer ("yes, but 4 variants", "prototype `/checkout` instead"). Logic and data questions stay in ordinary rounds. Whether a repo can have a Prototype is the Kit's call, from Kit config, never an agent's: a repo without a `ui` block never sees an offer, and a `prototype` output there is refused as a broken contract.
- **The request comment.** On a yes, the next turn records the request, and the push job posts a short comment on the issue saying which route and how many variants are being built, and that the round follows when they're ready. It mentions nobody, so only the round itself pings the Operator's phone, and it isn't a round, so it doesn't count toward the round number. The push job then adds `agent:design`, and the turn that starts is a prototype turn.
- **The prototype turn** is a turn of the same Design session, run as a Sandbox job on the Design model, with `roles.implement.timeout_minutes` as its timeout. It gets the same secrets as an Implement run and no GitHub write access. It holds the session's Design session slot, so `caps.design_sessions` still caps the sessions running, and only one turn of a session runs at a time: a reply sent while the Prototype builds waits for it, then reads the round. The agent follows the pinned `prototype` skill's UI branch on `prototype/<issue>`: 3 variants by default and 5 at most, of one route, switched by `?variant=` with a floating switcher. A later prototype round builds on the branch the last one left. A prototype turn refused on a Subscription's weekly limit restarts as a prototype turn on the next free one.
- **Capture** runs once the agent has exited, with Visual evidence's capture and no model turns: `sandbox.build`, then `ui.serve`, then each variant at the mobile and desktop widths, as a screenshot and a short scripted load-and-scroll video at each. They go into one self-contained HTML gallery, each variant under its letter and one-line summary with its mobile and desktop captures side by side, uploaded unzipped so it opens in one click, and kept about 30 days. Capture never fails the job.
- **The prototype round** is a round, numbered after the last, with the one @-mention of the Operator. It holds the agent's intro; links to `prototype/<issue>` and the gallery, saying the gallery expires in about 30 days and this comment is the record; each variant's letter, one-line summary and a link to its component at the pushed commit; and one numbered question, "Which variant?", with the agent's recommendation. When Kit config declares `preview.url`, the push job fills it in for `prototype/<issue>` and, once it answers, links each variant's preview with `?variant=<letter>`. A template that uses `{pr}` has no value for a Prototype, so its round says there's no preview for prototypes. The Operator answers as in any round ("B, with the bigger booking button from C"), and the session carries on. A reply can ask for another prototype round, with no cap beyond the session's own.
- **What the session records.** When the session finishes, its brief or Spec records the chosen variant, the Operator's tweaks, and links to `prototype/<issue>` and that variant's component, as a reference the Implementer rewrites. The Implement prompt says a Prototype linked from a Ticket is never code to merge, cherry-pick or copy wholesale. The Reviewer gets nothing from a Prototype: a Ticket's UI evidence is judged against the Ticket alone.
- **A failed prototype turn never ends the session.**
  - The build or dev server failed (`build-failed`, `server-did-not-start`): the branch is pushed, and a prototype failure round says what failed, links the branch and asks "Carry on without a prototype, or try again?", recommending carrying on, so a `yes` never spends another hour of Sandbox time.
  - Capture failed for any other reason: the branch is pushed, and the round still asks "Which variant?", linking the branch, each variant's component and the preview if any, with the reason in place of the gallery.
  - A branch that changes a Trust-root file is not pushed, and the failure round names the paths (ADR-0005). A turn that made no commits posts a failure round saying nothing was built.
  - An Infrastructure failure, such as 1Password, the model provider or a timeout, takes the usual Design-turn failure path. The Operator's next reply starts an ordinary turn, which can ask for the Prototype again.
- **`prototype/<issue>` is a throwaway reference**, like a research Decision's `research/<number>-<slug>`: it's never merged and never gets a PR, and the Kit never deletes it. Only the push job writes to it, fast-forward from the head the turn started on, once the Trust-root guard has passed it.
- **`/fabrik-live-design` offers a Prototype too**, on the same conditions. On a yes, the agent runs the `prototype` skill locally on `prototype/<issue>`, gives the Operator the one command to open it in their own browser, and pushes the branch. There's no capture, gallery or Sandbox job, and the live outcome records the chosen variant as an async one does.
- **Run records** gain `prototype`: `true` for a prototype turn, whose role stays `design`, and `false` for every other record. The Weekly summary counts prototype turns as Design-session turns, as before, and no Scorer samples them.
- **What it costs.** About 60 Sandbox minutes against the Subscription each time, spent only when the Operator said yes, plus one gallery to look through and one reply. It saves Implement runs building the wrong layout, and the Request-changes loops on UI pull requests that follow.
- No shim change, no new Kit config key, no new secret, label or role, and no setup step: Prototypes ride on Visual evidence's `ui` block. A prototype turn reads what's already there: `ui.serve` and `ui.url`, `sandbox.build`, the optional `preview.url`, the Design role's model and effort, and `roles.implement.timeout_minutes`. So a Product repo only merges the bump PR.

## It starts on taking the release

There's nothing to turn on: a Product repo with a `ui` block gets Prototypes once it merges the bump PR, and one without never sees an offer. Visual evidence's setup step writes that block, so a repo that took it needs nothing new. No Sandbox minute is spent on a Prototype until the Operator says yes to an offer.

1. **Take it in the Pilot first.** Merge this release's bump PR in the Pilot only. It has Visual evidence's `ui` block and declares no preview. Then open an issue there whose open question is how a page should look, and once its Design session has started, check:
   - a round offers a Prototype naming the route and the variant count, with a recommendation, and a yes posts the request comment, with no mention, before the prototype turn starts;
   - the prototype round, numbered after the last, links `prototype/<issue>` and a gallery that opens in one click, with each variant's mobile and desktop screenshots and videos under its letter, links each variant's component, and ends with "Which variant?" and a recommendation;
   - replying with a choice carries the session on, and the brief or Spec it ends with records the chosen variant, the tweaks and the links to the branch and that variant's component;
   - `prototype/<issue>` has no PR and is still there once the session has ended;
   - one prototype turn's cost and duration, from its Run record in `fabrik-runs` (role `design`, `prototype: true`), against the about 60 Sandbox minutes and `roles.implement.timeout_minutes`.
2. Once the Pilot is healthy, merge the bump PR in the other Product repos. Those with a `ui` block get Prototypes straight away, and the rest run as before.
