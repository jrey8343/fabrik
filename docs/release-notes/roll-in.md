# Release notes: The Roll-in

The notes for the release that ships the Roll-in ([#595](https://github.com/jrey8343/fabrik/issues/595), under ADR-0010): a Design session on an issue filed from a pull request is told about that pull request, and can finish by settling a Roll-in onto it, which only the Operator sends. Paste them into the release's notes file (see [releasing.md](../releasing.md)), with its version and pins.

## What changed

- **A Design session on an issue filed from a pull request is told about that pull request.** When the issue's body carries a `From PR #n` line outside code, as a Follow-up filed through its "Open as issue" link does, each turn's prompt has one more section after the issue, "The pull request this issue was filed from": which pull request it is, where it stands, and its description, fenced as data, never instructions. The Design job reads the pull request afresh on every turn, with its read-only token, so a turn after the pull request merged says it merged.
  - **Where it stands says whether a Roll-in is on offer.** The work of a pull request that has merged is on the default branch, and nothing will merge the branch of one closed unmerged, so a Roll-in is on offer on neither; nor on an open Plain pull request, where a Request changes means nothing. On an open agent pull request a Roll-in may be settled. One still in draft is with the Implementer or the Reviewer, so the Operator sends the Roll-in once it is at the Merge gate.
  - **The session can read an open agent pull request's branch.** Before the agent starts, and before any secret loads, the Design job fetches that pull request's head with its read-only token to `refs/fabrik/filed-from/<n>`, a ref no branch of the Product repo can collide with, with the history to compare it with the default branch. The section tells the turn where to read it. The default branch stays checked out, and nothing of the pull request's diff goes into the prompt. The token goes to that one step and no credential is left behind, in the checkout or for any later step, so the agent job still holds no GitHub credential (ADR-0002). The head of a merged, closed or Plain pull request is not fetched.
  - **A read or a fetch that fails** fails the turn before its agent starts, under the usual failure notice, so no session writes about a branch it could not see. A `From PR` line that names no pull request in the repo adds nothing: the turn runs as it did before the release.
- **The session's first Round asks whether to roll it in.** When the code the issue changes exists only on that pull request's branch, or the work is a small change to what the pull request builds, one question of the first Round asks whether to build the issue's work there, with a recommendation. The same Round settles whatever else an Implementer would need, so one reply can finish the session. A session never settles a Roll-in on its own judgement, only on the Operator's answer.
- **A new finish: settling a Roll-in.** On the Operator's yes the session finishes by settling a Roll-in (`"kind": "roll-in"`) onto an open agent pull request, which need not be the one the `From PR` line names: any the Operator agreed to in the thread. The issue closes as not planned, as that finish closes it (`needs-design` swapped for `wontfix`, the issues it blocks still blocked), under a closing comment headed "What to build on #n": a text with acceptance criteria that stands alone, since the Implementer and the Reviewer who build from it are never given the issue. There is no word cap on it. An issue whose work is to be built on a pull request finishes this way and never as not planned in the session's own words, so not planned keeps meaning "won't be built".
  - **The Kit refuses a text that names the issue or mentions someone.** The issue is named by `#` and its number or by a link to it. A mention is told by the test the Kit strips mentions with. Nothing is stripped: the turn gets one chance to put it right, and the push job checks again before anything lands.
  - **The comment says nothing has been sent:** "Nothing has been sent to #n. The Operator sends this Roll-in with a Request changes on #n that carries this text and names this issue, #m."
  - **The Kit refuses a Roll-in onto a pull request that can't take one:** one that has merged or is closed, a Plain pull request, or the one built from this very issue as its Ticket. The turn fails and nothing changes, under the usual failure notice, which names the pull request and why.
- **Only the Operator sends it,** with a Request changes on the pull request that carries the text and names the issue (ADR-0010). The Kit never sends it, and settling one puts nothing on the pull request: no comment, no label and no review, so no run there builds what has not been sent. Once sent it is a Request changes like any other.
- **A Roll-in never sent is not lost.** When the pull request merges or closes first, whoever closed it, the Kit reopens the issue, takes `wontfix` off, posts one line saying why, which mentions nobody, and adds `needs-triage`, which starts Triage, so the work can be built as its own Ticket. After a merge the line is "#n merged before this Roll-in was sent, so the Kit reopened this issue for Triage: its work can be built on `main` as its own Ticket." After a close it is "#n closed unmerged before this Roll-in was sent, so the Kit reopened this issue for Triage. The code the text above names may not be on `main`." An issue the Operator reopened themselves, or one whose session has finished another way since, is left alone.
  - **Name the issue when sending by hand.** A Roll-in is sent when a Request changes of the Operator's on that pull request, not dismissed, names the issue in the review's own text, by `#` and its number or by its link. One sent by hand in a Request changes that does not name the issue reads as unsent: when the pull request merges, the Kit reopens the issue for Triage though the work was built, and the Operator closes it.
