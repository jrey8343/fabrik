# An Operator session is trusted as the Operator up to a short list of acts, which stop at a pull request the Operator merges or at the Operator's own hands

An Operator session runs in a throwaway VM of Anthropic's, reads issue threads that quote text nobody in the factory wrote, and acts on GitHub as the Operator through a credential it can't read but any process in its VM can spend. The Operator wants it to hold as much power as its work needs, on GitHub and beyond it. So the posture assumes that any session can be steered by what it reads, and splits what a session does in two. A short list of acts that can't be undone gets a stop the session can't make or fake: a merge into a default branch, a production deploy, a release of the Kit, reading or writing a secret's value, deleting data or a resource, a DNS change, a message sent or a thing shared with someone as the Operator beyond GitHub, and anything that spends money. Everything else rides on auto mode and on the Operator being in the conversation, and can be undone from GitHub.

- **A session acts as the Operator and counts as the Operator.** Its one identity on GitHub is the Operator's own, through the Claude GitHub App's connection. It may change Trust-root files, and the Kit counts its labels, comments and reviews as the Operator's. That rests on its file changes going out in one pull request that only the Operator merges.
- **A session never merges.** The Operator merges its pull request from the Console, outside the session. On a Product repo the Console covers, GitHub refuses a merge from anywhere else (ADR-0019).
- **No repo-level Actions secret in a repo the Kit covers holds real power.** The Kit's service-account tokens are the secrets of an environment only the default branch may use (ADR-0004), so a workflow run on a branch a session pushed is given none of them. A Product repo's own credential that can reach production is held the same way, or is a role taken by OIDC. That is the repo's to keep, and Setup reports on it.
- **No credential the agent can read.** Power beyond GitHub arrives one of three ways, taken in this order: a network secret on the repo's own Session environment, wherever the system takes its credential as a request header; a workflow on the default branch that holds its own role, for a cloud account whose requests are signed; a connector on the Operator's Claude account, only where neither fits, and cut to reads by the vendor's own grant, a read scope at sign-in or a server with no tool that writes. An attached credential is cut to reads and reversible writes, and one that can't be cut that fine is not attached. A repo says what it attaches in `.fabrik/operator-session.md`, a Trust-root file, and a session takes a repo with no such file to attach nothing.
- **A short-list act beyond GitHub is a pull request the Operator merges, or the Operator's own hands** on the vendor's site, with the session guiding and checking. A message or a share is always the Operator's hands: the session drafts it in the conversation and the Operator sends it.
- **A short-list act a workflow does when it is started is held in two parts.** What it does is held by the merge: every job that takes a role names an environment held to the default branch and the workflow takes no input, so it runs merged code alone. That it starts is held where the start is the Operator's word that production takes a change, as where merges go to staging and production is promoted by hand, or a DNS change is applied by hand. Such a workflow is a Held workflow. Its first job reads a Start check, a check run only the Console's App can make, on the run's own commit, named for that one workflow and no more than 15 minutes old when the first job reads it, and stops before any role is taken when there is none. The Console makes one at the Operator's tap, on the default branch's head, and starts nothing. A workflow that deploys on every merge reads none, and refuses a run whose commit is not the default branch's head.
- **A Kit release is cut only by the Operator's hands, at a terminal.** A release tag reaches every Product repo's runs on its default branch, so it is the factory's production deploy. In `fabrik`, two tag rulesets cover every tag: one refuses moving and deleting and nobody may bypass it, the other refuses creating and only a deploy key may bypass it. That key is the Operator's release key, whose private half lives in 1Password and is spent with a tap. Immutable releases are on. A session, a workflow it pushes and the Operator's own `gh` token are all refused a new tag, and nobody moves one.
- **Production infrastructure is within reach; customers' records and the production database are not.**
- **A Product repo's rule against agents holding cloud credentials holds every AFK agent, and not an Operator session.** Until the Operator edits a repo's own rule to say so, the rule wins: a session sorts those steps to the Operator's hands and says the repo's rule is why.
- **One bare Session environment serves every repo that attaches nothing, and a repo that attaches a credential has its own,** since an attached credential reaches every session in its environment. Each exists under the same name on every Subscription the Operator opens sessions from, so an attached credential is a standing grant on each. Claude's form falls back without a word to the last-used environment when a link's name matches nothing, so each Session environment holds its own name in a variable, and a session that finds another name there, or none, says so and waits.
- **A session holds nothing of its own.** What it spends sits at Anthropic's proxy, on its Session environment and on the Operator's Claude account, so nothing is given back when a session is left, and nothing is built to end one.

## Considered options

- **Judge every act by the hard test,** with auto mode and the Operator's presence counting for nothing. A session could then do little beyond GitHub without something built to approve each act, and the Operator asked for more power than that.
- **Honour a Product repo's own rule.** It would keep a session out of the cloud accounts where a sixth of past Operator work was done. The Operator made the rule and lifts it here, for infrastructure alone.
- **Readable keys in the Session environment,** so that a command-line tool works as it does in a terminal. A readable key can be copied out by a steered agent or by an install script, is shared by every session in the environment, and lives until it is deleted.
- **Keys minted for an hour to one role.** They need a minter. The Console would hold a credential that mints others, or the Operator would paste keys into the conversation.
- **A tap in Claude's app before a short-list act,** on a tool the Console hosts and marks to prompt on every call. The Console's Worker would hold third-party credentials, and nobody has tried the prompt on a phone. It was ruled out with the Console's endpoint as a whole, and returns only on evidence from real sessions that a recurring short-list act is served by neither a pull request nor the Operator's hands.
- **A session with an identity of its own,** or one the Console's App mints. A cloud session swaps any token it is handed for its own credential, and the Console's App holds its private key for its own reads alone (`fabrik-console`'s ADR-0010).
- **Telling a session's tracker writes from the Operator's.** GitHub marks a write made through an App, so the Kit could. A Pairing session's work is mostly tracker writes made as the Operator, and every run a steered session started would still end at the Merge gate.
- **A record kept by the Kit of what each session did.** With attached credentials cut to reads and reversible writes, every act that needs an account of it passes through GitHub, which keeps one.
- **Keeping the Operator's connectors and cutting them tool by tool,** with Claude's per-tool Blocked setting or a deny rule in the repo. Blocked is documented for organizations where Claude Code is concerned, and a repo's deny rule is the session's to edit and stops applying at a second repo. Reads were the larger risk in any case.

## Consequences

- **A session's merge is stopped by the Console check on a Product repo the Console covers.** GitHub refuses a merge at any head the Console's App has not passed, from a session, from the Operator's terminal and from github.com alike. A head the Console has passed is open to a session until it is merged or the check is taken back, and that is a head the Operator tapped Merge on. On a repo outside the Merge gate nothing on GitHub stops a session merging, and the merge is held there by auto mode, which let one through as an MCP tool call.
- **`fabrik-console` is kept off the Claude GitHub App's installation list** until its default branch is under the Merge gate with the Console check. A merge there deploys the Worker that passes heads on every covered repo, so a session that reached it would undo the stop everywhere. Work on its issues stays a Pairing session in the Operator's terminal. `fabrik` stays on the list: a merge into its default branch reaches no Product repo without a release tag, a tag is made only with the Operator's release key, and Setup's bootstrap is fetched at a release tag, never from the default branch.
- **Auto mode is the everyday layer and it misses.** Anthropic's own figure is 17% of overeager actions. Its rules can't be changed for a cloud session on a personal plan, and the Operator picks the mode on Claude's form each time, so nothing here depends on the mode.
- **Auto mode also refuses what a session may be asked to do,** a production deploy among them. Such an act goes out as a pull request or is done by the Operator's hands.
- **A session's reach on GitHub is every repo the Claude GitHub App is installed on,** with push, unasked, and any public repo for reading. The App is installed on a selected list the Operator keeps by hand: `fabrik` and the Product repos, each of which has a hold a session can't pass. `fabrik-console` is off it until its default branch is under the Merge gate, and `fabrik-runs` is off it because nothing holds its default branch, where a run is given the repo's token. A session therefore reads no Run records. Any other repo is added when a session needs it, and one the Kit doesn't cover keeps its repo-level secrets within a steered session's reach. By the skill's rule a session attaches a second repo only to read it and to write to its tracker, and changes files in its own repo alone. That rule is manners and holds nothing.
- **Every Claude account the Operator opens sessions from must stay connected to GitHub through the App.** `/web-setup` on any of them would give its sessions the reach of the Operator's `gh` token. Disconnecting one account cuts that account's sessions alone.
- **An attached credential is a standing grant with no expiry,** spent by any session in its environment until the Operator deletes it.
- **A cloud account whose requests are signed with the key is reached only through workflows that hold a role.** Each call waits on a runner starting, and a new kind of call waits on a merged workflow.
- **A session's tracker writes steer the Loop as the Operator's do.** A steered session can dispatch a Ticket, amend one or leave words an agent weighs as the Operator's own. The cost is Subscription usage and noise.
- **A session can change `.claude/settings*` in its own checkout,** and a repo's deny rules and hooks stop applying once a session has a second repo. Neither is relied on.
- **The one way to cut every session off from GitHub at once** is suspending the Claude GitHub App on GitHub.
- **The Pairing session in the Operator's terminal still holds the Operator's whole `gh` token** beside whatever a branch runs, and carries the same Claude account's connectors as a session. On a repo whose Kit config holds `console.app_id` it merges nothing: a step that is a merge is the Operator's from the Console there, as in an Operator session. On any other repo it merges another pull request on the Operator's word, as today.
- **A refusal by Anthropic's proxy counts as no hold.** A session's own routes to a tag, a release, a ruleset and a deploy key are refused there today, and the docs promise none of it. Every stop the posture relies on is one the Operator owns on GitHub: a ruleset, an environment, a Required check, or a permission the Claude GitHub App doesn't hold.
- **`fabrik`'s default branch is open to a session.** Nothing on GitHub stops a session pushing to it or merging into it. What that reaches without a release is the Operator: the README they read, their own checkout when they pull, and the next release, which is cut from it. The release steps read what the default branch gained since the last tag before a tag is made.
- **A branch workflow can still edit a release's notes and may be able to mark an older release as the latest.** The worst that gives Setup, run with no release named, is a genuine older release, and Setup prints which release it runs. Not tried.
- **No release is cut from a phone.** The by-hand way past is switching the ruleset on creating off on github.com and back on, which needs the Operator's own sign-in.
- **The hold is settings on one repo, kept by hand.** Nothing watches it between releases. The release steps read it each time, and a release is the only moment it is used.
- **A connector reaches every session on its Claude account, with every tool it has,** whichever repo the session opened on and whichever Session environment it is in, the bare one included. On a personal plan nothing outside a session switches one off for a session, a Session environment or a repo, and Claude's own per-tool setting is not known to reach a cloud session. So a Subscription that sessions open from holds no connector but the ones a repo's `.fabrik/operator-session.md` names. The Operator's own, for mail, a calendar and files, are disconnected there, reads included: a mailbox holds reset links and one-time codes, and reading one is reading a secret's value. A connector a repo names is the last way taken, and what it reads can be read from a session in any repo.
- **The Operator gives up their own connectors on those accounts,** in Claude's chat and in their terminal as well as in a session.
- **Nothing outside a session can tell that a connector has been reconnected.** A session reads its own list of tools, names a connector its repo's file doesn't, and waits. A steered session would not.
- **A workflow that holds a role is as narrow as its merged steps.** Its job names an environment held to the default branch and its role's trust names that environment, so a branch's copy can't take the role, and no input reaches a command line except as a fixed choice. Its output is a job log, which everyone who can read the repo can read.
- **A start by the Operator's identity is no stop, so a Held workflow does not rest on one.** A session starts any workflow on the default branch that can be dispatched, and re-runs any run, as the Operator, and passes a check of the actor's name. A Held workflow stops at its first job until the Operator has tapped in the Console, whoever starts it: a session, the Operator's terminal and github.com alike. A workflow that does a short-list act and reads no Start check is held from a session only by auto mode, which has let through every dispatch put to it on trial, five of five, and held both re-runs, by the Kit's text and by the repo's own list of workflows a session never starts.
- **A Start check not yet spent is open to anyone who can start the workflow,** for 15 minutes and for more than one run. That is a commit the Operator has just tapped for.
- **A rollback is a revert merged through the Merge gate.** A re-run of an earlier run is refused, since the Console makes no Start check on an older commit and a deploy on the merge refuses any commit but the head. In a repo that promotes by hand, a revert takes a staging deploy and then a promote.
- **A run from before a workflow gained its step re-runs without it,** since a re-run uses the workflow file of its own commit, for the 30 days GitHub re-runs a run. The Console offers no session on a repo until its older runs are past that or deleted.
- **The Console's health is a condition of starting a Held workflow.** While it is down the way past is ADR-0019's by-hand way, used to merge the step out. No second way is built: a variable the workflow also accepted would make the stop only as strong as the Claude GitHub App's permission list.
- **The step is as strong as the default branch's copy of the workflow.** A branch's copy without it is given no role, and a merge that takes it out goes through the Merge gate.
- **A promote with no session open is done in two places,** the Console and then GitHub.
- **Which workflows are held is the Operator's judgement.** Nothing in code makes a repo list one, and Setup only says which dispatchable workflows that hold a role are not listed.
- **The Console's App has a private key, held as a Worker secret for its reads (`fabrik-console`'s ADR-0010).** Whoever holds it can make a Console check or a Start check with no tap of the Operator's. No session reaches a Worker secret, and the Console asks for an installation's token with read alone, so the key is a way past only for someone who has taken it from Cloudflare. It is revoked on the App's own page.
- **What only the Operator keeps is written in [the README's "Operator sessions" section](../../README.md#operator-sessions),** beside the checklist run once on each Subscription: the Claude GitHub App's list, each Claude account's connection to GitHub through the App and never `/web-setup`, and a Product repo's own rule against agents' cloud credentials, edited before that repo attaches one. Nothing in the Kit or the Console reads any of the three.
