# Dispatch is a separate trigger label, not `ready-for-agent`

An Implementer starts when the Kit adds `agent:implement` to a Ticket, not when the Ticket gets `ready-for-agent`. Matt Pocock's `to-spec` and `to-tickets` add `ready-for-agent` to the Spec itself (before it has any Tickets) and to every Ticket (blocked ones included), so a label-add trigger would start an Implementer on a whole Spec, or on Tickets before their blockers have merged. `ready-for-agent` therefore stays a state ("this is ready"), and Dispatch is the Kit's own decision. The Kit adds `agent:implement` only to an open `ready-for-agent` issue with no open blockers, no sub-issues, no open linked pull request and no `agent:implement` already.

## Consequences

- The Kit checks for Tickets to Dispatch whenever an issue closes, after a Design session, on the Fast path, when a push to the default branch changes the Kit config, when `ready-for-agent` is added to an open issue (#418) and on the hourly tick. `max_in_flight` caps how many Implementers run at once, and `0` pauses Dispatch.
- Labels the Kit adds must use a GitHub App token, because labels added with `GITHUB_TOKEN` don't start workflows.
- Matt's skills are used unchanged; only the trigger is Fabrik's.

**Amended (#98):** a blocker closed as *not planned* counts as a blocker too. Its work never landed, so the Ticket it blocks stays blocked until the Operator removes the blocked-by edge. A blocker closed any other way (completed, duplicate) no longer blocks.

**Amended (#417):** GitHub fires `labeled` only for a label newly added, so a trigger label left on (a claim job that failed before taking `agent:implement` off) made every later add, the Kit's or the Operator's, start nothing. Dispatch still adds `agent:implement` only to a Ticket without it. But when any plan adds a trigger label already on, and it was last added over ten minutes ago, the adapter takes it off and adds it again so its event fires, and the step summary says so. One added more recently is left alone: its run is still starting and will take it off, and a second event would start a second run. A role that declines a trigger label (`agent:implement`, `agent:review`, `agent:design`, `agent:research`) takes it off and comments one line saying why nothing started. A first Implement run's landing takes off an `agent:implement` its claim left on, so it stops holding a `max_in_flight` slot.

**Amended (#418):** adding `ready-for-agent` to an open issue also runs a Dispatch check, and so does the hourly tick. The label still starts nothing itself: the check weighs it as any other, so a blocked Ticket or a Spec stays put. Without this, a Ticket the Operator marked ready by hand, or one left waiting while every slot was full, waited for some unrelated issue to close. So that the hourly check can't start a broken Ticket again every hour, a Ticket whose latest Kit word is its Implement failure notice isn't eligible: as for a research Decision, only the Operator re-adding `agent:implement` runs it again.

**Amended (#419):** a trigger label whose run never started, as when the Kit job failed on an invalid Kit config or the run was cancelled or lost before its claim, held its slot and started nothing again, since GitHub fires `labeled` once. The hourly tick now sweeps open issues and pull requests, before its Dispatch and Design queue checks, for a trigger label with no run behind it: one last added at least 30 minutes ago with no job of its role unfinished anywhere in the repo. The first time, the Kit adds it again (cycling it, as #417 does) and says so on the issue. If it's still on, with no run behind it, at a later tick, the Kit takes it off and @-mentions the Operator, parking the work as that role's failed run does, so only the Operator adding the label again restarts it. The Kit retries once, not on every tick, because the usual cause (a broken Kit config) needs the Operator, and the tick itself only runs once the Kit config is valid again. A cancelled run is treated as a lost one: to stop a run, take its label off.

**Amended (#543):** GitHub sometimes leaves a Ticket open after a PR that closes it merged, and still lists that PR among its closing PRs. Such a Ticket's work has landed, so it isn't eligible, whichever event ran the check, and no Implement run starts on it, nor resumes an open PR of it, even when `agent:implement` is added by hand. Any merged closing PR counts, an agent's or a person's. The hourly tick closes each open `ready-for-agent` Ticket with one as completed, commenting first that the PR merged and GitHub left the Ticket open. No other check closes it: right after a merge GitHub may not have closed the Ticket yet, and the Kit would comment on almost every merge.
