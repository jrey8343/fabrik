# The Kit heals a red Required check no pull request caused, short of setting it aside

This refines ADR-0011 and ADR-0018, which stay as written apart from the two exceptions below. A Product's red Required check that no pull request caused (a Flaky check, or an Unrelated failure, ADR-0030) used to wait on the Operator: to read its log, to have it fixed, and to bring a held pull request up to date. The Kit now goes as far as it can without setting the check aside ([How far does the Kit go by itself with a Product's red Required check that no pull request caused?](https://github.com/jrey8343/fabrik/issues/723), built in [#774](https://github.com/jrey8343/fabrik/issues/774)):

- **The check's issue goes to Triage, as before.** The Kit files nothing more than the check's issue, labelled `needs-triage`, and never a Ticket or a Design issue itself. Triage now reads its Failure excerpts (ADR-0029) and routes it: to an Implementer when the excerpts point at test or product code and one pull request can fix all of them, to the Operator (`ready-for-human`) when the fix is in a Trust-root file or outside the repo's code, else into design. Triage never splits an issue; the size test sends that to a Design session.
- **One more re-run at the Merge gate.** On the first hourly Tick after a pass that names an Unrelated failure still red on the head it was given on, with the pull request at the Merge gate, the Kit re-runs that check's failed jobs once more on that head. It is skipped for a check from an outside service, and when the same check is red on `main`'s head, where a re-run can't help; a skip counts as the re-run done. Green, the check is a Flaky check under ADR-0018's rules, with nothing counted back, and GitHub opens the Merge gate. Red again, the pull request waits for the fix. The Tick's job holds no `actions: write`: the caller grants its `tick` job `actions: read` and only its `loop` job `actions: write`. So the Tick posts a quiet line whose marker records the head and the checks and adds a trigger label, `agent:rerun-checks`, which the Loop workflow routes to the **Re-run red checks** job, still the only job with `actions: write`, loading no secret, holding no Fabrik App token and checking out no Product code (ADR-0018). It re-runs past a run's first attempt this once, and the label comes off as the run starts. Later Ticks read what came of it from the head's check runs, and a refusal, or a label still on with no run behind it, is said on the pull request and counts as done. **This is the one exception to ADR-0018's "one round per head".**
- **Bringing a held pull request up to date when the fix lands.** When a check's issue closes as completed, each open agent pull request at the Merge gate whose latest pass, on its current head, names an Unrelated failure of that check that hasn't since read green there is brought up to date by ADR-0011's path, unchanged: a plain rebase onto `main` pushed with a lease, else one conflict-only run, one attempt per `main` head with the attempt marker, and the push starts a Review. A run in flight, an unbuilt Request changes and a `main` head already tried are left alone, as ADR-0011 leaves them, and so is a pull request carrying `ready-for-human`, whose Hand-back stands until the Operator takes the label off ([ADR-0036](0036-a-hand-back-on-a-pull-request-stands-until-the-operator-gives-it-back.md)). A pull request that already holds `main`'s head has nothing to bring in, and that counts as this move spent. The trigger is the issue closing, not `main`'s check going green, since `main` doesn't run every Required check. The issue-closed event acts at once, and the Tick's conflict check catches a close it missed. **This is the one exception to ADR-0011's "a pull request that's only behind `main` is left alone".** A Plain pull request, and an agent pull request no such pass names, are untouched.
- **The Operator is mentioned once, only when these moves are spent.** One comment on the pull request that @-mentions the Operator, once per pull request and check, by its own marker, which the hourly Tick weighs. It is posted when the pull request is at the Merge gate, held by an Unrelated failure still red on its head, the re-run there is done or skipped for that head, and the check's issue waits on the Operator (`needs-design`, `ready-for-human`, `needs-info`, or still `needs-triage` an hour after it was filed), or closed as not planned or a duplicate, or the head is one the Kit brought up to date after the issue closed as completed, or the pull request already held `main`'s head then. It names the check, links its issue, and says what's left: re-run it, fix it, or merge past it by hand as ADR-0019 describes. While the check's issue is `ready-for-agent`, or a pull request for it is open, nothing is posted. Until then the Operator hears of it as quietly as of a Flaky check: the pull request line that mentions nobody, the check's issue, and the Weekly summary's count.
- **The Standing follows the mention.** While the Kit still has a move of its own on the failure, the pull request's Standing is the Kit's: `check-healing`, not the Operator's and stopping no work, so a reader that files a row by whose move it is tells the Operator nothing before the mention does ([#795](https://github.com/jrey8343/fabrik/issues/795)). The mention's marker is the one sign that the Kit's moves are spent. Once it names the check on the pull request, on any head, the Standing is `check-failing`, the Operator's and stopping work, and says the Kit has nothing left to try. The Standing rule reads what these moves leave on the pull request and never works out "spent" a second time, nor decides anything for the Loop. A `check-healing` Standing turns Stuck at the repo's Stuck bar like any row waiting on the Kit, but never while the check's fix is under way, by the same test that keeps the mention quiet (the check's issue is `ready-for-agent`, or a pull request for it is open), and its clock restarts when the fix stops being under way, so it doesn't read Stuck at the moment a fix lands.

The Kit never takes a check off the Required list, skips it or merges past it. That would need Administration write, which ADR-0019 keeps from the Fabrik App, and it would make the Merge gate a choice the Kit makes. Quarantining one flaky test is a fix a Ticket may make, never a move of the Kit's.

## Considered options

- **The Kit files a Ticket for the check itself.** It skips Triage's duplicate check and its routing to the Operator, and Triage already did this well whenever it could see the failure.
- **The Kit sets the check aside while it's fixed,** by the Required list or a quarantine. It weakens the Merge gate, and a quarantine is a judgment about the Product's suite, which belongs in a Ticket.
- **Re-run on every Tick until green.** It spends CI minutes on a check that's red for a reason, and hides a broken suite as a flake.
- **Bring the pull request up to date when `main`'s check goes green.** `main` doesn't run every Required check (gradually-core never runs `e2e` there).
- **Widen the caller's `tick` job to `actions: write`,** so the Tick re-runs the check itself. #723 assumed the Tick's job already held it; it doesn't. Granting it is a change to every Product repo's caller workflow, so the release would be a major (docs/releasing.md), and the write credential would sit in the job that runs every hourly gate rather than the one job that already holds it. Rejected for the trigger label, which keeps the release a minor.

## Consequences

- A check that clears by itself opens the Merge gate within the hour without the Operator, and a fix that lands reaches every pull request it held without the Operator asking.
- The re-run at the gate takes up to two hourly Ticks: one to ask, and the next to read back what came of it. The mention waits for the re-run's read-back, so it comes at the earliest on the Tick after.
- `agent:rerun-checks` is a trigger label the Kit adds. Added anywhere else, or again for a head, by anyone, it comes off with one line saying why, and the stuck-trigger sweep leaves it to the gate re-run's own read-back.
- Bringing a pull request up to date for a fix puts it back in draft and starts a Review, which costs a Review run; a pass on the new head brings it back to the Operator.
- The mention reads only the check's issues the Tick reads: open ones, and those closed in the week before. A check whose issue closed longer ago, with nothing brought in, gets no mention, and the pull request stays held as it would have without this ADR.
- The Operator is mentioned at most once per pull request and check, whatever heads and failures follow; a different check on the same pull request gets its own.
- A check no mention ever reaches, one from an outside service or one whose issue closed more than a week ago, leaves the pull request's Standing the Kit's until the repo's Stuck bar has passed with no sign from the Kit. Then it reads Stuck, which is the Operator's to act on, so the pull request is never held unseen.
- The Weekly summary and the read library each read two more things for this: every open issue's body, whose marker says which check a Check's issue is about, and the Check's issues closed in the last week, as the Tick reads them.
