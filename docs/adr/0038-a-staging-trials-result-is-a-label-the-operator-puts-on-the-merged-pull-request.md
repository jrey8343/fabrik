# A Staging trial's result is a label the Operator puts on the merged pull request

The Loop ends at the merge, and ADR-0021 follows a merged agent pull request to one deployed environment, production. A Product repo that deploys every merge to a staging environment, and production only when the Operator says so, had three gaps. Nothing said a merged pull request was on staging, or linked the Operator to it. Nothing recorded that they had tried it there, so when they came to deploy production they couldn't see which merged changes they had never looked at. And the pull request read "no deploy seen" an hour after its merge, in a repo where production only ever deploys by hand.

A **Staging trial** is the Operator trying a merged change by hand on staging before they deploy it to production. Its result is one of two labels the Operator puts on the merged pull request, `fabrik:trial-accepted` or `fabrik:trial-problem`, and the read library reads the result back from that label.

- **Staging is a second environment, and only a reader reads it.** Kit config gains a `staging` block beside `production`: the staging site's base address and the name its deploys carry in GitHub's Deployments. Both are required, and the environment is never production's. In a repo that declares it, a merged agent pull request stands at a new place, Staging, from its merge until a production deployment contains it. As ADR-0021 has production, only a reader of the Kit reads any of it, with its own credential (ADR-0020): no Kit job reads staging, the Weekly summary says nothing past the merge, and the Fabrik App gains no permission. Kit config is a Trust-root file, so no agent can change where a staging link points. A repo with no `staging` block reads exactly as it did.
- **On staging needs the Main checks green, where Live does not.** A pull request is on staging when GitHub shows a successful Deployment in `staging.environment` of its merge commit or a later commit that contains it, read as ADR-0021 reads production's, and every Main check `monitor.main_checks` names (ADR-0025) is green on the commit of the newest such Deployment, read through the one rule the Monitor reads a Main check by. The Operator is about to be sent there to try the change, so they are never sent to a staging site its own checks call broken. A Main check still running reads as deploying, and a red one as a failed deploy. Production's Live stays as ADR-0021 has it: deployed, not checked.
- **A pull request needs a trial when it changed something the Operator can see.** That is one the Kit treated as a UI pull request, a failed capture and an Evidence miss included, unless its Implementer said nothing visible changes; and one that closes a Trial problem, UI evidence or not. Every other merged agent pull request changes no screen and waits on nobody.
- **The result is the Operator's own label.** Only a label event whose actor is Kit config's Operator, `operator` or the repo's owner when it is null, is read. Every other actor's event on the two labels is ignored, the Fabrik App's included, so no agent and no App can accept a change for the Operator. The result is the label of the Operator's latest labelling of either, and removing that label makes the pull request untried again. Setup creates both labels, and no Kit job adds, removes or reads them.
- **A problem becomes a Trial problem.** The issue the Operator files when a Staging trial finds a problem carries one line naming the pull request it was found on, and is an ordinary issue otherwise, with no label of its own. The pull request reads as accepted once the Trial problem is closed and each merged pull request GitHub records as closing it is accepted by this same rule. Any other ending leaves it at a problem found until the Operator labels it accepted.
- **How long a Standing at Staging lasts turns on whose move it is.** A pull request that needs a trial and has no result is the Operator's move, so it keeps its Standing, whatever its name and place, until it has a result or production takes it, however long that is, and is never marked as stopping work. Production takes it when a production deployment that contains it has succeeded; one that failed or is still running has not. One with a result keeps its Standing for 24 hours from the label event that gave it, or from its fix's acceptance. One that changes no screen keeps it for 24 hours from its merge, as ADR-0021 has every merged pull request.
- **It is advisory from end to end.** No Loop rule waits on staging, and neither the Kit nor the Console deploys production or refuses a deploy. The Operator's own dispatch of their production workflow is the approval. The Promote list, every pull request a production deployment would take with its result, only tells them what that deploy holds.

## Considered options

- **A list of environments.** The Kit has rules for two, the one every merge reaches and the one the Operator promotes to. A list would be a shape with no rules behind it.
- **Widening Follow-up.** The Reviewer's is optional and holds nothing back; a Trial problem always exists and holds acceptance back.
- **A comment, a review or the Console as the record.** A comment is context and never a trigger (ADR-0007), and the Console is never a record.
- **The result as detail on one name.** A Standing's name fixes its wording and whose move it is, and an accepted pull request and one with a problem differ in both.
- **A named subset of Main checks for staging.** A second list to keep in step with `monitor.main_checks`.
- **Linking an Evidence shot to its Sandbox path on staging.** An Evidence shot carries only the concrete path its Journey visited in the Sandbox, so the link opens a missing record, or with numbered ids somebody else's. A shot, like a Dynamic route, links to the staging site itself.
- **Following every ending of a Trial problem.** Much rule for cases the Operator settles with one label.
- **The Kit or the Console deploying production, or refusing a deploy.** The Operator's own dispatch is the approval.

## Consequences

- It is dormant until a Product repo turns it on: declare `staging` in Kit config, and run Setup again for the two labels.
- A reader reads a second environment's Deployments, the Main checks on the deployed commit and the label events on merged pull requests, all with its own credential.
- A Design session's rewrite of an issue's body keeps a Trial problem's line, as it keeps the other lines that mark an issue, or a Trial problem that went through one would stop naming its pull request. It is the one change to the Loop, and it is made in every repo, with a `staging` block or without one.
- In a repo that declares `staging`, "merged" and "no deploy seen" are only ever said at Staging, so a production the Operator promotes by hand is never reported as missing, and a pull request at Production is Live for 24 hours from the production deployment that took it, not from its merge. ADR-0021's 24 hours from the merge still holds everywhere else.
- A reader's gather reads past the last day in such a repo: the pull requests merged since the last production deployment, the 100 most recent at most.
- The Main checks are read on the newest successful staging Deployment that contains the merge, so an untried pull request can go back to a failed deploy when a later deploy's Main check goes red. One with a result is never moved by a later deploy.
- The Kit doesn't check when a label was put on, or that a Trial problem exists. A `fabrik:trial-problem` with no Trial problem reads as a problem with no issue named.
- Production's shot links stay as they are, with the flaw the staging link avoids, since changing what an export means is a major.
