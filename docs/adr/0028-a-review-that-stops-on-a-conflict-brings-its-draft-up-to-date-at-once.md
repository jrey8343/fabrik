# A Review that stops on a conflict brings its draft up to date at once

This builds on ADR-0016, which stays as written. A Review starts on `pull_request_target`, which GitHub runs even on a pull request that conflicts with its base. A Product repo's Required checks usually run on `pull_request`, which GitHub doesn't start on a pull request it can't merge. So on a draft agent pull request that conflicts with `main`, the Review's checks wait used to poll for checks that would never start, give up at its deadline, and hand the draft back as an `unreported-checks` Infrastructure failure. That notice blamed the workflows. ADR-0016's unreviewed-draft path did bring the draft up to date in the end, but only once its grace period had passed, 25 to 35 minutes after the hand-back in both reported cases (#704).

**The wait stops on a conflict.** While it waits, the Review's checks wait also reads the pull request's mergeable state. When GitHub says the pull request conflicts and at least one Required check hasn't reported on the head, the wait stops at once. It leaves a `merge-conflict` failure report naming the checks that never reported, with the head it waited on and for how long. While every Required check has reported or is running, it carries on as before: checks that started before `main` moved still finish, and their outcome is what counts. While GitHub hasn't worked the state out, it keeps waiting. Giving up with a Required check unreported is still `unreported-checks`, and its report now also records the head, the minutes waited and the last mergeable state read, so the notice can say what most likely kept the checks from starting.

**The Kit brings the draft up to date without the grace period.** The grace period is there so the Kit never cuts into a Review that may still be running. Here the Review it would wait on is known to have ended: it's the one that stopped. So when a Review fails with `merge-conflict`, the Loop reads the pull request's mergeable state itself, as it does for a Review that passed (#480), rather than trusting the wait's read. If the pull request conflicts, the Loop takes ADR-0016's path straight away, and every other rule on that path still applies. That means a plain rebase pushed with a lease, else one conflict-only run. An undelivered Request changes is acted on first, nothing happens while a run is in flight, there's one attempt per `main` head, it uses no retry, and the Verdict is counted as the unreviewed push's would have been. The Tick's and the push-to-`main` check's handling of a draft, the grace period included, is unchanged.

**It hands nothing back unless the Operator has to act.** The Kit's note on the pull request leads with what happened: Review couldn't start, because the pull request conflicts with `main` at its head commit, and GitHub doesn't run the named checks on a pull request it can't merge, so the workflows are fine. It then says in bold whether the Operator needs to do anything, and what the Kit did. When the Kit can't move the pull request on from here, the note says why. A run in flight or an undelivered Request changes still moves it on by itself, and the note names the way to move sooner: merge `main` into the branch and push. When the Kit already tried against this `main` head, or the Loop's own read shows the pull request no longer conflicts, only the Operator can move it on, because GitHub starts the checks on a push and nothing else. Only then does the note mention the Operator and carry a hand-back (`conflicted-review`). No `merge-conflict` note is an Infrastructure failure.

## Considered options

- **Fix the wording only, and leave recovery to the Tick.** The notice would stop blaming the workflows, but the draft would still wait out the Review's timeout and then the grace period, with nothing for the Operator to do in between. Rejected: the Kit knows the Review has ended, so the wait buys nothing.
- **Stop the wait on any conflict, whatever the checks.** Checks that started before `main` moved still finish, and a red one is an Execution flaw the Reviewer needn't run for. Stopping only while a Required check is unreported keeps those outcomes.
- **Trust the wait's read of the mergeable state.** By the time the push job runs, `main` may have moved again, or GitHub may have worked out a state it hadn't. The Loop reads it again, against `main` as it is.

## Consequences

- The `unreported-checks` hand-back marker is unchanged, so its readers still work. Its notice now says the likely cause first and that it needs the Operator. That it's an Infrastructure failure using no retry moves to a hidden line.
- A Review on a draft that conflicts with `main` ends within about a minute of its start, and the draft is brought up to date in the same Loop run that reports it.
- Naming the pull request whose merge caused the conflict needs a lookup from `main`'s head to its pull request, so the note names `main`'s head commit instead.
