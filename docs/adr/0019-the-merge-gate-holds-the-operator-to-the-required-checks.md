# The Merge gate holds the Operator to the Required checks

The Merge gate was two things Setup applied to a Product repo's default branch: branch protection (a pull request and the Required checks, with no bypass allowance and no approving review) and the `Fabrik Merge gate` ruleset, which lets only the repo admin role update the branch, so the Fabrik App can't merge. Neither held the Operator. Setup left admin enforcement as it found it, and a new repo has it off, so the Operator, as the repo's admin, could merge at a head whose Required checks had failed or never reported, and could push straight to the branch. On github.com that takes a tick-box. Through the API it takes nothing: on a throwaway repo protected exactly as Setup protects one, the merge call merged a pull request whose required check had failed, and one whose check had never reported, for a GitHub App's user access token and a fine-grained personal token alike, and either credential wrote a file to `main` with no pull request ([Try the Merge-gate moves with a GitHub App user access token on a throwaway repo](https://github.com/jrey8343/fabrik/issues/523)). The Console is to make the Operator's merges with just such a credential, and GitHub reports every open pull request on a Kit repo as blocked, green or red alike, so its own answer can gate nothing.

So Setup holds admins to the default branch's rules, in every Product repo: `enforce_admins` in branch protection, "Do not allow bypassing the above settings" in the branch's settings. GitHub then refuses a merge at a head whose Required checks haven't all passed, and any push straight to the branch, the Operator's included, from github.com, `gh`, the Console or a leaked credential. A pull request whose Required checks have passed still merges, because the ruleset's admin bypass is untouched. Setup owns the setting as it owns the pull request rule and the Required checks: its plan names the change, and a later run puts it back when it finds it off. There is no flag and no Kit config key. It is the Kit's rule, not a choice per repo.

The way past is by hand on github.com: in the branch's settings, switch off "Do not allow bypassing the above settings", or take a check that can no longer report off the required list; merge; then run Setup, which puts enforcement back. That is how the Operator merges past a check on purpose, and the only way out when a Required check can never report again, as after a CI job is renamed, when the pull request that corrects the Kit config's list can't itself go green.

It is cheap to reverse in code: one setting in a call Setup already makes. It is recorded because the Console's credential is safe to hold only because of it. Switching enforcement off needs Administration write, which the Console's GitHub App is not granted, so with it on a leaked token pair can do nothing to a default branch but merge a pull request whose Required checks have passed. Decided with the Operator on 2026-11-11 ([Who stops a merge that isn't green: the Console, or the Merge gate with admins held to it?](https://github.com/jrey8343/fabrik/issues/540)).

No Kit-made check is a Required check ([Do pull requests that aren't the Loop's get a row on Home and a Merge button on Review?](https://github.com/jrey8343/fabrik/issues/573)). `loop / Kit` reports several times on one head with the latest report winning, never reports on a first setup pull request, whose base branch has no caller workflow yet, and as a Required check would make the Loop's health a condition of merging the Loop's own fix. With admins held to the rules, a Required check that can't report is a branch nobody can merge into. So Setup requires what the Kit config lists, plus any check the branch already required, and never a check the Kit makes.

## Considered options

- **The Console alone refuses,** by reading the head's checks before it sends a merge. The guard would live in the Console's code and cover nothing else: github.com and `gh` keep the tick-box, and the Console's credential could still update `main` with no pull request.
- **The Merge gate alone,** with the Console trying the merge and reporting GitHub's refusal. Review would offer a button that fails, and on a repo where enforcement is off the merge would go through. So the Console reads the Required checks as well, to show which one is in the way and never offer a merge GitHub would refuse: the Merge gate stops, the Console shows.
- **A warning with "merge anyway".** It keeps the hole the trial found, one tap away, in the Console, whose credential is the one to worry about.
- **A Setup flag or a Kit config key to leave enforcement off.** A choice per repo, where the Console's credential is safe only if there is none.
- **`loop / Kit`, or a new Kit-made check, as a Required check.** Above.

## Consequences

- The Operator can no longer merge past a red, running or unreported Required check, or push to a Product repo's default branch, from anywhere, without first changing the branch's settings by hand. Measured before deciding: of 132 merged pull requests across the two Product repos none was merged with a Required check not green, and neither default branch had taken a commit without a pull request since adopting the Kit.
- GitHub's rollup of every check on a head is not the test. Twelve of those 132 merges had a rollup that read failed, and all twelve were a Kit job, never a Required check. A red Kit job doesn't stop a merge.
- Nothing in the Kit merges or pushes to a Product repo's default branch: Setup's files, Kit bumps and Skills bumps go through pull requests. So the Loop is unchanged. `fabrik-runs`, which the Kit writes to directly, is not a Product repo, and Setup doesn't protect it.
- A repo already on the Kit gets enforcement on its next Setup run. A Kit bump never runs Setup, so the release's notes say to run it, and until then the Operator can merge past as before.
- A Required check that never reports stops every merge, its own fix's included, until the Operator takes it off the branch's list by hand. Setup adds Required checks and never removes one.
- The Loop still doesn't react when a ready pull request's Required checks turn red at the Merge gate: the Operator still re-runs the check or sends a Request changes. Its Standing now names the check ([A ready agent pull request whose Required checks turn red gets no reaction from the Kit](https://github.com/jrey8343/fabrik/issues/564)), and the Kit now hears of it as a Flaky check through the hourly tick's read of the passed head, when the check has both failed and succeeded there ([#693](https://github.com/jrey8343/fabrik/issues/693)).
- The Review can pass a pull request while a check the branch requires, but the Kit config doesn't list, is red ([The Review waits on sandbox.checks alone when the branch requires more](https://github.com/jrey8343/fabrik/issues/565)). The Operator could once merge past that check; now the pull request waits at the Merge gate until it passes.
- Not tried when this was written: the trial's required check was a commit status, not an Actions job, and a check that never reported was not tried with enforcement on. That GitHub takes the latest of several reports of one name is its documented behaviour, and that `loop / Kit` never reports on a first setup pull request is read from its trigger; neither was tried.
