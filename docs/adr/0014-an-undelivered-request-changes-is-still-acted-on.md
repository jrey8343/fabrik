# A Request changes GitHub didn't deliver is still acted on, and its run brings main in

This refines ADR-0010 and ADR-0011. GitHub doesn't start workflows for `pull_request`-family events while a pull request conflicts with its base, so an Operator's Request changes on a conflicting agent pull request reaches the Loop through no event. The Kit now looks for one itself. On every push to `main` and every hourly tick, an Operator `CHANGES_REQUESTED` review on an open agent pull request counts as undelivered when it was submitted while the pull request was out of draft, is more than 10 minutes old, has had no Request-changes run outcome since (no push, Verdict or ended note), and no Kit comment names it yet. The Kit posts one comment naming every such review and, if the pull request conflicts with `main`, saying that GitHub doesn't start workflows for reviews then. It converts the pull request to draft and starts one Request-changes run for the latest review, which reads all the Operator's Request changes as amendments. The comment marks that run in flight, so the Kit never posts twice for the same review.

Any Request-changes run whose pull request conflicts with `main`, delivered or not, is told to **merge** `origin/main`, resolve the conflicts, and build the requested changes, listing each conflicted file and how it was resolved. While the Operator has a Request changes no run has built, ADR-0011's conflict check leaves the pull request alone, so the Request-changes run resolves the conflict instead. If a Review, Retry or conflict-only run is in flight, nothing starts until it lands (ADR-0006). If that Review gives an Execution flaw, the Verdict gives way: it calls for no Retry and doesn't count toward the Ticket's two, and the next check starts the Request-changes run, which reads its findings with the review. If the run can't merge `main` in, or the trust-root guard refuses it, the Kit says why on the pull request, adds `ready-for-human`, takes it out of draft and never closes it, as for a conflict-only run. That note counts as the attempt for that `main` head.

We chose to act rather than ask the Operator to resubmit because of jrey8343/penrith-physiotherapy-sports-centre#60. That pull request was `dirty` after #59 merged, and the Operator's Request changes started no run. Asking for a resubmit leaves the work stalled until they notice. Worse, with ADR-0011 the Kit's own rebase would push and start a Review of a head without the amendment. That Reviewer, reading the review as part of the Ticket (ADR-0010), can give an Execution flaw for the unbuilt change and so use a Retry. ADR-0010 says a Request changes must never cost one.

The run merges rather than rebases because it is the Implementer's work on a pull request the Operator has already reviewed, like a Retry. A merge leaves the commits they reviewed as they were. A conflict-only run rebases only because it finishes the plain rebase the Kit tried first (ADR-0011), and no plain rebase comes first here.

## Considered options

- **Ask the Operator to resubmit.** A comment could say GitHub dropped the review and ask for it again once the conflict is gone. But the Operator has nothing to fix, and the Kit's rebase in the meantime starts the Review that can use a Retry on the unbuilt amendment.
- **Act only after ADR-0011's rebase lands.** The rebase clears the conflict, and a resubmitted or re-read review would then be delivered. But that Review of the rebased head comes first, with the same Retry risk, and the pull request goes round the Loop twice for one request.

## Consequences

- The PR snapshot reads every Operator Request changes review with its submission time, the pull request's draft changes, and the Kit's comments with their times, so it can tell when a review was submitted relative to the Kit's notes.
- The trust-root guard (ADR-0005) still judges only the run's own changes. The merge brings in `main`'s commits, which aren't the run's. A conflict resolved inside a trust-root file is the run's change, and is handed to the Operator rather than closing the pull request.
- An Execution flaw that gave way carries a marker field, so the Retry count stays readable from the pull request's comments alone.
