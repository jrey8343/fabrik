# A Request changes GitHub didn't deliver is still acted on, and its run brings main in

This refines ADR-0010 and ADR-0011, and ADR-0006's Retry count and its rule that no Verdict lands while a run is in flight. GitHub doesn't start workflows for `pull_request`-family events while a pull request conflicts with its base, so an Operator's Request changes on a conflicting agent pull request reaches the Loop through no event. The Kit now looks for one itself, and marks every Request-changes run it starts on the pull request, so it can tell a review no run was started for from one whose run is under way.

Every Request-changes run is started by a Kit comment naming its reviews, which marks it in flight. For a delivered review, that's a short note as the run starts, which also names any earlier Request changes of the Operator's no run was started for. For an undelivered one, it's the note below. The run is in flight until it pushes, is given a Verdict or ends without pushing, or until the pull request leaves draft or the Operator dismisses every review it names. A Request changes the Operator submits on the draft while it's in flight counts too, and counts as noted, but it never keeps the run in flight, and the run never read it; anyone else's on the draft does nothing. While a run is in flight, no other head gets a Verdict (ADR-0006), no Retry lands, and only a run started for one of its reviews lands. A Request-changes run's push or Verdict settles the reviews there were when it started, which it read, and a pass settles every review before it, its Review having read them as part of the Ticket (ADR-0010). A review that came in mid-run stays unbuilt after the run's push, so an Execution flaw on it gives way. A run that ends without pushing settles nothing. One whose reviews the Operator dismissed while it worked pushes nothing, and the Kit says so: a Request changes of theirs no run has built gets its run started; otherwise, if an Execution flaw gave way to the review, that flaw's Retry starts; otherwise the pull request goes back to the Merge gate. A Request-changes run's own empty diff never gives way. A note whose pull request never went back to draft, because what followed it failed, has its run started by a check at least 10 minutes later.

On every push to `main` and every hourly tick, an Operator `CHANGES_REQUESTED` review on an open agent pull request at the Merge gate counts as undelivered when it was submitted while the pull request was out of draft, nothing has settled it, no Kit comment names it, and no Request-changes or conflict-only run is in flight. Once one is more than 10 minutes old, the Kit posts one comment naming and linking every such review. On a pull request that merges cleanly GitHub did deliver the review, so a run may be working for it whose claim never noted it, and the Kit waits for the Implement job's timeout instead. If the pull request conflicts with `main`, the comment says that GitHub doesn't start workflows for reviews then. The comment puts their Request-changes run in flight, for the latest review, which reads all the Operator's Request changes as amendments. The Kit then converts the pull request to draft and starts that run. The push-to-`main` check and the tick take turns, so the Kit never names the same review twice, and each reads `main` as GitHub does when it runs. While every Subscription is used up, the note says the run is held until the weekly limit resets.

Any Request-changes run whose pull request conflicts with `main`, delivered or not, is told to **merge** that `main` head, resolve the conflicts, and build the requested changes, listing each conflicted file and how it was resolved. The run records the head it was told to merge. The push job judges whether it resolved the conflict against that head, never `main` as it is by the time the run ends, and counts it only if it was one of `main`'s heads. While the Operator has a Request changes no run has started for, ADR-0011's conflict check leaves the pull request alone, so the Request-changes run resolves the conflict instead. If a Review, Retry or conflict-only run is in flight when the Kit finds the review, nothing starts until it lands. If that Review gives an Execution flaw, the Verdict gives way to every Request changes no run has built: it calls for no Retry, doesn't count toward the Ticket's two, names those reviews, and starts their Request-changes run itself, which fixes its findings too. If what the run built still conflicts with the head it was told to merge, if it committed nothing, or if the trust-root guard refuses it, the Kit says why on the pull request, adds `ready-for-human`, takes it out of draft and never closes it, as for a conflict-only run. That note counts as the attempt for that `main` head. Once `main` moves and the pull request is brought up to date, an Execution flaw on it still gives way to the Request changes.

We chose to act rather than ask the Operator to resubmit because of jrey8343/penrith-physiotherapy-sports-centre#60. That pull request was `dirty` after #59 merged, and the Operator's Request changes started no run. Asking for a resubmit leaves the work stalled until they notice. Worse, with ADR-0011 the Kit's own rebase would push and start a Review of a head without the amendment. That Reviewer, reading the review as part of the Ticket (ADR-0010), can give an Execution flaw for the unbuilt change and so use a Retry. ADR-0010 says a Request changes must never cost one.

The run merges rather than rebases because it is the Implementer's work on a pull request the Operator has already reviewed, like a Retry. A merge leaves the commits they reviewed as they were. This holds even when the Operator's review asks for a rebase. How the branch takes in `main` is how the Kit keeps a pull request current (ADR-0011), not part of the Ticket, so a Request changes amends what the pull request builds (ADR-0010), not how its history is kept. A Request changes on a pull request that doesn't conflict is unchanged: the run brings in `main` as the review asks. A conflict-only run rebases only because it finishes the plain rebase the Kit tried first (ADR-0011), and no plain rebase comes first here.

## Considered options

- **Ask the Operator to resubmit.** A comment could say GitHub dropped the review and ask for it again once the conflict is gone. But the Operator has nothing to fix, and the Kit's rebase in the meantime starts the Review that can use a Retry on the unbuilt amendment.
- **Act only after ADR-0011's rebase lands.** The rebase clears the conflict, and a resubmitted or re-read review would then be delivered. But that Review of the rebased head comes first, with the same Retry risk, and the pull request goes round the Loop twice for one request.
- **Tell a delivered review's run from the Verdict it followed.** Before this, a Request-changes run was in flight while the latest Verdict was a pass on the head the Operator's latest review was on. That missed a review on a head the Operator pushed, and it claimed a review that came in during the Kit's own rebase, which no run would ever build. A note per run costs one comment, mentioning nobody.

## Consequences

- The PR snapshot reads every Operator Request changes review with its submission time, the pull request's draft changes, and the Kit's comments with their times, up to a thousand comments. It leaves out a review older than the oldest comment or draft change it read, when there were more, since what settled it may be among those it didn't read.
- The trust-root guard (ADR-0005) still judges only the run's own changes. The merge brings in `main`'s commits, which aren't the run's, and a file the branch holds just as git's own merge of the pull request's head and the `main` the run brought in would have it is `main`'s too, even one the Operator had changed on the pull request. Which `main` that was, the push job works out for itself: `main` as it is at the push, or else as the Kit job read it before the run started, whichever the branch holds and the pull request's head didn't. The head the run's result names never decides it, as the agent job can write that result (ADR-0004), nor does a commit `main`'s history holds but `main` was never at, such as the middle of a multi-commit push. Merges follow the pull request's `.gitattributes` as they stood before the run. A conflict resolved inside a trust-root file is the run's change, and is handed to the Operator rather than closing the pull request.
- An Execution flaw that gave way carries the reviews it gave way to in its marker, so the Retry count stays readable from the pull request's comments alone. If the Operator dismisses all of them before their run lands, it is the Execution flaw it would have been: it counts toward the Ticket's two, and its Retry is owed. Once their run has pushed or been given a Verdict, it gave way for good. No Retry is in flight once the pull request has left draft since the Verdict that called for it.
- A Request-changes run lands only while it's in flight, so a second run started for the same review pushes nothing over the first.
