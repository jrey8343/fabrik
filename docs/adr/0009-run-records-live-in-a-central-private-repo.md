# Run records live in a central private repo, written only by the push job

Every AFK agent run gets one Run record, plus its gzipped stream-json transcript, in one private GitHub repo shared by all Product repos (`jrey8343/fabrik-runs`). Only the push job writes there, with a second Fabrik App token scoped to that repo and to Contents write. Records are append-only: the push job writes only what it knows when the run ends (the stream's `init`, `result` and last `rate_limit_event`, and what `FABRIK_NEEDS` and the agent result say). Later facts such as merges, reverts and Human touches are never written back. They are read live from GitHub when metrics are computed. Records and transcripts are kept forever, and each record carries a schema version and the Kit sha that wrote it.

We chose this because Scorers, Replay, the Retro and the weekly summary all need records that outlive the 90-day Actions retention and span several Product repos, and gradually-core is the second. A git repo costs nothing at this volume, needs no new vendor or secret, and can be read with `gh`, `git` and `jq`. Writing from the push job keeps ADR-0002's rule that the job running Product code never holds a write credential.

## Considered options

- **An orphan branch in each Product repo.** It needs no new App install. But it shows up in each repo's branch list, it can start Product CI on push, and it splits records across repos that cross-repo metrics need together.
- **Actions artifacts.** They are already the hand-off from agent job to push job. But they are per run, deleted after at most 400 days, and readable only through the Actions API.
- **Cloudflare R2 or S3.** These scale past a git repo, but each needs a new account and a new credential. Deferred until transcripts approach about 1 GB.
- **An OpenTelemetry backend.** Free tiers keep about 14 days, content is cut off at 60 KB, and the ingest token would sit in the agent job.

## Consequences

- The Fabrik App must be installed on `fabrik-runs` with Contents write. `fabrik-runs` must be at least as private as the most private Product repo, because a transcript can hold whatever the agent echoed.
- Parallel push jobs write one file per run and retry on conflict, so they never edit the same file.
- A Pairing session writes no record. It runs locally, has no push job, and counts as a Human touch instead.
- A run killed by its timeout still gets a record, with no result fields and, if the upload didn't survive, no transcript.

## Addendum: the Weekly summary is filed from `fabrik-runs`

The Weekly summary is one issue per week covering every Product repo, filed in `fabrik-runs` by a scheduled workflow there. Its App token therefore also gets Issues write on `fabrik-runs` and read access to the Product repos it summarises. The push job's token stays Contents-write only, and nothing in a Product repo's agent job gains a credential. Decided in [Operator inbox and weekly summary](https://github.com/jrey8343/fabrik/issues/84).

## Addendum: the score-record job is the judge run's own push job

Scorers add a second job that writes to `fabrik-runs`: the score-record job, which writes the judge run's transcript, its Run record (role `score`) and the score file, each create-only, save that a judge with scores replaces the skip score file a failed judge left; a judge re-run in a later attempt of the workflow run files its Run record under that attempt, so the failed judge's record and cost stay ([#451](https://github.com/jrey8343/fabrik/issues/451)). This refines "written only by the push job" rather than contradicting it. The score-record job is the judge run's own push job and has the same shape: it checks out only the Kit, runs no agent and no Product code, and mints a Fabrik App token scoped to `fabrik-runs` with Contents write only. The judge job, which runs the agent, holds no write credential, so ADR-0002's rule holds. The push job itself writes the score file of a run its scoring plan skips, with the store token it already holds. Decided in [Spec: Scorers](https://github.com/jrey8343/fabrik/issues/149).

## Addendum: the Retro evidence job reads `fabrik-runs`, read-only

The Retro reads the Run records, score files and transcripts in `fabrik-runs`, so a third Kit job reaches the store: the Retro evidence job, a Retro run's first job. It reads `fabrik-runs` with a Fabrik App token scoped to that repo and to Contents read only, and checks out only one Product repo's paths in it, under `runs/`, `scores/` and `transcripts/`. It refuses a store that isn't private. Like the score-record job, it refines this decision rather than contradicting it. It has the push job's shape: it checks out only the Kit, runs no agent and no Product code, and holds no write credential, so it writes nothing to the store, records included. It hands the evidence to the Retro job, which runs the agent, as an artifact, so nothing in a Product repo's agent job gains a credential and ADR-0002's rule holds. Decided in [Spec: Retro](https://github.com/jrey8343/fabrik/issues/151).

## Addendum: the replay-record job is the Replay's own push job

A Replay adds a third job that writes to `fabrik-runs`, after the push job and the score-record job: the replay-record job, which runs once for both arms of a replay Ticket. For each arm it writes the patch, at `replays/<owner>/<repo>/<replay-issue>/<ticket>-<arm>-<run>.patch`, and the arm's gates beside it, at `<ticket>-<arm>-<run>.gates.json`, the Implement and Review runs' Run records and transcripts, and the judge's record and score file, each create-only with the record writer's conflict retry. The arm is part of each path, because both arms run in one workflow run, and so is the workflow run, because a Ticket whose run never landed runs again, and create-only paths would keep the first run's files ([#448](https://github.com/jrey8343/fabrik/issues/448)). This refines "written only by the push job" in the same way the score-record job did. The replay-record job is the Replay's own push job and has the same shape: it checks out only the Kit, runs no agent and no Product code, and mints a Fabrik App token scoped to `fabrik-runs` with Contents write only, plus the App's token for the replay issue, which it then rewrites. The arm jobs that run the agent and the Product's code hold no write credential, so ADR-0002's rule holds.

A replay run's record carries `replay`: the replay issue, the arm, the Ticket and, for a `kit` variant, the candidate sha. That moves records to schema 4, not the schema 3 that [Spec: Replay](https://github.com/jrey8343/fabrik/issues/156) planned, because [UI prototypes](https://github.com/jrey8343/fabrik/issues/155) had already used 3 for `prototype`. Score files move to schema 2 and carry the same field. Older records read back with `replay: null`. Its `kitSha` stays the pinned release's. The Weekly summary and the Retro leave every replay record and score file out of their figures.

The scheduled tick also reads the store, only while the Product repo has an open replay issue. It reads the newest weekly-limit reading on each Subscription, which the spare-capacity gate weighs, and this repo's records, from which a waiting request's Tickets are picked. It reads them like the Retro evidence job does: a Fabrik App token scoped to `fabrik-runs` with Contents read only, a sparse checkout of the Run records alone, and no write. Decided in [Spec: Replay](https://github.com/jrey8343/fabrik/issues/156).

Every Implement run's record says why it ran on the Step-up model, as `stepUpReason` (`retry`, `marked`, `request-changes` or `conflict-only`, null when it didn't), which moves records to schema 5 ([#364](https://github.com/jrey8343/fabrik/issues/364), ADR-0014). Older records read back with a null reason, or `retry` when they Stepped up, since until then only the second Retry recorded a Step-up.

Every Implement run's record says whether its branch changed nothing, as `emptyDiff`, which moves records to schema 6 ([#448](https://github.com/jrey8343/fabrik/issues/448)). The push job's Loop step finds it and passes it to the record writer as a step output. A Replay takes a Ticket's first Implement run to be the one that built its branch, passing over an empty diff. Older records read back with `emptyDiff: false`.

## Addendum: the store's daily Tick check writes the Dead-tick issue into Product repos

The store's caller gains a daily job, the Tick check, and with it the one kind of issue the store writes into a Product repo: the Dead-tick issue, filed when no Tick has started its jobs there for 25 hours, and closed once one has. Until now the store wrote only to itself. The check mints a Fabrik App token of its own on every repo the installation lists, with Checks read (to find each repo's last `tick / …` check run on main), Contents read (for `fabrik.yml`'s pins and the store's Run records) and Issues write (to open and close the issue, in the Product repo, or in `fabrik-runs` for a repo the App can no longer reach). It checks out only the Kit and the store's `runs/`, runs no agent and no Product code, and writes nothing to the store's files.

We chose this because a dead Tick can't be watched from inside its own repo: a Tick that GitHub refuses at startup, or that never fires, runs nothing that could notice, and the store's caller is the only Kit code that keeps running when a Product repo's is dead. The Fabrik App already had all three permissions on its installation, so its permissions don't change. The Weekly summary's tokens stay as they were, read-only on the Product repos and Issues write on `fabrik-runs` alone. The Tick itself closes its repo's Dead-tick issue on its first run with the token it already holds; the daily check closes it too, for a Product repo pinned to a release from before the Tick did. Decided in [Nothing notices a dead hourly tick](https://github.com/jrey8343/fabrik/issues/461).
