# AFK secrets come from 1Password, with one service account per job role

Every secret an AFK job needs comes from 1Password at run time, not from repo Actions secrets. That covers the shared `CLAUDE_CODE_OAUTH_TOKEN`, each Product repo's test secrets and the Fabrik App key. The **job is the security boundary, not the step**. GitHub-hosted runners give passwordless `sudo`, so an agent can read every secret its job references out of the runner's worker process memory (that's how the March 2025 `tj-actions/changed-files` compromise stole secrets). So jobs are split by which **read-only service account** they reference. Each Product repo holds three, as the secrets of a GitHub environment named `fabrik` that only the default branch may use:

| Service account | Reads vault | Referenced by |
|---|---|---|
| agent | `Fabrik` (the Claude token) | Triage, Dispatch, Review, the judge |
| implement | `Fabrik` + `Fabrik Sandbox · <product>` (that repo's test secrets) | Implement, and a Design session's prototype turn, which builds and serves the Product too |
| push | `Fabrik App` (App ID + private key, and the `Sentry token`) | the push jobs (ADR-0002), the score-record job among them (ADR-0009), and the Monitor |

Even an agent that dumps memory reaches only the token it already has and, in Implement or a prototype turn, its own repo's test secrets. The Scorers' judge job (#149) is an agent job of this kind: beside the Claude token its job holds only the read-only `github.token` it reads the Ticket with, and no write credential (ADR-0002), so that is all a judge that dumps memory reaches. Kit config in `.fabrik/` lists test secrets as `op://` references. A Kit step resolves them with the service-account token in that step's env only, using `load-secrets-action` in output mode and never `configure`. The agent step then gets just the resolved values.

**The `fabrik` environment keeps the tokens from a workflow run on a branch.** Whoever can push a branch can push a workflow with it, and GitHub gives a repo-level secret to any run that names it. An Operator session can push one, and may be steered by what it reads. So no token is a repo-level secret. Each Kit job that reads a token names the environment, with `deployment: false` so that GitHub records no Deployment (ADR-0021), and GitHub fails a job that names it from any ref but the default branch. The caller workflow still passes each token by name. `fabrik-runs` holds its one token the same way. A pull request review is the one event of the Loop's that GitHub doesn't run as the default branch, so its run reads no token: it starts a run of the caller workflow on the default branch, naming the pull request and the review, and that run reads the review from GitHub before it acts on it. The environment does nothing about a job on the default branch, which is still the boundary described above.

## Considered options

- **Repo Actions secrets, filtered by a `FABRIK_SANDBOX_` prefix using `toJSON(secrets)`.** Reading `toJSON(secrets)` references every repo secret, the App key included, so the agent job would hold a write credential and break ADR-0002. Passing named secrets explicitly instead means editing `fabrik.yml` for every new test secret. That file is meant never to change between releases, and the App can't push it. Rotating a shared credential would also mean running `gh secret set` once per Product repo.
- **1Password as the source, with a wizard syncing values into Actions secrets.** This removes the runtime dependency, but it still needs explicit secret names to avoid the leak, and the values drift whenever someone forgets to re-sync.
- **One service account per repo.** It's simpler to set up, but any agent job could then read the App key.
- **1Password's Credential Broker.** Still in public preview on 2026-11-21, on 1Password's Business plan, and documented for GitHub organizations. It still stores a key on GitHub, and what holds a branch's run out is an optional condition on the branch or the environment, whose matching against GitHub's token isn't documented. It hands a job a whole 1Password Environment with no `op://` references, and is set up by hand in 1Password's own apps. What it adds is that a leaked key alone opens nothing, and each of our tokens reads only what its own job already holds. To be looked at again once it is generally released.
- **Repo-level secrets, as before.** A branch's workflow run is given every one, and the push account's reads the Fabrik App's private key.
- **One environment per job role.** Which token a job reads is fixed by the Kit's pinned workflow, so three environments add setup and no boundary.
- **"Protected branches only" as the environment's rule.** It lets every branch through in a repo with no branch protection rule.
- **Letting a pull request's merge ref into the environment's rule,** so that a review's run keeps its tokens. Anyone who can open a pull request and review it would be given them, with that pull request's copy of the caller workflow.
- **Leaving a Request changes to ADR-0015's check alone.** It would wait for the next push to `main` or Tick, up to 70 minutes.
- **A broker of our own that checks a job's OIDC token.** It is the only way that leaves nothing on GitHub and proves the Kit's own workflow is asking. It needs an always-on host that holds the tokens, and every run would depend on it.
- **GitHub's workflow execution protections,** rules on who and what may start a workflow. Whether one can hold a branch's workflow wasn't looked into, and the tokens would still sit at repo level.

## Consequences

- 1Password is a hard dependency of every run. It has no SLA, and the action neither retries nor caches. A failed load is an infrastructure failure, not an Execution flaw, so it doesn't use up the Ticket's retries. The one optional load is the Monitor's `Sentry token`, which can't fail its job: production errors are opt-in, so a missing or unreadable token is a quiet dormant note in the step summary, never a failure.
- Service-account permissions can't be changed after creation. Setup (ADR-0013) creates the three accounts per repo with `op service-account create`, with no expiry, and stores them in the `fabrik` environment. A repo that moves from repo-level secrets gets three new accounts, and holds six until the Operator deletes the old three on 1Password's site, against the limit of 100. 1Password's limit of 100 accounts caps Fabrik at about 33 Product repos.
- Rotating the Claude token is one edit to a 1Password item, and every repo picks it up on its next run. The token is stored as an API Credential with its expiry date, so Watchtower warns three months ahead. That warning only shows inside the app; the backstop is a run failing loudly with `authentication_failed`.
- The tokens are as safe as the default branch's workflow files and the environment's settings. The first is the Merge gate's to hold. The second only the repo's owner can change: not a run's own token, and not an Operator session.
- A private Product repo needs a GitHub plan with environments. Setup stops on one without, and keeps no repo-level fallback.
- GitHub creates an environment a workflow names and the repo lacks, with no rule and no secrets, and a secret passed by name then resolves to the repo-level one of that name. An environment set to "Selected branches and tags" with no rule in it is as open: every ref is given its secrets. So Setup adds the rule and reads it back before it stores a token, and on every run checks that the one rule is there, never only that the environment is.
- A run's own `GITHUB_TOKEN` can read the `fabrik` environment and the branch it is held to, and can change neither it nor its secrets.
- The run a review's hand-off starts has `github-actions[bot]` as its actor. Who reviewed is only what that run reads from GitHub.
- Whoever can start a workflow can start the hand-off's run, naming any pull request and review, so that run believes only what it reads from GitHub.
- A Request-changes run uses the default branch's caller workflow and Kit config, and starts one run later than the review's own. If the hand-off fails, ADR-0015's check finds the review.
- A Product repo's own secrets are its own to place. Setup names each repo-level one and says whether the production environment Kit config names is held to the default branch.
