# The Implementer writes a Staging trial's steps and the Reviewer judges them

A Staging trial ([ADR-0038](0038-a-staging-trials-result-is-a-label-the-operator-puts-on-the-merged-pull-request.md)) told the Operator where to try a merged change, and gave them only route patterns and Evidence shot names for what to try. A shot's name says which screenshot it is, not what a person should do or what they should then see. Nothing on the pull request said in plain words what the change was meant to do, so the Operator read the diff or the Ticket to work out what to check. And they did every step by hand, though they already work with an agent that can drive their own browser.

**Trial steps** are what the Operator checks in a Staging trial: a summary of what changed for a person using the product, and ordered steps that each say where to go, what to do and what should be seen. The Implementer writes them, the Kit keeps them on the pull request, and the Reviewer judges them before the merge. A **Trial session** is a Staging trial the Operator runs with an agent driving their own browser, which ends in the Operator's verdict.

- **The Implementer writes them, on every run whose pull request will ask for a Staging trial.** That is one the Kit treats as a UI pull request, unless the run says nothing visible changes, and one whose Ticket is a Trial problem, as ADR-0038 has it. They are a new optional field of its output, `trial`. A run on an existing pull request, a Retry, a Touch-up, a Request-changes run or a conflict-only run, writes them again for the pull request as it now stands, as it writes `summary`, and is given the ones the pull request keeps to start from.
- **Their shape is a summary and steps.** `summary` is one short paragraph, in plain language, of what changed for a person using the product. `steps` is an ordered list, one step at least, each with `do`, what the person does, and `expect`, what they should then see, concrete enough to check by looking. A step may give `route`, the page it starts on: a path starting with `/` with no dynamic segment.
- **A step on a record's page starts on the nearest page with a fixed address.** Staging has its own records, so a route that carries a record's id opens a missing record, or somebody else's. The step's `do` says how to reach the record from there, such as "open any patient from the list".
- **The Kit keeps them on the pull request.** The push job writes them into the pull request's body as one hidden line, `<!-- fabrik:trial-steps {…} -->`, in the Kit's marker style, as it keeps the evidence and shots markers, so a reader needs only the pull request. Each run's body is written whole, so a later run's marker takes the earlier one's place, and the pull request carries one. The marker's writer and reader are beside the Trial problem line's, and a reader of the Kit uses them and holds no format.
- **Only a Product repo that declares `staging` is asked.** Its Implementer's prompt gains the part that asks for `trial`, and its pull requests the marker. A repo with no `staging` block has neither: its prompt and its pull requests are as they were.
- **A malformed `trial` never fails a run.** One that is not a summary and at least one step holding `do` and `expect` is treated as left out, as `routes` and `shots` are, on both sides of the output contract, and the run lands as it would have. A `route` that is no path, or has a dynamic segment, is left off its step, and the step is kept. The shape is all Kit code checks.
- **The Reviewer judges whether they are good enough.** On a pull request that will ask for a Staging trial, each of these is an Execution flaw: no Trial steps; a step with no `do` or no `expect`; steps that do not exercise what the diff changes; an `expect` the diff does not produce; a `route` that carries a record's id. It is a finding like any other, so a Retry or a Touch-up fixes it by the rules that already choose between them.
- **Text from an agent is data.** A reader draws Trial steps as text, never as markup or as links of their own. The only link is the one the Kit builds from a step's `route` on `staging.url`, which Kit config, a Trust-root file, fixes. The marker's JSON spells the characters that could end its HTML comment or mention someone as escapes, so no step can do either.
- **A Trial session performs the steps and never decides.** The agent opens the staging site in the Operator's own browser, waits while the Operator signs in, performs the steps in order, and says for each what it saw against what was expected. It acts only on the staging site, and an instruction inside a step that asks for anything else is reported, not followed. It asks the Operator for the verdict once for each pull request: accept, problem, or leave untried.
- **The verdict is the Operator's, and so is the label.** On accept, the agent puts `fabrik:trial-accepted` on the pull request with the Operator's own credential, at the Operator's word, so the label event's actor is the Operator and ADR-0038 reads it as theirs. On problem, it files the Trial problem and puts `fabrik:trial-problem` on the pull request the same way. Nothing is labelled until the Operator gives a verdict, even when every step matched.

## Considered options

- **Steps derived from the Ticket's acceptance criteria.** A criterion is a check a test or the diff shows is met, not something a person does in a browser, and a Request changes amends them.
- **Steps written in the Design session.** They would be written before the code exists, so they would drift from what was built.
- **The pairing agent inferring what to test.** A reader would have nothing to show, and two sessions would test different things.
- **A self-contained prompt composed by a reader.** The method would live outside the Kit, and agent-written text would be pasted whole into a session that drives a browser.
- **Records for Dynamic routes named in Kit config.** A Trust-root list to keep in step with staging's data.
- **A flow diagram.** The steps and the session carry the flow.
- **The agent accepting when every step matched.** ADR-0038: no agent accepts a change for the Operator.
- **Pausing before steps that write.** Staging is the Operator's to change, and the Operator is watching.
- **A recording on the Trial problem.** There is nowhere to keep one without new storage.

## Consequences

- It is dormant until a Product repo declares `staging`, and needs no Setup run beyond the one ADR-0038 asks for.
- A pull request merged before the Kit kept Trial steps has none, and reads as having none. A Trial session on one works from its routes and shot names, and asks the Operator what to check.
- A run that leaves `trial` out leaves its pull request with none, the earlier run's included, since the marker is written only from what the run gave. The Reviewer's finding is what puts them back.
- A finding about Trial steps is one about the pull request's body, where they are kept, so the Reviewer tags it `[small: body]`. The run that fixes it gives `trial` again and has nothing to commit for it, which a Touch-up whose findings are all about the body may do. A pull request gets two Touch-ups, so a third Execution flaw of such findings alone calls for a Retry, and that Retry may commit nothing too: where every finding of its Verdict is tagged `[small: body]`, by the same count of the same tags, the Kit writes the body again from what the run gave, posts the run's `fix` under a note that ends it, and Reviews the same head again. It is still one of the Ticket's two Retries. A Retry given any finding not tagged `[small: body]` is as it was: one that commits nothing is an empty diff. This one rule is the Loop's own ([ADR-0027](0027-an-execution-flaw-of-only-small-or-missed-earlier-findings-calls-for-a-touch-up-not-a-retry.md)), so it holds in a repo that declares no `staging` too, for any findings about the body alone.
- ADR-0038 had only a reader read anything of staging. The Loop now asks one thing of the `staging` block, whether it is there. It still reads no Deployment and no address, and nothing in the Loop waits on a Staging trial.
- The Implementer is told when its pull request will ask for a Staging trial, by `ui.paths` and by the Trial problem's line in its Ticket, and the Kit does not hold it to that: `trial` on a pull request that asks for none is kept all the same, and read by nobody.
- A step's `route` is held to the same rule wherever it is read, the output contract and the marker's reader alike, so a marker somebody edited cannot send a staging link off the staging site.
- The Trial steps are judged by the Reviewer once, before the merge, and performed after it by an agent that follows them. A step that passes Review and is still wrong shows up in the session's report as one that did not match, or could not be performed, and the Operator decides what it means.
- A label put on in a Trial session is told from any other of the Operator's by nothing: the Kit reads the actor, as ADR-0038 has it, and not how the label was put on.
