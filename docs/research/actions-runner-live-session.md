# Can a GitHub Actions runner host a live session the Operator reaches from a phone?

Research for [#799](https://github.com/jrey8343/fabrik/issues/799), a Decision on the map [#796](https://github.com/jrey8343/fabrik/issues/796). Date: 2026-11-19.

**Question.** Can a GitHub-hosted Actions runner host an Operator session: a live, many-turn conversation between the Operator and an agent acting as them, reached from a phone, on the Operator's Claude subscription, with no machine of the Operator's running?

**Method.** Desk research only. Nothing was installed, no workflow was run and Remote Control was not tried. Sources, all fetched 2026-11-19:

- Claude Code's docs at code.claude.com, as raw `.md` pages (Remote Control, authentication, environment variables, errors, permissions, settings, model configuration, mobile, Channels, headless, Agent SDK sessions, cloud sessions and environments, self-hosted environments, GitHub Actions, legal and compliance, and the changelog, whose newest entry was v2.1.327 of 2026-11-17).
- `anthropics/claude-code-action` at `main` (`5a85689`, 2026-11-18): `action.yml` and `docs/`.
- GitHub's docs (Actions limits, billing, runner pricing, hosted runners, `workflow_dispatch`, the workflows REST API, App permissions, environments, OIDC, `GITHUB_TOKEN`, the Actions terms).
- Anthropic's Consumer Terms (effective Oct 8, 2025).

Each fact carries its source. **Inferred** marks my reasoning from the docs, not something they state. "Silent" means I looked and the docs say nothing. Anything billed per token through an API key is out of scope and is named in a line where it comes up.

`docs/research/remote-surfaces.md` (2026-11-02) was the starting point. Its Remote Control row still holds. What is new here is the credential Remote Control needs, what `claude remote-control` does with no terminal, and what an Actions job costs and loses.

## Answer

**Not with what the Kit's jobs hold today, and not by any path the docs describe end to end.**

- **The Kit's credential can't do it (documented).** The one-year token from `claude setup-token` "can only make model requests, so it can't establish Remote Control sessions". Remote Control needs a full claude.ai sign-in.
- **A sign-in without a browser exists, half documented.** `claude auth login` will exchange a refresh token given in `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`. The docs say this in one table row and nowhere say where such a token comes from. It "works once", and a sign-in has a time limit, so a runner would have to write the renewed credential back somewhere after every job. Whether this holds up from a fresh VM each time is unknown.
- **Three more things stop the server on a fresh runner (documented):** a workspace trust check that refuses "at once" when `CI` is set, a one-time "Enable Remote Control?" question, and a spawn-mode question. Only the last has a flag.
- **If the server did start, the rest is ordinary Remote Control (documented for any host, inferred for a runner):** the session is listed in the Claude app's Code tab, pushes reach the phone, and the Operator picks the model (Fable included) and the effort from the phone.
- **Other ways exist, and none is a live session in Claude's own app.** A chat of one job per turn (`claude -p --resume`) runs on the token the Kit already holds. Channels put the conversation in Telegram or Discord. Self-hosted environments, which would make a runner a real cloud-session host, are Team and Enterprise only.
- **It costs** $0.006 a minute on a private repo for as long as the job is alive, idle or not (free on a public repo), ends at 6 hours at the latest, and takes the working tree and the local transcript with it.
- **Whether it is allowed is not settled by the docs.** The Operator signing in to the unmodified binary on their own subscription is the permitted case. But the credential Anthropic documents for CI is the one that excludes Remote Control, and the docs are silent on keeping a full sign-in in a CI secret store.

**Inferred from these.**

- The only non-interactive route to a full sign-in on a fresh runner is the refresh-token exchange. The scope `user:sessions:claude_code` in the docs' own example reads like the one Remote Control needs, but no page says so.
- The refresh token would have to be read out of a sign-in's `.credentials.json`, since the docs name no other place one appears.
- Because the exchange "replaces" the token, the copy in the secret store is dead after one job. The job must write the new credential back before it ends, and a job that dies first leaves nothing valid behind. The Kit's 1Password service accounts are read-only and "can't be changed after creation" (ADR-0004), so the write-back needs a credential the Kit doesn't have today.
- Two jobs can't start from the same stored token at once.
- Whether the exchange also ends the sign-in the token was taken from (the Operator's laptop, say) is not stated.

## 3. What a runner has that a cloud session doesn't

**On the runner (documented by GitHub and by the Kit's ADRs).**

- **Repo and environment secrets.** "Secrets stored in an environment are only available to workflow jobs that reference the environment. If the environment requires approval, a job cannot access environment secrets until one of the required reviewers approves it." Limits by GitHub plan: "If you are on a GitHub Free, GitHub Pro, or GitHub Team plan, required reviewers are only available for public repositories", and on GitHub Free environment secrets are public-repo only. ([Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments))
- **OIDC.** "your cloud provider issues a short-lived access token that is only valid for a single job, and then automatically expires". ([OpenID Connect](https://docs.github.com/en/actions/concepts/security/openid-connect))
- **A `GITHUB_TOKEN` per job**, scoped by the workflow's `permissions`, that "expires when the job finishes". ([GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token))
- **The Fabrik App's token**, minted in a job of its own from a key read out of 1Password, and the Kit's own steps that resolve `op://` references with a read-only service account per job role (ADR-0002, ADR-0004).
- **A whole VM.** "each GitHub-hosted runner is a new virtual machine", with "passwordless `sudo`". `ubuntu-latest` is 4 CPUs and 16 GB on a public repo, 2 CPUs and 8 GB on a private one, with 14 GB of disk. ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners))
- **A start the Console's token can send.** `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches` takes a `ref` and `inputs`, and answers 200 with `workflow_run_id`, `run_url` and `html_url`. It needs the "Actions" repository permission at write, for a user access token or an installation token. "The maximum number of top-level properties for `inputs` is 25", "The maximum payload for `inputs` is 65,535 characters", and "This event will only trigger a workflow run if the workflow file exists on the default branch." ([REST: workflows](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event); [Permissions required for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps); [Events: workflow_dispatch](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch))

**In a cloud session, for contrast (documented by Anthropic).**

- Environment variables are not secret: "Anyone who uses the environment can read the values." A network secret is attached "after each request leaves the session's VM, so the key itself stays outside the VM", per host, and never to GitHub or the Anthropic API. ([Cloud environments](https://code.claude.com/docs/en/cloud-environments#add-network-secrets))
- GitHub goes through a proxy that serves only "the repositories attached to the session" and "rejects requests to GitHub's GraphQL endpoint", so `gh pr` and `gh issue` fail. ([GitHub proxy](https://code.claude.com/docs/en/cloud-environments#github-proxy))
- "Interactive auth like AWS SSO" is "Not supported. SSO requires browser-based login that can't run in a cloud session". The page describes no OIDC identity for a session. ([What carries over](https://code.claude.com/docs/en/cloud-environments#what-carries-over-from-your-setup))
- It has what the runner lacks: no sign-in to provision, no minutes bill, and a conversation that outlives its VM ("Restored: your conversation history"). ([Environment expired](https://code.claude.com/docs/en/claude-code-on-the-web#environment-expired))

**Inferred.** ADR-0004's reasoning applies to an Operator session on a runner unchanged: "an agent can read every secret its job references out of the runner's worker process memory". A job that hosts the session would hold the Operator's full claude.ai sign-in beside whatever else it references, and that sign-in is a wider credential than the model-only token ADR-0002 lets an agent job hold. An environment's required reviewer gates a job's start, so a grant made part-way through a session would need a second job.

## 5. Whether it is allowed

**Anthropic, documented.**

- The Consumer Terms list among the things a subscriber may not do: "Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it, to access the Services through automated or non-human means, whether through a bot, script, or otherwise." They also say "You may not share your Account login information, Anthropic API key, or Account credentials with anyone else." ([Consumer Terms](https://www.anthropic.com/legal/consumer-terms), effective Oct 8, 2025)
- "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Ultra, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." ([Legal and compliance: Authentication and credential use](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use))
- Addressed to developers building products for others: "developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." (same)
- The exception that fits one Operator: "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code". (same)
- "Advertised usage limits for Pro, Max, and Ultra plans assume ordinary, individual usage of Claude Code and the Agent SDK." "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice." "For questions about permitted authentication methods for your use case, please contact sales." (same page)
- The Remote Control page speaks throughout of "your machine". The nearest it comes to a server is "If you run `claude` from a terminal on a remote machine, start it inside `tmux` or `screen`", and the self-hosted page says "To run Claude Code on your own always-on machine and drive it from other devices, use Remote Control". Neither names CI. ([Remote Control: Limitations](https://code.claude.com/docs/en/remote-control#limitations); [Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments))

**What the docs don't settle.**

- A live session the Operator drives is plainer "ordinary, individual usage" than the AFK fleet is. **Inferred.**
- The credential Anthropic documents for CI is the `setup-token` token, and it is the one that can't open Remote Control. Whether that is a policy line or only a scope the token happens to lack is **silent**.
- Whether the Operator may keep their own full sign-in, or a refresh token from it, in a secret store for a CI job to use is **silent**. The "must complete through Anthropic's own flow" sentence is written about developers and their users; the docs don't say how it reads for one person's own automation. The refresh-token variable exists and is documented, which suggests a supported use, but the docs don't say whose.
- Only Anthropic can answer it; the legal page gives the contact.

**GitHub, documented.** On hosted runners Actions should not be used for "any other activity unrelated to the production, testing, deployment, or publication of the software project associated with the repository where GitHub Actions are used", nor for "Any activity that places a burden on our servers, where that burden is disproportionate to the benefits provided to users". "You may only access and use GitHub Actions to develop and test your application(s)." ([Additional product terms: Actions](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features#actions), effective August 27, 2026) A session that works an issue in the repo it runs in looks like development of that project (**inferred**); a job held open and idle for hours is the part those terms would read least kindly.

## 6. The last resort: an always-on box

An always-on machine of the Operator's is the case the Remote Control docs are written for: "To run Claude Code on your own always-on machine and drive it from other devices, use Remote Control, which is also available on Pro, Max, and Ultra plans." It would need Claude Code installed and one interactive `/login` as the Operator, repeated whenever the sign-in nears its time limit (the docs warn three days ahead and don't give the length). It would run `claude remote-control --spawn worktree` once in each repo's checkout, answering the trust and "Enable Remote Control?" questions once at a terminal, kept alive in `tmux` or under a service manager that restarts on exit codes 4 and 69. From then on the Operator can start a session from the phone against the running server, each in its own worktree, with pushes, model and effort as in section 1, and nothing for the Console to start. It would also need each repo cloned and kept current, whatever credentials a session's work needs kept on the box, and patching and uptime that nothing announces when they fail. ADR-0002 records that the Operator won't run such a box for Fabrik, and this map ranks it last. ([Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments); [Remote Control](https://code.claude.com/docs/en/remote-control); [Changelog](https://code.claude.com/docs/en/changelog) v2.1.325)

## What it would take

For Remote Control on a runner, each step with what backs it:

1. **A full claude.ai sign-in on the runner**, by `CLAUDE_CODE_OAUTH_REFRESH_TOKEN` and `CLAUDE_CODE_OAUTH_SCOPES` then `claude auth login` (documented in one row), from a refresh token taken from a sign-in the Operator made (inferred; the source of the token is undocumented).
2. **A write-back of the renewed credential** before the job ends, to a store the job can write (inferred from "works once"). The Kit's service accounts are read-only.
3. **No `CLAUDE_CODE_OAUTH_TOKEN`, API key or `apiKeyHelper` in that job** (documented: any of them takes precedence and Remote Control refuses).
4. **The checkout marked trusted** in `~/.claude.json` before the server starts (the key is documented; that Remote Control honours it is inferred), because with `CI` set the server refuses instead of asking.
5. **The "Enable Remote Control?" acceptance carried onto the VM** (where it is saved is undocumented), and `--spawn` passed.
6. **The push toggles turned on once** by the Operator in a terminal session (documented as saved to the account for one of the two).
7. **A `workflow_dispatch` workflow on the default branch of every repo a session can open on**, and a token for the Console with Actions at write on those repos (documented). `fabrik` has no caller workflow today (the map's notes).
8. **A way to tell the Operator the session is up**: its name in the app's list, or its `claude.ai/code` URL posted from a hook that reads `CLAUDE_CODE_BRIDGE_SESSION_ID` (documented variable; the posting is inferred).
9. **Work pushed before the job ends**, since the VM is not kept (inferred).

For the one-job-per-turn chat instead: the token the Kit holds, a transcript file carried between jobs (documented), and a conversation drawn somewhere other than Claude's app.
