# Fabrik

A software factory: an agent-driven engineering loop that takes work from idea → spec → tickets → shipped code.

Status: building v1. See the Spec in GitHub Issues (#28).

## Layout

- `src/loop/` holds the **Loop rules core**: a pure function, `planFor(event, snapshot, config)`, that returns a plan. It does no I/O, and its tests (`*.test.ts`, next to the code) are the Loop's behaviour, one sentence each.
- `src/__fixtures__/` holds the snapshot builders the core's tests use.
- `src/kit/` holds the **Kit config** loader (`resolveKitConfig`: defaults and validation) and the caller workflow release check (`checkCallerWorkflow`), which `checkKit` makes together. All are pure; every run, the Kit job's included, calls them before anything else, so no agent starts on an invalid Kit. `src/kit/pushJob.ts` decides what the push job applies from how the jobs before it ended.
- `src/github/` holds the thin **GitHub adapter**: `events.ts` maps an Actions event, or what an agent job passed out, to a Loop event; `snapshot.ts` gathers the snapshot, reading the Kit's comment markers back through `threads.ts`; `apply.ts` applies the plan; `client.ts` is the API client.
- `src/main.ts` is what the push, claim and Dispatch jobs run (`node src/main.ts`, Node 24, no build step and no runtime dependencies). In the push job (`FABRIK_NEEDS`), it applies an agent job's output, or its failure notice, instead of the Actions event.
- `src/agent/` holds the **agent job** runner (`node src/agent/run.ts triage`, `design`, `prototype`, `implement`, `review`, `audit`, `retro` or `research`): Sandcastle with `noSandbox()` on the runner VM, the metered-billing preflight as the last `onSandboxReady` step, the `init` check, the step summary, and the role's output passed out as `agent-result.json`. Only agent jobs install the runtime dependencies (Sandcastle, the Claude Code CLI and Playwright, pinned exactly).
- `src/evidence/` holds **Visual evidence** (see `ui` in the [Kit config](#kit-config)): `uiEvidence.ts` is the pure UI evidence module (whether a PR is UI, which routes to capture and why, the capture result every later reader shares, the Reviewer's images, and the PR body's evidence section and its marker), `gallery.ts` the one-page gallery and a Prototype's, `capture.ts` the pure capture core, and `capture-main.ts` the capture step of the Implement job and of a prototype turn, the one Kit program that imports Playwright. `src/kit/previewLink.ts` is the push job's preview steps, which its `link-preview` action runs for a UI PR (`src/kit/preview-main.ts`) and its `link-prototype-preview` action for a prototype round, the same program given the round.
- `src/review/` holds the Review checks job's step (`node src/review/wait.ts`), which waits for an agent PR's required checks, and the pure rule for how they ended.
- `src/preflight/` holds the metered-billing preflight (pure) and the command the hook runs.
- `src/skills/` and `skills.lock.json` pin Matt Pocock's skills, the Base skills, at a commit SHA and install them into a Product checkout's gitignored `.claude/skills/` (ADR-0003), beside the Extra skills a Product repo picks from its own Skills sources (ADR-0008, see [Extra skills](#extra-skills)). `src/skills/fetch.ts <product checkout> [role]` installs them; `src/skills/pinnedManifests.ts` is the Kit job's check of the picks against each source's manifest at its pin.
- `src/skills/bump.ts` decides the weekly skills bump PR (`.github/workflows/skills-bump.yml`), with the upstream diff in its body; `src/skills/bump-main.ts` is its step. The same planner decides a Product repo's bump PRs for its own Skills sources, which `src/skills/sourceBumps.ts` pushes from the scheduled tick (`src/skills/source-bumps-main.ts`, gated by `src/skills/source-bumps-due.ts`).
- `src/release/` checks that each release pins Sandcastle, the Claude Code CLI and Playwright at exact versions, which Dependabot bumps (`.github/dependabot.yml`). See [docs/releasing.md](docs/releasing.md) for the release process.
- `src/kit/jobs.ts` is the Kit job's step: it checks the Kit config and the caller workflow's pins, asks the Loop rules core what the event calls for, and routes it to an agent job (when the plan starts an agent run), to the push job, or nowhere.
- `prompts/` holds the Kit's agent prompts, and `prompts/scorers/` the Scorers' versioned rubrics (Efficiency, Ticket compliance and Skill use), which `src/kit/kitFiles.ts` reads and `src/kit/rubrics.ts` parses. A rubric changed without a version bump fails its tests' version guard. The `run-judge` action has the Kit's fixed judge model apply them to a finished Implement run's transcript, with no tools and no write credential (`src/kit/judge-main.ts`), and the `write-score-record` action writes the score file and the judge's own Run record to `fabrik-runs` (`src/kit/score-record-main.ts`), which, like `src/main.ts`, imports no runtime dependency: a test holds every program an action runs without `npm ci` to that. `loop.yml`'s judge job (`score`) and score-record job run them.
- `.github/workflows/loop.yml` is the reusable workflow a Product repo calls. It holds wiring only. The steps its jobs share are composite actions in `.github/actions/`: `prepare-agent` readies an agent job (installs the Kit, fetches the skills, and reads the agent's inputs through `src/agent/inputs.ts`), and `run-loop` runs the Loop as the Fabrik App. After it, the push job's `write-run-record` writes the run's Run record and transcript to the `fabrik-runs` store (`src/kit/runRecord.ts`, `src/kit/recordWriter.ts`, ADR-0009), with the store token its `store-token` action mints, as `write-score-record` does. It never fails the push job, and a Product whose Operator hasn't set up `fabrik-runs` gets one step-summary line saying so. For a record in the store, the same step runs the Scorers' scoring plan (`src/kit/scorer.ts`, `src/kit/scoreRecord.ts`): it writes a skipped run's score file itself, and for a picked run the judge job (`score`) and then the score-record job, the judge run's own push job, run after the push job. Nothing in the Loop waits on them, and Dispatch never counts the judge job as an Implement run.
- `.github/workflows/schedule.yml` is the reusable scheduled tick the caller workflow runs hourly, for the Loop's time-based rules (closing the weekly-limit issue after its reset and, with Subscription rotation on, resuming the runs held until then, opening the week's pending Audit and pending Retro, and taking the Replays' next step), a Dispatch check and a Design queue check, once a week the Product repo's skills bumps, and in a job of its own the Monitor. Like the push job, it never touches Product code.
- `src/monitor/` holds the **Monitor**, which the scheduled tick runs hourly in its own job, with no model call and no Run record: `core.ts` is the pure Monitor core (what it files, rewrites, holds and closes, and the step summary's lines), `redMain.ts` its red-main part, `issues.ts` what both parts share of a Monitor issue and its body, `sentry.ts` the pure Sentry translator, `sentryApi.ts` the Sentry API reads, and `main.ts` the thin program that gathers the facts, with the GitHub reads in `src/github/monitorFacts.ts`, and applies the plan. `errors-set.ts` is the job's gate, so the Sentry token loads only when the Kit config sets `monitor.errors`. See `monitor` in the [Kit config](#kit-config).
- `.github/workflows/weekly-summary.yml` is the reusable Weekly summary the `fabrik-runs` store's caller runs each Monday morning. Its `file-weekly-summary` action reads the store's Run records, its score files and every Product repo's GitHub facts (`src/github/facts.ts`), builds the summary (`src/kit/weeklySummary.ts`, its metrics read through the Retro evidence module, `src/kit/retroEvidence.ts`) and files it in `fabrik-runs` (`src/kit/weeklyFiling.ts`). Its **Scores** section, shown only in a week with score files, gives each rubric version's runs scored, median score and share passing against last week, the skips by reason, and what scoring cost as a share of the week's cost, which cost per merged PR and per Spec leave out. It never lists a run's own scores. It never touches Product code either.
- `src/loop/kitIssues.ts` holds the Kit-owned issues: the "Rotate the Claude token" issue (label `fabrik:token-rotation`) and the weekly-limit issue (label `fabrik:weekly-limit`), each one per Subscription with rotation on, and the usage-credits issue (label `fabrik:usage-credits`), which buzz the Operator once per repo, or once per limit window, instead of once per Ticket. `src/loop/subscriptions.ts` chooses each run's Subscription (see `subscriptions` in the [Kit config](#kit-config)), `src/loop/heldRun.ts` names the runs held while every Subscription is used up, and `src/loop/resume.ts` resumes them at the reset.
- `src/loop/audit*.ts` holds the Audit (label `fabrik:audit`, see [Audit](#audit)): the audit gate the scheduled tick runs (`auditGate.ts`), the pending Audit's Auditor run (`audit.ts`), the Audit output parser (`auditOutput.ts`), filling the Audit in (`auditLanding.ts`), and starting and failing its run (`weeklyRuns.ts`, which starts and fails a Retro run the same way).
- `src/loop/retro*.ts` holds the Retro (label `fabrik:retro`, see [Retro](#retro)): the retro gate the scheduled tick runs (`retroGate.ts`, with what it shares with the audit gate in `weeklyGate.ts`), the pending Retro's run (`retro.ts`), the Retro output parser (`retroOutput.ts`), and filling the Retro in (`retroLanding.ts`). Its evidence bundle is built by the pure Retro evidence module, `src/kit/retroEvidence.ts`, from what `src/kit/retro-evidence-main.ts` reads in `loop.yml`'s Retro evidence job (the `gather-retro-evidence` action), and the Retro job (the `run-retro` action) runs the agent on it.
- A Replay (labels `fabrik:replay` and `agent:replay`, see [Replay](#replay)): the pure Replay module, `src/kit/replay.ts`, reads the request (`src/kit/replayRequest.ts`), picks the Tickets and gives each its two arms (`src/kit/replayPick.ts`), and keeps the plan, progress and results in the replay issue's body. The scheduled tick's replay step and spare-capacity gate are `src/loop/replayGate.ts`, on the slice `src/github/snapshot.ts` and `src/github/replaySlice.ts` gather from a checkout of the store the tick's `replay-store` action makes only while a replay issue is open. `src/loop/replayRun.ts` starts a Ticket's run and lands it. In `loop.yml`, the claim job, each arm's `replay-implement`, `replay-gates`, `replay-review` and `replay-score` jobs and the `replay-record` job run the actions of the same names.
- `src/loop/research*.ts` holds the Researcher (labels `agent:research` and `wayfinder:research`, see [Maps](#maps)): starting its run on a research Decision (`research.ts`, whose rule for which Decisions it may run on Dispatch and the Weekly summary share), the Decision's branch and findings paths (`researchPaths.ts`), the research output parser (`researchOutput.ts`), and landing the findings (`researchLanding.ts`), whose line on the Map `decisionsSoFar.ts` appends. `src/loop/mapCap.ts` is the Map cap, which the Design turn's landing, its inputs and the Weekly summary share, and the Design session's `map` outcome lands in `design.ts`.
- A Design session's Prototypes (see [Prototypes](#prototypes)): `design.ts` posts the prototype request and starts the prototype turn it asks for, `src/github/threads.ts` reads the session's pending request back, `src/agent/prototype.ts` is the runner's prototype mode, on `prompts/prototype.md`, and `src/loop/prototypeLanding.ts` lands the turn: the Trust-root guard, the push of `prototype/<issue>`, and the prototype round or its failure round.
- `templates/fabrik.yml` is the caller workflow a Product repo installs as `.github/workflows/fabrik.yml`. Its `run-name` names each run on the Actions tab for what it starts and on which issue or PR, such as `Implement #12`, `Review PR #60`, `Triage #87` or `Tick`, or else for its event, such as `#87 labeled bug` (#477): GitHub names a run from the caller only. A Product repo set up before it gets the names by updating its `.github/workflows/fabrik.yml` from `templates/fabrik.yml`; until then every run shows as `Fabrik`, though the Implement and Review jobs still name their Ticket and PR.
- `templates/claude-settings.json` holds the `SessionStart` hook entry a Product repo merges into `.claude/settings.json`, and disables the `mattpocock-skills` plugin there. The entry reads the release from `fabrik.yml`, downloads Fabrik at that tag (public, no credentials) and runs `src/session/start.ts`, which installs the skills that release's `skills.lock.json` pins, the same commit the Kit step installs in Actions, plus Fabrik's own `skills/` (`fabrik-live-design`, `fabrik-pair` and `fabrik-visual-evidence`). It also removes the `fabrik-setup` skill earlier releases installed there, and warns the Operator while their personal skills hold an old copy of it.
- `setup.sh` is the bootstrap script the Operator's Setup command runs (see [Adopting the Kit](#adopting-the-kit)): it downloads a release into a temporary folder, runs that release's setup program on the Operator's terminal, and deletes the folder afterwards.
- `src/setup/` is that setup program: `program.ts` runs the checks, asks the questions and shows the plan, `oneRun.ts` is one run's order from the Operator's yes to the setup PR, `plan.ts` is the pure planner (what a Product repo holds now in, the steps it's missing out), `shims.ts` merges the Kit-owned files into the Product's own, `gather.ts` and `apply.ts` read and change the repo and 1Password with `gh` and `op`, and `wizard.sh` is the wizard it runs for the steps only the Operator can take. `templates/` holds what it installs. Beside it, `visualEvidence.ts` is the pure Visual evidence writer, and `visual-evidence-main.ts` the program `/fabrik-visual-evidence` runs it through, which needs no `gh` admin and no `op`.

## Adopting the Kit

The Operator adopts the Kit in a Product repo by running Setup in their own terminal, from the root of the repo's clone, on its default branch:

```sh
curl -fsSL https://raw.githubusercontent.com/jrey8343/fabrik/main/setup.sh | bash -s --
```

There's nothing to copy or install first. `setup.sh` checks for Node 24.3 or later and `gh`, downloads Fabrik's latest release into a temporary folder, runs that release's setup program, and deletes the folder whatever the outcome. To set up another release, name it after the `--`, as an exact tag such as `v1.0.0`:

```sh
curl -fsSL https://raw.githubusercontent.com/jrey8343/fabrik/main/setup.sh | bash -s -- v1.0.0
```

`--release=v1.0.0`, anywhere after the `--`, names it too. `setup.sh` refuses an empty `--release=`, two different releases, and a tag that isn't exact, before it downloads anything.

Setup's flags go after the release, if one is named: `--account=<1Password account>`, `--time-zone=<IANA zone>`, `--second-subscription`, `--paused` and `--plan`. Each question's flag also has a `--no-` form, and Setup asks only what the flags left out.

Setup first checks that it's in the clone's root, on the default branch, clean and the same as on `origin`; that `gh` is signed in as the repo's admin with the `workflow` scope; that `op` is signed in as the Operator, not as a service account (it stops when `OP_SERVICE_ACCOUNT_TOKEN` is set); and that Node is 24.3 or later. With several 1Password accounts it asks which one holds this Product's secrets, offering the one `OP_ACCOUNT` names, if it's set, for an Enter; without a terminal, `OP_ACCOUNT` or `--account=` names it. Then it asks three questions: the Operator's time zone for the Weekly summary, whether to add a second Subscription (not when the Kit config already lists two or more, which Setup leaves as they are, or lists `Claude token 2`), and whether to pause Dispatch. It shows its plan, naming the 1Password account on the first line. With `--plan`, or without a terminal, it stops there. On the Operator's yes it applies the plan on the branch `fabrik/setup-<release>`, runs the wizard, then commits, pushes and opens the setup PR with the files:

- **Kit-owned files**, put back whenever they drift: `.github/workflows/fabrik.yml` with every Fabrik `uses:` line pinned to the release, the `SessionStart` hook entry and the `mattpocock-skills` plugin switched off in `.claude/settings.json`, `.claude/skills/` in `.gitignore`, and a `.github/dependabot.yml` entry that bumps only the Fabrik pin, every pinned Fabrik workflow in one grouped PR, with no cooldown, and never to a major, which arrives only through Setup. Each is merged into the Product's own file. A caller pinned to an earlier major is migrated; within a major, Dependabot owns the pin. On a pull request that changes the caller, a bump PR say, the Kit job checks that each job grants what the workflows at the release it pins ask for, and fails the PR's `loop / Kit` check naming the job and the line when one doesn't, since a caller that grants too little fails every run at startup (ADR-0003).
- **Starters**, written once and the Product's from then on: `.fabrik/config.json` with every v1 default, `docs/agents/*` with Fabrik's fixed answers (GitHub Issues, the triage labels plus `needs-design`, a single-context glossary and ADRs), and an `## Agent skills` block pointing at them in `CLAUDE.md`, or in `AGENTS.md` when there's no `CLAUDE.md`.
- **Labels**: `needs-triage`, `needs-info`, `needs-design`, `ready-for-agent`, `ready-for-human`, `wontfix`, `agent:implement`, `agent:design`, `agent:review`, `agent:research`, `agent:replay`, `bug`, `enhancement`, `fabrik:token-rotation`, `fabrik:weekly-limit`, `fabrik:usage-credits`, `fabrik:audit`, `fabrik:retro`, `fabrik:replay`, `fabrik:monitor`, `fabrik:step-up`, `wayfinder:map`, `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling` and `wayfinder:task`.
- **1Password** (ADR-0004): the `Fabrik`, `Fabrik App` and `Fabrik Sandbox · <repo>` vaults when they're missing, and three read-only service accounts with no expiry, `fabrik-<owner>-<repo>-agent` (reads `Fabrik`), `-implement` (reads `Fabrik` and the Sandbox vault) and `-push` (reads `Fabrik App`), stored as the Actions secrets `FABRIK_OP_AGENT_TOKEN`, `FABRIK_OP_IMPLEMENT_TOKEN` and `FABRIK_OP_PUSH_TOKEN`.
- **Branch protection** on the default branch: a PR, the checks in `sandbox.checks` (plus any already required), and no bypass allowance for anyone. No approving review is required, since the solo Operator can't approve their own PRs. Those are the only settings Setup changes, and its plan names each change, from what to what. Every other one it leaves as it finds it, strict checks, linear history, conversation resolution and admin enforcement included: unless the branch already enforces its rules for admins, the Operator, as the repo's admin, can still merge past them.
- **The Merge gate ruleset** (`Fabrik Merge gate`): only repo admins may update the default branch, merging a PR included. The Operator owns the repo, so only they can merge; the Fabrik App, never an admin, can't.

With `--paused`, or a yes when Setup asks, the starter `.fabrik/config.json` is written with `max_in_flight: 0`, every other byte as the starter has it, so Dispatch starts no Implementer until the Operator raises it (see `max_in_flight` in the [Kit config](#kit-config)). Without it, Dispatch starts on the repo's open `ready-for-agent` issues as soon as the setup PR merges, and the plan's notes say how many there are. `--paused` changes only the starter: a Kit config the repo already has is left alone, and the plan's note gives its `max_in_flight` to set to `0` by hand. Until the setup PR merges, the starter on `fabrik/setup-<release>` is still Setup's own: a later run there asks again, offering what the starter holds, and sets its `max_in_flight` to `0` or back to the v1 default to match. The setup PR and Setup's last lines say when the Kit config the PR merges pauses Dispatch.

The wizard (`src/setup/wizard.sh`, made with the `wizard` skill) runs in the same terminal, for what only the Operator can do: installing the Fabrik App on the repo (Issues, Pull requests and Contents, plus Checks: read for the Monitor's red main; no `workflows`) and storing its `client-id` and `private-key` in the `Fabrik App` item; `claude setup-token` into the `Claude token` API Credential in the `Fabrik` vault, with its expiry; a Sentry token (`event:read` and `project:read`) into the `Sentry token` API Credential in the `Fabrik App` vault, one token every Product repo in the 1Password account shares, which is harmless to store before the repo reports to Sentry (the Monitor reads Sentry only once `monitor.errors` names a project) and fine to skip until then; GitHub mobile pushing only mentions, assignments and review requests, with Actions off; and watching the repo on All activity. Setup asks for the setup PR's merge only once the Fabrik App is installed on the repo, its key stored and the token of the first Subscription the Kit config lists in `subscriptions` stored, the Claude token in the starter: the first runs read that one, and the Kit moves to a later one only once those before it are used up. A later Subscription's missing token is a note in the plan instead. Until then the PR says which of them is missing, and running Setup again walks the wizard for them, apart from a Subscription listed under a name no wizard stage stores, whose token the Operator stores by hand.

Once the setup PR is merged, Setup's command is the way back to the wizard. On the default branch with nothing to apply, Setup checks what a wizard stage stores that 1Password lacks: the App's key, the Claude token while the Kit config lists it, the second Subscription's token, `Claude token 2`, once the Kit config lists it, or lists one Subscription and the Operator says yes to a second, and the Sentry token once `monitor.errors` names Sentry. The wizard stores no other Subscription's token, so one the Kit config lists under another name, such as a third or one listed alone, is a note in the plan to store by hand. With none missing, it says the install is complete and walks no wizard. Otherwise it names each one and asks whether to walk the wizard now (no, unless the Operator says yes). Then it reads 1Password again and plans again. A file that plan writes, such as the `subscriptions` line once `Claude token 2` is stored, goes in a setup PR as on any run. With no file to write there's no setup branch or PR, and Setup says what's still missing, or that the install is complete. Without a terminal, or with `--plan`, it names what's missing and says to run Setup in a terminal. Setup can't read the App's install or the last two stages, which are GitHub settings, so it never walks the wizard for them alone. To set them by hand: in the GitHub mobile app, under Profile → Settings → Notifications, turn push on for Direct mentions, Assigned and Review requested, and off for Actions; then on the repo's page, click Watch → All Activity.

Every Product repo in this 1Password account, the one Setup uses, shares its `Fabrik` and `Fabrik App` vaults, and with them the App key, the Claude token and the Sentry token. So on the next Product repo in it, the wizard finds them already stored. One 1Password account per Product is a normal setup too. A new account holds none of them yet, which the wizard says is expected, and the wizard stores them there.

Setup leaves Visual evidence off. Once the setup PR is merged, the Operator turns it on by running `/fabrik-visual-evidence` in a Claude session in the repo, where the `SessionStart` hook has installed it (see `ui` in the [Kit config](#kit-config)).

Running Setup again on a working install changes nothing, once 1Password holds what the wizard stores. On a broken one it repairs only what's missing: a missing label is created, and a missing secret gets a new service account (1Password shows a token only once, so delete the old account by hand). A repair that writes no file opens no setup PR, and leaves the clone on the default branch, brought up to date with `origin`'s. After a run that stopped partway, Setup picks up on its `fabrik/setup-<release>` branch, and says to switch to it when the clone is on the default branch. A setup branch, the clone's or `origin`'s, is done with once merging it into `origin`'s default branch would change nothing, or, with no setup PR open from it, once it's a head a merged setup PR from it had, or a commit before one: the PR's last head, or one a force-push replaced, as GitHub's "Update with rebase" does. Then Setup starts the branch again from the default branch, so a squash or rebase merge leaves nothing to pick up. To migrate to a new major release, name that release:

```sh
curl -fsSL https://raw.githubusercontent.com/jrey8343/fabrik/main/setup.sh | bash -s -- v2.0.0
```

Setup never moves a caller workflow back to an earlier major, and within a major Dependabot owns the pin.

Setup was once the `fabrik-setup` skill, copied by hand into `~/.claude/skills/`. A copy left there is stale: Setup offers to delete it, and the `SessionStart` hook warns while it's there.

## Vision and Roadmap

A Product repo may keep two files that hold its Product intent, both free prose with no schema: `docs/product/vision.md`, the **Vision** (a short paragraph per kind of End user, the problem the product solves for them, how its success is measured, and what it deliberately doesn't do), and `docs/product/roadmap.md`, the **Roadmap** (Now / Next / Later, one line per item, and no "Not doing" list, since the Vision holds that). Both are optional, and both are Operator-only Trust-root files: the Operator writes them by hand or in a Pairing session, and the push job refuses any agent branch that touches `docs/product/` (see [Implementation](#implementation)). Only that folder at the repo root counts, so a `docs/product/` inside a package stays ordinary. Without them nothing refuses to run, and nothing asks the Operator to write them.

[`docs/examples/vision.md`](docs/examples/vision.md) and [`docs/examples/roadmap.md`](docs/examples/roadmap.md) are a commented example of each, for a made-up product. The Operator writes their own by copying one into the Product repo's `docs/product/` and rewriting it. Setup never installs them, and the Loop never reads the examples.

## Triage

An idea too foggy for one Design session fails the Fast path's size test, so Triage sends it to `needs-design` as usual, and its comment adds one line: `This looks too foggy for one Design session.` A clear but large idea goes to `needs-design` without the line. Triage never charts a Map itself: that's the Operator's call in the Design session (see [Maps](#maps)).

Triage compares each issue against the recent issues: every open issue and every issue closed in the last 30 days, the 50 most recently created, each with the first 500 characters of its body, the Monitor's issues included. The job's read-only token reads them before the agent starts. When the issue reports the same request or defect as one of them, Triage chooses `wontfix` and names that original (`"duplicateOf": <n>` in its output). The issue then closes with state reason *duplicate*, and Triage's comment ends `Closing as a duplicate of #<n>.` A merely related issue isn't a duplicate, and in doubt Triage sorts as usual. Any other `wontfix` still closes as *not planned*. The original gets no comment, label or link.

A sub-issue you file by hand with no state label gets no `needs-triage` from Intake, since a skill usually files sub-issues with their state; instead one quiet comment says so: add `needs-triage` for Triage to look at it, or a state label yourself.

A person's reply on a `needs-info` issue swaps `needs-info` for `needs-triage`, which starts Triage again; a bot's reply does nothing. Deleting the reply doesn't undo the swap: Triage still runs, reads the thread without the reply, and most likely asks its questions again, one more round and one more notification.

## Design session (async)

Adding `needs-design` to an open issue starts a Design session, once a slot is free. Each turn is a fresh run of the Design-session agent job (Opus 5.5, 30 minutes by default, `roles.design` in the Kit config, plus `.fabrik/design.md` when present), one at a time per issue, rebuilding its context from the issue thread, the issue's parent Spec when it has one, and the repo. A turn ends in one of these ways (see [Back to design](#back-to-design) for splitting a Ticket):

- **The next round**: the Fabrik App posts numbered questions with recommended answers, @-mentioning the Operator. The Operator's reply starts the next turn. Comments from anyone else, and from any bot, do nothing. A turn answers the reply as it read it: edit the reply before the turn starts and it sees the edit; to change an answer after that, post a new reply, since an edit never starts a turn. Delete the reply before its turn posts and the turn posts nothing; only a turn that fails still posts its failure notice.
- **An agent brief**: the issue body is rewritten in place as the brief and its acceptance criteria, a closing comment (no mention) records the decisions, and `needs-design` is swapped for `ready-for-agent`. A brief with `"stepUp": true` also adds `fabrik:step-up`, and one with `"stepUp": false` takes it off; leaving it out keeps the label as it stands. Finishing the session counts as the Operator approving it.
- **A Prototype request**: on a repo with a `ui` block, once the Operator says yes to a Prototype, the turn asks for it, and the next turn is a prototype turn that builds the variants and posts a prototype round. See [Prototypes](#prototypes).
- **A Map**: when the destination is too foggy for one session and the Operator says yes to "Chart this as a Map instead?", the issue is rewritten in place as a Map, its first Decisions are filed as its sub-issues, and `needs-design` is swapped for `wayfinder:map`. See [Maps](#maps).
- **Not planned**: when the Operator decides the issue won't be built, the session finishes as not planned (`{ "kind": "not-planned", "comment": … }`). The closing comment (no mention) gives the session's reasoning, `needs-design` is swapped for `wontfix`, and the issue closes with state reason *not planned*. It works the same on a Ticket that came back to design. Its work never lands, so the issues it blocks stay blocked: Dispatch treats a blocker closed as not planned as still blocking until the Operator removes the edge, and the closing comment names those issues. The reasoning lives only in that comment.

Only rounds notify: the Kit strips @-mentions from everything the agent writes.

At most `caps.design_sessions` Design sessions (2 by default) are open in a Product repo at once. A session holds its slot from its first turn until it ends: while a turn runs, after a round, and after a turn fails. Any outcome above, a live outcome, closing the issue or removing `needs-design` frees it. Adding `needs-design` by any route (Triage, the Operator, a Design flaw, Retries used up, an empty diff or the Merge gate) runs a Design queue check, which adds `agent:design` to start round 1 when a slot is free; the label comes off as the turn starts. While both slots are taken the issue just waits: it keeps `needs-design`, gets no comment or label, and nobody is notified. The run's step summary says which issues wait. When a slot frees, re-designs (a Ticket sent back to design) start first, then the oldest by when it got `needs-design`, then the lowest number. A queue check runs whenever a session ends, an issue closes, the Kit config changes and on the hourly tick, so a slot freed by removing `needs-design` by hand is used within the hour. The Operator's comment on a waiting issue starts nothing: round 1 reads the whole thread, so it is context. A live outcome on a waiting issue still lands.

A turn that fails for Infrastructure leaves `needs-design` on the issue, so it stays in its session: the failure notice asks the Operator to reply, and their reply runs the turn again.

## Design session (live)

The Operator can take a Design session live in a claude.ai/code or iOS cloud session, or a local Claude Code session, on the Product repo. The `SessionStart` hook installs the pinned skills into `.claude/skills/` and returns `reloadSkills: true`, because Claude Code discovers skills before `SessionStart` hooks finish. Then `/fabrik-live-design <issue>` runs the session (`skills/fabrik-live-design/SKILL.md`):

- It posts nothing on the issue until it ends, since every Operator comment on a `needs-design` issue starts an async turn.
- It reads the [Vision and Roadmap](#vision-and-roadmap) when the Product repo has them. An issue that touches Product intent opens with who the change serves, why, how its success is measured and what it leaves out, with recommendations drawn from the Vision, or asked directly without one; a Ticket sent back to design, and internal or technical work, skips that. Every Spec gets a Product intent section and every agent brief a "Who and why" line. It never edits either file: a decision the Vision doesn't yet say becomes an "Update `vision.md`" Operator step with the exact lines.
- It runs with the Operator's own `gh` credentials and publishes the outcome itself: the issue body rewritten as its agent brief or its Operator brief, the Spec and its Tickets (category label and `ready-for-agent`, Tickets as sub-issues with native blocked-by edges), or the issue body rewritten as a Map with its first Decisions (each a sub-issue with its `wayfinder:<type>` label and native blocked-by edges). It checks the [Map cap](#maps) before it offers a Map.
- It offers a [Prototype](#prototypes) on the same conditions as an async session. On a yes it builds the variants itself, in the session's checkout, with the pinned `prototype` skill's UI branch on `prototype/<issue>`, pushes that branch on the Operator's credentials, and gives the Operator the one command that opens it in their own browser. There's no Sandbox job, capture or gallery, and its outcome records the chosen variant as an async one does.
- Its last act is one comment whose first line is `<!-- fabrik:live-outcome brief -->`, `<!-- fabrik:live-outcome operator-brief -->`, `<!-- fabrik:live-outcome spec -->` or `<!-- fabrik:live-outcome map -->`. From the Operator, that comment makes the Kit land the outcome as an async finish would: `brief` swaps `needs-design` for `ready-for-agent`, `operator-brief` swaps `needs-design` for `ready-for-human` and assigns the issue to the Operator, ready for a Pairing session, `spec` removes `needs-design` and closes the issue as completed, and `map` swaps `needs-design` for `wayfinder:map`. All four run a Design queue check, and all but `operator-brief` a Dispatch check. Without the marker, a summary comment is an ordinary answer, and the async session carries on from it.

## Maps

An idea too foggy for one Design session, because what done looks like isn't settled or its open questions hang on one another, can be charted as a **Map** instead of being forced into a premature Spec. The Map names the destination, and its children are **Decisions**, each resolved on its own by research, a prototype, a grilling or a task, never by a pull request. The Kit runs research Decisions AFK; the others are the Operator's, worked live with `/wayfinder`.

- **The Map question**: capture stays a blank issue, and [Triage](#triage) flags fog with one line in its comment. When that line is there, or the Design session judges the destination can't be designed in one session, round 1 asks "Chart this as a Map instead?" with a recommendation. The Operator decides: no keeps the session designing, and any later round can still end in a Map when the Operator asks for one. An issue the session can design gets no Map question, and a Ticket under a Spec never becomes a Map.
- **The `map` outcome** rewrites the issue in place as the Map, with `## Destination`, `## Notes`, an empty `## Decisions so far`, `## Not yet specified` and `## Out of scope`, carrying its `From audit`, escape and `From retro` lines as a brief does. Its first Decisions are filed as its sub-issues, blockers first, each with its `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling` or `wayfinder:task` label, native blocked-by edges, and no state or category label, so Intake leaves them alone. The closing comment (no mention) lists the Decisions filed, `needs-design` is swapped for `wayfinder:map`, the issue keeps its category label, and the Kit runs a Dispatch check and a Design queue check. A `map` outcome with no Decisions breaks the output contract. A [live session](#design-session-live) can end the same way.
- **The Researcher** (Opus 5.5, 30 minutes by default, `roles.research`, plus `.fabrik/research.md` when present): Dispatch adds `agent:research` to each open research Decision on an open Map that nobody is assigned to, no open issue blocks and whose last run didn't fail, and the label comes off as the run starts. Research runs share `max_in_flight` with Implement runs: Tickets and research Decisions are released together, lowest issue number first, and `0` pauses both. Adding `agent:research` by hand starts a run now; assigning yourself a Decision keeps Dispatch off it. The Research job is read-only, like the Auditor: a checkout of the default branch, only the agent service account, no GitHub credential, no production secrets, and none of the code run. It gets the Base skills alone and follows the pinned `research` skill, reading primary sources. It's given the Decision, its Map's body and the findings path the Kit derives from the Decision's number and title, `docs/research/<number>-<slug>.md`, and writes that one file, deciding nothing. The runner commits it to the throwaway branch `research/<number>-<slug>` and passes it out as a bundle.
- **Landing the findings**: when the branch changes only its findings file, the push job pushes it (it's never merged and gets no PR), posts a resolution comment on the Decision with the gist, the key facts and a link to the file on the branch, and closes the Decision as completed, which unblocks the Decisions that wait on it. Then it appends one line to the end of the Map's Decisions so far, the Decision's title linking its resolution and the gist, re-reading the Map's body right before it writes and changing nothing else, so the Operator's own edits stay. Last, it runs a Dispatch check. A run that lands after its Decision closed, lost `wayfinder:research` or left its Map, or after the Map closed, posts nothing and changes nothing, but still runs a Dispatch check, since the slot it held is free. A branch that changes any other path, a Trust-root file included, is refused: nothing is pushed, and the Decision gets the failure notice. The Kit never edits Not yet specified, Out of scope or any other Decision: graduating the fog stays the Operator's.
- **A failed run**, a reply that breaks the research output contract included, posts the Kit's usual failure notice on the Decision, classed as for any other role, so a dead token or the weekly limit also goes on the rotation or weekly-limit issue. Dispatch doesn't run that Decision again until the Operator re-adds `agent:research`. Every research run leaves a Run record in role `research`, and no Scorer samples it.
- **The Map cap**: `caps.maps` (default 1) caps how many Maps are open in a Product repo at once, counting every open `wayfinder:map` issue, one charted by hand included. It holds silently. While it's full, a Design session offers no Map, and if the Operator asks for one, it names the open Map that holds the cap. A `map` outcome that lands while the cap is full anyway is refused with a comment naming the open Map, mentioning nobody, and the session carries on from the Operator's next reply: until then the Weekly summary lists it in Waiting on you, as it does a Design session whose last turn failed. Closing a Map frees the cap.
- **Reaching the destination** is a `/wayfinder` convention, not Kit code. The Map's last Decision files each Spec-to-be as a new `needs-design` issue that links the Decisions it rests on. Each skips Intake, since it already has a state label, and goes to a Design session, which treats those Decisions as settled. The Operator closes the Map once its Spec issues are filed. The Kit never closes a Map, and Spec closing never mistakes one for a Spec: it closes only a parent with a `ready-for-agent` or `ready-for-human` state label.
- **In the Weekly summary**: each open Map is in its repo's Waiting on you, with its age and how many of its Decisions wait on the Operator (its open grilling, prototype and task Decisions), and so is each research Decision whose last run failed, until the Operator re-adds `agent:research`. Held shows the Map cap when it's full, naming the open Map.

## Prototypes

On a Product repo whose Kit config has a `ui` block (see `ui` in the [Kit config](#kit-config)), a Design session can settle how a page should look by looking at it. A **Prototype** is throwaway variants of one route on the branch `prototype/<issue>`, which is never merged and never gets a PR, and which the Kit never deletes. It has no setup step and no Kit config key of its own: a repo without a `ui` block never gets an offer, and a `prototype` output there breaks the output contract.

- **The offer**: when a session's open question is how a page looks, a round may ask, with a recommendation, "Prototype the booking page (`/book`) as 3 variants first?": 3 variants by default, from 2 to 5. Nothing is built until the Operator says yes, and the yes may change the route or the count. Logic and data questions stay ordinary questions.
- **The request**: on a yes, the next turn ends in `prototype`, naming the route, the variant count and what each variant explores. The push job posts a comment that mentions nobody, saying what's being built, with the request in a hidden `<!-- fabrik:prototype-request … -->` marker, then adds `agent:design` afresh. It isn't a round, and the session keeps its slot.
- **The prototype turn**: `agent:design` on an issue whose session has a pending request whose prototype turn hasn't started yet starts a prototype turn, `loop.yml`'s `prototype` job, in the design job's place, and the Kit marks the request's comment started (an edit, which notifies nobody). It runs on the Design model and effort within the Implement timeouts, holds the implement service account (the Claude token and the test secrets) and no GitHub write, and shares the session's concurrency group, so a reply sent meanwhile waits for it. The agent follows `prompts/prototype.md` and the pinned `prototype` skill's UI branch: every variant on the one route, switched by `?variant=` and its letter, each in its own component, with a floating switcher, committed on `prototype/<issue>`, which a later round builds on. The job then builds and serves the branch and captures each variant at mobile and desktop width, a screenshot and a short load-and-scroll video at each, into one gallery, uploaded unzipped and kept 30 days. Capture never fails the job. A prototype turn refused on its Subscription's weekly limit, re-run or held, has that mark taken off, so it restarts as a prototype turn on the next free one, while an ordinary turn a reply started meanwhile restarts as an ordinary turn.
- **The prototype round**: the push job runs the Trust-root guard over the branch, pushes it as a fast-forward of `prototype/<issue>`, and posts a numbered round that @-mentions the Operator: the agent's intro, links to the branch and the gallery (the round is the record once the gallery expires), each variant's letter, summary and component at the pushed commit, its preview when `preview.url` is set, and "Which variant?" with a recommendation. The Operator's reply is an ordinary answer, and can ask for another round.
- **When it fails**, the session carries on. A branch that changes a Trust-root file isn't pushed, and a turn with no commits pushes nothing: each gets a prototype failure round saying why. A build or server that failed still pushes the branch, and its failure round asks "Carry on without a prototype, or try again?", recommending carrying on. Any other capture failure still asks "Which variant?", with the reason in the gallery's place. An Infrastructure failure posts the usual failure notice, which ends the request, and so does a turn whose output breaks its contract, or whose branch moved while it ran (a live session's push, say): the Kit only fast-forwards `prototype/<issue>` from the head the turn started on, so it pushes nothing then.
- **The outcome** records the chosen variant, the Operator's tweaks and links to the branch and that variant's component, for the Implementer to rewrite, never to merge. The Reviewer gets nothing from a Prototype. A [live session](#design-session-live) can offer and build one too.
- **In the Run records**: each prototype turn's record has role `design` and `prototype: true`. The Weekly summary counts it as a Design-session turn, and no Scorer samples it.

## Pairing session

The Operator works through a `ready-for-human` issue with an agent beside them by running `/fabrik-pair <issue>` in a cloud or local Claude Code session on the Product repo (`skills/fabrik-pair/SKILL.md`). It runs with the Operator's own `gh` credentials:

- It counts as the Operator, so it may change Trust-root files. It refuses an issue that isn't open and `ready-for-human`, except the weekly-limit issue: there it waits for the reset before restarting the stalled Tickets, and still finishes the restart after the Kit has closed the issue. The issue body's `- [ ]` task list is the plan; with none, the session agrees one with the Operator and writes it in below the original text. A rerun resumes at the first unticked step.
- It talks the Operator through simple steps, and builds a wizard (`.claude/skills/wizard`) in a temp folder, never committed, for dashboards, credentials or a run of commands.
- It ticks each step once a command confirms it (`gh secret list`, `gh api`, `op item get`, reading the file) or, where nothing can, once the Operator does. File changes, Trust-root files included, go out in one pull request whose body has `Closes #<n>`, never pushed to the default branch.
- It ends with a comment saying what was done, and closes the issue, or leaves that to the pull request's merge. Stopping partway, it comments where it stopped and leaves the issue open and assigned. No comment names a secret's value or @-mentions anyone.

The token-rotation and weekly-limit issues the Kit opens write their steps as a task list and point at `/fabrik-pair`.

## Implementation

Dispatch adding `agent:implement` to a Ticket starts its Implementer (Sonnet 5.5, 60 minutes by default, `roles.implement`, plus `.fabrik/implement.md` when present), one run per Ticket at a time. The label comes off as the run starts, and the draft PR appears only when the run lands, once its push job has run; until then the run is on the Actions tab under the Ticket's number, its Implement job named `Implement #<n>` (`Implement #<n> (Retry <r>)` for a retry). Adding `ready-for-agent` to an open issue, by Triage or by hand (re-marking a refused Ticket, say, or a sub-issue that skipped Intake), runs a Dispatch check, as does the hourly tick, so a ready Ticket left waiting while every slot was full starts within the hour (#418). A Ticket whose Implement run failed before it opened a PR is left alone: its failure notice (`<!-- fabrik:implement-run-failed -->`) keeps Dispatch off it until you re-add `agent:implement`, so no check starts a broken Ticket again by itself.

A trigger label (`agent:implement`, `agent:design`, `agent:review`, `agent:research` or `agent:replay`) with no run behind it, as when the Kit job failed on an invalid Kit config, or the run was cancelled or lost before it started, no longer holds its slot for good (#419). The hourly tick looks for one on an open issue or PR that was last added at least 30 minutes ago with no job of its role unfinished anywhere in the repo, and adds it again so the run starts, saying so on the issue (`<!-- fabrik:stuck-trigger-readded <label> -->`). If it's still on, with no run behind it, at a later tick, the Kit takes it off and @-mentions you: check the Loop's Actions runs, fix the cause, then add the label again. Until you do, the work is parked as after that role's failed run, so Dispatch and the Design queue leave it alone. A Design session keeps its slot meanwhile. Cancelling a Loop run before it starts doesn't stop the work, since the tick adds the label back: to stop a run, take its label off.

Closing by hand stops the work, never restarts it (#428). Closing a Ticket, by hand or otherwise, closes its open agent draft PR unmerged, keeping its branch, with a comment on the PR saying why, so it frees its `max_in_flight` slot and gets no more Reviews. Closing an agent PR unmerged yourself, a draft or one at the Merge gate, means stop: the Kit doesn't dispatch its Ticket again, but swaps `ready-for-agent` for `ready-for-human`, assigns you, and comments that the PR was closed by hand and its branch `fabrik/ticket-<n>` kept. To have an Implementer try again, mark the Ticket `ready-for-agent`: the new run starts from `main` and replaces that branch. The Kit's own closes (Send it back, back to design, a refused run, a closed Ticket's PR) and a merge do neither: they leave the Ticket as they put it, and only free the slot.

- **The Sandbox** is a fresh clone of `main` on the runner, on the branch `fabrik/ticket-<n>`. The job holds only the implement service account. The Claude token and the test secrets listed in `sandbox.secrets` are resolved from 1Password into the Implement step's env only, so adding a test secret never means editing the caller workflow. `sandbox.setup` runs before the agent starts (daemonise any stubs it starts), and the prompt gives the Implementer the `build` and `test` commands to run.
- **The prompt** carries the Ticket, its parent Spec, `GLOSSARY.md`, the ADRs under `docs/adr/` and the Product's implement instructions, and starts the `implement` skill, which works test-first with `tdd`.
- **The push job** rebuilds the branch from the git bundle the agent job passed out and runs the trust-root guard on every path any of its commits changes:
  - **Allowed**: the Fabrik App pushes the branch and opens one draft PR to `main` with `Closes #<n>`, which starts CI. Nobody is notified.
  - **Refused** (it touches `AGENTS.md`, `CLAUDE.md`, `CODING_STANDARDS.md` at the repo root, `.claude/settings*`, `.claude/skills/`, the Kit's role prompts `prompts/<role>.md` and its Scorers' rubrics `prompts/scorers/` (a Product's other `prompts/` files are its own), `.fabrik/`, `.github/workflows/` or `docs/product/` at the repo root, where the [Vision and Roadmap](#vision-and-roadmap) live): nothing is pushed. The Ticket moves to `ready-for-human`, is assigned to the Operator, and gets a comment listing the paths. A refused retry or Request-changes run also closes its PR unmerged, keeping its branch, so it no longer holds a `max_in_flight` slot. A Request-changes run told to merge `main` in is the exception: the comment listing the paths goes on its PR instead, which gets `ready-for-human` and stays open, and the Ticket is left as it is (see **Request changes** under [Merge gate](#merge-gate)). This uses no retry.
  - **Empty diff**: an Execution flaw, never a pass. The Implementer runs again, silently, up to 2 times (the second a Step-up), and a third empty diff sends the Ticket to `needs-design`. Each such run is one of the Ticket's two Retries: if a later run opens the PR, its Verdicts count on from them (#415).
- **Changed existing tests** (#463): the push job lists every test file (`*.test.*`, `*.spec.*`, `*_test.*`, `test_*.*`, or anything under `test/`, `tests/` or `__tests__/`) the run's own commits changed, moved or deleted that was already there before the run, on the head it built on. The PR body gets a "Changed existing tests" section, between the summary and `Closes #n`, ending in a hidden `<!-- fabrik:changed-tests [...] -->` marker; a retry or Request-changes run's list adds to the earlier runs'. The Implementer is told to explain each such change in its summary, and the Reviewer gets the list and judges each change on its merits: an assertion weakened or removed without a reason in the PR body is an Execution flaw. A PR whose runs changed no existing test gets no section, and its Reviewer no extra text.
- **UI evidence**: in a repo whose Kit config has a `ui` block, once the Implementer's agent has ended well, the job builds and serves a branch that changes a `ui.paths` file and screenshots the routes the change shows on, and a UI PR's body gets an evidence section linking a gallery of them. Capture never blocks the PR or uses a retry. See `ui` in the [Kit config](#kit-config).

## Review

Every agent draft PR is reviewed before the Operator sees it. The Fabrik App opening the PR, or pushing to it, starts a Review; adding `agent:review` to the PR resumes one after a failure. One Review runs per PR at a time, within the Review timeout (30 minutes by default, `roles.review`).

- **Required checks** come first. The Review checks job waits for them on the PR's head: the checks named in `sandbox.checks` when it lists any, otherwise the branch protection's required checks. A skipped or cancelled check never counts as passed.
- **Red checks** are an Execution flaw. The Reviewer doesn't run.
- **Green checks** start the read-only Reviewer (Opus 5.5 by default, plus `.fabrik/review.md` when present) in a checkout of the PR's head. It holds only the agent service account and runs none of the PR's code. It judges the PR against its Ticket, the Ticket's Spec, the repo's standards and, when the repo has one at its root, `CODING_STANDARDS.md`, which only the Reviewer is given. On a UI PR it also sees up to 8 of the PR's UI evidence screenshots, and a visual failure is an Execution flaw like any other (see `ui` in the [Kit config](#kit-config)).
- **The Verdict contract**: the Reviewer's reply starts with exactly one line, `verdict: pass`, `verdict: execution-flaw` or `verdict: design-flaw`, then its findings. Anything else, an empty reply or a provider error, is an Infrastructure failure, never a pass.
- **Follow-ups**: a pass has no nits. Its findings are what the Reviewer checked, and it may end with Follow-ups: work that deserves its own issue but lies outside the Ticket's scope. They come after the findings and before any `operator comments considered:` line, as a `follow-ups:` line, then one `- <title>` item per Follow-up with its Markdown body indented two spaces beneath it. The Verdict comment shows them under `### Follow-ups`, each with an **Open as issue** link to the Product repo's new-issue form, prefilled with its title and its body ending `From PR #<n>`, cut short to fit GitHub's URL limit. The Kit never files one itself. A flaw drops a Follow-ups block, and a malformed block on a pass stays in the findings as plain text, so the Verdict still lands.
- **Posting**: the push job posts every Verdict, red checks' included, as a PR comment from the Fabrik App, linking its run. The comment's first line is a marker, `<!-- fabrik:verdict {"verdict":…,"source":"reviewer"|"ci"|"empty-diff","requestChanges":…,"headSha":…} -->`, with `"conflictRun":true` before `headSha` on a Verdict after a conflict-only run, and `"requestChangesFirst":[<review ids>]` on an Execution flaw that gave way to the Operator's Request changes no run had built (#341), so a PR's review history can be read from its comments alone. The marker is only read from bot comments. A Verdict is posted once per head commit, and never for a commit the PR has moved on from.
- **A pass** takes the PR out of draft and requests the Operator's review, the event's one notification. A flaw is posted and mentions nobody.

## Execution-flaw retries

An Execution flaw gets fixed without the Operator, silently: no mention, assignment or review request.

- **The trigger**: an Execution-flaw Verdict, from the Reviewer or red CI, adds `agent:implement` to the PR's Ticket. On a Ticket whose agent PR is open, that label resumes the PR's Implement run rather than starting a new branch: the Implementer runs again on the PR's own branch, in a fresh clone checked out at its head, with the latest Verdict's findings in its prompt. The label comes off as the run starts.
- **The count**: a Ticket gets 2 retries in all, one pool counted from its empty diffs before the PR opened (its `<!-- fabrik:empty-diff -->` comments since its last Design session) and the PR's earlier Verdict comments (#415). So after one empty diff the PR's first Execution flaw starts Retry 2, stepped up, and after two the stepped-up run that opened the PR was Retry 2, so its first flaw sends the Ticket back to design: no Ticket drops back to the Implementer's model once it's stepped up. Every Execution flaw counts, whoever pushed the flawed head, the Operator included (ADR-0006), except one that gave way to your Request changes (see **Request changes** under [Merge gate](#merge-gate)), which never counts or calls for a retry. A Request-changes run itself uses no retry, but an Execution flaw on its push (its Verdict marked as from a Request-changes run) calls for one, and that retry counts like any other (#393). An Infrastructure failure posts no Verdict, so it never uses one up: re-adding `agent:implement` on the Ticket runs the same retry again, on whatever head the PR is at by then. It resumes a stalled Request-changes run the same way, which the Kit's note that started it marks in flight on the PR.
- **In flight**: a retry is in flight from the Verdict that calls for it until it pushes (its note opens `<!-- fabrik:retry-push -->`), ends in an empty diff or is refused, and that includes the stall after an Infrastructure failure, unless the PR has left draft since that Verdict. A Request-changes run is in flight from the Kit's note that started it, or the Execution flaw that gave way to it, until it pushes, is given a Verdict or ends, until the PR leaves draft, or until you dismiss every review it's for. Meanwhile a push to the PR, the Operator's included, starts no Review and gets no Verdict, so it uses no retry: the run's own push starts the next Review, which judges the PR as it then stands. A retry that finishes while a Request-changes or conflict-only run is in flight lands nothing, and a Request-changes run lands only while it's the one in flight for its review, as a retry does only while it's the Retry in flight for the flaw it was started for, by number and by the head that flaw was given on. A run's push note (a retry's, a Request-changes run's or a conflict-only run's) goes up just before its push, so the Review the push starts sees it, and names the head it pushes on a `<!-- fabrik:pushed-head <sha> -->` line (#420). A note whose head never reached the PR's branch, as when the push failed or its lease refused it because you pushed meanwhile, counts as no push: the run stays in flight and the reviews it was for stay unbuilt, re-running the push job lands its work, and a Review of your push gets no Verdict.
- **The Step-up**: the first retry runs on the Implementer's model (`roles.implement`), the second on the Step-up model (Opus 5.5 by default, `roles.step_up`), for that PR only. The Kit never drops to a cheaper model or skips a Step-up for any reason, except when you take `fabrik:step-up` off.
- **A Stepped-up start**: a Ticket labelled `fabrik:step-up`, by the Design session that wrote or rewrote it (its Ticket JSON's or agent brief's `"stepUp": true`, which a brief's `"stepUp": false` takes off again) or by you, runs every Implement run on the Step-up model while the label is on, its first run, Retries and Request-changes runs alike (ADR-0014). The label is read as each run starts, so adding it between Retries steps up the next one, and removing it drops back to `roles.implement`. A marked Ticket still gets 2 Retries, and a third Execution flaw is a Design flaw. Triage never marks a Ticket. Each Implement run's Run record says whether it Stepped up (`stepUp`) and why (`stepUpReason`: `retry`, `marked`, `request-changes` or `conflict-only`), and the Weekly summary breaks Step-ups down by reason, beside the marked Tickets merged that week and how many needed no Retry.
- **The push**: the push job runs the trust-root guard on the run's own changes and updates the PR's branch, which starts Review again. It also replaces the PR body with the run's `summary`, which describes the whole PR as it now stands, so the next Review never reads a stale one, and posts the run's `fix` (what it was asked to fix and what it changed) as a comment. A retry may merge `main` in when a finding needs work that has since landed there (the Reviewer asks for a merge, never a rebase), and a Request-changes run brings `main` in as its review or a conflict needs (see **Request changes** under [Merge gate](#merge-gate)): the guard then judges only the run's own commits (a merge showing only what was changed by hand) and the paths it changed that read neither as `main` has them nor as git's own merge of the PR's head and the `main` the run brought in would, never what `main` already has, and the push may replace the branch, with a lease. The only heads of `main` it counts are `main` as the Kit job read it before the run started and `main` as it is at the push, never a commit the run's result names or one `main`'s history holds but `main` was never at, and it merges as the PR's `.gitattributes` said before the run. Only the agent branch is ever pushed. A retry that commits nothing is posted as an Execution-flaw Verdict with source `empty-diff`, and counts like any other. A Request-changes run that commits nothing on a PR that doesn't conflict with `main` gets no Verdict and calls for no retry (#388): its `<!-- fabrik:request-changes-run-empty -->` note is its outcome, which ends its time in flight and settles the reviews it read (see **Request changes** under [Merge gate](#merge-gate)).
- **A branch that moved**: if the PR's branch moved while the run worked, say because the Operator pushed, the push job rebases the run's own commits onto the new head, without a working tree, and pushes that (ADR-0006). The guard and the empty-diff rule judge only the run's own commits, never the ones it landed on, so the Operator's commits in between may touch trust-root files. If the rebase conflicts, or the run had rewritten the history it built on, nothing is pushed: the Kit comments on the PR that the run's work was discarded and starts the same run again on the new head, with the same findings or review, using no retry. Restarts aren't capped.
- **Used up**: a third Execution flaw is posted, starts no retry, and counts as a Design flaw, unless you have a Request changes on the PR no run has built, when it gives way to that instead.

## Back to design

A Ticket that can't be built as designed goes back to the Operator. A Design-flaw Verdict, or a third Execution flaw (unless it gives way to your Request changes no run has built), closes the PR unmerged (its branch `fabrik/ticket-<n>` stays), and the Fabrik App posts a note on the Ticket linking the closed PR and its Verdict. Its first line is a marker, `<!-- fabrik:back-to-design <pr> <verdict url> -->`, read only from bot comments. Then `ready-for-agent` comes off the Ticket and `needs-design` goes on, which starts a Design session.

- **What the session sees**: every turn of that session gets the closed PR set out after the issue: every Verdict the Fabrik App gave it, oldest first, each with the head commit it judged (or, when the Operator sent it back, the Operator's reviews on it with their inline comments), then its kept branch's commits, changed files and diff against the base branch. A diff over 60,000 characters is cut short with a marker; the file list stays whole. Nobody else's comments on the PR are included. The agent job reads all of it through its read-only token, so the agent itself still holds no GitHub token.
- **Round 1** of that session says the Ticket came back from the closed PR and links its Verdict. Its @-mention of the Operator is the event's one notification: the failed review, the closed PR and the note mention nobody.
- **The outcome** rewrites the Ticket in place as an agent brief, or splits it into sibling Tickets under the same Spec (a `split` outcome: each a sub-issue of the Spec, with native blocked-by edges, and the Ticket closed as superseded). A Ticket under a Spec never gets a Spec of its own, and only a Ticket under a Spec can split. When a Spec or a split supersedes an issue, its new Tickets take the issue's place among its blockers: each Ticket nothing else in the outcome blocks takes on the issue's open blockers, each open issue it blocked waits on the Tickets that finish last, and the closing comment lists what moved.
- **The model**: a Step-up applies only to the PR it ran on, so a rewritten or split Ticket starts again on the Implementer's default model, unless the session marks it for a Stepped-up start. A Ticket rewritten in place keeps any `fabrik:step-up` already on it.

## Merge gate

A passing PR leaves draft and requests the Operator's review. Only the Operator merges; the Merge gate ruleset and branch protection, which Setup applies, enforce it. The Operator has three moves:

- **Merge**: the PR's `Closes #<ticket>` closes the Ticket, which runs a Dispatch check. When that was the last open Ticket under its Spec, the Kit closes the Spec as completed, with a comment listing each Ticket's merged PRs. The comment mentions nobody.
- **Request changes**: a review from the Operator that requests changes on an agent PR out of draft puts it back in draft and starts one Implementer run on the Step-up model, on the PR's branch, with the review and its inline comments as input, and every other Request changes of yours on the PR, oldest first, which it builds where the PR doesn't meet them yet (one asking for a rebase never rewrites the PR's history: the run merges `main` in if the PR lacks it). The review amends the Ticket for that PR (ADR-0010): the run builds it however large it is, the requested changes win wherever they conflict with an acceptance criterion, and its fix comment names each criterion it amended. The run also answers two independent yes/no questions about the review it was started for, and only that one (#369): whether it holds a Review miss (a point asking for what the pass should already have caught under the Ticket as it then stood, its Spec or the repo's standards, each such point named), and whether it amends the Ticket. A review asking only for a rebase, a squash or a retitle is no to both. Output without both answers breaks the run's contract. The Kit records them on the PR, under the run's push note or its note that it committed nothing, as a `<!-- fabrik:request-changes-answers {...} -->` marker naming the review and the lines "Review miss: yes, <point>" or "Review miss: no" and "Amends the Ticket: yes" or "no". The Implementer's output is their only source: there's no Operator override, and nothing re-judges them. The Weekly summary's Metrics table counts the week's Request changes, by when each was submitted, with a Review miss, amending the Ticket, and unanswered (a run held, failed, replaced by Send it back, or from before the answers), each against last week, and each repo's **Review misses this week** links each one's review, the comment holding the answer and the Review run whose pass it followed. Each Request changes in the Retro's evidence carries both answers, or null for each when unanswered. Every later Review and retry on the PR is given all the Operator's Request changes reviews on it but those deferred during a Retry (below), oldest first with their inline comments, as amendments to the Ticket, apart from the Operator's comments. A later review wins over an earlier one, either wins over the Ticket, and an amendment may widen scope. The Reviewer judges the PR against the Ticket as amended and gives a Design flaw from an amendment only when the amended Ticket contradicts itself, never for a change's size, and a retry never reverts a requested change. The Kit never rewrites the Ticket: the PR's reviews are the record. To send a PR back to Design instead, use Send it back. It isn't a retry. Its push carries a `<!-- fabrik:request-changes-run -->` note, so the Verdict Review gives it is marked as from a Request-changes run. The run itself uses no retry, but an Execution flaw on its push calls for the next one and counts like any other (#393), so after both retries are used it sends the Ticket back to design. On a PR that doesn't conflict with `main`, a run that commits nothing gets no Verdict and calls for no retry (#388); the empty-diff rule judges only its own commits. Its `<!-- fabrik:request-changes-run-empty -->` note ends it and settles the reviews it read, so no check starts another run for them. If the PR's head moved while it worked, as when you pushed the change yourself, the Kit adds `agent:review`, and that head's Verdict, marked as from a Request-changes run, decides what's next. Otherwise the note @-mentions you that your requested changes aren't built, and the Kit adds `ready-for-human` and takes the PR out of draft, never closing it. Unlike the conflicting case below, that note counts as no conflict attempt. On a pass the PR leaves draft and the Operator's review is requested again, the event's one notification. The Kit notes the run on the PR as it starts it (`<!-- fabrik:request-changes-run-started <reviews> -->`), naming the review and any earlier one of yours no run was started for, mentioning nobody: that note marks it in flight, so no other head gets a Verdict until it lands, and it ends once the run pushes, is given a Verdict or ends, once you take the PR out of draft, or once you dismiss every review it's for. A Request changes of yours on the draft while the run works counts too, though the run never read it, so neither check notes it: the run's push settles only the reviews it read, and an Execution flaw on that push gives way to the newer one. Anyone else's on the draft starts nothing. If you dismiss every review the run is for, the run is over and its work isn't pushed: a Request changes of yours no run has built, as one you submitted on the draft meanwhile, gets its run started instead, and otherwise the PR goes back to the Merge gate, saying so, even when an Execution flaw gave way to the review. That happens as the run lands, or, if no run is working, as after an Infrastructure failure, when `agent:implement` is re-added. If the PR's head moved since its last Verdict, as when you pushed, the Kit adds `agent:review` instead of handing it back, and that head's Verdict decides; a Verdict on a push after the dismissal ends the run too. If the note went up but the PR never went back to draft, as when what followed it failed, a check at least 10 minutes later starts the run. So does a check, at least 10 minutes after the note, on a draft with the run in flight and no Implement job under way anywhere in the repo, as when only a failed claim was re-run after its Implement job had already gone (#387). The Fabrik App can't read workflow runs, so each check reads them with its job's own read-only `GITHUB_TOKEN`, which is why the caller workflow's `tick` job grants `actions: read`. While every Subscription is used up, the note says the run is held until the weekly limit resets. A conflict with `main` after another PR merged needs no review: the Kit resolves it itself (see **Conflicts with main** below), and hands the PR to you only when it can't. On a PR that conflicts with `main`, the run is told to merge `origin/main` in first, never rebasing, even if the review asks for a rebase, and its fix comment lists each conflicted file; the push job judges what it built against the `main` head it was told to merge, not `main` as it is by then. That head is the run's own word, so it counts only if it's `main` as the Kit job read it before the run or as it is at the push, and otherwise the run is judged against `main` as it is; a run whose word names no head is still judged, against `main` as it started or as it is at the push, if the PR's head, as the push job reads it, conflicts with that, and a merge that can't be made at all counts as a conflict. If what it built still conflicts with that head, or it committed nothing, or the trust-root guard refuses it, the Kit says why on the PR, @-mentioning you, adds `ready-for-human` and takes the PR out of draft, never closing it, and the Request changes still goes first once `main` moves. On a PR that doesn't conflict, a review that asks for it still gets `main` brought in, merged or, if it asks for a rebase, rebased onto, and the push may then replace the branch, with a lease. GitHub starts no workflow for a review on a PR that conflicts with its base, so the push to `main` check and the hourly tick also look for one no run was started for: once one is more than 10 minutes old (on a PR that merges cleanly, older than the Implement job's timeout, since GitHub did start a run for it, which may still be working), they post one note naming and linking each such review (`<!-- fabrik:undelivered-request-changes <ids> -->`), put the PR back in draft and start its Request-changes run, for the latest review, using no retry; while one waits, they don't rebase the PR themselves. The two checks take turns, so neither notes a review the other has. If a Review is in flight when it's found, nothing starts until it lands: a pass settles the review, which the Reviewer read as part of the Ticket, and an Execution flaw gives way, calling for no Retry and using none, and starts the Request-changes run itself, which fixes its findings too. A Request changes of yours on the draft while a Retry is in flight, up to the Verdict on its push, is deferred (#427): the Kit says so on the PR, mentioning nobody, and neither that Review nor a Retry is given it. A pass or an Execution flaw on the Retry's push then gives way to it as though it had just arrived at the Merge gate: the PR stays in draft, its Request-changes run starts, and no retry is used; a Design flaw still sends the Ticket back to design. Otherwise, a review on a draft PR does nothing, and a Request changes from anyone else starts nothing: a person's gets one line on the agent PR, mentioning nobody, saying only the Operator's reviews start runs, and a bot's gets none. The caller workflow runs on `pull_request_review` (submitted) for this. GitHub has no `_target` form of that event, so the run uses the PR's copy of the caller workflow and Kit config, which an agent branch can never change (ADR-0005).
- **Conflicts with main**: when a push to `main` leaves an agent PR out of draft conflicting with it, the Kit brings the PR up to date without you (ADR-0011). It first rebases the PR's branch onto `main` itself, with no agent, without a working tree: if that's clean, it puts the PR back in draft and pushes with a lease, and the push starts a full Review of the combined head, whose pass requests your review again. If the lease refuses the push, because the branch moved meanwhile, the PR comes back out of draft with a comment saying so and no attempt recorded, for the next check. If the rebase conflicts, it puts the PR back in draft and starts one conflict-only run: an Implementer run on the Step-up model, on the PR's branch, told to rebase onto `origin/main`, resolve the conflicts and change nothing else. Its fix comment lists each conflicted file and how it was resolved. Neither uses a retry itself. The run's push carries a `<!-- fabrik:conflict-run -->` note, so the Verdict Review gives it is marked as from a conflict-only run. The run itself uses no retry, but an Execution flaw on its push calls for the next one and counts like any other (#415), as for a Request-changes run, so no Retry number starts twice on one PR. While the run is in flight, no other head gets a Verdict. A PR that's only behind `main` is left alone, and so is a draft, a PR with a Retry or Request-changes run in flight, or one with a Request changes from you that no run has started for yet, whose Request-changes run brings `main` in instead. Each PR gets one attempt per `main` head, recorded by a `<!-- fabrik:conflict-attempt <sha> … -->` note on the PR. If the conflict-only run fails, changes nothing, doesn't bring `main` in, its output breaks the contract, or the trust-root guard refuses it (the run's rebase rewrites the PR's commits, so they all count as its own: a conflict resolved inside a trust-root file, or any earlier Operator commit on the PR that touched one, is refused), the Kit says why on the PR, @-mentioning you, adds `ready-for-human`, and takes the PR out of draft again, never closing it; it tries again only once `main` moves to a new head. The check runs on every push to the default branch and on the hourly tick, which catches a PR whose mergeable state GitHub hadn't worked out within the push's short poll. The checks take turns, and each judges the PRs against `main` as GitHub reads it when the check runs, which may be past the push that started it. The caller workflow's `push` trigger fires on any push to the default branch for this, not only a Kit config change: a Product repo set up before it must update its `.github/workflows/fabrik.yml` from `templates/fabrik.yml` (the Fabrik App has no `workflows` permission), and until then relies on the tick.
- **Send it back**: adding `needs-design` to an open agent PR takes the Design-flaw route: the PR closes unmerged, keeping its branch, and the Ticket swaps `ready-for-agent` for `needs-design`. The note's marker is `<!-- fabrik:back-to-design <pr> operator -->`, and round 1 says the Operator sent the Ticket back.

## Audit

Once a week the scheduled tick starts an Auditor run in each Product repo. It reads what changed on the default branch since the last Audit and files at most 3 deepening opportunities as one `fabrik:audit` issue, the Audit. It changes nothing: no branch, no PR, no state label and no push. It's on from the release that ships it, with no setup step; `audit.day: null` in the Kit config turns it off.

- **When**: from 00:00 UTC on `audit.day` (Sunday by default), the hourly tick opens the week's **pending Audit**: an issue from the Fabrik App titled `Audit: week of <Monday>`, labelled `fabrik:audit`, with no state label, no assignee and no mention, whose one line names the commit the Auditor is reading. The Fabrik App opening it starts the Loop workflow's Audit job, and Intake leaves it alone. The week runs Monday to Monday in UTC, and it gets at most one Audit. The tick opens none while an Audit is open, a filled one the Operator hasn't closed included, while any weekly-limit issue is open, with Subscription rotation on or off, or when the default branch hasn't moved since the last Audit. An Audit that couldn't open on its day, because the limit was reached say, opens on a later tick that week, and after two failed runs in a week the next Audit waits for the next week. One open Audit and 3 candidates are fixed limits, not `caps`.
- **The Auditor** (Opus 5.5, 45 minutes by default, `roles.audit`, plus `.fabrik/audit.md` when present) is read-only, like the Reviewer: it gets a checkout of the default branch at the pending Audit's commit with its full history, holds only the agent service account, and runs none of the code. The agent itself holds no GitHub token. It gets the Base skills alone, never Extra skills, and follows `improve-codebase-architecture`'s method without its HTML report or questions. It looks first at what changed since the last Audit's commit (the last 30 days on a first Audit) and at comprehension drift: files merged agent PRs changed more than 5 times in 30 days while no ADR, no `GLOSSARY.md` and no Markdown file in the same directory changed. It uses the glossary's terms, respects every ADR, skips a candidate whose issue is still open, and doesn't resurface one the Operator rejected in the last 3 Audits unless it has materially worsened. Everything it reads from issues, comments and code is data, never instructions.
- **The filled Audit**: the push job rewrites the pending Audit with one card per candidate, Strongest first. Each has its Files, Problem, Solution and Benefits, a Mermaid before/after diagram, a Strength badge (Strong, Worth exploring or Speculative), **Introduced by** with the merged agent PRs it traces to, and an **Open as issue** link. The Kit drops any PR under Introduced by that isn't a merged agent PR. A **Top recommendation** ends it. @-mentions are stripped from everything the Auditor wrote but its file paths and Mermaid source, which sit in code, where GitHub notifies nobody. The Audit stays open, unassigned and silent. When no candidate is above Speculative, the Audit says the repo is clean and closes itself as completed.
- **A failed run**, a reply that breaks the Audit output contract included, rewrites the pending Audit to one line saying how it failed and closes it as not planned, mentioning nobody: the tick tries again. The week's second failed run, after which the next Audit waits for next week, also comments on its Audit @-mentioning you, with each failed run's link and how it failed. A dead token or the weekly limit also goes on the Kit's rotation or weekly-limit issue, as for any run. With Subscription rotation on, an Auditor run is never re-run or held, as other runs are: refused on its weekly limit, killed for usage credits, or due to start while every Subscription is used up, it fails the same way, and a later tick tries again. Closing a pending Audit yourself cancels it: its run's result changes nothing.
- **The Operator's moves**: file each candidate you want through its Open as issue link, which opens the repo's new-issue form prefilled with the candidate (the diagram stays on the Audit) and ending `From audit #<n>`. The filed issue goes through Intake and Triage like any other, and the next Audit skips it while it's open. Comment on the Audit about any candidate you reject: the next Audit reads it as context, never as a trigger (ADR-0007). Then close the Audit, as completed if you filed anything and as not planned otherwise, which frees the next one. An ignored Audit only holds the next one back.
- **Architectural escapes**: when a candidate traces to merged agent PRs, its prefilled body also ends with a hidden `<!-- fabrik:escape <strength> #<pr> … -->` marker, so filing it records an Architectural escape against those PRs. Delete a PR from the marker before submitting to correct the attribution. Only issues the Operator opened count, and only for PRs that are merged agent PRs. A link too long for GitHub's URL limit cuts the candidate's text, never `From audit` or the marker, and a Design session that rewrites the filed issue keeps both lines.
- **In the Weekly summary**: the Metrics table's **Architectural escape rate (90 days)** is the merged agent PRs named in at least one escape out of the agent PRs merged in the trailing 90 days, as "n of m (x%)" beside last week's, or "no merged agent PRs" when there were none. A line under the table counts the 90 days' escapes by Strength. Each repo's **Architectural escapes this week** lists the escapes filed that week, each PR with the last passing Review run that missed it and whether the Operator pushed to it. An open Audit, filled or still pending, is in the repo's Waiting on you with its age, and an Audit that failed twice in a week, the second time that week, is under Stuck, linking both. An Auditor run leaves a Run record like any agent run, and counts in the week's total cost but never in cost per merged PR or per Spec.

## Retro

Once a week the scheduled tick starts a Retro run in each Product repo that has the `fabrik-runs` store. It reads the repo's Run records, transcripts and scores in the store, and the Operator's feedback on its agent PRs, since the last Retro, and files at most 3 proposals to change how the factory works in that repo as one `fabrik:retro` issue, the Retro. It changes nothing itself: no branch, no PR, no state label and no push. The Operator files what they want through each proposal's link. It's on from the release that ships it, with no setup step beyond the store; `retro.day: null` in the Kit config turns it off.

- **When**: from 00:00 UTC on `retro.day` (Saturday by default, a day before the Audit), the hourly tick opens the week's **pending Retro**: an issue from the Fabrik App titled `Retro: week of <Monday>`, labelled `fabrik:retro`, with no state label, no assignee and no mention, whose one line says when its window starts. The window runs from where the last Retro's ended (the 7 days before the tick on a first Retro) up to the tick that opened it, so nothing falls between two Retros, and a failed Retro is never the last one. The Fabrik App opening it starts the Loop workflow's Retro evidence job and then its Retro job, and Intake leaves it alone. The week runs Monday to Monday in UTC, and it gets at most one Retro. The tick opens none while a Retro is open, a filled one the Operator hasn't closed included, while any weekly-limit issue is open, with Subscription rotation on or off, so that a Retro never competes with Tickets for what's left of a weekly limit, or when nothing is new since the last Retro: no agent PR merged or closed and no escape filed. It opens none, and says nothing about it, while the `fabrik-runs` store isn't ready: the Fabrik App isn't on it, or it isn't private. A Retro that couldn't open on its day opens on a later tick that week, and after two failed runs in a week the next Retro waits for the next week. One open Retro and 3 proposals are fixed limits, not `caps`.
- **The evidence**: the Retro evidence job runs no agent and no Product code. Like the push job, it checks out only the Kit and loads the Fabrik App key through the push service account, then mints a token with Contents read on `fabrik-runs` alone and a read-only token on the Product repo (ADR-0009's addendum). It refuses a store that isn't private and reads only this repo's paths in it. It builds one bundle: the window's Architectural escapes, each with the last passing Review run that missed it; the Operator's feedback on agent PRs (Request changes reviews with their inline comments, the Operator's own pushes with their patches, and the Operator's comments); the Follow-ups on passing Verdicts, with whether the Operator opened each; the runs a Scorer failed; a fixed one-in-ten sample of the merged agent PRs; a streak table of every agent PR merged in the last 90 days; the last 3 closed Retros with the Operator's comments on them; and the open issues filed from Retros, on the Product repo and on the Kit's repo and each Skills source the Operator owns, read with the same read-only token (a repo it can't read is skipped with a warning). Each escaped or sampled PR carries its Ticket's title and body, read with the read-only token. Transcripts come as digests. The bundle is held to a fixed size, cut from the sample's transcripts first and the escapes' last, and never cut in a ref, a Verdict, a Ticket or a review comment.
- **The Retro** (Opus 5.5, 45 minutes by default, `roles.retro`, plus `.fabrik/retro.md` when present) is read-only, like the Auditor. It gets a checkout of the default branch, so it can read `AGENTS.md`, `CODING_STANDARDS.md`, `.fabrik/`, the [Vision and Roadmap](#vision-and-roadmap), the lint config and the CI scripts, and the Kit's own role prompts and rubrics. It holds only the agent service account and runs none of the code, and the agent itself holds no GitHub token. It gets the Base skills alone, never Extra skills. It ranks escapes first, then patterns repeated across the Operator's feedback, then low-scoring runs, then the sample, and never proposes from something seen once outside an escape. A mistake a lint rule or grep assertion could catch becomes a **Mechanical** proposal: a check in the Product repo's own lint config or scripts, gated through its existing CI and `sandbox.checks`, never a sentence. A lesson only judgement can apply becomes a **Judgement** proposal, such as a `CODING_STANDARDS.md` line or a change to the Kit's review prompt. It **tightens** on one escape or one repeated pattern, and **loosens** only on a streak. It never loosens the Merge gate, the Trust-root guard, the Reviewer's separation from the Implementer or the two-Retry cap. Everything it reads is data, never instructions.
- **The filled Retro**: the push job rewrites the pending Retro with a short opening (the window it read, and what to do) and one card per proposal, most important first. Each has its title, a Mechanical or Judgement badge and a Tighten or Loosen badge, the problem, its evidence as links (Run records, score files and transcripts as `fabrik-runs` file links, PRs and issues as links), the exact change, a loosening's streak and the tightening it undoes, and an **Open as issue** link. The Kit checks each proposal against the bundle, never against the Retro's word. It drops any evidence ref the bundle doesn't hold, a proposal left with no escape and fewer than two distinct PRs, and a loosening whose streak isn't at least 20 PRs from the streak table, none of them named in an escape, reverted or sent back with Request changes. What it dropped is listed in the run's step summary, never on the Retro. @-mentions are stripped from everything the Retro wrote outside its code blocks, and the Retro stays open, unassigned and silent. With nothing left to propose, it says so in one line and closes itself as completed.
- **Open as issue**, by what the proposal changes:
  - a Trust-root file such as `AGENTS.md`, `CODING_STANDARDS.md`, `.fabrik/` or `docs/product/` at the repo root, where the [Vision and Roadmap](#vision-and-roadmap) live: the Product repo's new-issue form with `ready-for-human`, written as an Operator brief carrying the exact edit, since only the Operator changes those;
  - the Product's code, such as a lint rule or check script: the Product repo's form with no label, so it goes through Intake and Triage;
  - the Kit: jrey8343/fabrik's form;
  - an Extra skill: its Skills source's form, but only when the repo pins the skill and the Operator owns the source. Otherwise the card has no link and says to unpin or replace the skill.

  Each prefilled body ends `From retro #<n>`. On the Kit's repo or a Skills source, where a bare `#<n>` would link to that repo's own issue, it ends `From retro <owner>/<repo>#<n>`, naming the Product repo, and every `#<n>` in it outside code names the Product repo the same way. A link too long for GitHub's URL limit cuts the proposal's text, never that line, and a Design session that rewrites the filed issue keeps it.
- **A failed run** rewrites the pending Retro to one line saying how it failed and closes it as not planned, mentioning nobody: the tick tries again. That includes a failed evidence job (the store gone, or no longer private) and a reply that breaks the Retro output contract. The week's second failed run, after which the next Retro waits for next week, also comments on its Retro @-mentioning you, with each failed run's link and how it failed. A dead token or the weekly limit also goes on the Kit's rotation or weekly-limit issue, as for any run. With Subscription rotation on, a Retro run is never re-run or held, as other runs are: refused on its weekly limit, killed for usage credits, or due to start while every Subscription is used up, it fails the same way, and a later tick tries again. Closing a pending Retro yourself cancels it: its run's result changes nothing.
- **The Operator's moves**: file each proposal you want through its Open as issue link; the next Retro skips one whose `From retro` issue is still open, wherever it was filed. Comment on the Retro about any proposal you reject: the next Retros read the comments on the last 3 closed Retros as context, never as a trigger (ADR-0007), and don't propose it again without new evidence. Then close the Retro, as completed if you filed anything and as not planned otherwise, which frees the next one. An ignored Retro only holds the next one back.
- **In the Weekly summary**: an open Retro, filled or still pending, is in the repo's Waiting on you with its age, and a Retro that failed twice in a week, the second time that week, is under Stuck, linking both. A Retro run leaves a Run record like any agent run (the evidence job, which is no agent run, leaves none), and counts in the week's total cost but never in cost per merged PR or per Spec. Scores still never show in the summary: a low score reaches the Operator only through a Retro's proposals.

## Replay

A Replay tests one change to how the factory works before the Operator makes it. It re-runs recent merged Tickets from the commit each one's first Implement run started from, once as the Ticket was built then (the **baseline**) and once with one thing changed (the **variant**), and sets the two side by side. Nothing changes in the Product repo: no branch, no PR, and no label or comment except on the replay issue. It's on from the release that ships it, in every Product repo with the `fabrik-runs` store, and costs nothing until the Operator files a replay issue.

- **Filing one**: open an issue labelled `fabrik:replay` whose body holds one request block, below any text of your own:

  ````
  ```replay
  review.effort: high
  tickets: #41, #12
  ```
  ````

  The block names exactly one variable: `implement.model`, `implement.effort`, `review.model` or `review.effort`, set to a value, or `kit`, set to a full 40-character Fabrik commit sha whose prompts and Base skills the variant loads in place of the pinned release's, as a Retro proposal's would. Efforts are Kit config's: `low`, `medium`, `high`, `xhigh` or `max`. A model must be a full Claude model name such as `claude-opus-5-5`, so the record says exactly which model ran: CLI aliases like `opus` are refused, and so are Fable and `best`, for Kit config's reason. A `kit` sha changes only the role prompts and the Base skills lock, never the workflows, the Scorers' rubrics or the Kit's code, and it must be a commit in jrey8343/fabrik, on a branch or not, as a merged Retro proposal's still is once its branch is deleted: ADR-0003's addendum refines the pinned release for it. `tickets` is optional and lists up to 10 Ticket numbers. Only the Operator's replay issues count: one anyone else files gets no comment and runs nothing. Intake leaves a replay issue alone, and no agent ever files one.
- **"Replay this"**: a new-issue link with the `fabrik:replay` label and a prefilled request block (`replayThisUrl` in `src/kit/replayRequest.ts`), such as a Retro proposal's PR can carry, so testing a proposal takes one click.
- **Accepting it**: the next hourly tick reads the request. A request that doesn't read (no variable or two, an unknown role, a refused model or effort, a short sha or one that isn't a Fabrik commit, more than 10 Tickets), or picks no eligible Ticket, gets one comment saying why. Edit the body to fix it, and the next tick reads it again. A valid request is accepted once: the tick picks its Tickets then and lists them in the body, below your text, which the Kit never rewrites. Only merged, never-reverted Tickets built by Implement runs are eligible, whose first Implement run left a Run record with its `baseSha`, and whose merged PR changed no Trust-root file. The first Implement run is the one that cut the branch that merged: a first run that left an empty diff, which its record says, is passed over for the fresh run after it. A Ticket is also left out when its Kit config at `baseSha` doesn't resolve under this release, or already runs the variable's value, as `review.effort: high` on a Ticket built with Review at `high` already, so its two arms would be the same. This is a deliberate refinement of the Spec, whose eligibility rules name neither case: a Ticket the arms can't compare would only spend a run. With no `tickets`, it picks 5: the most recent eligible ones, spread across thirds of their original cost. A listed Ticket left out is named with why. A picked Ticket keeps its flags: Human touches, a Ticket or Spec edited since its first run, or a merged PR with no test files ("no hidden tests").
- **How each Ticket runs**: both arms in one workflow run, on the pinned release, each one Implement run and one Review, with no Retry and no Step-up. A marked Ticket's baseline runs Implement on the Step-up model and effort, as it was built, unless the variable sets `implement.model` or `implement.effort`; no arm reads the `fabrik:step-up` label. Each arm checks out the Ticket's `baseSha`, so Kit config and Extra skills are the ones it was built with. Its Implement and Review jobs fetch that one commit alone, with no branch or tag, so neither agent can read the merged result from the checkout; only the gates, which run no agent, fetch the history that holds the merged PR's tests. Each arm rebuilds a first Implement run's input from the Ticket and its Spec as GitHub holds them now. The baseline runs the models and efforts Kit config held at `baseSha`; the variant differs only in the variable. The replay Implement job holds no write credential, as a live one doesn't (ADR-0002), passes its diff out as a patch rather than pushing it, and is never named `Implement`, so it never takes a Dispatch slot. Each arm's gates run `sandbox.setup`, `sandbox.build` and `sandbox.test` on its patch, then lay the merged PR's test files over the tree and run the tests again. Its Review judges the diff against the Ticket, with no PR, whether or not the gates passed. The three Scorers score every replay Implement run, never a sample, at the pinned release's rubrics, unless it left no transcript, ended in an Infrastructure failure or read near its weekly limit, as for any run.
- **Spare capacity only**: the tick starts at most one Ticket, both arms, per hour, and only while Dispatch has no ready, unblocked Ticket or research Decision to start, no Subscription has an open weekly-limit, usage-credits or token-rotation issue, and the last weekly-limit reading on the Subscription it would use is `allowed` and under 50% (no reading counts as spare). A reading whose limit has reset since counts as spare too, whatever it said, since the week it read is over. This is a deliberate refinement of the Spec, which counts only no reading as spare: in a quiet repo the newest reading can come from before the reset, and nothing runs to replace it, so without it a Replay could wait on a stale reading for good. Only one replay Ticket runs at a time across every replay issue, the oldest issue first, and the claim checks it again as the run starts. Adding `agent:replay` to a replay issue by hand starts its next Ticket at once, as adding `agent:implement` by hand starts past Dispatch's cap: only a replay Ticket already in progress, on any of your replay issues, or a used-up Subscription stops it, never Dispatch's queue or the last reading. A replay run is never held or re-run on another Subscription: refused on a weekly limit, it opens the weekly-limit issue as any run does, and its Ticket waits for a later tick. Any other Infrastructure failure is tried once more on a later tick, then shown as failed. A `kit` variant whose candidate sha the Kit job can't lay, as one GitHub has no commit for, runs neither arm and fails its Ticket at once, with no retry, its row naming `kit-sha-unavailable` and why.
- **What you read**: the body grows a results table as Tickets finish, your request kept at the top: a row per arm with its gates, Verdict, hidden tests, the three scores, cost, turns, duration, a link to its patch in `fabrik-runs` and its flags. Below it come the totals per arm beside the original runs, each mean score with how many of the Tickets done it was scored over, as `0.95 (2/5)`, the baseline's gap from the original, which shows how much results vary by chance, and a headline the Kit computes from the totals, such as `variant: hidden tests 4/5 vs 5/5; cost −38%`. A Ticket whose first run had no Review, its checks red, is left out of the original's totals and the gap, which say so. No model judges the results or recommends anything. When the last Ticket is in, one comment mentions you, and the issue stays under Waiting on you in the Weekly summary until you close it. Act on it yourself, by changing a Kit config default or merging the Retro PR, then close it.
- **Cancelling**: close the replay issue. The tick ignores a closed one, and a run already going finishes and keeps its records in the store but doesn't rewrite the body. Anyone who can edit the issue can edit its body, so keep replay issues to repos whose collaborators you trust with your Subscriptions.
- **A run that never lands**: the replay-record job lands each run whatever its arms came to, a cancelled one included. If it can't, as when 1Password is down, the Ticket's progress marker still says when its claim started it, and the tick releases it once it's been in progress longer than a run can last: every replay job's timeout end to end at your Kit config's, plus an hour to queue (210 minutes at the defaults). The replay step goes by that time, not by workflow runs. A released Ticket counts as an Infrastructure failure: it runs once more on a later tick, then shows as failed, so no Ticket holds every Replay back for good.
- **In the store**: every replay run gets a Run record, at schema 4, whose `replay` field names the replay issue, the arm and the Ticket, plus a `kit` variant's candidate sha. Records, transcripts, score files, each arm's patch, at `replays/<owner>/<repo>/<replay-issue>/<ticket>-<arm>-<run>.patch`, and its gates beside it, at `<ticket>-<arm>-<run>.gates.json`, are written create-only by the replay-record job, the Replay's own push job (ADR-0009's addendum). The Weekly summary and the Retro leave replay records and score files out of every figure. The week's total gains a **Replay spend** line, judge runs included, in a week that had any. A Replay costs about twice the original Tickets' first Implement runs and their Reviews: two Implement runs, two Reviews and two judge runs per Ticket, all under the 50% line.

## How loud each kind is

The Kit pushes to the Operator's phone only when it is their move, and once a week for the Weekly summary, through GitHub mobile's @-mentions, assignments and review requests ([#22](https://github.com/jrey8343/fabrik/issues/22)). Each event pushes once, by one of them.

| Kind | Level | How |
|---|---|---|
| Design-session round | Push | @-mentions the Operator. Round 1 is the push for a Ticket sent back to design too, and a prototype round, or its failure round, is a round. |
| Merge gate | Push | Requests the Operator's review. |
| A Kit run fails | Push | The failure notice @-mentions the Operator. |
| The push job or claim job fails | Push | One comment on the run's issue or PR @-mentions the Operator, saying what the Kit was landing, what failed and how to recover. |
| `needs-info` | Push | Triage's comment @-mentions the issue's author, or the Operator when the Monitor filed it. A Monitor issue in `needs-info`, or one the Operator filed, stays in the Weekly summary's Waiting on you until someone answers. |
| `ready-for-human` | Push | Assigns the Operator. |
| Claude token expired or revoked | Push, once per repo, or once per Subscription with rotation on | The rotation issue assigns the Operator. With rotation on, each Subscription gets its own, naming it: the refused run is re-run on the next free Subscription with no Ticket comment, and the Kit runs nothing on the dead one until the Operator closes its issue. |
| Sentry token rejected or missing | Push, once per dead token | The Monitor's "Rotate the Sentry token" issue assigns the Operator, once the Monitor has filed an issue for a Sentry group; it closes the issue itself once Sentry reads again. |
| Weekly usage limit reached | Push, once per window per repo | The weekly-limit issue @-mentions the Operator. With rotation on, see the next two rows. |

| Usage credits spent on a Subscription | Push, once per Subscription | The usage-credits issue (label `fabrik:usage-credits`) assigns the Operator, and the Kit runs nothing on that Subscription until the Operator closes it. |
| Weekly summary | Push, once a week | The Weekly summary issue in `fabrik-runs` @-mentions the Operator once, for every Product repo, and closes last week's. A week with nothing to report files nothing. A Product repo the run couldn't read on GitHub gets a line in its section saying why. |
| The Weekly summary run fails | Push | One comment on the newest Weekly summary, or a `Weekly summary failed` issue in `fabrik-runs` when there's none, @-mentions the Operator with the run link and what failed, so a failed run is never taken for a quiet week. |
| Implement draft PR, Execution-flaw retry, back-to-design note | Silent | The PR and the Verdict are the record. |
| Fast path, Design session finished, Spec closed, `wontfix` | Silent | |
| A Ticket closed by hand closes its agent draft PR | Silent | The comment on the PR mentions nobody. An agent PR you close by hand stops its Ticket in `ready-for-human`, whose assignment is the push. |
| Skills-source bump PR | Silent | The PR requests no review; the Operator merges it when they choose. |
| Monitor issues | Silent | An error or red-main issue gets `needs-triage` from Intake and reaches the Operator through Triage, never a push of its own: if Triage asks for more, its question @-mentions the Operator. The Monitor never comments, apart from the note it closes its red-main issue with. |
| Audit | Silent | No state label, assignee or mention; a failed run closes it the same way. It surfaces in the Weekly summary's Waiting on you while it's open. |
| Retro | Silent | No state label, assignee or mention, and no push; a failed run closes it the same way. It surfaces in the Weekly summary's Waiting on you while it's open. |

- **Held work is silent.** Work a full cap holds (see `caps` in the [Kit config](#kit-config)) waits with no comment, label or notification. It pushes when its slot opens, as a Design session's round 1 does, and the Weekly summary's **Held** section shows, per Product repo, how many `needs-design` issues wait for a slot and how long the oldest has waited, how many Sentry error groups wait for a Monitor issue slot, which open Maps fill the Map cap, and, with Subscription rotation on, each Held run with its role and the weekly-limit issue holding it, beside each open weekly-limit issue and its reset. A Held run is never listed under Stuck, its failed run and its draft PR included: the Kit resumes it itself.
- **A red push or claim job says why, and Re-run failed jobs recovers it.** Setup turns Actions notifications off, so when the push job or the claim job fails, whether GitHub refused or failed a call (the Kit's GitHub client already tries a failed read, and a write GitHub never took, twice more first) or the Loop wouldn't land the run, the job's step summary and one comment on the run's issue or PR say what it was landing, what failed, which of its plan's actions landed and which didn't. An agent's finished work waits in the run's `fabrik-agent-result` artifact, which Actions keeps for 7 days: open the run and choose **Re-run jobs → Re-run failed jobs** before then, and the push job lands it. A push to `main` has no issue to comment on, so only its step summary says.
- **There is no push budget.** Every push but the Weekly summary is the Operator's move, and the Weekly summary is one a week, so the Kit never holds one back: it caps the sources, never the pushes.

## Kit config

A Product repo's Kit config lives in `.fabrik/`. Every file is optional and every field has a default, so a release never needs a config edit. An invalid config, or an unknown field, fails the run with a message naming the field.

What Setup and the Visual evidence writer write in `.fabrik/config.json` is printed as Prettier prints JSON with its default options, 80 columns wide. A Product whose own Prettier settings set another width (`printWidth` in `.prettierrc` or in `package.json`'s `prettier` key, or `max_line_length` in `.editorconfig`) can fail `prettier --check` on the setup PR's `subscriptions` line or on the Visual evidence PR. Then run the Product's own `prettier --write .fabrik/config.json` and commit it in that PR.

- Leave a field out to take its default. `null` is accepted only where the default is `null` (the Sandbox commands, `effort`, `monitor.errors`, `operator`, `ui`, `ui.before_url`, `preview` and `preview.url`), and in `audit.day` and `retro.day`, where it turns the Audit or the Retro off. A `null` effort means the Claude Code CLI's default; otherwise set it to `low`, `medium`, `high`, `xhigh` or `max`.
- `sandbox.env` holds non-secret values. `sandbox.secrets` maps an env var name to an `op://` reference; a literal secret is refused.
- A model naming Fable (or the `best` alias) is refused in every role, because Fable can bill metered usage.
- `max_in_flight` caps how many Tickets and research Decisions are in flight at once: open agent draft PRs, Implement and Research runs in progress, and Tickets and research Decisions dispatched but not yet started. Set it to `0` to pause Dispatch: the Kit adds `agent:implement` to no new Ticket and `agent:research` to no research Decision, while Intake, Triage, Design, Review, the Merge gate, retries and Request-changes runs carry on. Set it back above `0` and Dispatch resumes straight away: a push to the default branch that changes `.fabrik/config.json` runs a Dispatch check. A Product repo set up before the caller workflow had a `push` trigger gets it by running Setup again; until then Dispatch resumes at the next Dispatch check, on the hourly tick at the latest.
- `caps` holds the attention budget: per-repo caps on what the Kit opens in front of the Operator. A cap can only be lowered: a value above its Kit default is a Kit config error that names the field and the default.
  - `caps.design_sessions` (default 2) caps how many Design sessions are open in the repo at once; set it to `1`, or to `0` to pause new Design sessions while those already open carry on. Raising it back starts waiting issues straight away, as the config push runs a Design queue check. See [Design session (async)](#design-session-async).
  - `caps.monitor_issues` (default 5) caps how many error issues the Monitor keeps open in the repo at once. Past it, new error groups are held, `fatal` ones first and then the most users affected, and filed on later ticks as slots free up; the newest open error issue's stats block says how many are held. Set it to `0` to pause new error filings. The red-main issue never counts toward it, and still files and closes at `0`.
  - `caps.maps` (default 1) caps how many Maps are open in the repo at once, counting every open `wayfinder:map` issue, whoever made it. Set it to `0` to stop new Maps; Maps already open carry on. See [Maps](#maps).
- `monitor` says what the Monitor watches. It files issues with the `fabrik:monitor` label and no state label, so Intake gives them `needs-triage`, except its Sentry token issue, which is `ready-for-human`. It never reopens them, and its only comments are the notes it closes its red-main issue and its Sentry token issue with. An invalid `monitor` block is a Kit config error like any other. Each source it can't read yet, for a setup step not done, is a quiet note in the hourly tick's step summary, never a failed run.
  - `monitor.errors` is where it reads production errors. `null`, the default, leaves them off. To turn them on, set it to `{ "provider": "sentry", "org": "<org slug>", "project": "<project slug>" }`, then run Setup again: while 1Password lacks the Sentry token, it walks the wizard's Sentry stage to store it. `provider` takes only `sentry`, and `org` and `project` are the slugs in the project's Sentry URL. Once the Monitor has filed an issue for a Sentry group, a token Sentry rejects (with a `::warning`) or a `Sentry token` item that goes missing gets one "Rotate the Sentry token" issue, `ready-for-human` and assigned to the Operator, which the Monitor closes itself on the first tick that reads Sentry again. `url` (default `https://sentry.io`) points it at another Sentry region or a Sentry-compatible host such as GlitchTip, and must be `https://`, since the token is sent there. `min_events` (default 3) is how many events in 24 hours an unresolved `error` group needs before it's filed; a `fatal` group needs none. Each qualifying group gets one issue, whose stats block the Monitor rewrites in place while it's open. A group that comes back after its issue was closed as completed gets a new issue, "Regressed from #n"; one closed as not planned or as a duplicate, or labelled `wontfix`, is never filed again. The issue quotes only Sentry's title, culprit, counts, release and in-app frames (file, line and function), never request data, breadcrumbs, user context, tags or variables.
  - `monitor.red_main` (default `true`) has the Monitor file one issue while the default branch's newest decided commit is red, and close it itself, with a "green at" note, once the newest decided commit is green. Set it to `false` to turn it off. It needs the Fabrik App's Checks: read, and at least one gating check that runs on pushes to the default branch: the checks in `sandbox.checks` when it lists any, else every check but those of Fabrik's own `loop` and `tick` jobs. A commit is decided once its gating checks have all finished and one failed or timed out (red), or none did and one passed (green); cancelled, skipped and neutral results decide nothing. A red-main issue the Operator closes stays closed until the default branch is seen green.
- `audit.day` is the UTC day of the week the Audit is due, `"monday"` to `"sunday"` (default `"sunday"`, so it's open by Monday's Weekly summary), or `null` to turn the Audit off in this repo. `roles.audit` sets the Auditor's model, effort and timeout like any role: by default the Reviewer's frontier model, Opus 5.5, with the CLI's effort and 45 minutes. See [Audit](#audit).
- `retro.day` is the UTC day of the week the Retro is due, `"monday"` to `"sunday"` (default `"saturday"`, a day before the Audit's default, so the two frontier runs never share an hour and both are open by Monday's Weekly summary), or `null` to turn the Retro off in this repo. `retro` takes no other field. `roles.retro` sets the Retro's model, effort and timeout like any role: by default the Reviewer's frontier model, Opus 5.5, with the CLI's effort and 45 minutes, within which its evidence job runs too. See [Retro](#retro).
- `roles.research` sets the Researcher's model, effort and timeout like any role: by default Opus 5.5, with the CLI's effort and 30 minutes. See [Maps](#maps).
- `subscriptions` lists the Subscriptions the Kit runs agents on, each the name of an item in the `Fabrik` 1Password vault that holds that Claude account's token, as `claude setup-token` gives it. The default is the one V1 item, `Claude token`. List one and rotation is off: every run uses it, as before. List two or more, such as `["Claude token", "Claude token 2"]`, and Subscription rotation is on. Setup lists the second one itself: when the Operator says yes to a second Subscription, in the run that installs the Kit or any later one, Setup walks the wizard's "A second Subscription" stage, which creates the `Claude token 2` item, and then lists it after the first, in the setup PR. Setup never adds to a list of two or more: it doesn't ask about a second Subscription then, `--second-subscription` has no effect but to say so, and the wizard's stage says to list a `Claude token 2` it stores there by hand. A list that names `Claude token 2` already, alone or not, has nothing for Setup to list, so it doesn't ask then either. With rotation on:
  - **The order is the Operator's, and the Kit fails over, never balances.** Every run starts on the first listed Subscription with no open weekly-limit, usage-credits or token-rotation issue, so the second is used only while the first is used up. Each run's Kit job step summary names the Subscription it gave the run, and its Run record names it too. A Kit job whose plan does nothing, as for an event the Loop declines, says why in its step summary instead.
  - A run refused on its Subscription's weekly limit opens that Subscription's own weekly-limit issue quietly and is re-run on the next free one, with no comment on its Ticket. Once every Subscription is used up, the issue that sees it @-mentions the Operator once, naming the first reset. Until then each run due is held, not started: its trigger label comes off and the weekly-limit issue names it. An Auditor or Retro run, which has no trigger label, is never held: its Audit or Retro fails, and a later tick opens the next one. At the reset the scheduled tick closes that Subscription's issue and resumes the held runs itself, in the order they were held, under `max_in_flight` and `caps.design_sessions` as usual; one whose issue or PR has closed or moved on is dropped. There is nothing to re-add. A Subscription freed any other way resumes them too, ahead of any newer Ticket: closing its usage-credits or token-rotation issue resumes them straight away, as does listing another Subscription, and the next hourly tick catches anything else. Closing a weekly-limit issue yourself says its Subscription works again, so the runs held on it resume straight away too. When the Kit doesn't know when a limit resets, the issue says so and asks you to close it once agent runs work again.
  - **Usage credits must be off on every listed Subscription.** With rotation on, a run whose stream shows usage credits being spent is killed, and that Subscription gets a "Turn off usage credits" issue, labelled `fabrik:usage-credits` and assigned to the Operator. The killed run is re-run on the next free Subscription, and the Kit skips that one until the Operator closes the issue.
  - **A dead token makes its Subscription used up too.** A run whose token is refused (`authentication_failed`), as when a `claude setup-token` token expires, opens that Subscription's own "Rotate the Claude token of the `<name>` Subscription" issue, labelled `fabrik:token-rotation` and assigned to the Operator, and is re-run on the next free Subscription with no comment on its Ticket. The Kit skips that Subscription until the Operator stores a new token and closes the issue. With no other Subscription free, the run is held as for the weekly limit while a weekly-limit issue is open, and otherwise gets the usual failure comment. A rotation issue that names no Subscription, as one opened before this did, is read as the first listed one's.
  - The Weekly summary reports usage per Subscription: one line each, with its cost and its last weekly-limit reading.
  - The list must be non-empty, and each name a non-empty string listed once; anything else is a Kit config error naming the field.
  - The wizard stores only `Claude token` and `Claude token 2`. A Subscription listed under any other name, such as a third, or one listed alone in place of `Claude token`, is the Operator's to store by hand: its account's `claude setup-token`, as an API Credential of that name, with its expiry date, in the `Fabrik` vault. Setup's plan names each one the vault lacks.
- `ui` turns on **Visual evidence**: screenshots of a UI pull request's pages, for the Operator and the Reviewer. It also lets a Design session offer a [Prototype](#prototypes), which a prototype turn builds with `sandbox.build`, serves with `ui.serve` and captures under `ui.url`. `null`, the default, leaves both off: nothing is captured, no Design session offers a Prototype, and each Implement run's Kit job step summary says so in one quiet line. To turn it on, or change its answers, the Operator runs `/fabrik-visual-evidence` in a Claude session in the repo. It suggests each answer from the repo for the Operator to confirm or correct, then writes them with the Kit's writer program, from the release the repo pins, and opens a PR with the change for the Operator to merge. The writer checks the answers against these rules first, and writes nothing when any would be refused, naming each problem. It writes only the `ui` and `preview` blocks, printed as Prettier prints JSON with its default 80 columns (a Product with another Prettier width runs its own `prettier --write .fabrik/config.json` in the PR, as above), and keeps every other byte of `.fabrik/config.json`. A field the answers leave out keeps its value, and running it again with the same answers writes nothing. The block:
  - `paths` (required, at least one): globs of the files whose change makes a pull request UI, such as `src/pages/**`, read as Node's path globs. Whether a PR is UI is the push job's call, never an agent's: from the run's changes against these globs, or, on a retry, from the evidence marker the Fabrik App already wrote in the PR's body. A PR that isn't UI gets no evidence section, and its Reviewer no screenshots or extra text.
  - `serve` (required): the command run in the background, after `sandbox.build`, to serve the branch, such as `npm run preview`. `url` (required): the local `http://` or `https://` base URL it serves on, such as `http://localhost:4321`, which capture waits up to 3 minutes to answer, and captures routes under. Something already answering on its port, such as a server the agent left running, is stopped first, so a stale server is never captured.
  - `before_url` (default `null`): the production site's base URL, which Before screenshots of the same routes are taken from. Without it Before is skipped.
  - `default_routes` (default `[]`): the routes captured when neither the Ticket nor the Implementer names one, each a path starting with one `/`.
  - **Pages behind a sign-in** (ADR-0012): three fields, all absent by default, which come together; a `ui` block that sets none captures as above. `sign_in` maps each Capture identity, a named kind of fake user such as `owner`, to the command that signs it in, such as `{ "owner": "pnpm sign-in owner" }`: at least one, each name letters, digits, `-` and `_`, and no command blank. `sign_in_path` is the route the app sends a signed-out visitor to, such as `/sign-in`. `signed_in_routes` is an ordered, non-empty list of rules such as `{ "route": "/console/**", "as": "operator" }`, saying which Capture identity views a route: the first rule whose `route` matches the route's path wins, its query left out, so a Prototype's `?variant=a` changes nothing; `as: null`, or no rule matching, views it signed out. In a rule's `route`, `*` matches within one path segment and `**` across segments, and `/**` matches `/` too. Every `as` must be `null` or one of `sign_in`'s identities, and Kit config is refused when `sign_in_path` or `signed_in_routes` is set without `sign_in`, or `sign_in` is set and `url`'s host isn't loopback (`localhost`, a name under `.localhost`, `127.0.0.1` or `[::1]`): a sign-in only ever reaches the Sandbox's own server, with fake users. Once `ui.serve` answers, and before any screenshot, capture runs the sign-in command of each Capture identity its routes need, once each, and none for a capture of public routes alone, Implement and prototype capture alike. Each runs in the Product directory with the env `ui.serve` gets, never `sandbox.secrets`, plus `FABRIK_STORAGE_STATE`: a temp file, outside the evidence folder so it's never uploaded, to write a Playwright storage state to, a JSON object with `cookies` and `origins` lists, which a Product can write by hand without Playwright. Each signed-in route's screenshots, and a prototype turn's takes, load that identity's state at both viewports; every public shot, and every Before, loads none. So a signed-in route has no Before: `before_url` is a deployed site, which these sessions can't reach and must not. The evidence section, both galleries and the Reviewer's prompt name the Capture identity on each signed-in shot. A command that fails, runs past 3 minutes, or leaves no state that reads stops capture as `sign-in-failed` before any screenshot; so does a signed-in shot whose page ends on `sign_in_path`, whose image is thrown away, the shots before it kept. A public shot is never checked, so a public route can show the sign-in page. An app that shows its sign-in form without redirecting to `sign_in_path`, or keeps its session in sessionStorage or memory, isn't caught.
  - **Capture**: once the Implementer's agent has ended well, on first, retry and Request-changes runs alike, the Implement job diffs the branch against the default branch, and when it touches a file matching `ui.paths` in that commit's Kit config, never the branch's own, it installs Chromium, runs `sandbox.build`, starts `ui.serve`, and screenshots each route, a PNG one screen high from the top of the page, at mobile (390 by 844) then desktop (1440 by 900): After from the branch, then Before. Build and server get `sandbox.env`, but never `sandbox.secrets`, the Claude token or a GitHub token. No model turn is used. Capture has its own 20-minute timeout, and the Implement job's timeout is the Implement role's plus those 20 plus 10 minutes, while the agent still stops at the role's own, so capture never cancels the job.
  - **The routes**: every route the Ticket names, as the path alone in backticks such as `` `/book` `` (outside a fenced code block), then the ones the Implementer names in its output, or `default_routes` when neither names one. Each is captured once, and the list stops at 4, though every route the Ticket names is captured even past that.
  - **The evidence section**: a UI PR's body gets one, between the summary and `Closes #n`, ending in a hidden `<!-- fabrik:ui-evidence {"run":…,"artifact":…,"failure":…} -->` marker, which records the Implement run that holds its screenshots and why its capture failed (`null` when it captured). It links the gallery, one self-contained HTML page of every screenshot, Before and After side by side, kept as an unzipped Actions artifact so it opens in one click; it and the zipped screenshots are kept 30 days. It lists each captured route with why it was chosen, flags any that answered with a server error, links the preview deployment or says why there's none, and, when capture failed, says why: `build-failed`, `server-did-not-start`, `timeout`, `no-routes`, `sign-in-failed`, `error`, or `no-result` when the push job got no capture result it could read. A failed capture keeps the screenshots it took first. It never blocks the PR, uses a retry or counts as an Infrastructure failure. Every retry and Request-changes run captures again and replaces the section, so it matches the PR's head.
  - **The Reviewer** gets at most 8 of the screenshots in its working directory: After before Before, mobile before desktop, then the Ticket's routes, the Implementer's and the defaults, so with 4 routes all 8 are After. Its prompt names each one's route, viewport and side, and asks whether they show what the Ticket asked for, whether there's plain breakage, and whether a part the Ticket didn't touch regressed against Before. Taste stays the Operator's, and a visual failure is an Execution flaw naming the route and the screenshot. When the PR's head has moved on since capture, as after the Operator's own push or a Retry's rebase, the prompt says the screenshots were captured at that earlier commit, so later commits may change what they show. When capture failed, the prompt says why, from the marker when there are no screenshots to read, and the Reviewer reviews the code as usual.
  - To ask for a visual change, use Request changes and cite a screenshot: no reaction is a trigger (ADR-0007).
- `preview.url` (default `null`) is where a UI PR's preview deployment appears, as a template that may use only `{pr}`, the PR's number, `{sha}`, its full head commit as the push left it, and `{branch_slug}`, its branch in lower case with each run of characters other than `a` to `z` and `0` to `9` made one `-`, and no `-` at either end (so `fabrik/ticket-12` is `fabrik-ticket-12`; the Kit never shortens it, though a host may). It must fill in to an `http://` or `https://` URL. Once it has pushed a UI PR, the push job polls that URL for 4 minutes at most, in a step with its own timeout that never fails the job, and links it in the evidence section once it answers with a 2xx page, redirects followed, or says it never answered. For a prototype round it fills the template in for `prototype/<issue>` and the head it pushed, polls the approved route's page on it the same way, and once it answers links it beside each variant with `?variant=` and the variant's letter, or says in the round it never answered. A template that uses `{pr}` has nothing to fill in for a Prototype, so its round says there's no preview for prototypes. The Kit never calls a hosting provider's API and needs no new secret. `null`, or a `preview` block of `null`, links no preview.
- `operator` is the Operator's GitHub login: the one person whose comments drive a Design session, whom its rounds and failure notices @-mention, and to whom `ready-for-human` work is assigned. `null` means the repo's owner; set it for a repo an organization owns.
- Per-phase instructions are optional Markdown files: `.fabrik/triage.md`, `.fabrik/design.md`, `.fabrik/implement.md` and `.fabrik/review.md`, the Auditor's `.fabrik/audit.md`, the Retro's `.fabrik/retro.md` and the Researcher's `.fabrik/research.md`.
- `CODING_STANDARDS.md` at the repo root is optional too, though it isn't Kit config: it holds the repo's coding standards. The Reviewer judges every PR against it when it's there (see [Review](#review)), the Implementer is never given it, and the Retro proposes Judgement lessons as lines for it. It's a Trust-root file, so only the Operator changes it, and the Kit ships no template for it.
- `roles.triage`, `roles.design`, `roles.implement` and `roles.review` each take an optional `skills` list of Extra skills (see [Extra skills](#extra-skills)). `roles.dispatch`, `roles.step_up`, `roles.audit`, `roles.retro` and `roles.research` don't: a Step-up run is an Implement run and gets implement's, and the Auditor, the Retro and the Researcher get the Base skills alone (ADR-0008).

### Extra skills

Every run gets the Base skills, which Fabrik's own `skills.lock.json` pins and which move only with a Kit release, plus Fabrik's own skills. A Product repo that needs more pins its own public **Skills sources** in `.fabrik/skills.lock.json` and gives **Extra skills** from them to roles in `.fabrik/config.json` (ADR-0008). A repo with neither runs exactly as before and pays nothing.

`.fabrik/skills.lock.json` is a list of pins, each a repository and a full 40-character lowercase commit SHA:

```json
[{ "repository": "jrey8343/skills", "sha": "0123456789abcdef0123456789abcdef01234567" }]
```

Each role's picks name the source, then the skill by the name it installs as under `.claude/skills/` (the last segment of its folder in the source's `.claude-plugin/plugin.json`):

```json
{
  "roles": {
    "design": { "skills": ["jrey8343/skills/event-storming"] },
    "review": { "skills": ["jrey8343/skills/event-storming"] },
    "implement": { "skills": ["jrey8343/skills/deciders"] }
  }
}
```

- Write a source's first pin and the picks by hand; Setup writes neither. After that, the Kit's scheduled tick checks each source's default branch on the Monday tick in the 04:00 UTC hour and opens, or refreshes, one PR per source on `fabrik/skills-bump/<owner>-<name>`, pushed with the Fabrik App token. It changes only that source's SHA, shows the upstream diff under the picked skills' folders, lists the other changes in one line, and flags a picked skill removed upstream as breaking. A week in which no picked skill changed opens nothing. The Loop ignores these PRs; only the Operator merges them.
- Each AFK run installs the Base skills plus only its own role's Extra skills, before any secret loads, and its prompt gets one Kit line naming them. A local, Pairing or live Design session's `SessionStart` hook installs every pick, and warns, still installing the Base and Kit skills, when a pick is wrong.
- Say when to use an Extra skill in that phase's instructions, `.fabrik/<phase>.md`, not in the Kit config. The Kit's line only says the skills are there and that this repo's instructions say when to use them.
- These are Kit config errors, which stop the Loop before any agent starts: a malformed lockfile or pick; the same repository pinned twice; a pick naming an unpinned source, or a skill its source's manifest doesn't list at the pin; a pinned source no role picks from; a source with no readable manifest; and a pick named like a Base skill, a Kit skill (one of Fabrik's own) or a pick from another source. The Kit job reads each source's manifest from public GitHub at its pin, only when the repo pins a source.
