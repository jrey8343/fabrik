# Fabrik

A software factory: an agent-driven engineering loop that takes work from idea → spec → tickets → shipped code.

Status: building v1. See the Spec in GitHub Issues (#28).

## Layout

- `src/loop/` holds the **Loop rules core**: a pure function, `planFor(event, snapshot, config)`, that returns a plan. It does no I/O, and its tests (`*.test.ts`, next to the code) are the Loop's behaviour, one sentence each.
- `src/__fixtures__/` holds the snapshot builders the core's tests use.
- `src/kit/` holds the **Kit config** loader (`resolveKitConfig`: defaults and validation) and the caller workflow release check (`checkCallerWorkflow`), which `checkKit` makes together. All are pure; every run, the Kit job's included, calls them before anything else, so no agent starts on an invalid Kit. `src/kit/pushJob.ts` decides what the push job applies from how the jobs before it ended.
- `src/github/` holds the thin **GitHub adapter**: `events.ts` maps an Actions event, or what an agent job passed out, to a Loop event; `snapshot.ts` gathers the snapshot, reading the Kit's comment markers back through `threads.ts`; `apply.ts` applies the plan; `client.ts` is the API client.
- `src/read/` holds the **read library**: `index.ts`, its one entry, re-exports what another program may use to read the Kit, and nothing else (see [Reading the Kit from another program](#reading-the-kit-from-another-program)). `exports.fixture.ts` names every export with a call or a value of each, and the tests beside it hold the entry to it, walk the entry's imports, and run every call as a Worker would.
- `src/main.ts` is what the push, claim and Dispatch jobs run (`node src/main.ts`, Node 24, no build step and no runtime dependencies). In the push job (`FABRIK_NEEDS`), it applies an agent job's output, or its failure notice, instead of the Actions event.
- `src/agent/` holds the **agent job** runner (`node src/agent/run.ts triage`, `design`, `prototype`, `implement`, `review`, `audit`, `retro`, `research` or `digest`): Sandcastle with `noSandbox()` on the runner VM, the metered-billing preflight as the last `onSandboxReady` step, the `init` check, the step summary, and the role's output passed out as `agent-result.json`. Only agent jobs install the runtime dependencies (Sandcastle, the Claude Code CLI and Playwright, pinned exactly).
- `src/evidence/` holds **Visual evidence** (see `ui` in the [Kit config](#kit-config)): `uiEvidence.ts` is the pure UI evidence module (whether a PR is UI, which routes to capture and why, the capture result every later reader shares, the Reviewer's images, and the PR body's evidence section and its marker), `shotsEvidence.ts` its parts for a Product repo that uses Evidence shots (the names rule, the shots section and marker, the Kit's words for an Evidence miss, and the Reviewer's block of named shots), `evidencePage.ts` the Evidence page and a Prototype's, `shotsManifest.ts` the pure reader of an Evidence shots manifest and the artifact's rules (see [Evidence shots](#evidence-shots)), `capture.ts` the pure capture core, and `capture-main.ts` the capture step of the Implement job and of a prototype turn, the one Kit program that imports Playwright. `src/kit/previewLink.ts` is the push job's preview steps, which its `link-preview` action runs for a UI PR (`src/kit/preview-main.ts`) and its `link-prototype-preview` action for a prototype round, the same program given the round.
- `src/review/` holds the Review checks job's step (`node src/review/wait.ts`), which waits for an agent PR's required checks, and the pure rule for how they ended, and the review job's Evidence shots steps (`node src/review/shots-main.ts find|read`), which find the named check's run at the head and read its artifact (`shotsRun.ts`, `shotsRead.ts`, and `src/evidence/shotsCollect.ts`, the pure reading against a PR's names).
- `src/preflight/` holds the metered-billing preflight (pure) and the command the hook runs.
- `src/skills/` and `skills.lock.json` pin Matt Pocock's skills, the Base skills, at a commit SHA and install them into a Product checkout's gitignored `.claude/skills/` (ADR-0003), beside the Extra skills a Product repo picks from its own Skills sources (ADR-0008, see [Extra skills](#extra-skills)). `src/skills/fetch.ts <product checkout> [role]` installs them; `src/skills/pinnedManifests.ts` is the Kit job's check of the picks against each source's manifest at its pin.
- `src/skills/bump.ts` decides the weekly skills bump PR (`.github/workflows/skills-bump.yml`), with the upstream diff in its body; `src/skills/bump-main.ts` is its step. The same planner decides a Product repo's bump PRs for its own Skills sources, which `src/skills/sourceBumps.ts` pushes from the scheduled tick (`src/skills/source-bumps-main.ts`, gated by `src/skills/source-bumps-due.ts`).
- `src/release/` checks that each release pins Sandcastle, the Claude Code CLI and Playwright at exact versions, which Dependabot bumps (`.github/dependabot.yml`). See [docs/releasing.md](docs/releasing.md) for the release process.
- `src/kit/jobs.ts` is the Kit job's step: it checks the Kit config and the caller workflow's pins, asks the Loop rules core what the event calls for, and routes it to an agent job (when the plan starts an agent run), to the push job, or nowhere. The Kit job's last step does nothing, and its name is one line of JSON saying what the job routed, held and declined included (`src/kit/kitSaid.ts`).
- `prompts/` holds the Kit's agent prompts, and `prompts/scorers/` the Scorers' versioned rubrics (Efficiency, Ticket compliance and Test-first), which `src/kit/kitFiles.ts` reads and `src/kit/rubrics.ts` parses. A rubric changed without a version bump fails its tests' version guard. The `run-judge` action has the Kit's fixed judge model, at its fixed `medium` effort, apply them to a finished Implement run's transcript, with no tools and no write credential (`src/kit/judge-main.ts`), and the `write-score-record` action writes the score file and the judge's own Run record to `fabrik-runs` (`src/kit/score-record-main.ts`), which, like `src/main.ts`, imports no runtime dependency: a test holds every program an action runs without `npm ci` to that. `loop.yml`'s judge job (`score`) and score-record job run them.
- `.github/workflows/loop.yml` is the reusable workflow a Product repo calls. It holds wiring only. The steps its jobs share are composite actions in `.github/actions/`: `prepare-agent` readies an agent job (installs the Kit, fetches the skills, and reads the agent's inputs through `src/agent/inputs.ts`), and `run-loop` runs the Loop as the Fabrik App. After it, the push job's `write-run-record` writes the run's Run record and transcript to the `fabrik-runs` store (`src/kit/runRecord.ts`, `src/kit/recordWriter.ts`, ADR-0009), with the store token its `store-token` action mints, as `write-score-record` does. It never fails the push job, and a Product whose Operator hasn't set up `fabrik-runs` gets one step-summary line saying so. For a record in the store, the same step runs the Scorers' scoring plan (`src/kit/scorer.ts`, `src/kit/scoreRecord.ts`): it writes a skipped run's score file itself, and for a picked run the judge job (`score`) and then the score-record job, the judge run's own push job, run after the push job. Nothing in the Loop waits on them, and Dispatch never counts the judge job as an Implement run.
- `.github/workflows/schedule.yml` is the reusable scheduled Tick the caller workflow runs hourly, for the Loop's time-based rules (closing the weekly-limit issue after its reset and, with Subscription rotation on, resuming the runs held until then, opening the week's pending Audit and pending Retro, and taking the Replays' next step), a Dispatch check and a Design queue check, once a week the Product repo's skills bumps, and in a job of its own the Monitor. Any run of it closes the repo's open Dead-tick issue (`deadTickClosed` in `src/loop/kitIssues.ts`), naming the release it ran on. Like the push job, it never touches Product code.
- `src/monitor/` holds the **Monitor**, which the scheduled tick runs hourly in its own job, with no model call and no Run record: `core.ts` is the pure Monitor core (what it files, rewrites, holds and closes, and the step summary's lines), `redMain.ts` its red-main part, `issues.ts` what both parts share of a Monitor issue and its body, `sentry.ts` the pure Sentry translator, `sentryApi.ts` the Sentry API reads, and `main.ts` the thin program that gathers the facts, with the GitHub reads in `src/github/monitorFacts.ts`, and applies the plan. `errors-set.ts` is the job's gate, so the Sentry token loads only when the Kit config sets `monitor.errors`. See `monitor` in the [Kit config](#kit-config).
- `.github/workflows/weekly-summary.yml` is the reusable Weekly summary the `fabrik-runs` store's caller runs each Monday morning. Its `file-weekly-summary` action reads the store's Run records, its score files and every Product repo's GitHub facts (`src/github/facts.ts`), builds the summary (`src/kit/weeklySummary.ts`, its metrics read through the Retro evidence module, `src/kit/retroEvidence.ts`) and files it in `fabrik-runs` (`src/kit/weeklyFiling.ts`). Its **Scores** section, shown only in a week with score files, gives each rubric version's runs scored, median score and share passing against last week, the skips by reason, and what scoring cost as a share of the week's cost, which cost per merged PR and per Spec leave out. Cost per merged PR and spend that never merged each sum a Ticket's Implement, Review and Digest runs. It never lists a run's own scores. Each repo's section has a **Loop** line (`src/kit/loopHealth.ts`, read by `src/github/loopHealthFacts.ts`): the week's runs of `fabrik.yml` that never started (`startup_failure`) and that failed or timed out, from the Actions API with the Fabrik App's Actions: read, and the last started Tick, read as the daily Tick check reads it. A repo whose Tick hasn't started in 25 hours has the line lead its section, saying the waits below include time the Loop was down, and an unhealthy Loop keeps a week from being quiet. Without Actions: read the summary still files, and the line says the run counts are unread. Each repo's **Waiting on you**, **Stuck** and **Held** are read off its Standings (`src/kit/standing.ts`), never off the Run records, which feed only the metrics. Waiting on you is every Standing whose move is yours, oldest first, but a weekly-limit issue, which stays under Held, and a Map's Decisions, folded into the Map's line. A `ready-for-human` issue, a Map or a grilling, prototype or task Decision blocked by an issue in any repo that is open or closed as not planned, or by one in a repo the Fabrik App can't read, isn't yours: it stands blocked, nobody's move, until that blocker closes (#770, #771). Its line names a blocker in another repo as `owner/name#N`, and counts the ones the Fabrik App can't read. A Decision goes by its own blockers, never its Map's: one with none on a blocked Map is listed by itself, and a Map's line counts only its unblocked Decisions; of the Plain pull requests only one ready to merge is listed. Work the Kit handed back is there from the moment its notice says so: a run that ended in an Infrastructure failure, a Broken run that used no retry, a trigger label the hourly check took off, and a draft you put back in draft after its pass among them. A pull request at the Merge gate stays there whatever you comment or approve after its pass: only a Request changes hands the move back to the Kit. **Stuck** is work whose next move is the Kit's, with nothing running or held, that the Kit has made no sign on for longer than its own recoveries take. Each Product repo has one bar, worked out from its own Kit config: the slowest recovery's wait plus two hourly Ticks (`stuckBarMinutes` in `src/loop/recoveryWaits.ts`), which is 3 hours 30 minutes on default timeouts (the Implement job's 90-minute timeout, which the unstarted-Retry and undelivered-Request-changes checks wait out, plus 120), and longer with a longer Implement or Review timeout. Only the Kit's own signs restart the clock, its comments, labels, pushes and draft changes; your comment on a lost draft doesn't. Each Stuck line, longest first, says what the Kit last asked for and what to do. When the runs in progress can't be read, the summary still files, and a Stuck section that lists anything opens by saying a run may be working on some of them. It never touches Product code either.
- `.github/workflows/tick-check.yml` is the reusable daily Tick check the `fabrik-runs` store's caller runs every morning at the same time, since a dead Tick can't be watched from its own Product repo (ADR-0009's addendum). Its `check-ticks` action mints one Fabrik App token on every installed repo with Checks read, Contents read and Issues write, reads each Product repo's last started Tick (`src/github/tickFacts.ts`) and the store's recent Run records, and opens or closes the Dead-tick issues the Dead-tick module plans (`src/kit/deadTick.ts`, run by `src/kit/dead-tick-main.ts`): a `fabrik:dead-tick` issue in each Product repo where no Tick has started for 25 hours, and one in `fabrik-runs` for each Product repo the App can no longer reach. A store caller written before it has no daily schedule, so nothing runs until Setup rewrites it. Setup moves a store caller pinned to an earlier release in the same major up to its own release, so its Tick check job never names a workflow its pin doesn't have.
- `src/loop/kitIssues.ts` holds the Kit-owned issues: the "Rotate the Claude token" issue (label `fabrik:token-rotation`) and the weekly-limit issue (label `fabrik:weekly-limit`), each one per Subscription with rotation on, and the usage-credits issue (label `fabrik:usage-credits`), which buzz the Operator once per repo, or once per limit window, instead of once per Ticket. `src/loop/subscriptions.ts` chooses each run's Subscription (see `subscriptions` in the [Kit config](#kit-config)), `src/loop/heldRun.ts` names the runs held while every Subscription is used up, and `src/loop/resume.ts` resumes them once one is free.
- `src/loop/audit*.ts` holds the Audit (label `fabrik:audit`, see [Audit](#audit)): the audit gate the scheduled tick runs (`auditGate.ts`), the pending Audit's Auditor run (`audit.ts`), the Audit output parser (`auditOutput.ts`), filling the Audit in (`auditLanding.ts`), and starting and failing its run (`weeklyRuns.ts`, which starts and fails a Retro run the same way).
- `src/loop/retro*.ts` holds the Retro (label `fabrik:retro`, see [Retro](#retro)): the retro gate the scheduled tick runs (`retroGate.ts`, with what it shares with the audit gate in `weeklyGate.ts`), the pending Retro's run (`retro.ts`), the Retro output parser (`retroOutput.ts`), and filling the Retro in (`retroLanding.ts`). Its evidence bundle is built by the pure Retro evidence module, `src/kit/retroEvidence.ts`, from what `src/kit/retro-evidence-main.ts` reads in `loop.yml`'s Retro evidence job (the `gather-retro-evidence` action), and the Retro job (the `run-retro` action) runs the agent on it.
- A Replay (labels `fabrik:replay` and `agent:replay`, see [Replay](#replay)): the pure Replay module, `src/kit/replay.ts`, reads the request (`src/kit/replayRequest.ts`), picks the Tickets and gives each its two arms (`src/kit/replayPick.ts`), and keeps the plan, progress and results in the replay issue's body. The scheduled tick's replay step and spare-capacity gate are `src/loop/replayGate.ts`, on the slice `src/github/snapshot.ts` and `src/github/replaySlice.ts` gather from a checkout of the store the tick's `replay-store` action makes only while a replay issue is open. `src/loop/replayRun.ts` starts a Ticket's run and lands it. In `loop.yml`, the claim job, each arm's `replay-implement`, `replay-gates`, `replay-review` and `replay-score` jobs and the `replay-record` job run the actions of the same names.
- `src/loop/research*.ts` holds the Researcher (labels `agent:research` and `wayfinder:research`, see [Maps](#maps)): starting its run on a research Decision (`research.ts`, whose rule for which Decisions it may run on Dispatch and the Weekly summary share), the Decision's branch and findings paths (`researchPaths.ts`), the research output parser (`researchOutput.ts`), and landing the findings (`researchLanding.ts`), whose line on the Map `decisionsSoFar.ts` appends. `src/loop/mapCap.ts` is the Map cap, which the Design turn's landing, its inputs and the Weekly summary share, and the Design session's `map` outcome lands in `design.ts`.
- A Design session's Prototypes (see [Prototypes](#prototypes)): `design.ts` posts the prototype request and starts the prototype turn it asks for, `src/github/threads.ts` reads the session's pending request back, `src/agent/prototype.ts` is the runner's prototype mode, on `prompts/prototype.md`, and `src/loop/prototypeLanding.ts` lands the turn: the Trust-root guard, the push of `prototype/<issue>`, and the prototype round or its failure round.
- `templates/fabrik.yml` is the caller workflow a Product repo installs as `.github/workflows/fabrik.yml`. Its `run-name` names each run on the Actions tab for what it starts and on which issue or PR, such as `Implement #12`, `Review PR #60`, `Triage #87` or `Tick`, or else for its event, such as `#87 labeled bug` (#477): GitHub names a run from the caller only. A Product repo set up before it gets the names by updating its `.github/workflows/fabrik.yml` from `templates/fabrik.yml`; until then every run shows as `Fabrik`, though the Implement and Review jobs still name their Ticket and PR.
- `templates/claude-settings.json` holds the `SessionStart` hook entry a Product repo merges into `.claude/settings.json`, and disables the `mattpocock-skills` plugin there. The entry reads the release from `fabrik.yml`, downloads Fabrik at that tag (public, no credentials) and runs `src/session/start.ts`, which installs the skills that release's `skills.lock.json` pins, the same commit the Kit step installs in Actions, plus Fabrik's own `skills/` (`fabrik-live-design`, `fabrik-pair` and `fabrik-visual-evidence`). It also removes the `fabrik-setup` skill earlier releases installed there, and warns the Operator while their personal skills hold an old copy of it.
- `setup.sh` is the bootstrap script the Operator's Setup command runs (see [Adopting the Kit](#adopting-the-kit)): it downloads a release into a temporary folder, runs that release's setup program on the Operator's terminal, and deletes the folder afterwards.
- `src/setup/` is that setup program: `program.ts` runs the checks, asks the questions and shows the plan, `oneRun.ts` is one run's order from the Operator's yes to the setup PR, `plan.ts` is the pure planner (what a Product repo holds now in, the steps it's missing out), `shims.ts` merges the Kit-owned files into the Product's own, `gather.ts` and `apply.ts` read and change the repo and 1Password with `gh` and `op`, and `wizard.sh` is the wizard it runs for the steps only the Operator can take. `templates/` holds what it installs. Beside it, `visualEvidence.ts` is the pure Visual evidence writer, and `visual-evidence-main.ts` the program `/fabrik-visual-evidence` runs it through, which needs no `gh` admin and no `op`.

## Adopting the Kit

The Operator adopts the Kit in a Product repo by running Setup in their own terminal, from the root of the repo's clone, on its default branch:

```sh
curl -fsSL https://raw.githubusercontent.com/jrey8343/fabrik/main/setup.sh | bash -s --
```

There's nothing to copy or install first. `setup.sh` checks for Node 24.3 or later and `gh`, downloads Fabrik's latest release into a temporary folder, runs that release's setup program, and deletes the folder whatever the outcome. To set up another release, name it after the `--`, as an exact tag such as `v1.0.0`:

```sh
curl -fsSL https://raw.githubusercontent.com/jrey8343/fabrik/main/setup.sh | bash -s -- v1.0.0
```

`--release=v1.0.0`, anywhere after the `--`, names it too. `setup.sh` refuses an empty `--release=`, two different releases, and a tag that isn't exact, before it downloads anything.

Setup's flags go after the release, if one is named: `--account=<1Password account>`, `--time-zone=<IANA zone>`, `--second-subscription`, `--paused`, `--production-url=<address>`, `--production-environment=<environment>`, `--no-production`, `--staging-url=<address>`, `--staging-environment=<environment>`, `--no-staging` and `--plan`. The time zone's, the second Subscription's and pausing's flags also have a `--no-` form, an empty value answers no (an empty `--production-environment=` names no environment, and an empty `--staging-environment=` leaves staging out, since staging needs one), and Setup asks only what the flags left out.

Setup first checks that it's in the clone's root, on the default branch, clean and the same as on `origin`; that `gh` is signed in as the repo's admin with the `workflow` scope; that `op` is signed in as the Operator, not as a service account (it stops when `OP_SERVICE_ACCOUNT_TOKEN` is set); and that Node is 24.3 or later. With several 1Password accounts it asks which one holds this Product's secrets, offering the one `OP_ACCOUNT` names, if it's set, for an Enter; without a terminal, `OP_ACCOUNT` or `--account=` names it. Then it asks five questions: the Operator's time zone, offering the one `fabrik-runs` holds, else the Kit config's `time_zone`, else this machine's, which it writes both to the store's caller, for the Weekly summary, and to the Kit config's `time_zone` (ADR-0023), whether to add a second Subscription (not when the Kit config already lists two or more, which Setup leaves as they are, or lists `Claude token 2`), whether to pause Dispatch, where production is, for the Kit config's `production` block, and where staging is, for its `staging` block (each only while the Kit config declares none). For production it reads the repo's Deployments with the Operator's `gh` and offers an environment, `production` when the repo has Deployments by that name, else the only one it has, else a choice among them, then an address, `ui.before_url`, else the one on that environment's newest successful Deployment. A repo that reports no Deployments is told that merged work won't be followed to production until its deploy runs from an Actions job that names an environment, and gets the address alone, with `environment` null; a refused read of the Deployments is one line, and the question goes on. Without a terminal, `--production-url=` alone writes the address with `environment` null, and without it no block is written. For staging it offers, from the same read of the Deployments, the environment named `staging` when the repo has one, else a choice among the others it has, by number or by name, or takes a name the Operator types. It never offers the environment production's deploys carry, and never another environment for an Enter, since a repo's only other one is as likely its previews'. Then it offers an address, the one on that environment's newest successful Deployment. `staging` needs both, so none for the environment or no for the address leaves the block out, and without a terminal only `--staging-url=` and `--staging-environment=` together write it. It shows its plan, naming the 1Password account on the first line. With `--plan`, or without a terminal, it stops there. On the Operator's yes it applies the plan on the branch `fabrik/setup-<release>`, runs the wizard, then commits, pushes and opens the setup PR with the files:

- **Kit-owned files**, put back whenever they drift: `.github/workflows/fabrik.yml` with every Fabrik `uses:` line pinned to the release, the `SessionStart` hook entry and the `mattpocock-skills` plugin switched off in `.claude/settings.json`, `.claude/skills/` in `.gitignore`, and a `.github/dependabot.yml` entry that bumps only the Fabrik pin, every pinned Fabrik workflow in one grouped PR, with no cooldown, and never to a major, which arrives only through Setup. Each is merged into the Product's own file. A caller pinned to an earlier major is migrated; within a major, Dependabot owns the pin. On a pull request that changes the caller, a bump PR say, the Kit job checks that each job grants what the workflows at the release it pins ask for, and fails the PR's `loop / Kit` check naming the job and the line when one doesn't, since a caller that grants too little fails every run at startup (ADR-0003).
- **Starters**, written once and the Product's from then on: `.fabrik/config.json` with every v1 default, `docs/agents/*` with Fabrik's fixed answers (GitHub Issues, the triage labels plus `needs-design`, a single-context glossary and ADRs), and an `## Agent skills` block pointing at them in `CLAUDE.md`, or in `AGENTS.md` when there's no `CLAUDE.md`.
- **Labels**: `needs-triage`, `needs-info`, `needs-design`, `ready-for-agent`, `ready-for-human`, `wontfix`, `agent:implement`, `agent:design`, `agent:review`, `agent:digest`, `agent:rerun-checks`, `agent:research`, `agent:replay`, `bug`, `enhancement`, `fabrik:token-rotation`, `fabrik:weekly-limit`, `fabrik:usage-credits`, `fabrik:audit`, `fabrik:retro`, `fabrik:replay`, `fabrik:dead-tick`, `fabrik:monitor`, `fabrik:flaky-check`, `fabrik:step-up`, `fabrik:kept-branch`, `fabrik:trial-accepted`, `fabrik:trial-problem`, `wayfinder:map`, `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling` and `wayfinder:task`.
- **1Password** (ADR-0004): the `Fabrik`, `Fabrik App` and `Fabrik Sandbox · <repo>` vaults when they're missing, and three read-only service accounts with no expiry, `fabrik-<owner>-<repo>-agent` (reads `Fabrik`), `-implement` (reads `Fabrik` and the Sandbox vault) and `-push` (reads `Fabrik App`), stored as the Actions secrets `FABRIK_OP_AGENT_TOKEN`, `FABRIK_OP_IMPLEMENT_TOKEN` and `FABRIK_OP_PUSH_TOKEN`.
- **Branch protection** on the default branch: a PR, the checks in `sandbox.checks` (plus any already required), no bypass allowance for anyone, and admins held to the rules, so the [Merge gate](#merge-gate) holds the Operator too. No approving review is required, since the solo Operator can't approve their own PRs. Those are the only settings Setup changes, and its plan names each change, from what to what, such as `admins held to the rules: no → yes`. Holding admins to the rules is the Kit's rule, not a choice per repo: there's no flag and no Kit config key for it. Every other setting Setup leaves as it finds it, strict checks, linear history and conversation resolution included.
- **The Merge gate ruleset** (`Fabrik Merge gate`): only repo admins may update the default branch, merging a PR included. The Operator owns the repo, so only they can merge; the Fabrik App, never an admin, can't.

With `--paused`, or a yes when Setup asks, the starter `.fabrik/config.json` is written with `max_in_flight: 0`, every other byte as the starter has it, so Dispatch starts no Implementer until the Operator raises it (see `max_in_flight` in the [Kit config](#kit-config)). Without it, Dispatch starts on the repo's open `ready-for-agent` issues as soon as the setup PR merges, and the plan's notes say how many there are. `--paused` changes only the starter: a Kit config the repo already has is left alone, and the plan's note gives its `max_in_flight` to set to `0` by hand. Until the setup PR merges, the starter on `fabrik/setup-<release>` is still Setup's own: a later run there asks again, offering what the starter holds, and sets its `max_in_flight` to `0` or back to the v1 default to match. The setup PR and Setup's last lines say when the Kit config the PR merges pauses Dispatch.

The wizard (`src/setup/wizard.sh`, made with the `wizard` skill) runs in the same terminal, for what only the Operator can do: installing the Fabrik App on the repo (Issues, Pull requests and Contents, plus Checks: read for the Monitor's red main and Actions: read for the Weekly summary's Loop line; no `workflows`) and storing its `client-id` and `private-key` in the `Fabrik App` item; `claude setup-token` into the `Claude token` API Credential in the `Fabrik` vault, with its expiry; a Sentry token (`event:read` and `project:read`) into the `Sentry token` API Credential in the `Fabrik App` vault, one token every Product repo in the 1Password account shares, which is harmless to store before the repo reports to Sentry (the Monitor reads Sentry only once `monitor.errors` names a project) and fine to skip until then; GitHub mobile pushing only mentions, assignments and review requests, with Actions off; and watching the repo on All activity. Setup asks for the setup PR's merge only once the Fabrik App is installed on the repo, its key stored and the token of the first Subscription the Kit config lists in `subscriptions` stored, the Claude token in the starter: the first runs read that one, and the Kit moves to a later one only once those before it are used up. A later Subscription's missing token is a note in the plan instead. Until then the PR says which of them is missing, and running Setup again walks the wizard for them, apart from a Subscription listed under a name no wizard stage stores, whose token the Operator stores by hand.

Once the setup PR is merged, Setup's command is the way back to the wizard. On the default branch with nothing to apply, Setup checks what a wizard stage stores that 1Password lacks: the App's key, the Claude token while the Kit config lists it, the second Subscription's token, `Claude token 2`, once the Kit config lists it, or lists one Subscription and the Operator says yes to a second, and the Sentry token once `monitor.errors` names Sentry. The wizard stores no other Subscription's token, so one the Kit config lists under another name, such as a third or one listed alone, is a note in the plan to store by hand. With none missing, it says the install is complete and walks no wizard. Otherwise it names each one and asks whether to walk the wizard now (no, unless the Operator says yes). Then it reads 1Password again and plans again. A file that plan writes, such as the `subscriptions` line once `Claude token 2` is stored, goes in a setup PR as on any run. With no file to write there's no setup branch or PR, and Setup says what's still missing, or that the install is complete. Without a terminal, or with `--plan`, it names what's missing and says to run Setup in a terminal. Setup can't read the App's install or the last two stages, which are GitHub settings, so it never walks the wizard for them alone. To set them by hand: in the GitHub mobile app, under Profile → Settings → Notifications, turn push on for Direct mentions, Assigned and Review requested, and off for Actions; then on the repo's page, click Watch → All Activity.

Every Product repo in this 1Password account, the one Setup uses, shares its `Fabrik` and `Fabrik App` vaults, and with them the App key, the Claude token and the Sentry token. So on the next Product repo in it, the wizard finds them already stored. One 1Password account per Product is a normal setup too. A new account holds none of them yet, which the wizard says is expected, and the wizard stores them there.

Setup leaves Visual evidence off. Once the setup PR is merged, the Operator turns it on by running `/fabrik-visual-evidence` in a Claude session in the repo, where the `SessionStart` hook has installed it (see `ui` in the [Kit config](#kit-config)).

Running Setup again on a working install changes nothing, once 1Password holds what the wizard stores. On a broken one it repairs only what's missing: a missing label is created, a missing secret gets a new service account (1Password shows a token only once, so delete the old account by hand), and a default branch whose admin enforcement was switched off by hand, as for the way past the [Merge gate](#merge-gate), is made to hold admins to its rules again. A repair that writes no file opens no setup PR, and leaves the clone on the default branch, brought up to date with `origin`'s. After a run that stopped partway, Setup picks up on its `fabrik/setup-<release>` branch, and says to switch to it when the clone is on the default branch. A setup branch, the clone's or `origin`'s, is done with once merging it into `origin`'s default branch would change nothing, or, with no setup PR open from it, once it's a head a merged setup PR from it had, or a commit before one: the PR's last head, or one a force-push replaced, as GitHub's "Update with rebase" does. Then Setup starts the branch again from the default branch, so a squash or rebase merge leaves nothing to pick up. To migrate to a new major release, name that release:

```sh
curl -fsSL https://raw.githubusercontent.com/jrey8343/fabrik/main/setup.sh | bash -s -- v2.0.0
```

Setup never moves a caller workflow back to an earlier major, and within a major Dependabot owns the pin.

Setup was once the `fabrik-setup` skill, copied by hand into `~/.claude/skills/`. A copy left there is stale: Setup offers to delete it, and the `SessionStart` hook warns while it's there.

## Reading the Kit from another program

Another program can know what the Kit knows (where each piece of work stands, the Run records, a repo's Kit config and the release its caller workflow pins) by running the Kit's own reading of it, with its own credential, rather than a second definition of what a label, a marker or a Verdict means. That reading is the **read library**, and its one entry is `src/read/index.ts`: the only address the Kit promises. Anything it doesn't export can move or change in any release.

- **There is no package.** The Kit isn't published anywhere. A reader downloads the Kit's source at the release tag it pins (say `https://github.com/jrey8343/fabrik/archive/refs/tags/v1.3.0.tar.gz`) into a directory it does not commit, and imports the entry by path. The repo is public, so the download needs no credential. Moving the pin is the reader's own change, and its checks are where a break shows.
- **Nothing to install.** No module the entry reaches imports an npm package, and the only Node built-ins it imports are `node:crypto`, `node:path` and `node:fs/promises`, the three seen to load in a Worker with Node.js compatibility on. None of its calls reaches `path.posix.matchesGlob`, which a Worker doesn't implement.
- **Hand it a client.** Every read takes a `ReadClient`, the three calls the Kit's GitHub client makes: a REST call, a GraphQL query, and a file's text at a ref. The Kit's own `GitHub` class is one; a reader can hand in its own, one that counts what a read costs or refreshes its credential.
- **Files at a commit.** `readFiles` reads several paths of one repo at one commit in one GraphQL query, made through the client's own `graphql`, and gives each as its text or as null for no file, the text the client's file read gives. A path with nothing at it, a directory and a submodule are each no file. A file GitHub won't give whole in a query (a binary one, or one it truncates), and a symbolic link, whose text in a query is the path it points at, is read singly by the client's file read. To know a link, the query also asks for the whole listing of each directory the paths are in, each entry's name and mode, so its answer grows with how many entries sit in those directories, not only with how many paths were asked: a reader that reads one large directory's files in batches is given that directory's whole listing with every batch. It throws a refusal of the query or of a file read, and asks nothing for no path. The gather reads a repo's caller workflow and its Kit files with it, at the default branch's head its first query gave, so a gather of a Product repo whose files are all text makes no REST request; a refusal of that query fails the gather, as a refused read of the caller workflow did (#895).
- **Plain data.** Every value a read or a rule returns comes back equal after being written as JSON and read again, so a reader can keep it, or serve it from a fake GitHub in its own tests.
- **Read back what you kept.** A reader that keeps rows or Standings across a move of its pin reads them back through `readRow` or `readStanding` before handing them to anything else, and holds no step of its own between releases (ADR-0020).
  - **`readStanding`** gives a kept Standing at the current schema, `STANDING_SCHEMA`: one already at it as it is, and one of any earlier schema brought forward. A schema 1 `blocked` Standing, which kept its own repo's Blockers by number, names each by the Standing's own repo, with none hidden.
  - **`readRow`** reads each Standing a kept row holds the same way, its own and, on a Pairing session's row, the issue's own under `plainPullRequest.own`, and gives a row kept before a field was added that field with none of it: `shots` is null on a row kept before v4.1.0. A Follow-up kept before it had a `kind` reads as an idea, as every Follow-up was then a link (#885). `staging` is an optional key, on a row only in a repo whose Kit config declares `staging`, so a row kept before it has none and reads as it was kept. Every other field is as it was kept.
  - **Null** from either is something that didn't read: not a Standing or a row at all, or one a newer Kit wrote than the reader pins. `newerStandingSchemaOf` gives a kept Standing's schema when it is newer than `STANDING_SCHEMA`, and null otherwise, so a reader can say which. Neither checks more than the schema.
  - **A Standing of another schema is refused.** Every export that takes a kept Standing or kept rows (`wordStanding`, `standingAt`, `joinRuns`, `joinChecks`, `joinDeployments`, `joinStaging`, `headsToCheck`, `mergesToRead`, `stagingMergesToRead`, `commitsToCheck` and `owedRollInsOf`) throws when a Standing it is given, or one a row holds, has a `schema` other than `STANDING_SCHEMA` or none, and the error names the Standing's schema, the Kit's and `readStanding`. A schema 1 Standing that isn't `blocked` is refused too, though only its `schema` differs.
- **What a reader's toolchain needs:**
  - imports with a `.ts` suffix, as the Kit's modules import each other: TypeScript's `allowImportingTsExtensions`, with `noEmit` or a bundler that resolves them;
  - Node.js compatibility on in the Worker (the `nodejs_compat` compatibility flag);
  - Node's types beside the Workers types, since the Kit's modules import from `node:`;
  - a `lib` of ES2023 or later;
  - its own tests kept off the Kit's: the downloaded directory holds the Kit's `*.test.ts` files, which the reader's test runner leaves out.
- **The promise.** The library reads whatever any earlier release wrote: a Run record of any earlier schema reads at the current one through `readRunRecord`, so does every marker the Loop already reads back, and so does a Standing or a row the library gave at an earlier release and a reader kept, through `readStanding` or `readRow`. A test holds the name and a value of everything the entry exports. A release that removes any of it, or changes what one means, is a major ([Choosing the version](docs/releasing.md#choosing-the-version)); a new export, a new field or a new Standing name is not, so a reader leaves alone what it doesn't know.
- **Runs in flight.** `readRuns` reads a repo's Actions whole: every workflow run created in the last 24 hours, a page for each hundred, one listing of each unfinished run's jobs, and the Tick's scheduled runs. Its 24 hours are counted back from the `now` it is handed, or from the clock when that is no time. Its listing's `created` bound is rounded down to the hour, so the listing is asked at one address all hour and a reader that asks conditionally is answered from what it holds; a run from before the 24 hours, to the second, is left out after the listing, so the answer is the one a bound to the second gave (#898).
  - **Named runs.** A reader that knows which workflow runs changed, from a job's delivery say, asks `readNamedRuns` about those alone: two requests at most for each, the run and, while it is unfinished and inside the 24 hours, its jobs, and none for the Tick. Each run comes back with the runs in flight it tells of, by the rule `readRuns` tells them by: none once it has ended, when it routed no agent run, or when it is older than the 24 hours. A run GitHub refuses is `"unread"`, that run alone, and the read never throws.
  - **The fold.** `foldNamedRuns` puts a named read into the runs read a reader keeps, by the Kit's rule: each run read has its entries replaced by the answer's, so one that ended has none, and an unread run, every run not named, the Tick and the kept read's `readAt` are left as kept. Runs kept unread stay unread. The answer folded in last wins, whenever it was read, so a reader folds its named reads in the order it made them: two reads of one run awaited side by side and folded out of that order can put back a run that has ended. A named read never finds a run nobody named, so a reader still makes the whole read now and then.
- **Evidence shots.** On a Product repo whose Kit config sets `ui.shots` (see [Evidence shots](#evidence-shots)), an agent pull request's row carries its named shots under `shots`, from the shots marker in its body, where a route marker's row carries its captured routes under `evidence`, which is then null. A row with a route marker is as it was, with `shots` null.
  - **On the row.** `shots` has the `head` the pictures are from, the one the named check ran at (null while the section waits for it), the Review `run` and `artifact` that hold the Evidence page, the `failure` when nothing of the run could be read (`no-artifact` or `bad-manifest`, the Product repo's wiring), what came of the `preview`, the Implementer's `nothingVisible` sentence, in its own words, when that is what the pull request has, with no shots, and `nothingNamed` when it has neither. `named` is each name in the pull request's order, with its `journey` and `path` once the artifact has been read, whether it was `produced`, and `missed`: why not (`not-produced`, `ambiguous-name` or `refused`), or each size it lacks (`size-missing` and its `viewport`). A shot with a `path` has a `preview` link when the preview is linked and, on a merged pull request's row in a repo whose Kit config declares `production`, a `production` link, each built as a captured route's is; a shot with no `path` has neither. `producedNamedShots` gives a shots marker's produced names, the ones a Digest's picture may name.
  - **A pull request with no section.** The Kit writes a section only on an agent pull request it reviews, so a Plain pull request, a Pairing session's among them, has no named shots on its row, and an agent pull request's section keeps saying which head its pictures are from when the Operator has pushed another at the Merge gate. A reader gets a head's shots straight from the named check's artifact, as the Kit does: the newest attempt of the check `ui.shots.check` names, among the Actions runs at the head, and the artifact named `ui.shots.artifact` (`DEFAULT_SHOTS_ARTIFACT`, `fabrik-evidence-shots`, when the block names none) that attempt's run uploaded. The fetch is the reader's own, with its own credential, as for a capture result. It unzips the artifact and hands `readShotsManifest` the text of `SHOTS_MANIFEST_FILE` (null when the artifact has none) and each other file's name, size and first bytes, and gets the shots that passed the artifact's rules and each entry dropped with its reason (`DROP_REASONS`, worded by `droppedShotSentence`). `namedShots` then answers, for a list of names, which were produced and at which sizes, or why not. `shotsMarkerIn` reads a shots marker from a body, which counts only when the Fabrik App wrote it.
- **The Digest.** A reader gets a pull request's [Digest](#digest) as data, or that none is readable, and never reads the comment's hidden lines or its Markdown itself, so the Kit can change how the data rides with no change to a reader (ADR-0022).
  - **On the row.** The row of every open agent pull request has `digest`, worked out from the comments the gather already reads, with no further request; every other row's is null. It is always about the pull request's current head: the newest Digest of the Fabrik App's whose head is that head, or the Kit's no-Digest line for that head, whichever is newer, and never a Digest for an earlier head. It is one of four: `readable`, with the `head`, `carriedFrom`, when the comment was posted (`at`), its `url`, the top as `data` and the `folds`, the comment's Markdown from the folds line down, which a reader renders; `unreadable`, with why and the comment's `markdown` as GitHub would render it, its hidden lines left out; `not-written`, with how the attempt ended, from the no-Digest line; and `none`, a head nothing names, such as a draft still in the Loop, a pull request with the Digest off or one from before the release. With anything but `readable` a reader draws nothing from the Digest, and nothing is ever worked out from Markdown.
  - **Unreadable** is `unknown-version`, a data line at a version the library does not know; `malformed`, one that does not parse, is not the shape its version names or is not there; or `edited`, a Digest whose body GitHub records an edit of after it was posted. The Kit never edits a Digest, so an edit is a person's. It is told from GitHub's own record of an edit to the body (`lastEditedAt`), never from when the comment was last updated, which collapsing a comment moves: a collapsed Digest nobody edited is `readable`.
  - **The last hundred comments.** The gather reads the last hundred comments of a pull request. A Digest is posted as the pull request reaches the Merge gate, so it is among them unless a hundred comments follow it, when the row says `none`.
  - **The places' lines** are a read of their own, `readDigestPlaces`, for one pull request, made when a screen opens and never in a gather. Given a readable Digest it fetches each file a place names, once, at the Digest's head, and the pull request's files as GitHub's API gives them, and nothing else. A place whose lines at the head no longer match its fingerprint is left out, so what is shown is what the Digest writer meant, and the others keep their positions (`item` and `place`, from 0). Code that is `inDiff` comes back as its diff hunk (`show: "hunk"`): the hunk's lines from the place's first to its last, each with its marker, with every removed line that sits between them or directly above the first. Code outside the diff, and words, come back as the plain lines from the head (`show: "lines"`), as does a hunk GitHub gives no patch for, or one that no longer holds the place's lines because the pull request has moved on. It gives `"unread"` when GitHub refuses or fails a request, and never throws.
  - **A Digest run in flight** is in the runs read with role `digest`: read exactly from the Kit job's closing line, with its Ticket and its pull request, or by its job's name, `Digest PR` and the number, with its pull request alone, for a run with no closing line.
  - **What a reader may keep.** `folds` and `markdown` are the Digest writer's Markdown and may quote lines of the repo, and a place's `text` is the repo's own. A reader that keeps a row or a place read keeps those with it, which bears on what the Console may keep.
- **An owed Roll-in.** A Design session that finishes by settling a Roll-in onto an open agent pull request closes its issue as not planned, and the Operator has still to send it (see [Design session (async)](#design-session-async)). Until then the row of that pull request carries it under `related`, beside the candidates, as an entry of `kind: "owed"`: the issue and its title, when the Roll-in was settled (`at`, the closing comment's time), the closing comment's `url`, and the `text` to send as data, a `summary` and its `acceptanceCriteria`. The text is read from the hidden line Kit code wrote beside the closing comment, never from the comment's Markdown. `text` is null when that line is missing, does not parse or carries a version the library does not know; the Roll-in is still owed, and `url` leads to the comment. It is on the row wherever the pull request is on the Loop, in draft as at the Merge gate, and never under `mentions`. A Follow-up that has exactly its title is marked filed with its issue's number. When to show it is the reader's.
  - **It stops being owed** when a Request changes of the Operator's on the pull request, not dismissed, names the issue, by `#` and its number or by its link; when the pull request merges or closes; and when the issue is open again, by the Kit's hand or the Operator's. An issue the Operator reopened that still carries its `From PR` line is then a candidate like any other. Which Roll-ins are owed is the Loop's own rule, the one by which the Kit reopens an issue for Triage when its pull request merges or closes with the Roll-in unsent, so the library ceasing to report one and the Kit reopening its issue are one decision. Only the Fabrik App's closing comment counts, so a comment that quotes its mark makes nothing owed, and a not-planned closing comment with no mark, as every earlier release wrote, is an ordinary finish.
  - **From the issue's side.** The issue is closed, so it has no row, and no row's `relatedTo` names it. `owedRollInsOf` takes a repo's rows and returns every owed Roll-in with its issue and its pull request, and nothing else, so a reader holding either number finds the other.
  - **What the gather reads for it.** With each cross-reference to an open agent pull request the gather keeps how the issue was closed. Only when one in the same repo is closed as not planned does it make one more query, by number, for those issues' comments; a repo with none makes no such query. It reads the latest 50 cross-references of a pull request and the last hundred comments of an issue, so a Roll-in whose issue or closing comment lies beyond those is not reported.
- **Follow-ups.** An agent pull request's row carries the Follow-ups its pass named under `followUps`, each with its `title`, its `body`, its `kind`, a `fault` or an `idea` (see **Follow-ups** under [Review](#review)), and `filedAs`, the issue it was opened as, or null (#885).
  - **On an open pull request's row** they are those of the pass on its head, and `filedAs` is the related issue with exactly its title, as it was.
  - **On a merged pull request's row** they are those of its last Verdict, when that is a pass, then each fault only an earlier pass named that the Kit's comment at the merge records, opened or left over the cap: the merge opens every pass's faults. A fault's `filedAs` names the issue the Kit opened for it at the merge (see **Faults open as issues** under [Merge gate](#merge-gate)), read from the hidden lines of the Kit's comment there. Any other's is the open issue the Operator opened whose `From PR` line names the pull request and whose title is its own, or null.
  - **What the gather reads for it.** One more query, by number, for the latest 50 comments of each agent pull request merged in the last 24 hours, and none in a repo where none merged. The facts keep what those comments say under `mergedFollowUps`. So a merged row carries its Follow-ups for those 24 hours: one that stands longer, as a row waiting at Staging does, carries none after them.
- **Staging.** On a Product repo whose Kit config declares `staging` (see [Kit config](#kit-config)), a merged agent pull request stands at Staging, a place between the Merge gate and Production, from its merge until a production deployment that contains it has started, and the Operator's Staging trial of it there ends in a label (ADR-0038). A repo that declares none is read exactly as before: the same gather, the same rows.
  - **The staging read** is the reader's own, with its own credential, as production's Deployments read is. It is a `StagingRead`: `deployments`, a `readDeployments` of `staging.environment`, called with `{ newest: true }` as its sixth argument so that each success in its `DeployOf` carries `newest`, the newest successful Deployment that contains the merge; and `mainChecks`, a `readMainChecks` of the commits those deployed, which gives a `MainChecksRead`: each Main check asked of each `CommitToCheck` as a `MainCheckOf`, green, red or undecided by the rule the Monitor reads a Main check by. `rowsOf` takes it as its sixth argument, and its fourth is still production's read. Left out or null, every staging deploy is unread. The Main checks read needs Checks read: with a credential that can't read check runs, in a repo that names Main checks, a merge whose staging deploy succeeded stays Deploying, its Main checks unread, and is never on staging.
  - **On the row.** A merged agent pull request's row carries `staging`, at Staging and at Production: the `site`, the staging `pages` of its captured routes, its named `shots` and what `toTry`. A route that is not a Dynamic route links to its page on staging; a Dynamic route and every Evidence shot link to the site itself, so no link opens a record staging may not hold. Its Standing carries `detail.staging`, with whether it needs a Staging trial and why, its result, and `standsUntil`, null while it waits on the Operator. The key is on no row of a repo that declares no `staging`, and a row kept before it has none.
  - **The joins.** `joinStaging` settles kept rows against a fresh `StagingRead` with no gather; `stagingMergesToRead` gives the merges to ask a staging Deployments read about, and `commitsToCheck`, given that read, the commits to ask a Main checks read about. `mergesToRead` gives every row at Staging too, where Kit config names production's environment. Join production's read first, with `joinDeployments`, then staging's, with `joinStaging`: the first moves a row from Staging to Production once a production deployment that contains it has started, or back to Staging with its staging deploys unread when production's read holds no such Deployment any more, and the second then settles it. The joins agree with the rule only in that order. A join never makes a row: a pull request whose Standing at Staging has ended gets its Live row at the first gather after production takes it.
  - **The trial's result** is read from the Operator's own label events on the merged pull request: `TRIAL_ACCEPTED_LABEL`, `fabrik:trial-accepted`, and `TRIAL_PROBLEM_LABEL`, `fabrik:trial-problem`. A label anyone else put on is ignored, an App's included, so a reader that records a result for the Operator puts the label on with the Operator's own credential. A Trial problem's body carries the line `trialProblemLine` writes, such as `From Staging trial of PR #50`, and `trialProblemIn` reads it, so a reader holds no format. A Design session's rewrite of the issue keeps that line, as it keeps a `From PR #n` line, which is the one thing Staging trials change in the Loop, and it does so in every repo.
  - **The Promote list.** `promoteListOf` takes a gather's facts and the `StagingRead` made for the rows, and gives a `PromoteList`, or null for a repo that declares no `staging`: the `repo`; its `start`, the newest successful production Deployment, or the first successful staging one where production has none; its `entries`, a `PromoteEntry` for each pull request merged since, agent or Plain, newest first, the 100 most recent; `notAccepted`, how many need a Staging trial and are not accepted; `leftOut`, how many older merges it holds no entry for; and `dispatchPage`, GitHub's page for the workflow `production.workflow` names, or null. An agent pull request's entry carries its `result` and, beside it, `standing`, its Standing at Staging for the same facts, which `wordStanding` words, so a reader words no result itself. Nothing in it deploys, dispatches or refuses anything.
  - **Fake data.** `aStagingFacts` builds what the gather reads past the last day, `aStagingRead` a staging read and `aMainChecksRead` a Main checks read, as `aDeploymentsRead` builds production's read, so a reader's fake data is the Kit's own facts.
  - **What the gather reads for it.** In such a repo the gather reads past the last day: the pull requests merged since that start, agent and Plain together, the 100 most recent at most, with their label events and the Trial problems that name them. Those 100 are the Promote list's entries, and the agent ones among them are the pull requests production has not taken that have a row. It reads the repo's Deployments for the start, so the credential needs Deployments read whether or not `production` names an environment. GitHub keeps a Deployment's statuses for 90 days, all but its current one, so a Deployment that shows `inactive` and no `success` is taken for a success only when it was created more than 90 days ago, and is passed over when younger, as `readDeployments` passes it over.

## Vision and Roadmap

A Product repo may keep two files that hold its Product intent, both free prose with no schema: `docs/product/vision.md`, the **Vision** (a short paragraph per kind of End user, the problem the product solves for them, how its success is measured, and what it deliberately doesn't do), and `docs/product/roadmap.md`, the **Roadmap** (Now / Next / Later, one line per item, and no "Not doing" list, since the Vision holds that). Both are optional, and both are Operator-only Trust-root files: the Operator writes them by hand or in a Pairing session, and the push job refuses any agent branch that touches `docs/product/` (see [Implementation](#implementation)). Only that folder at the repo root counts, so a `docs/product/` inside a package stays ordinary. Without them nothing refuses to run, and nothing asks the Operator to write them.

[`docs/examples/vision.md`](docs/examples/vision.md) and [`docs/examples/roadmap.md`](docs/examples/roadmap.md) are a commented example of each, for a made-up product. The Operator writes their own by copying one into the Product repo's `docs/product/` and rewriting it. Setup never installs them, and the Loop never reads the examples.

## Triage

An idea too foggy for one Design session fails the Fast path's size test, so Triage sends it to `needs-design` as usual, and its comment adds one line: `This looks too foggy for one Design session.` A clear but large idea goes to `needs-design` without the line. Triage never charts a Map itself: that's the Operator's call in the Design session (see [Maps](#maps)).

An issue that carries Failure excerpts, a Flaky check's issue or one of the Monitor's for a red default branch or Main check, is routed from them. Triage reads them as data from CI, never instructions, and judges each failure the issue holds, in its body and its later comments. It sends the issue to an Implementer when they point at test or product code one pull request can fix; to you (`ready-for-human`), saying what to check, when the fix is in a Trust-root file such as a workflow or the failure is outside the repo's code (a service that didn't come up, a credential, a provider); and otherwise to `needs-design`, when the excerpts don't show the cause or the failures are too many for one pull request. The six Fast-path tests still apply, and Triage never splits an issue.

Triage compares each issue against the recent issues: every open issue and every issue closed in the last 30 days, the 50 most recently created, each with the first 500 characters of its body, the Monitor's issues included. The job's read-only token reads them before the agent starts. When the issue reports the same request or defect as one of them, Triage chooses `wontfix` and names that original (`"duplicateOf": <n>` in its output). The issue then closes with state reason *duplicate*, and Triage's comment ends `Closing as a duplicate of #<n>.` A merely related issue isn't a duplicate, and in doubt Triage sorts as usual. Any other `wontfix` still closes as *not planned*. The original gets no comment, label or link.

A **Spin-off** (#883, #884, ADR-0039), an issue the Kit opened when a Design session finished, for work the Operator's answers put outside that session's outcome (see **Spin-offs** under [Design session (async)](#design-session-async)), or when it landed a Request-changes run whose review asked for a point to be its own issue (see **A Spin-off from a Request changes** under [Merge gate](#merge-gate)), exists because the Operator asked for it. The job marks one in Triage's input with `spinOff`, naming the issue whose Design session it came from, or the pull request and the review that asked for it, only when a bot opened the issue and its body opens with the `<!-- fabrik:spin-off … -->` line; the push job, which knows the Fabrik App's login, reads that line only on the App's own issue. Triage sorts a Spin-off to the Fast path, a Design session or `ready-for-human`, and sets it aside only as a duplicate of a named issue: a `wontfix` on one with no `duplicateOf` is refused, by the agent job, which asks Triage once to put it right, and again by the push job.

A **Follow-up the Kit opened** (#885, ADR-0039), the issue of a fault a passing Review named, which the Kit opened when the pull request merged (see **Faults open as issues** under [Merge gate](#merge-gate)), rests on the Reviewer's judgement and not on the Operator's word. The job marks one in Triage's input with `followUp`, naming its pull request, only when a bot opened the issue and its body opens with the `<!-- fabrik:follow-up … -->` line. Triage sorts it as any issue, and may set it aside: it is no Spin-off, so a `wontfix` on one needs no `duplicateOf`.

A sub-issue you file by hand with no state label gets no `needs-triage` from Intake, since a skill usually files sub-issues with their state; instead one quiet comment says so: add `needs-triage` for Triage to look at it, or a state label yourself.

A person's reply on a `needs-info` issue swaps `needs-info` for `needs-triage`, which starts Triage again; a bot's reply does nothing. Deleting the reply doesn't undo the swap: Triage still runs, reads the thread without the reply, and most likely asks its questions again, one more round and one more notification.

## Design session (async)

Adding `needs-design` to an open issue starts a Design session, once a slot is free. Each turn is a fresh run of the Design-session agent job (Opus 5.5, 30 minutes by default, `roles.design` in the Kit config, plus `.fabrik/design.md` when present), one at a time per issue, rebuilding its context from the issue thread, the issue's parent Spec when it has one, the pull request the issue was filed from when its body names one in a `From PR` line, and the repo. A turn ends in one of these ways (see [Back to design](#back-to-design) for splitting a Ticket):

- **The next round**: the Fabrik App posts numbered questions with recommended answers, @-mentioning the Operator. The round also carries its fields in a hidden line, one versioned line of JSON under its marker (its number, its intro, its questions with their recommendations, the PR a Ticket came back from on round 1, and whether it asks "Chart this as a Map instead?"), so a reader of the Kit never parses the Markdown. The visible comment is unchanged, a round that would pass GitHub's limit for a comment with the line is posted without it, and no agent is handed it. A round an earlier release posted has no line, and reads as a round with no data. The Operator's reply starts the next turn. Comments from anyone else, and from any bot, do nothing. A turn answers the reply as it read it: edit the reply before the turn starts and it sees the edit; to change an answer after that, post a new reply, since an edit never starts a turn. Delete the reply before its turn posts and the turn posts nothing; only a turn that fails still posts its failure notice.
- **An agent brief**: the issue body is rewritten in place as the brief and its acceptance criteria, a closing comment (no mention) records the decisions, and `needs-design` is swapped for `ready-for-agent`. A brief with `"stepUp": true` also adds `fabrik:step-up`, and one with `"stepUp": false` takes it off; leaving it out keeps the label as it stands. A brief with `"keptBranch": true` also adds `fabrik:kept-branch` (see [Back to design](#back-to-design)); with `false`, or left out, the label is taken off if it's on. Finishing the session counts as the Operator approving it.
- **A Prototype request**: on a repo with a `ui` block, once the Operator says yes to a Prototype, the turn asks for it, and the next turn is a prototype turn that builds the variants and posts a prototype round. See [Prototypes](#prototypes).
- **A Map**: when the destination is too foggy for one session and the Operator says yes to "Chart this as a Map instead?", the issue is rewritten in place as a Map, its first Decisions are filed as its sub-issues, and `needs-design` is swapped for `wayfinder:map`. See [Maps](#maps).
- **On a Check's issue** (ADR-0037), the issue the Kit files for a red Required check, the session keeps the tie to the check however it ends, so the Kit brings held PRs up to date when the fix lands, and not before (see **Bringing a held PR up to date when the fix lands** under [Review](#review)). An agent brief or an Operator brief opens its body with the issue's `<!-- fabrik:flaky-check-issue … -->` marker line, kept only on an issue the Fabrik App opened, and the issue keeps `fabrik:flaky-check`. A Spec takes the issue's place: its body opens with the marker line and it carries `fabrik:flaky-check` beside its category label and `ready-for-agent`, so a red run of the check comments on the Spec, and the Spec closing as completed is the fix landing. Before the issue closes as superseded, its body loses the marker line, the rest as it was, and `fabrik:flaky-check` comes off, so its close is never read as a fix. Every Ticket and Operator step of that Spec carries `fabrik:flaky-check` too, as does each sibling split from such a Ticket, so each `ready-for-agent` one is a check's fix. A Check's issue never becomes a Map.
- **Not planned**: when the Operator decides the issue won't be built, the session finishes as not planned (`{ "kind": "not-planned", "comment": … }`). The closing comment (no mention) gives the session's reasoning, `needs-design` is swapped for `wontfix`, and the issue closes with state reason *not planned*. It works the same on a Ticket that came back to design. Its work never lands, so the issues it blocks stay blocked: Dispatch treats a blocker closed as not planned as still blocking until the Operator removes the edge, and the closing comment names those issues. The reasoning lives only in that comment.
- **A Roll-in**: when the Operator says the issue's work is to be built on an open agent pull request, the session finishes by settling a Roll-in (`{ "kind": "roll-in", "pullRequest": <n>, "summary": …, "acceptanceCriteria": […] }`): what to build there and at least one acceptance criterion, written to stand alone, with no word cap. Two refusals are part of the contract. The output is refused when the summary or a criterion names the session's own issue, by `#` and its number or by a link to it, because the Implementer and the Reviewer are never given the issue. It is also refused when either mentions someone, by the same test the Kit strips mentions with, because the Operator sends the text as their own: an address such as `a@b.c` is no mention, and neither is a name written straight after a backtick, as `` `@scope/name` `` is. Nothing is stripped: the agent job asks the turn once to put the output right, and the push job checks it again. The push job then reads the pull request the output names, which must be open, an agent pull request, and not the one built from this very issue as its Ticket; if not, the turn fails and nothing changes. It need not be the pull request the issue's `From PR` line names. The issue then closes as a not-planned finish closes it (`needs-design` swapped for `wontfix`, state reason *not planned*, the issues it blocks still blocked), under a closing comment (no mention) that the Kit renders from the output: the heading "What to build on #n", the summary, the criteria, and a line saying that nothing has been sent and how the Operator sends it. The comment opens with two hidden lines, the Roll-in's mark naming the pull request and the text as one versioned line of JSON, so a reader of the Kit never parses the Markdown. The Kit sends nothing and puts nothing on the pull request, no comment, label or review: only the Operator sends a Roll-in, with a Request changes on that pull request that carries the text and names the issue (ADR-0010). A Roll-in never sent is not lost: when that pull request merges or closes with it unsent, the Kit reopens the issue for Triage (see [Implementation](#implementation)).

Only rounds notify: the Kit strips @-mentions from everything the agent writes.

**Acceptance criteria**: every criterion a session writes, an agent brief's, each Ticket's in a Spec or a split, and a Roll-in's, is one check that a test the Required checks run, or the diff itself, shows is met. It never asks for a Trust-root change, a GitHub write, a commit, branch or state the run isn't given, a suite or command no Required check runs, or anything only the Operator can do, and is never a literal no output can meet: those are what the prompts mean by a criterion no run can meet. A Ticket back from a Design flaw for one is rewritten, dropped or made an Operator step on the usual path, Kept branch included, and when nothing is left to build it finishes as an Operator brief and the Operator reopens the PR. Each turn is given the Required checks the Kit config's `sandbox.checks` lists, under "The Required checks" after the issue, which says so when it lists none and that GitHub may require more on the main branch, and reads `.github/workflows/` to see what each runs. A test a Required check doesn't run is moved where one does or its criterion dropped; when that needs a workflow change, the change is an Operator step that blocks the Ticket. A prototype turn writes no criteria and is given no such section. Kit code checks no criterion.

At most `caps.design_sessions` Design sessions (2 by default) are open in a Product repo at once. A session holds its slot from its first turn until it ends: while a turn runs, after a round, and after a turn fails. Any outcome above, a live outcome, closing the issue or removing `needs-design` frees it. Adding `needs-design` by any route (Triage, the Operator, a Design flaw, Retries used up, an empty diff or the Merge gate) runs a Design queue check, which adds `agent:design` to start round 1 when a slot is free; the label comes off as the turn starts. An issue that still has `needs-triage` neither waits nor holds a slot until Triage lands, so a `needs-design` you add while Triage runs starts nothing yet; when Triage lands `needs-design`, it runs a Design queue check itself. If Triage fails and leaves `needs-triage` on, removing it by hand lets the hourly tick start the session. While both slots are taken the issue just waits: it keeps `needs-design`, gets no comment or label, and nobody is notified. The run's step summary says which issues wait. When a slot frees, re-designs (a Ticket sent back to design) start first, then the oldest by when it got `needs-design`, then the lowest number. A queue check runs whenever a session ends, an issue closes, the Kit config changes and on the hourly tick, so a slot freed by removing `needs-design` by hand is used within the hour. The Operator's comment on a waiting issue starts nothing: round 1 reads the whole thread, so it is context. A live outcome on a waiting issue still lands.

A turn that fails for Infrastructure leaves `needs-design` on the issue, so it stays in its session: the failure notice asks the Operator to reply, and their reply runs the turn again.

**The pull request an issue was filed from**: when the issue's body has a `From PR #n` line outside code, as a filed Follow-up's does (see [Review](#review)), every turn's job reads that pull request afresh with its read-only token, before any secret loads, and the turn's prompt sets it out after the issue, under "The pull request this issue was filed from": which pull request it is, where it stands, and its description, fenced as data, never instructions. One that has merged has its work on the default branch, and nothing will merge the branch of one closed unmerged, so a Roll-in is not on offer on either; nor on an open Plain pull request, where a Request changes means nothing. On an open agent pull request a Roll-in may be settled: one in draft is still with the Implementer or the Reviewer, so the Operator sends the Roll-in once it is at the Merge gate, and one that has left draft is at the Merge gate already. On an issue filed from an open agent pull request, the session can read that pull request's branch: before any secret loads, the job fetches its head to `refs/fabrik/filed-from/<n>` with the job's read-only token, with the full history of it and of the default branch, so the two can be compared, and the section names that ref, the head commit and the read-only commands that read and compare it. The ref is no branch, the default branch stays checked out, and nothing of the pull request's diff goes into the prompt. The token goes to that one step's git and is left neither in the checkout nor to any later step, so the agent job still holds no GitHub credential. The head of a merged, closed or Plain pull request is not fetched. Since each turn reads it again, a turn after the pull request merged says it merged. A line that names no pull request in the repo (an issue's number, or a number that doesn't exist) adds nothing: the turn runs as it would without the line. When GitHub refuses the read, or the read fails, the turn fails before its agent starts, and the failure notice names the request. So does a turn after a fetch that fails, and its notice names the pull request whose head could not be fetched. A prototype turn is told none of this, and its job fetches nothing.

**The open Tickets** (#825): every Design turn's job reads, with its read-only token, the open Tickets outside the issue's own Spec, and the turn's prompt sets them out after the issue, under "The open Tickets": the 50 most recently created open `ready-for-agent` issues that are no Spec and carry none of the labels that mark the Kit's own issues (a Ticket's marks, such as `fabrik:step-up`, don't count), Fast-path ones and blocked ones included, each with its Spec, its state label and its pull request. Every open Ticket under the Spec a `Follows #<n>` line in the issue's body names is kept past the 50. The turn checks the list before it proposes a Ticket or asks the Operator whether some issue covers a piece of work: a Ticket it files leaves out what an open Ticket holds, or waits on it with that Ticket's number in its `blockedBy`, which the Kit links as a native blocker. Only the agent job checks a number against the list, and refuses one not in it; the push job takes any issue's number. An Operator step never asks the Operator to open an issue: work that needs an issue of its own is a Spin-off, which the Kit opens (see **Spin-offs** below). A prototype turn is told none of this.

**Spin-offs** (#883, ADR-0039): a session opens the issue for work the Operator's answers put outside its outcome, with no Operator step and no link to click. Any finish but a Map can carry `spinOffs`: an agent brief, an Operator brief, a Spec, a split, a Roll-in and not planned. A round and a Map take none, and an output that gives one there is refused. Each Spin-off has a `title`, a `body` that stands alone, a `restsOn`, one line naming the Operator's answer it rests on, and a `blockedBy`. The session writes one only when an answer of the Operator's states or implies that the work is wanted but is not part of this outcome, such as "not now" or "later": never for work the Operator did not speak to, never for work an open Ticket already holds, which the closing comment names instead, and it asks no question only to confirm one. Work the session designed fully is a Ticket of its Spec. The Kit opens each Spin-off in the plan that finishes the session, as the Fabrik App, in the same repo, with `needs-triage` and no other label, as a Check's issue is opened, so Intake leaves it alone and a Triage run follows (see [Triage](#triage)). Its body opens with one hidden line, `<!-- fabrik:spin-off {"from":"design","issue":<n>} -->`, which says it is a Spin-off and names the issue whose session it came from. That line is the whole mark: there is no label, and Kit code reads it only as the first line of an issue the Fabrik App opened. When the finish writes a Spec or a split, the body ends `Follows #<Spec> (its Tickets: …)`, naming the Spec and the Tickets filed with it by the numbers the Kit gave them, so a Design session on the Spin-off is given those Tickets. `blockedBy` becomes native blocked-by edges: to the issue the Kit opened for a Ticket or an Operator step of the same finish, named by its key; to an open Ticket in "The open Tickets", named by its number, which the agent job checks against the list as it does a Ticket's; and, on an agent brief, to the issue the brief rewrites. The edges hold Dispatch, not Triage, which runs at once. The closing comment ends with a list of the Spin-offs, each with its number, its title and its `restsOn` line, which the session writes none of. A Spin-off mentions nobody and is assigned to nobody. `newIssue` is gone: a Ticket or an Operator step that carries one is refused with a message that names `spinOffs`, and the Kit writes no Open as issue link on an Operator step. An Operator step already open keeps the link its body has. A live Design session files as the Operator, so nothing it opens is a Spin-off to the Kit.

## Design session (live)

The Operator can take a Design session live in a claude.ai/code or iOS cloud session, or a local Claude Code session, on the Product repo. The `SessionStart` hook installs the pinned skills into `.claude/skills/` and returns `reloadSkills: true`, because Claude Code discovers skills before `SessionStart` hooks finish. Then `/fabrik-live-design <issue>` runs the session (`skills/fabrik-live-design/SKILL.md`):

- It posts nothing on the issue until it ends, since every Operator comment on a `needs-design` issue starts an async turn.
- It reads the [Vision and Roadmap](#vision-and-roadmap) when the Product repo has them. An issue that touches Product intent opens with who the change serves, why, how its success is measured and what it leaves out, with recommendations drawn from the Vision, or asked directly without one; a Ticket sent back to design, and internal or technical work, skips that. Every Spec gets a Product intent section and every agent brief a "Who and why" line. It never edits either file: a decision the Vision doesn't yet say becomes an "Update `vision.md`" Operator step with the exact lines.
- It runs with the Operator's own `gh` credentials and publishes the outcome itself: the issue body rewritten as its agent brief or its Operator brief, the Spec and its Tickets (category label and `ready-for-agent`, Tickets as sub-issues with native blocked-by edges), or the issue body rewritten as a Map with its first Decisions (each a sub-issue with its `wayfinder:<type>` label and native blocked-by edges). It checks the [Map cap](#maps) before it offers a Map.
- It holds every acceptance criterion it writes to the async session's rule (see **Acceptance criteria** under [Design session (async)](#design-session-async)). The Kit gives it nothing, so it reads the Required checks from `sandbox.checks` in the Kit config in its checkout, as it reads the Map cap there, and `.github/workflows/` for what they run.
- It offers a [Prototype](#prototypes) on the same conditions as an async session. On a yes it builds the variants itself, in the session's checkout, with the pinned `prototype` skill's UI branch on `prototype/<issue>`, pushes that branch on the Operator's credentials, and gives the Operator the one command that opens it in their own browser. There's no Sandbox job, capture or Evidence page, and its outcome records the chosen variant as an async one does.
- Its last act is one comment whose first line is `<!-- fabrik:live-outcome brief -->`, `<!-- fabrik:live-outcome operator-brief -->`, `<!-- fabrik:live-outcome spec -->` or `<!-- fabrik:live-outcome map -->`. From the Operator, that comment makes the Kit land the outcome as an async finish would: `brief` swaps `needs-design` for `ready-for-agent`, `operator-brief` swaps `needs-design` for `ready-for-human` and assigns the issue to the Operator, ready for a Pairing session, `spec` removes `needs-design` and closes the issue as completed, and `map` swaps `needs-design` for `wayfinder:map`. All four run a Design queue check, and all but `operator-brief` a Dispatch check. Without the marker, a summary comment is an ordinary answer, and the async session carries on from it.
- On a Check's issue (ADR-0037), a brief keeps the issue's `<!-- fabrik:flaky-check-issue … -->` line as its body's first line, as it keeps the Monitor's. A Spec or a Map isn't finished live: the Kit reads a check's marker only on an issue the Fabrik App opened, so the skill stops with a summary comment and the async session lands the Spec. A `spec` or `map` outcome on a Check's issue is refused: the Kit says why on the issue, in a comment that opens like a failed turn's notice, leaves `needs-design` on and closes nothing, and the Operator's reply starts the async turn.

## Maps

An idea too foggy for one Design session, because what done looks like isn't settled or its open questions hang on one another, can be charted as a **Map** instead of being forced into a premature Spec. The Map names the destination, and its children are **Decisions**, each resolved on its own by research, a prototype, a grilling or a task, never by a pull request. The Kit runs research Decisions AFK; the others are the Operator's, worked live with `/wayfinder`.

- **The Map question**: capture stays a blank issue, and [Triage](#triage) flags fog with one line in its comment. When that line is there, or the Design session judges the destination can't be designed in one session, round 1 asks "Chart this as a Map instead?" with a recommendation. The Operator decides: no keeps the session designing, and any later round can still end in a Map when the Operator asks for one. An issue the session can design gets no Map question, and neither a Ticket under a Spec nor a Check's issue ever becomes a Map: a red check whose cause isn't known finishes as a Spec whose first Ticket finds the cause (ADR-0037).
- **The `map` outcome** rewrites the issue in place as the Map, with `## Destination`, `## Notes`, an empty `## Decisions so far`, `## Not yet specified` and `## Out of scope`, carrying its `From audit`, escape, `From retro` and `From PR` lines as a brief does. Its first Decisions are filed as its sub-issues, blockers first, each with its `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling` or `wayfinder:task` label, native blocked-by edges, and no state or category label, so Intake leaves them alone. The closing comment (no mention) lists the Decisions filed, `needs-design` is swapped for `wayfinder:map`, the issue keeps its category label, and the Kit runs a Dispatch check and a Design queue check. A `map` outcome with no Decisions breaks the output contract. A [live session](#design-session-live) can end the same way.
- **The Researcher** (Opus 5.5, 30 minutes by default, `roles.research`, plus `.fabrik/research.md` when present): Dispatch adds `agent:research` to each open research Decision on an open Map that nobody is assigned to, no Blocker holds (an issue in any repo that is open or closed as not planned, or one the Fabrik App can't read, as for a Ticket, #771) and whose last run didn't fail, and the label comes off as the run starts. Research runs share `max_in_flight` with Implement runs: Tickets and research Decisions are released together, lowest issue number first, but a check's fix (a `ready-for-agent` Ticket carrying `fabrik:flaky-check`) goes ahead of both, and `0` pauses both. Adding `agent:research` by hand starts a run now; assigning yourself a Decision keeps Dispatch off it. The Research job is read-only, like the Auditor: a checkout of the default branch, only the agent service account, no GitHub credential, no production secrets, and none of the code run. It gets the Base skills alone and follows the pinned `research` skill, reading primary sources. It's given the Decision, its Map's body and the findings path the Kit derives from the Decision's number and title, `docs/research/<number>-<slug>.md`, and writes that one file, deciding nothing. The runner commits it to the throwaway branch `research/<number>-<slug>` and passes it out as a bundle.
- **Landing the findings**: when the branch changes only its findings file, the push job pushes it (it's never merged and gets no PR), posts a resolution comment on the Decision with the gist, the key facts and a link to the file on the branch, and closes the Decision as completed, which unblocks the Decisions that wait on it. Then it appends one line to the end of the Map's Decisions so far, the Decision's title linking its resolution and the gist, re-reading the Map's body right before it writes and changing nothing else, so the Operator's own edits stay. Last, it runs a Dispatch check. A run that lands after its Decision closed, lost `wayfinder:research` or left its Map, or after the Map closed, posts nothing and changes nothing, but still runs a Dispatch check, since the slot it held is free. A branch that changes any other path, a Trust-root file included, is refused: nothing is pushed, and the Decision gets the failure notice. The Kit never edits Not yet specified, Out of scope or any other Decision: graduating the fog stays the Operator's.
- **A failed run**, a reply that breaks the research output contract included, posts the Kit's usual failure notice on the Decision, classed as for any other role, so a dead token or the weekly limit also goes on the rotation or weekly-limit issue. Dispatch doesn't run that Decision again until the Operator re-adds `agent:research`. Every research run leaves a Run record in role `research`, and no Scorer samples it.
- **The Map cap**: `caps.maps` (default 1) caps how many Maps are open in a Product repo at once, counting every open `wayfinder:map` issue, one charted by hand included. It holds silently. While it's full, a Design session offers no Map, and if the Operator asks for one, it names the open Map that holds the cap. A `map` outcome that lands while the cap is full anyway is refused with a comment naming the open Map, mentioning nobody, and the session carries on from the Operator's next reply: until then the Weekly summary lists it in Waiting on you, as it does a Design session whose last turn failed. Closing a Map frees the cap.
- **Reaching the destination** is a `/wayfinder` convention, not Kit code. The Map's last Decision files each Spec-to-be as a new `needs-design` issue that links the Decisions it rests on. Each skips Intake, since it already has a state label, and goes to a Design session, which treats those Decisions as settled. The Operator closes the Map once its Spec issues are filed. The Kit never closes a Map, and Spec closing never mistakes one for a Spec: it closes only a parent with a `ready-for-agent` or `ready-for-human` state label.
- **In the Weekly summary**: each open Map is in its repo's Waiting on you, unless an issue in the repo blocks it (open, or closed as not planned), with its age and how many of its Decisions wait on the Operator (its open grilling, prototype and task Decisions), and so is each research Decision whose last run failed, until the Operator re-adds `agent:research`. Held shows the Map cap when it's full, naming the open Map.

## Prototypes

On a Product repo whose Kit config has a `ui` block (see `ui` in the [Kit config](#kit-config)), a Design session can settle how a page should look by looking at it. A **Prototype** is throwaway variants of one route on the branch `prototype/<issue>`, which is never merged and never gets a PR, and which the Kit never deletes. It has no setup step and no Kit config key of its own: a repo without a `ui` block never gets an offer, and a `prototype` output there breaks the output contract.

- **The offer**: when a session's open question is how a page looks, a round may ask, with a recommendation, "Prototype the booking page (`/book`) as 3 variants first?": 3 variants by default, from 2 to 5. Nothing is built until the Operator says yes, and the yes may change the route or the count. Logic and data questions stay ordinary questions.
- **The request**: on a yes, the next turn ends in `prototype`, naming the route, the variant count and what each variant explores. The push job posts a comment that mentions nobody, saying what's being built, with the request in a hidden `<!-- fabrik:prototype-request … -->` marker, then adds `agent:design` afresh. It isn't a round, and the session keeps its slot.
- **The prototype turn**: `agent:design` on an issue whose session has a pending request whose prototype turn hasn't started yet starts a prototype turn, `loop.yml`'s `prototype` job, in the design job's place, and the Kit marks the request's comment started (an edit, which notifies nobody). It runs on the Design model and effort within the Implement timeouts, holds the implement service account (the Claude token and the test secrets) and no GitHub write, and shares the session's concurrency group, so a reply sent meanwhile waits for it. Before the agent starts, the Sandbox runs `sandbox.setup` then `sandbox.build`, as for an Implement run. The agent follows `prompts/prototype.md` and the pinned `prototype` skill's UI branch: every variant on the one route, switched by `?variant=` and its letter, each in its own component, with a floating switcher, committed on `prototype/<issue>`, which a later round builds on. The job then builds and serves the branch and captures each variant at mobile and desktop width, a screenshot and a short load-and-scroll video at each, into one Evidence page, uploaded unzipped and kept 30 days. Beside it the job keeps its captures, the folder capture wrote with each variant's screenshots and videos and the capture result, as it is, zipped and kept 30 days, as the Implement job keeps a pull request's UI evidence, whenever capture recorded a result, whether it captured or failed. Capture never fails the job, and nor does keeping either. A prototype turn refused on its Subscription's weekly limit, re-run or held, has that mark taken off, so it restarts as a prototype turn on the next free one, while an ordinary turn a reply started meanwhile restarts as an ordinary turn.
- **The prototype round**: the push job runs the Trust-root guard over the branch, pushes it as a fast-forward of `prototype/<issue>`, and posts a numbered round that @-mentions the Operator: the agent's intro, links to the branch and the Evidence page (the round is the record once the Evidence page expires), each variant's letter, summary and component at the pushed commit, its preview when `preview.url` is set, and "Which variant?" with a recommendation. Like any round, it carries its fields in a hidden line, the third, under its two markers: the approved route, each variant's letter, summary, component address and, once the preview step links it, preview address, the question and recommendation, the advised variant's letter, `recommended`, which the prototype turn names beside its recommendation, and `captures`, the Actions run and the id of the artifact that keeps the zipped captures, as a pull request's evidence marker names its run and artifact, null when the job kept none. A letter that isn't one of the variants' is left out and noted in the run's step summary, never failing the turn. A prototype failure round's line holds what stopped the prototype, its question and "Try again" as the other answer. The Operator's reply is an ordinary answer, and can ask for another round.
- **When it fails**, the session carries on. A branch that changes a Trust-root file isn't pushed, and a turn with no commits pushes nothing: each gets a prototype failure round saying why. A build or server that failed still pushes the branch, and its failure round asks "Carry on without a prototype, or try again?", recommending carrying on. Any other capture failure still asks "Which variant?", with the reason in the Evidence page's place. An Infrastructure failure posts the usual failure notice, which ends the request, and so does a turn whose output breaks its contract, or whose branch moved while it ran (a live session's push, say): the Kit only fast-forwards `prototype/<issue>` from the head the turn started on, so it pushes nothing then.
- **The outcome** records the chosen variant, the Operator's tweaks and links to the branch and that variant's component, for the Implementer to rewrite, never to merge. The Reviewer gets nothing from a Prototype. A [live session](#design-session-live) can offer and build one too.
- **In the Run records**: each prototype turn's record has role `design` and `prototype: true`. The Weekly summary counts it as a Design-session turn, and no Scorer samples it.

## Pairing session

The Operator works through a `ready-for-human` issue with an agent beside them by running `/fabrik-pair <issue>` in a cloud or local Claude Code session on the Product repo (`skills/fabrik-pair/SKILL.md`). It runs with the Operator's own `gh` credentials:

- It counts as the Operator, so it may change Trust-root files. It refuses an issue that isn't open and `ready-for-human`, except the weekly-limit issue: there it waits for the reset before restarting the stalled Tickets, and still finishes the restart after the Kit has closed the issue. The issue body's `- [ ]` task list is the plan; with none, the session agrees one with the Operator and writes it in below the original text. A rerun resumes at the first unticked step.
- It talks the Operator through simple steps, and builds a wizard (`.claude/skills/wizard`) in a temp folder, never committed, for dashboards, credentials or a run of commands.
- It ticks each step once a command confirms it (`gh secret list`, `gh api`, `op item get`, reading the file) or, where nothing can, once the Operator does. File changes, Trust-root files included, go out in one pull request whose body has `Closes #<n>`, never pushed to the default branch.
- It ends with a comment saying what was done, and closes the issue, or leaves that to the pull request's merge. Stopping partway, it comments where it stopped and leaves the issue open and assigned. No comment names a secret's value or @-mentions anyone.

The token-rotation and weekly-limit issues the Kit opens write their steps as a task list and point at `/fabrik-pair`.

## Implementation

Dispatch adding `agent:implement` to a Ticket starts its Implementer (Sonnet 5.5, 60 minutes by default, `roles.implement`, plus `.fabrik/implement.md` when present), one run per Ticket at a time. The label comes off as the run starts, and the draft PR appears only when the run lands, once its push job has run; until then the run is on the Actions tab under the Ticket's number, its Implement job named `Implement #<n>` (`Implement #<n> (Retry <r>)` for a retry). Adding `ready-for-agent` to an open issue, by Triage or by hand (re-marking a refused Ticket, say, or a sub-issue that skipped Intake), runs a Dispatch check, as does the hourly tick, so a ready Ticket left waiting while every slot was full starts within the hour (#418). A Ticket whose Implement run failed before it opened a PR, as an Infrastructure failure, is left alone: its failure notice (`<!-- fabrik:implement-run-failed -->`) keeps Dispatch off it until you re-add `agent:implement`, so no check starts a failed Ticket again by itself. A first run whose branch builds on commits it didn't start from, as one that reset onto or merged in a commit `main`'s head doesn't hold, fails in its Implement job, its comment naming those commits, since the push job rebuilds the branch from that head alone and could never land it; its commits are kept as any failed run's are (#535). That's a Broken run (below), which the Kit re-runs itself, so nothing holds its Ticket back (#434).

A trigger label (`agent:implement`, `agent:design`, `agent:review`, `agent:research` or `agent:replay`) with no run behind it, as when the Kit job failed on an invalid Kit config, or the run was cancelled or lost before it started, no longer holds its slot for good (#419). The hourly tick looks for one on an open issue or PR that was last added at least 30 minutes ago with no job of its role unfinished anywhere in the repo, and adds it again so the run starts, saying so on the issue (`<!-- fabrik:stuck-trigger-readded <label> -->`). If it's still on, with no run behind it, at a later tick, the Kit takes it off and @-mentions you: check the Loop's Actions runs, fix the cause, then add the label again. Until you do, the work is parked as after that role's failed run, so Dispatch and the Design queue leave it alone. A Design session keeps its slot meanwhile. Cancelling a Loop run before it starts doesn't stop the work, since the tick adds the label back: to stop a run, take its label off. `agent:digest` is the one trigger label the tick never adds again or hands to you: see **A lost start** under [Digest](#digest). Nor does it touch `agent:rerun-checks`, which starts no agent: see **One more re-run at the Merge gate** under [Review](#review).

Closing by hand stops the work, never restarts it (#428). Closing a Ticket, by hand or otherwise, closes its open agent draft PR unmerged, keeping its branch, with a comment on the PR saying why, so it frees its `max_in_flight` slot and gets no more Reviews. Closing an agent PR unmerged yourself, a draft or one at the Merge gate, means stop: the Kit doesn't dispatch its Ticket again, but swaps `ready-for-agent` for `ready-for-human`, assigns you, and comments that the PR was closed by hand and its branch `fabrik/ticket-<n>` kept. To have an Implementer try again, mark the Ticket `ready-for-agent`: the new run starts from `main` and replaces that branch, unless you also add `fabrik:kept-branch`, when it carries on that branch instead (see [Back to design](#back-to-design)). The Kit's own closes (Send it back, back to design, a refused run, a closed Ticket's PR) and a merge do neither: they leave the Ticket as they put it, and only free the slot. Whoever closes an agent PR, merged or unmerged, each Roll-in settled onto it and left unsent (no Request changes of yours on it, not dismissed, names the issue by `#` and its number or by its link; see [Design session (async)](#design-session-async)) has its issue reopened for Triage: the Kit reopens it, takes `wontfix` off, posts one line that mentions nobody, saying the PR merged, or that it closed unmerged so the code the text names may not be on `main`, and adds `needs-triage`, which starts Triage.

- **The Sandbox** is a fresh clone of `main` on the runner, on the branch `fabrik/ticket-<n>`. The job holds only the implement service account. The Claude token and the test secrets listed in `sandbox.secrets` are resolved from 1Password into the Implement step's env only, so adding a test secret never means editing the caller workflow. Before the agent starts, the Sandbox runs `sandbox.setup` (daemonise any stubs it starts), then `sandbox.build`, so the Implementer starts with the Product's dependencies installed. Each runs only if the one before it passed, and a failure fails the run before the agent takes a turn. The prompt gives the Implementer the `build` and `test` commands, saying the Kit has already run `build`, and to run it again after changing the dependencies or before testing what it built.
- **The prompt** carries the Ticket, its parent Spec, `GLOSSARY.md`, the ADRs under `docs/adr/`, `CODING_STANDARDS.md` when the repo has one at its root, and the Product's implement instructions, and starts the `implement` skill, which works test-first with `tdd`. A run that finds an acceptance criterion out of reach, one no run can meet (a Trust-root change, a GitHub write, a commit, branch or state it wasn't given, a suite no Required check runs, something only the Operator can do, or a literal no output can meet), builds the rest, commits it, and names the criterion, quoted, with the reason, under **Criteria no run can meet** in its summary, so the PR opens and is Reviewed as any is. Only a Ticket that has nothing buildable without one ends in no commits (#764).
- **The push job** rebuilds the branch from the git bundle the agent job passed out and runs the trust-root guard on every path any of its commits changes:
  - **Allowed**: the Fabrik App pushes the branch and opens one draft PR to `main` with `Closes #<n>`, which starts CI. Nobody is notified.
  - **Refused** (it touches `AGENTS.md`, `CLAUDE.md`, `CODING_STANDARDS.md` at the repo root, `.claude/settings*`, `.claude/skills/`, the Kit's role prompts `prompts/<role>.md` and its Scorers' rubrics `prompts/scorers/` (a Product's other `prompts/` files are its own), `.fabrik/`, `.github/workflows/` or `docs/product/` at the repo root, where the [Vision and Roadmap](#vision-and-roadmap) live): nothing is pushed. The Ticket moves to `ready-for-human`, is assigned to the Operator, and gets a comment listing the paths. A refused retry or Request-changes run also closes its PR unmerged, keeping its branch, so it no longer holds a `max_in_flight` slot. A Request-changes run told to merge `main` in is the exception: the comment listing the paths goes on its PR instead, which gets `ready-for-human` and stays open, and the Ticket is left as it is (see **Request changes** under [Merge gate](#merge-gate)). This uses no retry.
  - **Empty diff**: an Execution flaw, never a pass. The Implementer runs again, silently, up to 2 times (the second a Step-up), and a third empty diff sends the Ticket to `needs-design`. Each such run is one of the Ticket's two Retries: if a later run opens the PR, its Verdicts count on from them (#415).
  - **Broken run** (#434): an Implement run whose work the Kit can't land because of what the agent did: its output breaks the run's contract, it left its branch, or it built on commits its branch didn't start from. On a first run, or the Retry after an empty diff or another Broken run, it's handled like an empty diff and counts in the same pool. A `<!-- fabrik:broken-run -->` comment on the Ticket, mentioning nobody, says which it was, quotes the agent job's detail and points to any commits it made, kept for 7 days as `agent-branch.bundle` in the run's `fabrik-agent-failure` artifact. The Kit then re-runs it from where it started, `main` or the Kept branch for a Kept-branch start, never from its commits. The second re-run is a Step-up, and once both Retries are used the next one sends the Ticket to `needs-design`. The comment carries no failure marker, so Dispatch doesn't hold the Ticket back. On a Retry it's an Execution flaw Verdict on the PR instead (see **The count** under [Execution-flaw retries](#execution-flaw-retries)). On a Request-changes or conflict-only run it uses no retry: its notice names it a Broken run and waits for you, as an Infrastructure failure's does. A timeout, a crash, and anything from the provider, a credential or 1Password stay Infrastructure failures, and so do a Reviewer's missing Verdict and a broken prototype turn. The run's Run record names the Broken run in `brokenRun`, never in `infrastructureFailure`, the Scorers score it, and the Weekly summary's Metrics table counts the week's Broken runs against last week. One that used no retry is under the Weekly summary's Waiting on you from its notice until you re-add `agent:implement`. A Ticket left on an older notice that called one of these an Infrastructure failure stays as it is: re-adding `agent:implement` runs it as before.
- **Changed existing tests** (#463): the push job lists every test file (`*.test.*`, `*.spec.*`, `*_test.*`, `test_*.*`, or anything under `test/`, `tests/` or `__tests__/`) the run's own commits changed, moved or deleted that was already there before the run, on the head it built on. The PR body gets a "Changed existing tests" section, between the summary and `Closes #n`, ending in a hidden `<!-- fabrik:changed-tests [...] -->` marker; a retry or Request-changes run's list adds to the earlier runs'. The Implementer is told to explain each such change in its summary, and the Reviewer gets the list and judges each change on its merits: an assertion weakened or removed without a reason in the PR body is an Execution flaw. A PR whose runs changed no existing test gets no section, and its Reviewer no extra text.
- **UI evidence**: in a repo whose Kit config has a `ui` block, once the Implementer's agent has ended well, the job builds and serves a branch that changes a `ui.paths` file and screenshots the routes the change shows on, and a UI PR's body gets an evidence section linking an Evidence page of them. Route capture never blocks the PR or uses a retry. On a Product repo whose UI evidence comes from [Evidence shots](#evidence-shots), the job captures nothing, and an Evidence miss does both: a UI PR whose Implementer named no shot and didn't say that nothing visible changes goes back to it with the Kit's own Execution flaw, which uses a Retry (ADR-0033). See `ui` in the [Kit config](#kit-config).

## Review

Every agent draft PR is reviewed before the Operator sees it. The Fabrik App opening the PR, or pushing to it, starts a Review; adding `agent:review` to the PR resumes one after a failure. One Review runs per PR at a time, within the Review timeout (30 minutes by default, `roles.review`).

- **Required checks** come first. The Review checks job waits for them on the PR's head: the checks named in `sandbox.checks` plus any the default branch requires, the branch's list read from the branch when the wait starts. A check on the head in neither list, such as `loop / Kit`, never gates the Review, and with neither listing any, nothing does. If the branch can't be read, the wait fails with a notice rather than judging against `sandbox.checks` alone. A skipped or neutral check counts as passed, as it does for GitHub's merge, and the Reviewer and the Digest are told it ran nothing; a cancelled one is failing. Its log names the checks it still waits on whenever that changes, and every 5 minutes while it doesn't, and it gives up 3 minutes short of the Review timeout. A Required check that never reported on the PR's head, such as a renamed job or a workflow its `paths:` filter skipped, fails the Review with a notice naming it, which re-adding `agent:review` won't change. Since Setup never takes a check off the branch, dropping it from `sandbox.checks` alone doesn't stop the wait: fix the workflow, or take the check off the default branch's required list on github.com and out of `sandbox.checks` too; checks still running when it gives up, or a GitHub request that fails while it waits, fail it with a notice naming those.
- **Red checks are re-run once** (ADR-0018). The Re-run red checks job re-runs the failed jobs of the workflow runs behind the red GitHub Actions checks, once on the same head, holding only `actions: write` on the workflow token, which the caller workflow's `loop` job grants; a run already re-run on this head isn't re-run again. A second wait, with a Review timeout of its own, reads the checks again. A check that passes then is a Flaky check: the Reviewer runs as usual, and the Kit posts one line on the PR, mentioning nobody, and files the check's ``Flaky check or Unrelated failure: `<name>` `` issue (`needs-triage`, `fabrik:flaky-check`), or comments on it while it's open (one filed before #781 keeps its old title, `Flaky required check: <name>`), each with the Failure excerpt of the check's first attempt, which the Review checks job read before the re-run (#778). A required check from an outside service (Vercel, Buildkite, a commit status) only its owner can re-run, so it isn't.
- **Red checks** still red after everything the Kit could do go to the Reviewer (#779): the re-run's wait ended red, or the first wait ended red and nothing was re-run (only outside checks, a refusal, or a run already re-run on this head). The Reviewer is given each red check with its attempts, its result on the default branch's head (passed, failed with its link, still running, or not run there) and its Failure excerpt, as data from CI, and judges the code as on any Review. A GitHub Actions check's excerpt carries the other failed jobs of its workflow run too, up to ten, each with its failed step and error annotations, so a check that only gathers other jobs' results still names the test that failed (#890). It also judges each red check, in a `red-checks:` block, as `caused` by the PR or `unrelated`, an Unrelated failure, with a one-line reason (#780). It calls a check unrelated only on positive evidence (the same check red on the default branch, a failure in code the change can't reach, two attempts failing on different things, or a failure from the runner or a service), and a check it leaves out, misnames or can't tell about is caused. Its Verdict holds its findings, then a "Red Required checks" part: each check under its name, grouped by whether it failed again when the Kit re-ran it, is an outside one, or wasn't re-run and why, with its judgment and reason, its excerpt and job link. A `design-flaw` sends the Ticket back to design. With a caused check, anything else, a pass included, lands as an Execution flaw that counts, calling for a Retry, never a Touch-up, whatever its findings' tags. An Unrelated failure counts toward nothing: with only those, an `execution-flaw` calls for a Touch-up or a Retry by its findings' tags as on green, and the Retry is told to leave them alone; a pass is a pass, which goes to the Merge gate, where GitHub holds the merge until the check is green on the head. Each head's red checks are judged afresh. Ahead of the Verdict, one line on the PR, mentioning nobody, says each Unrelated failure is still red and links the check's issue, the one its Flaky checks use, which the Kit files with the Reviewer's reason and the red run's Failure excerpt, or comments on while it's open; the Verdict links it too (#781). One that later passes on that head is reported as a Flaky check, with nothing counted back. Its marker records the caused checks in `checks` and the Unrelated failures in `unrelated`; its `tags` count findings only. Once every caused check such a Verdict named has since passed on its head, as when you re-run it by hand, the hourly tick reads it: one with no untagged finding is counted back, with one line on the PR, mentioning nobody, saying it was a Flaky check, so it stops counting toward the Ticket's two Retries; one with an untagged finding counts for that, so the line reports its checks as Flaky checks and the count stands. Either way the check's issue is filed or commented on, with the red run's Failure excerpt, which the tick reads on its job's own `actions: read` and the Fabrik App's Checks: read (#778). A Retry already in flight keeps running, and a Back to design that already happened isn't undone. The tick reads check runs with the Fabrik App's Checks: read; without it nothing is counted back. The Weekly summary's Metrics table counts the week's Flaky checks, found either way, and Unrelated failures, against last week's. A red-check Verdict from before #779, with source `ci`, reads and is counted back as it always was.
- **One more re-run at the Merge gate** (#783): the first hourly tick after a pass that names an Unrelated failure still red on the head it was given on, with the PR at the Merge gate, re-runs that check's failed jobs once more on that head, so a check that clears by itself opens the gate without you. The tick's job holds no `actions: write`, and the caller workflow doesn't change, so the tick posts a quiet line on the PR, mentioning nobody, whose marker records the head and the checks (`<!-- fabrik:gate-rerun {...} -->`), and adds `agent:rerun-checks`. The Loop routes that label to the Re-run red checks job, still the only job with `actions: write`, which re-runs the failed jobs of the workflow runs behind the named checks on that head, past a run's first attempt this once; the claim job takes the label off as the run starts. On the Actions tab it shows as the run `PR #<n> labeled agent:rerun-checks`, with its Kit, Claim the work and Re-run red checks jobs, and no Review or push job. Later ticks read the head's check runs: a check green again is a Flaky check, reported by the tick's read of the passed head, with nothing counted back; a check red again by a run started after the line, a re-run that started no run, and a label still on at the next tick with no run behind it (which then comes off) are each said once on the PR and count as done (`<!-- fabrik:gate-rerun-done {...} -->`). A check from an outside service, and one whose latest result on the default branch's head is red, aren't re-run: the line says so and the re-run counts as done. The Kit asks once per PR, head and check and never tries twice on one head: added anywhere else, or again for the same head, by anyone, `agent:rerun-checks` comes off with one line saying why. The stuck-trigger sweep leaves it to this rule.
- **Bringing a held PR up to date when the fix lands** (#784, ADR-0031): when a check's issue closes as completed, each open agent PR at the Merge gate whose latest pass, on its current head, names an Unrelated failure of that check that hasn't since passed there is brought up to date by ADR-0011's path, though it's only behind the default branch: into draft, a plain rebase pushed with a lease, else one conflict-only run, one attempt per default-branch head, and the push starts a Review. Its notes say the fix for the check landed, naming its issue, under a `<!-- fabrik:check-fix {...} -->` marker. A PR that already holds the default branch's head has nothing to bring in, and one note says so. The hourly tick catches a close the issue-closed event missed. An issue closed as not planned or a duplicate brings nothing up to date. A check's issue a Design session rewrote as a brief is still the check's issue; one a Spec superseded is not, since the session moves its marker and `fabrik:flaky-check` onto the Spec, so its close brings nothing up to date and the Spec's closing as completed does (ADR-0037).
- **The Operator's mention** (#785, ADR-0031): once the Kit's own moves on an Unrelated failure are spent, the hourly tick posts one comment on the PR that @-mentions you, once per PR and check, with its own marker (`<!-- fabrik:operator-mention {...} -->`). It does so when the PR is at the Merge gate, held by an Unrelated failure still red on its head, one more re-run there is done or skipped for that head, and the check's issue is `needs-design`, `ready-for-human` or `needs-info`, or still `needs-triage` an hour after it was filed; or it closed as not planned or a duplicate; or the head is one the Kit brought up to date after the issue closed as completed, or the PR already held the default branch's head then. It names the check, links its issue, and says what's left: re-run it, fix it, or merge past it by hand as ADR-0019 describes. While the check's issue is `ready-for-agent`, or a PR for it is open, nothing is posted. A later tick, a new head or another failure of the same check posts no second mention; a different check on the PR gets its own. A commit status from an outside service gets no mention: the tick's tokens hold no Commit statuses: read, so it can't tell whether the status is still red. The Kit never takes a check off the Required list, skips it or merges past it.
- **The Standing follows the mention** (#795, ADR-0031): until the Kit mentions you, a PR at the Merge gate held only by Unrelated failures stands as `check-healing`, the Kit's move, not yours and stopping no work, so the Weekly summary doesn't list it under Waiting on you and a reader of the read library doesn't file it as yours. Its sentence says the check is failing on the passed head, that the Reviewer judged it an Unrelated failure, and what the Kit does next: it re-runs the check at its next hourly check, the re-run is asked for, or the re-run is done or skipped and the PR waits for the check's fix, naming the check's issue. Once the mention names the check the Standing is `check-failing`, yours and stopping work, and says the Kit has nothing left to try. A failing check the pass didn't name, or one never reported, makes it `check-failing` at once, as before, and so does a head that moved since the pass. A `check-healing` Standing turns Stuck at the repo's Stuck bar, counted from the pass or the Kit's latest sign on the PR or its Ticket, but never while the check's fix is under way (its issue is `ready-for-agent`, or a PR for it is open), and the clock restarts when the fix stops being under way. That is how a check no mention reaches, such as an outside service's, still gets to you.
- **Green checks**, and red ones as above, start the read-only Reviewer (Opus 5.5 by default, plus `.fabrik/review.md` when present) in a checkout of the PR's head. It holds only the agent service account and runs none of the PR's code. It judges the PR against its Ticket, the Ticket's Spec, the repo's standards and, when the repo has one at its root, `CODING_STANDARDS.md`. On a UI PR it also sees up to 8 of the PR's UI evidence screenshots, and a visual failure is an Execution flaw like any other (see `ui` in the [Kit config](#kit-config)). On a Product repo whose UI evidence comes from [Evidence shots](#evidence-shots), the Review's jobs first collect the head's shots from the named check's artifact, and a named shot the green check didn't produce sends the PR back before the Reviewer starts.
- **Full Review** (#747): a PR's first Review is a Full Review. The Kit works out the kind when it starts a Review, from the PR's Verdict markers alone: it is Full when no head of the PR has a Verdict from the Reviewer, since a Verdict from red checks, an empty diff or a Broken run judges no head, and when the latest Reviewer Verdict has no change line under it (one from before #643). Otherwise it is a later Review, judged against that Verdict's head, the last judged head. A new PR after Back to design or from a Kept-branch start has no Verdicts, so its first Review is Full. Only a Full Review's prompt carries the Full Review section: it is the only full Review the PR gets, so code it doesn't name is settled, and it names every flaw it finds at once, reads the whole diff and every changed file without cutting its own output, searches the repo for every name the change renames, removes or changes the meaning of, and says when a check it tried couldn't run. The Review's Run record says which kind it was, as `fullReview` (schema 11; a schema 1 to 10 record reads `null`).
- **Later Review** (#748, ADR-0026): every other Review is a later Review, which judges what changed since the last judged head. Before the Reviewer starts, a Kit step of the Review job reads, with the job's read-only token, every earlier Reviewer Verdict on the PR with the head it judged, the Kit's note of each Implement run's push with the `fix` comment the run wrote (each named `Retry n`, `Touch-up n`, `Touch-up n, body only` for a body-only Touch-up's note, `Request-changes run` or `conflict-only run`, and given as data, never proof), the kind of run that pushed the head (none for an Operator push or the Kit's rebase), and the PR's own change since the last judged head. That change is worked out with git: each of the two heads is diffed against its merge base with `main`, so what `main` brought in by a merge or a rebase is no part of it, and each of the PR's own files whose own change differs comes with the difference between its own diff then and now. When a rebase dropped the last judged head, the Reviewer gets instead the PR's own files whose hashes differ from the fingerprint on that head's change line, and reads their whole own change. Only a later Review's prompt carries the later-Review section: it judges whether each finding of the Verdict before was fixed, everything the PR's own change gained since in full, every acceptance criterion and the body across the whole PR, and in settled code only a behaviour bug, tagged `[missed earlier]`. A Design flaw stays open to it, and on a conflict-only run's push it judges only how the run changed the PR's own diff, plus the criteria and body.
- **The Verdict contract**: the Reviewer's reply starts with exactly one line, `verdict: pass`, `verdict: execution-flaw` or `verdict: design-flaw`, then its findings. Anything else, an empty reply or a provider error, is an Infrastructure failure, never a pass.
- **Tags** (#749): on an Execution flaw each finding is a top-level `- ` item, which may open with `[small: body]` (the PR body doesn't match the branch), `[small: comment]` (a comment or doc the change left stale that no acceptance criterion asks for and isn't the deliverable) or `[missed earlier]` (a behaviour bug in settled code, on a later Review only). The Kit reads the tags and checks nothing in code; any other item counts, and prose outside the items carries no tag. A Reviewer's Execution-flaw marker counts its findings by tag, as `"tags":{"small":…,"missedEarlier":…,"counted":…,"smallBody":…}`, where a `[missed earlier]` on a Full Review counts as untagged; a pass and a Design flaw carry none. The posted Verdict shows the tags as written, and the Review's Run record carries the counts as `findingTags` (schema 11; a schema 1 to 10 record reads `null`). A Reviewer's Execution flaw whose items are all tagged calls for a Touch-up instead of a Retry while one is left; any other calls for a Retry (see **Touch-ups** under [Execution-flaw retries](#execution-flaw-retries)).
- **A criterion no run can meet** (#765): an acceptance criterion that asks for a Trust-root change, a GitHub write, a commit, branch or state the run isn't given, a suite or command no Required check runs, or anything only the Operator can do, or a literal no output can meet, is a Design flaw on the first Verdict that finds it, on a Full Review or a later one, whether the PR body names it under "Criteria no run can meet" or the Reviewer sees it for itself. Its findings name the criterion and why no run can meet it. The review prompt lists the Trust-root files the guard refuses, says an Implementer holds no GitHub credential, works only on the branch the Kit checked out and runs only what its Sandbox has, and points the Reviewer at `sandbox.checks` and `.github/workflows/` in its checkout for what the Required checks run. When the Reviewer disagrees with the body's claim, it gives an Execution flaw whose untagged finding says how a run can meet the criterion. A PR with an unmet criterion never passes, whatever its body says. No Verdict, marker field or tag is added: the Design flaw goes Back to design as any does, and the PR's branch becomes the Kept branch.
- **Follow-ups**: a pass has no nits. Its findings are what the Reviewer checked, and it may end with Follow-ups: work that deserves its own issue but lies outside the Ticket's scope. Each is a fault or an idea (#885, ADR-0039). A fault is something already wrong, such as a bug, a test that is missing or fails, or a doc that is stale, and its body says where it is, by file and line, and what shows it is wrong. An idea is anything else, such as an improvement, a refactor or a feature, and so is a problem the Reviewer cannot show as a fault's body requires. They come after the findings and before any `operator comments considered:` line, as a `follow-ups:` line, then one `- [fault] <title>` or `- [idea] <title>` item per Follow-up with its Markdown body indented two spaces beneath it; an item with neither mark is an idea. The Verdict comment shows them under `### Follow-ups`, the ideas first and then the faults. An idea has an **Open as issue** link to the Product repo's new-issue form, prefilled with its title and its body ending `From PR #<n>`, cut short to fit GitHub's URL limit, and the Kit opens nothing for it. A fault has, in place of a link, the line "The Kit opens this fault as an issue when the pull request merges." (see **Faults open as issues** under [Merge gate](#merge-gate)). A Design session that rewrites an issue opened from either keeps its `From PR` line, so the issue stays tied to the pull request it was filed from. A flaw drops a Follow-ups block, and a malformed block on a pass stays in the findings as plain text, so the Verdict still lands.
- **Posting**: the push job posts every Verdict, red checks' included, as a PR comment from the Fabrik App, linking its run. The comment's first line is a marker, `<!-- fabrik:verdict {"verdict":…,"source":"reviewer"|"ci"|"empty-diff","requestChanges":…,"headSha":…} -->`, with `"conflictRun":true` before `headSha` on a Verdict after a conflict-only run, and `"requestChangesFirst":[<review ids>]` on an Execution flaw that gave way to the Operator's Request changes no run had built (#341), so a PR's review history can be read from its comments alone. Its second line, `<!-- fabrik:change {"v":1,"all":…,"product":…,"files":…} -->`, is a fingerprint of the PR's own change at that head (the lines it adds and removes against its merge base with the default branch, hashed per file, so a rebase onto a moved `main` leaves it equal), which the push job reads with git, leaves off when it can't be read, saying so in its step summary, and keeps out of what any agent is given. The marker is only read from bot comments. A Verdict is posted once per head commit, and never for a commit the PR has moved on from.
- **Yield** (#735): each Implement run's Run record names the PR and head its push left, as `pushed`, so the Weekly summary's Metrics table shows **First-pass yield**, **Retry 1 yield** and **Retry 2 yield** straight after Tickets dispatched: of the runs of each kind whose push got its first Verdict in the week, from the Reviewer or red Required checks, the share that passed, as `35% (24 of 69)` beside last week's, or `no judged runs`. An empty diff or a Broken run counts as not passing in the week it ended. A Verdict later counted back as a Flaky check leaves its run out, and so does a run that pushed nothing or whose head was never judged. Request-changes runs, conflict-only runs, Touch-ups and Replay arms are in no Yield, though a first run whose Verdict called for a Touch-up counts as not passing, and nor is a run whose record was written before `pushed` (schema 1 to 9), since its passing runs name no push: in the first week on the release, last week reads `no judged runs` and the change `–`.
- **Retries per merged PR** (#736): straight after the Yield rows, the Metrics table's **Retries per merged PR** is, for each agent PR merged in the week, the Retries on its Ticket's whole path that ended before the week's end, on any of its PRs, averaged to one decimal, beside last week's. A merged PR with no Ticket counts 0. A Retry counts once for its Ticket, PR and Retry number, so one started again after a failed landing is one Retry, here and in the **Retries** row. A Touch-up is no Retry, here or there.
- **Touch-ups per merged PR** (#754): straight after Retries per merged PR, the Metrics table's **Touch-ups per merged PR** is, for each agent PR merged in the week, the Touch-ups on its Ticket's whole path, walked as Retries per merged PR walks it, averaged to one decimal, beside last week's. A Touch-up counts once for its Ticket, PR and Touch-up number, so one started again after a failed landing is one Touch-up. A record written before `touchUp` (schema 1 to 10) counts 0.
- **Missed earlier per merged PR** (#753): straight after Touch-ups per merged PR, the Metrics table's **Missed earlier per merged PR** is, for each agent PR merged in the week, the findings tagged `[missed earlier]` across the Review records on its Ticket's whole path, walked as Retries per merged PR walks it, averaged to one decimal, beside last week's: how much a Full Review still misses, in behaviour only. A Review counts only when its Verdict landed, that is when its PR has the Fabrik App's Reviewer Verdict on the record's head, posted by the record's own run attempt, so a stale Review counts nothing. A Full Review's `[missed earlier]` counts as untagged, so it adds nothing here. A record written before `findingTags` (schema 1 to 10) counts 0, so the first week on the release reads low.
- **A pass** starts the Digest writer: after its Verdict the push job adds `agent:digest` to the PR, which stays in draft with no review requested. The Operator's review is requested when that attempt ends, with a [Digest](#digest) or without one, and that request is the event's one notification. With `digest.enabled` false, the pass itself takes the PR out of draft and requests the Operator's review. A pass that keeps the PR in draft adds no label: one on a PR that conflicts with `main`, which is brought up to date first, so the pass on that head brings the Digest, and one that gives way to a Request changes deferred during a Retry. A flaw is posted and mentions nobody, and never adds the label.

## Digest

A Digest is the Kit's plain-English account of an agent pull request as it stands at one head, written for the Operator to decide from (ADR-0022). It is a comment of its own on the pull request, written by a role of its own, the Digest writer, never the Reviewer. Nothing in the Loop moves because of what a Digest says.

- **The label**: adding `agent:digest` to an agent pull request, whoever adds it, starts a Digest run at the pull request's head. It is honoured only on an open agent pull request whose latest Verdict is a pass on its current head, with no Retry, Request-changes run or conflict-only run in flight on it, and with `digest.enabled` on. Otherwise it comes off with one line saying why, as a declined `agent:review` does; on an issue it comes off with one line saying where it goes. It stays on until the attempt ends. Added by hand to a pull request already at the Merge gate, it moves nothing there: the pull request's draft state and its review request are left as they are (see **The gate**).
- **The Digest writer** (the Reviewer's model, and the effort a repo's own `roles.review` sets or else `medium`, unless `roles.digest` sets its own, 10 minutes by default, plus `.fabrik/digest.md` when present) is read-only, like the Reviewer: it gets a checkout of the head the pass was given on with its full history, holds only the agent service account and no GitHub credential, and runs none of the code. It gets the Base skills alone (ADR-0008). Its job is named `Digest PR #<agent PR>`, and one runs per pull request at a time. It is given the Ticket and its Spec; the pull request's title and body; the Operator's Request changes with their line comments, and the Operator's comments, as the Reviewer is given them; every Verdict, with the head it judged; the Kit's own notes on the thread, oldest first; and whether UI evidence exists, and the routes it captured, or, on a pull request whose UI evidence is Evidence shots, the named shots that were produced. Beside these it is given Kit code's facts, as a block of their own (see **Kit code's facts**). It is given no transcript, no Run record and no earlier Digest. It writes for the Operator and changes nothing, and beyond whether each thing asked for is in the head (see **Needs your eyes**) it judges nothing. Its reply is eight fields (`asks`, `items`, `whatItDoes`, `howItGotHere`, `followUps`, `walkthrough`, `decided` and `roundsLine`), checked in its own job and again in the push job, which Kit code lays out.
- **The comment**: the push job posts the Digest once, as the Fabrik App, and never edits it. Its first line is a marker, `<!-- fabrik:digest {"head":…,"asks":[…],"carriedFrom":null} -->`, naming the head it is written as of and the asks it answered (see **Needs your eyes**), and under it is its data line (see **Places and data**). Then come a line naming the pull request and that head; the top's four sections, which are **Needs your eyes**, **What it does**, on what changes for the End user, **How it got here** and **Follow-ups**; under a hidden `<!-- fabrik:digest-folds -->` line, which only Kit code writes (one in the writer's own words is taken out), four folds, which are **Walk me through it**, **Decided without you, and left alone**, **The rounds** and **The criteria and how each was checked**; and a link to the run. The bullets below say what each holds. Every mention is taken out, as a Verdict's findings lose theirs. A Digest is dropped, with nothing posted, when its pull request is closed, has moved on from that head, has a run now in flight on it, or has a latest Verdict that is no longer that pass. Posted or dropped, `agent:digest` comes off.
- **No Digest**: a run that fails, one that runs past its time limit and a reply Kit code refuses each post the no-Digest line on the pull request. Kit code refuses a reply that breaks its shape; one that leaves an ask of yours unanswered, whose items do not cover every ask that is not in the head, or whose top runs over 180 words (see **Needs your eyes**); one that names a Follow-up Kit code did not list, or names a fault among the Follow-ups to show (see **Kit code's facts**); and a Digest too long for one comment (see **Places and data**). The line is one comment: its first line is `<!-- fabrik:no-digest {"head":…,"how":…} -->`, then "No Digest could be written for this head", the short head, how (`failed`, `timed-out`, or `refused` with Kit code's reason) and a link to the run. Two more ways have no run to link: `no-subscription` (see **Never held**) and `never-started` (see **A lost start**). It mentions nobody, no failure notice follows, nothing counts against the Ticket's Retries, and `agent:digest` comes off. Adding the label again asks for another attempt.
- **The gate**: the Merge gate waits for the Digest writer's attempt, never for its success (ADR-0022). A pass adds `agent:digest` in place of opening the gate (see [Review](#review)), and the gate opens when that attempt ends: once a Digest is posted, or the no-Digest line for an attempt that failed, ran past its time limit or was refused, `agent:digest` comes off, the pull request leaves draft and the Operator's review is requested, in that order. Two passes open the gate themselves, adding no label: one whose last Digest is carried forward (see **Carried forward**), and one given with Subscription rotation on and every Subscription used up (see **Never held**). A dropped attempt opens no gate: a head that moved gets a Review of its own, whose pass brings the next Digest; a run in flight lands first; a closed pull request has no gate. The gate opens once for a pass, only while the pull request is a draft that has not left draft since that pass. On one already at the Merge gate, as when the Operator added the label by hand, or one the Operator put back in draft after the gate opened, the Digest or the line is posted, the label comes off and nothing else moves: no second review request. A passed draft waiting on its Digest is still a draft, so it keeps its `max_in_flight` slot until the gate opens.
- **Never held**: A Digest run is never a Held run. With Subscription rotation on and every Subscription used up, where any other run due would be held, a pass adds no label: it posts the no-Digest line with `no-subscription` and opens the gate in the same step. `agent:digest` added then gets the same line and comes off, and the gate opens if it has not. No Held line is written on the pull request and no held marker on a Kit-owned issue. With rotation off, the run starts and fails as any run does, and the gate opens with the line. A Digest run refused on a Subscription's weekly limit, killed for spending usage credits or refused a dead token still opens or comments on that Kit-owned issue, as any run's failure does: that is how the Kit learns a Subscription is used up. The Digest run itself is not run again on another Subscription and is not held: the no-Digest line is posted and the gate opens.
- **A lost start**: the stuck-trigger sweep (see [Implementation](#implementation)) neither adds `agent:digest` again nor hands it to you. When the label has been on for 30 minutes with no `Digest PR #<that pull request>` job unfinished, the hourly tick posts the no-Digest line with `never-started`, takes the label off and opens the gate. A Digest job on another pull request doesn't count, and with the Actions API unread the label is left alone, as every label is. The usual cause is GitHub itself: it starts no workflow for a pull request that conflicts with its base (ADR-0015), as when `main` moves just after the pass. A lost start on a pull request overtaken since, with a run now in flight on it or no pass on its head, is dropped as any attempt is: the label comes off, nothing is posted and the gate stays closed. On anything but an open agent pull request the label comes off with one line saying why.
- **Spend**: a Digest run writes a Run record in role `digest`, on its Ticket, naming its pull request, with its model, cost, outcome and transcript, and its Infrastructure failure when it failed. The Run-record schema is unchanged: the role is a new value, not a new field. A run that never started writes none. A failed Digest run posts no Verdict, so nothing counts it against the Ticket's Retries. The Weekly summary's cost per merged PR and spend that never merged count a Ticket's Digest runs beside its Implement and Review runs; until the `fabrik-runs` store's caller is on this release, they leave Digest runs out. No Scorer judges a Digest run: only Implement runs are picked for scoring.
- **Kit code's facts**: everything in a Digest that can be counted is worked out by Kit code from the pull request's thread, and the Digest writer words it and may not contradict it. The facts are: the rounds, oldest first, each with who and what (each Verdict, from the Reviewer, red Required checks or the Kit itself; each push the Kit noted, which is the first run, a Retry with its number, a Request-changes run, a conflict-only run or the Kit's own rebase onto `main`, the push that opened the pull request being the Retry it was when the Ticket's runs before it landed nothing; each Request changes of yours; and each failure notice, an Infrastructure failure or a Broken run, a failed conflict-only run's among them); each Verdict's effect on the code against the Verdict before it (product code, tests only, none, or not known), from the fingerprints the Verdicts record; the counts of each kind of Verdict, of Retries, conflict-only runs, Request changes and Infrastructure failures; how many Retries are left, by the count under [Execution-flaw retries](#execution-flaw-retries); the Follow-ups of every pass on the pull request, each with an id (`f1`, `f2`, …), its kind, a fault or an idea, its title and, on an idea, its Open as issue link as its Verdict has it; and whether the product code changed since the first Verdict, whatever that Verdict's source: unchanged, changed with the files that differ, or could not be established when either Verdict records no fingerprint; and the Required checks that passed on the head only by being skipped or reporting neutral, as the pass there records them, which the writer may not offer as checking anything. The writer is given them as a block of their own, and two fields of its reply answer them: `followUps`, the ids of the ideas to show, and `roundsLine`. The comment has **Follow-ups** after How it got here: first every fault, each once by its title, as a line with its title and "the Kit opens this fault as an issue when the pull request merges", then each idea shown as a line with its title and its link, or "None named." with neither. Kit code shows every fault itself, whatever the writer's `followUps` holds, and the writer's choice among the ideas gates nothing (#885). Then comes a third fold, **The rounds**: Kit code's table of who, what and the effect on the code, built from the push job's own read of the thread, then the writer's one closing line. A reply naming a Follow-up Kit code did not list is refused, and so is one naming a fault's id, and the no-Digest line says so. Nothing checks the writer's sentences against the facts: its prompt holds it to them, and the table beside them is Kit code's own.
- **Needs your eyes**: the one thing the Digest writer judges is whether each thing you asked for is in the head, against a list it cannot skip. Kit code lists the asks among its facts: every Request changes of yours on the pull request as the Reviewer is given them, so neither a dismissed one nor one deferred during a Retry, and every line comment in each. Each has an id made from GitHub's own id of the review or of the line comment (`review-<id>`, `inline-<id>`), the same at every head, and a review whose own text is empty is listed by its line comments alone. The writer adds the Ticket's acceptance criteria, as any Request changes amended them, each under an id of its own (`c1`, `c2`, …) with the criterion in one line, and answers every ask: in the head, not in the head, or could not tell, with where it looked and how it was checked (a test, an end-to-end test, reading, a search, or Required checks). An ask the Kit opened a Spin-off from (#884) carries them among Kit code's facts, as `spinOffs`, and the fourth fold shows them under it: the writer answers such an ask for what was to be built, or set aside, when the whole of it was, which needs no item. Its reply holds `asks`, those answers, and `items`. In the comment, **Needs your eyes** is first and always there: at most four items, each a bold claim and one or two sentences on what is true at this head and why it falls to you, or "Nothing." An item has one of three kinds, shown in this order: asked for and not here, which is something you asked for (a Request changes, or a criterion unmet as written) that is not in the head or could not be told, and which names the asks it is about; yours to judge, which is what only you can judge, such as words an End user reads, prices or policy; and not proven, such as no picture of a changed screen or a check that was not run. There is no fourth kind: a refactor's Needs your eyes may say "Nothing." The comment also has a fourth fold, **The criteria and how each was checked**: Kit code's table of every ask, yours and then the criteria, each with its answer, how it was checked and where the writer looked, one that is not in the head or could not be told marked in bold. The comment's first line records, as `asks`, the ids of Kit code's asks the Digest answered. An item that is asked for and not here, or not proven, may carry a suggested request of at most 40 words: an instruction that would get the thing built or shown, which an Implementer run could carry out in its Sandbox. It is not shown on GitHub. A reply is refused, and the no-Digest line says which, for: more than four items, an unknown kind or answer, or an id used twice; an ask of Kit code's left unanswered, or an answer under an id that is neither Kit code's nor a criterion's; an ask answered not in the head or could not tell that no asked-for-and-not-here item names; an asked-for-and-not-here item that names no ask, or one answered in the head or set aside, and an item of another kind that names any; set aside for an ask the Kit opened no Spin-off from, or for a criterion; and Needs your eyes, What it does and How it got here coming to more than 180 words between them, where a word is a run of characters between spaces, counted over each item's claim and sentence and the two texts. Not refused: a section a few words over its own cap, 90 words for Needs your eyes and 40 each for the other two, which the prompt gives the writer; a suggested request on an item that is yours to judge, or one over its 40 words, which Kit code drops, keeping the item; and items out of kind order, which Kit code puts in order, keeping the writer's order within a kind. Kit code holds no list of the criteria, so it cannot tell that the writer left one out: only a skipped Request changes or line comment refuses a Digest.
- **Places and data**: The Digest points and never quotes, so nothing you judge was retyped by a model. Each item of the writer's reply names the lines it is about as `places`: none, or up to three places, each a `path`, `start`, `end` (a file in the head and its first and last line, both included) and whether it is `code` or `words` an End user reads. A fourth place on an item breaks the reply's shape, so the Digest is refused. Before the Digest lands, Kit code checks each place against what the head holds, which the push job reads through GitHub's API: the text at that head of each file a place names, and the pull request's files with their patches. A place whose file is not in the head, whose lines run past the end of the file, or whose first line is after its last is dropped, and its item is kept: a wrong line number costs that one link, never the Digest. A place longer than 40 lines is cut to its first 40. Each place that lands is marked `inDiff`, which says it can take a pinned comment: every line of it lies in one hunk of that file's diff in the pull request, on the head's side, the hunk's unchanged lines counting, and it is false in a file the pull request does not change and in one GitHub gives no patch for. Each carries a `fingerprint`, the first 12 hex characters of the SHA-256 of its lines at the head, after the cut, joined by newlines. In the comment each item ends, after its sentence, with its places as plain links to the file and its lines at the head, and no code appears above the folds. The whole top is also there as data: the comment's second line, directly under the first, is the hidden `<!-- fabrik:digest-data {"v":1,…} -->`, one line of JSON that Kit code writes from the same fields it rendered, never parsed from the Markdown. It holds `items`, in the order shown and none when Needs your eyes says "Nothing.", each with its `kind`, `claim`, `sentence`, its `places` (each with `path`, `start`, `end`, `as`, `inDiff` and `fingerprint`), `picture` (see **A picture**) and `suggestedRequest`, which is in the data alone; then `whatItDoes`, `howItGotHere`, `followUps`, each idea shown with its `title` and its `url`, and `faults`, each fault with its `title`, which a data line written before a Follow-up had a kind has none of and reads as none. The asks an item names are checked before landing and are not in the data, and the four folds carry none. Like the first line, it is read only from a comment the Fabrik App wrote, and it is spelled as the Kit's other text-carrying markers are, so no text in it can close the comment early or mention anyone. The version, `v`, goes up only when a field is removed or changes meaning; a reader says of a version it does not know that it cannot read the Digest, and of a line that does not parse that it is malformed, and never falls back on the Markdown. The first line also holds `carriedFrom`, the head a Digest carried forward was first written at, which is null on one written fresh. A Digest whose comment, data line included, would be longer than the 65,536 characters GitHub takes is refused, never cut (see **No Digest**).
- **A picture**: an item may point at one picture, named as a route the pull request's UI evidence captured. Each item of the writer's reply has `picture`: one route, or null, and a reply with a list of them there breaks its shape. The Digest never embeds or links an image: a reader such as the Console draws the picture from the artifact the evidence marker names. The captured routes are the `routes` of the evidence marker in the pull request's body (see `ui` in the [Kit config](#kit-config)), the routes its evidence section lists under "Captured routes", so a route whose every shot was missed is among them. There are none on a pull request with no UI evidence, which is one with no evidence marker or one whose capture kept no screenshots, and none under a marker that names no routes, as one written before markers recorded them. The writer is told the captured routes, or that there are none, and its prompt has an item about a screen name one of them, and a changed screen with no captured route be an item that is not proven. Before the Digest lands, Kit code checks each picture against the captured routes, which the push job reads again from the body as the Loop's snapshot reads its marker, only from a body the Fabrik App wrote. The route is compared exactly: a route with a query, a slash after it or letters in another case is not the captured one. A picture whose route is not among them is dropped, and its item is kept, as for a place that does not resolve. In the data line the item's `picture` is the route, or null. In the comment the route is named in words after the item's places, as `Picture: the captured route` and the route. On a pull request whose UI evidence is [Evidence shots](#evidence-shots), a picture is instead one of the named shots that were produced, by its name, and everything else here holds as for a route. Those are the names in the shots marker in the pull request's body, read only from a body the Fabrik App wrote, but for a named shot missed as `not-produced`, `ambiguous-name` or `refused`; one that lacks only a size is among them. There are none before the Review's jobs have read the named check's artifact, and none when nothing of it could be read. The writer is told those names, or that there are none, and a changed screen with no named shot that was produced is an item that is not proven: a pull request whose one named shot was missed, the miss shown with no Retry left, gets a Digest that says its screen is not proven. The name is compared exactly: a name in another case, or with a space more or less, is not the shot, and neither is a shot of the run that the pull request didn't name. In the data line the item's `picture` is the shot's name, or null, and in the comment it is named as `Picture: the Evidence shot` and the name.
- **Carried forward**: when a pull request comes back to the Merge gate at a new head and only `main` moved under it, no model runs: the Kit posts its last Digest again for the new head. The last Digest is the newest Digest comment on the pull request, whatever head it names. On a pass that would open the gate, with the Digest on and before anything else is tried, it is carried when all of these hold: it reads back, data line included; the pass has a fingerprint of the pull request's own change, a Verdict on that Digest's head has one, and their `all` is equal (see [Review](#review)); and the Kit's list of asks is the list that Digest answered, by the ids on its first line. So a changed line in the pull request's own change, however small, a Request changes since that Digest, even one that left the lines the same, a pass or an earlier Verdict with no fingerprint, and a Digest that does not read back each carry nothing, and the pass adds `agent:digest` as usual. The carried Digest is a new comment, posted in the step that lands the pass. Its first line names the new head, the same `asks` and `carriedFrom`, the head the Digest was written at; one carried a second time keeps the first `carriedFrom`. Under its opening line is one added line: "Carried over from", the short head it was written at, "because only `main` moved." The top is rendered again from the data, with a fresh data line under the first, and the folds are reused as they were written, character for character, from the folds line down, with the link to the run that wrote them. Its words, its counts and its rounds table are as they were when it was written, which is what the added line says; the fresh pass on the new head is what covers a change on `main` that makes an old item wrong. Each place is re-pointed, since its lines may sit elsewhere after the rebase and the Digest holds only their fingerprint: the push job reads the file at the new head and slides a window of the place's length over it. A window that matches exactly once is the place, at its new lines; with no match, more than one, or no such file, the place is dropped and its item kept. `inDiff` is worked out afresh at the new head, and a picture is kept as it was. Then the older Digests are collapsed, the one it was carried from among them, and the gate opens. No label is added, no run starts and no Run record is written. If the files cannot be read at the new head, or the carried comment would be too long for GitHub, nothing is carried and the pass goes on as if no Digest could be: it adds `agent:digest`, or with every Subscription used up posts the no-Digest line. A list of asks that could not be read carries nothing either, and the push job's step summary says so.
- **Collapsed**: a pull request that comes to the Merge gate three times has three Digests on its thread, and the current one is the newest whose head is the pull request's head. So once a Digest is posted, and before the gate opens, the push job collapses each older Digest on that pull request as outdated: one GraphQL `minimizeComment` call, with the classifier `OUTDATED`, for each one not collapsed already, made as the Fabrik App with the Pull requests write it comments with. Only Digests are collapsed, never a no-Digest line, a Verdict or any other comment, and nothing is ever un-collapsed. A collapsed Digest is still returned whole by GitHub's API, so everything that reads one reads it as before. A call GitHub refuses stops nothing: the push job's step summary names it, the remaining calls are still made, the gate still opens and the job stays green, since the current Digest is found by its head either way.
- **The Operator's moves**: the Operator's moves win while a Digest is being written, and the attempt under way never holds one up. A Request changes of the Operator's on a passed draft whose gate has yet to open (a draft whose latest Verdict is a pass on its head, which has not left draft since that pass and has no run in flight on it) is acted on at once, as one at the Merge gate is: the Kit's note starts the Request-changes run, on the Step-up model, using no Retry, the pull request stays in draft, and `agent:digest` comes off. It counts as one given at the Merge gate everywhere the Kit counts them: it is unbuilt until a run builds it, a pass settles it, and one GitHub never delivered is found by the check for those once the pull request is out of draft (see [Merge gate](#merge-gate)). The Digest attempt that was under way lands on a pull request with a run in flight, so it is dropped, and the pass on the run's push brings the next Digest. A Request changes on any other draft does what it always did: on one with no pass on its head, on one the Operator put back in draft after the gate opened, and on one a pass kept in draft with a run in flight on it, to be brought up to date with `main` or for a Request changes deferred during a Retry. Send it back, `needs-design` on the pull request, closes it as it does any agent pull request, and the Digest that lands on the closed pull request is dropped. A push to the draft starts a Review of the new head, and the old head's Digest is dropped. Marking the pull request ready by hand does not stop the Digest: it lands and the label comes off, and nothing else moves, with no review requested, since the gate was opened by hand.
- **Never an agent's input**: a Digest is words for the Operator only, so no agent run is ever given one to read. A Digest comment and a no-Digest line, each told by its hidden first line on a comment of the Fabrik App's, are left out of every agent's input: the pull request's comments a Retry, a Request-changes run or a conflict-only run is given; the Kit's notes the Digest writer itself is given, so it never reads an earlier Digest; the Reviewer's input, which carries no comments but the Operator's; and what a Design session is given of a pull request sent back to it, which is its Verdicts and the Operator's words. The Retro's evidence carries neither, and leaves out every Run record in role `digest` with its transcript, which holds the Digest, as it leaves out a judge's run.

## Execution-flaw retries

An Execution flaw gets fixed without the Operator, silently: no mention, assignment or review request.

- **The trigger**: an Execution-flaw Verdict, from the Reviewer or red CI, adds `agent:implement` to the PR's Ticket. On a Ticket whose agent PR is open, that label resumes the PR's Implement run rather than starting a new branch: the Implementer runs again on the PR's own branch, in a fresh clone checked out at its head, with the latest Verdict's findings in its prompt. The label comes off as the run starts.
- **The count**: a Ticket gets 2 retries in all, one pool counted from its empty diffs and Broken runs before the PR opened (its `<!-- fabrik:empty-diff -->` and `<!-- fabrik:broken-run -->` comments since its last Design session) and the PR's earlier Verdict comments (#415), a Broken run's among them (#434). So after one empty diff the PR's first Execution flaw starts Retry 2, stepped up, and after two the stepped-up run that opened the PR was Retry 2, so its first flaw sends the Ticket back to design: no Ticket drops back to the Implementer's model once it's stepped up. Every Execution flaw counts, whoever pushed the flawed head, the Operator included (ADR-0006), except one that gave way to your Request changes (see **Request changes** under [Merge gate](#merge-gate)), which never counts or calls for a retry. A Request-changes run itself uses no retry, but an Execution flaw on its push (its Verdict marked as from a Request-changes run) calls for one, and that retry counts like any other (#393). An Infrastructure failure posts no Verdict, so it never uses one up: re-adding `agent:implement` on the Ticket runs the same retry again, on whatever head the PR is at by then. A Broken run is the exception (#434): a Retry that was one posts an Execution flaw Verdict (`"source":"broken-run"`), mentioning nobody, which counts like any other, so the next Retry starts on the PR's head as it is then, or the Ticket goes back to design. It resumes a stalled Request-changes run the same way, which the Kit's note that started it marks in flight on the PR.
- **In flight**: a retry is in flight from the Verdict that calls for it until it pushes (its note opens `<!-- fabrik:retry-push -->`), ends in an empty diff or a Broken run, or is refused, and that includes the stall after an Infrastructure failure, unless the PR has left draft since that Verdict. A Request-changes run is in flight from the Kit's note that started it, or the Execution flaw that gave way to it, until it pushes, is given a Verdict or ends, until the PR leaves draft, or until you dismiss every review it's for. Meanwhile a push to the PR, the Operator's included, starts no Review and gets no Verdict, so it uses no retry: the run's own push starts the next Review, which judges the PR as it then stands. A retry that finishes while a Request-changes or conflict-only run is in flight lands nothing, and a Request-changes run lands only while it's the one in flight for its review, as a retry does only while it's the Retry in flight for the flaw it was started for, by number and by the head that flaw was given on. A run's push note (a retry's, a Request-changes run's or a conflict-only run's) goes up just before its push, so the Review the push starts sees it, and names the head it pushes on a `<!-- fabrik:pushed-head <sha> -->` line (#420). A note whose head never reached the PR's branch, as when the push failed or its lease refused it because you pushed meanwhile, counts as no push: the run stays in flight and the reviews it was for stay unbuilt, re-running the push job lands its work, and a Review of your push gets no Verdict.
- **The Step-up**: the first retry runs on the Implementer's model (`roles.implement`), the second on the Step-up model (Opus 5.5 by default, `roles.step_up`), for that PR only. A Retry called for by an Execution flaw on a conflict-only or Request-changes run's push (both run on the Step-up model) steps up too, recorded under that run's reason (`conflict-only` or `request-changes`), unless it's the second retry (`retry`) or the Ticket is marked (`marked`); an earlier stepped-up run whose push didn't get that flaw doesn't step it up, except that a Retry after a Touch-up keeps the Step-up that Touch-up ran with (see **Touch-ups**). A conflict-only run on a Request-changes run's push records `conflict-only`. The Kit never drops to a cheaper model or skips a Step-up for any reason, except when you take `fabrik:step-up` off before a Retry that would step up only for it.
- **A Stepped-up start**: a Ticket labelled `fabrik:step-up`, by the Design session that wrote or rewrote it (its Ticket JSON's or agent brief's `"stepUp": true`, which a brief's `"stepUp": false` takes off again) or by you, runs every Implement run on the Step-up model while the label is on, its first run, Retries and Request-changes runs alike (ADR-0014). The label is read as each run starts, so adding it between Retries steps up the next one, and removing it drops back to `roles.implement`, except for Retry 2, a Retry that follows a conflict-only or Request-changes run's flaw (see **The Step-up**), and a Touch-up or a Retry that follows a stepped-up run's (see **Touch-ups**). A marked Ticket still gets 2 Retries, and a third Execution flaw is a Design flaw. Triage never marks a Ticket. Each Implement run's Run record says whether it Stepped up (`stepUp`) and why (`stepUpReason`: `retry`, `marked`, `request-changes` or `conflict-only`), and the Weekly summary breaks Step-ups down by reason, beside the marked Tickets merged that week and how many needed no Retry.
- **The push**: the push job runs the trust-root guard on the run's own changes and updates the PR's branch, which starts Review again. It also replaces the PR body with the run's `summary`, which describes the whole PR as it now stands, so the next Review never reads a stale one, and posts the run's `fix` (what it was asked to fix and what it changed) as a comment. A retry may merge `main` in when a finding needs work that has since landed there (the Reviewer asks for a merge, never a rebase), and a Request-changes run brings `main` in as its review or a conflict needs (see **Request changes** under [Merge gate](#merge-gate)): the guard then judges only the run's own commits (a merge showing only what was changed by hand) and the paths it changed that read neither as `main` has them nor as git's own merge of the PR's head and the `main` the run brought in would, never what `main` already has, and the push may replace the branch, with a lease. The only heads of `main` it counts are `main` as the Kit job read it before the run started and `main` as it is at the push, never a commit the run's result names or one `main`'s history holds but `main` was never at, and it merges as the PR's `.gitattributes` said before the run. Only the agent branch is ever pushed. A retry that commits nothing is posted as an Execution-flaw Verdict with source `empty-diff`, and counts like any other. A Request-changes run that commits nothing on a PR that doesn't conflict with `main` gets no Verdict and calls for no retry (#388): its `<!-- fabrik:request-changes-run-empty -->` note is its outcome, which ends its time in flight and settles the reviews it read (see **Request changes** under [Merge gate](#merge-gate)).
- **An Evidence miss** (#819, ADR-0033): on a Product repo that uses [Evidence shots](#evidence-shots), a run whose push leaves a UI PR with no names and no `nothingVisible` gets the Kit's own Execution flaw at the head it pushed, with source `evidence-miss`, posted after its push note. It counts like any other, a first run's after the Ticket's empty diffs and Broken runs, and calls for a Retry, never a Touch-up. With no Retry left the Kit gives none, and Review goes ahead with the miss shown. A named shot the green named check didn't produce, at a head an Implementer run pushed, gets the same flaw from the Review's push job in place of the Reviewer's Verdict (#820).
- **A branch that moved**: if the PR's branch moved while the run worked, say because the Operator pushed, the push job rebases the run's own commits onto the new head, without a working tree, and pushes that (ADR-0006). The guard and the empty-diff rule judge only the run's own commits, never the ones it landed on, so the Operator's commits in between may touch trust-root files. If the rebase conflicts, or the run had rewritten the history it built on, nothing is pushed: the Kit comments on the PR that the run's work was discarded and starts the same run again on the new head, with the same findings or review, using no retry. Restarts aren't capped.
- **Used up**: a third Execution flaw is posted, starts no retry, and counts as a Design flaw, unless you have a Request changes on the PR no run has built, when it gives way to that instead.
- **Touch-ups** (#750, ADR-0027): a Reviewer's Execution flaw with at least one item, every item tagged (see **Tags** under [Review](#review)), calls for a Touch-up instead of a Retry while the PR has one left. `agent:implement` on the Ticket starts it on the PR's branch as it starts a Retry, and its prompt says it is a Touch-up and which. A PR gets two, in a pool of their own counted from its Verdict markers (`"touchUp":n`), using none of the Ticket's Retries: a third all-tagged flaw counts like any other, calling for the next Retry or, once they're used up, sending the Ticket back to design, while one after Retry 2 still gets a Touch-up if one is left. An unbuilt Request changes (#341) and a Ticket no longer `ready-for-agent` (#416) come first, and a Verdict from red checks, an empty diff or a Broken run never calls for one. A Touch-up is in flight, held, restarted and refused as a Retry is, and its push note opens `<!-- fabrik:touch-up-push n -->`. It runs on the model of the run whose push its flaw judged, with that run's Step-up reason from its push note (#746), and a Retry after a Touch-up keeps that Step-up too (#464). `fabrik:step-up` on the Ticket reads as `marked`, and taking it off drops back to what the Retry rules give that run without it (ADR-0014). One that commits nothing, or is a Broken run, gets the Verdict a Retry would, which counts. One whose findings are all `[small: body]` (#751) may commit nothing: the Kit replaces the body with its `summary`, posts its `fix` under a `<!-- fabrik:touch-up-body-only n <sha> -->` note, which ends it but is no push, and starts the Review of the same head, which may give that head a second Verdict. A Touch-up's Run record names its number as `touchUp` (schema 11; 0 for every other run, and on a schema 1 to 10 record), with `retry` 0.

## Back to design

A Ticket that can't be built as designed goes back to the Operator. A Design-flaw Verdict, or a third Execution flaw (unless it gives way to your Request changes no run has built), closes the PR unmerged (its branch `fabrik/ticket-<n>` stays), and the Fabrik App posts a note on the Ticket linking the closed PR and its Verdict. Its first line is a marker, `<!-- fabrik:back-to-design <pr> <verdict url> -->`, read only from bot comments. Then `ready-for-agent` comes off the Ticket and `needs-design` goes on, which starts a Design session.

- **What the session sees**: every turn of that session gets the closed PR set out after the issue: every Verdict the Fabrik App gave it, oldest first, each with the head commit it judged (or, when the Operator sent it back, the Operator's reviews on it with their inline comments), then its kept branch's commits, changed files and diff against the base branch. A diff over 60,000 characters is cut short with a marker; the file list stays whole. Nobody else's comments on the PR are included. The agent job reads all of it through its read-only token, so the agent itself still holds no GitHub token.
- **Round 1** of that session says the Ticket came back from the closed PR and links its Verdict. Its @-mention of the Operator is the event's one notification: the failed review, the closed PR and the note mention nobody.
- **The outcome** rewrites the Ticket in place as an agent brief, or splits it into sibling Tickets under the same Spec (a `split` outcome: each a sub-issue of the Spec, with native blocked-by edges, and the Ticket closed as superseded). A Ticket under a Spec never gets a Spec of its own, and only a Ticket under a Spec can split. When a Spec or a split supersedes an issue, its new Tickets take the issue's place among its blockers: each Ticket nothing else in the outcome blocks takes on the issue's Blockers, in any repo, open or closed as not planned, each open issue it blocked, in any repo, waits on the Tickets that finish last, and the closing comment lists what moved. GitHub writes a blocked-by edge only from the blocked issue's side, so an edge on an issue in a repo the Fabrik App can't write to, and a blocker it can't read, are named in the closing comment for the Operator to move by hand (#771).
- **The model**: a Step-up applies only to the PR it ran on, so a rewritten or split Ticket starts again on the Implementer's default model, unless the session marks it for a Stepped-up start. A Ticket rewritten in place keeps any `fabrik:step-up` already on it.
- **The Kept branch** (#536, ADR-0017): every Back to design takes `fabrik:kept-branch` off the Ticket, and round 1 of a session on a Ticket back from its PR asks whether the next Implement run carries on the closed PR's branch, its Kept branch, or starts again from `main`. A brief with `"keptBranch": true` puts the label back on with `ready-for-agent`; a split's Tickets are new and always start from `main`. When nothing is left to build, the session tells you to reopen the closed PR and merge it yourself. While the label is on and the Ticket has no open PR, its Implement run, first run or Retry after an empty diff, checks out the Kept branch instead of cutting one from `main`, merges `main` in first when the branch lacks it, never rebasing, and builds what the rewritten Ticket says is left. Only the run's own commits go to the trust-root guard: neither the kept commits, which the Kit pushed through it or someone with write access pushed, nor `main`'s. One that commits nothing of its own, or only merges `main` in, is an empty diff. Its push fast-forwards the branch, with a lease on the head it built on, and opens one new draft PR against `main`, whose body ends "Carries on from #<closed PR>." above its Closes line; its changed-tests section and UI evidence cover the whole branch against `main`. The closed PR's Verdicts don't count against the new one. The label stays on until the next Back to design, and you can add or remove it by hand, as after a PR you closed yourself. With it on and the branch gone, no run starts: the Ticket swaps `ready-for-agent` for `ready-for-human` and is assigned to you, with a comment saying to take the label off to start from `main`, and Dispatch never adds `agent:implement` to it. The run's model follows `fabrik:step-up` as for any run, and its Run record says `keptBranch: true`.

## Merge gate

A passing PR leaves draft and requests the Operator's review. Only the Operator merges, and only at a head whose Required checks have passed; the Merge gate ruleset and branch protection, which Setup applies, enforce it (ADR-0019). Branch protection holds admins to its rules, so GitHub refuses a merge at a head whose Required checks haven't all passed, whether one failed, is still running or never reported, and refuses any push straight to the branch, the Operator's included, from github.com, `gh` or anywhere else. Everything on the default branch arrives through a PR. A PR whose Required checks have passed merges as before, and the Fabrik App, never an admin, still can't merge. The Operator has three moves:

- **Merge**: the PR's `Closes #<ticket>` closes the Ticket, which runs a Dispatch check. When that was the last open Ticket under its Spec, the Kit closes the Spec as completed, with a comment listing each Ticket's merged PRs. The comment mentions nobody.
- **Faults open as issues** (#885, ADR-0039): when an agent pull request merges, the Kit opens each fault its passes named (see **Follow-ups** under [Review](#review)) as an issue of its own, with no step of yours. It gathers every fault any pass on the pull request named, in the order named, and drops one whose title, outer spaces aside, repeats an earlier one's. It leaves out one that is an issue already: one you opened whose body has the `From PR #<n>` line and whose title is the fault's, open or closed. It opens each of the rest, in order, as the Fabrik App, in the same repo, with `needs-triage` and no other label, so a Triage run follows; its body opens with one hidden line, `<!-- fabrik:follow-up {"pullRequest":<n>} -->`, then holds the Reviewer's text, and ends `From PR #<n>`. It opens them only up to the room under `caps.follow_up_issues` (see [Kit config](#kit-config)), and a fault over the cap stays a link. Then it posts one comment on the merged pull request, which mentions nobody: each issue it opened, each fault left over the cap with its Open as issue link, and each fault that was an issue already. That comment's first line, `<!-- fabrik:follow-ups-opened -->`, makes this happen once: a second look at the same merge opens nothing more, and hidden lines under it record which issue each fault became, one the Fabrik App opened in an earlier look that failed part-way included. An idea is never opened: it stays the link on its Verdict. A Plain pull request has no Verdict, so nothing opens for one, and nothing opens for a pull request closed unmerged. There is no veto before the merge: close an issue you don't want, and nothing reopens it. A Design session that rewrites such an issue keeps its hidden line, so it counts toward the cap for as long as it is open.
- **Request changes**: a review from the Operator that requests changes on an agent PR out of draft puts it back in draft and starts one Implementer run on the Step-up model, on the PR's branch, with the review and its inline comments as input, and every other Request changes of yours on the PR, oldest first, which it builds where the PR doesn't meet them yet (one asking for a rebase never rewrites the PR's history: the run merges `main` in if the PR lacks it). The review amends the Ticket for that PR (ADR-0010): the run builds it however large it is, but for a point you ask, in words, to be its own issue (see **A Spin-off from a Request changes** below), the requested changes win wherever they conflict with an acceptance criterion, and its fix comment names each criterion it amended. The run also answers two independent yes/no questions about the review it was started for, and only that one (#369): whether it holds a Review miss (a point asking for what the pass should already have caught under the Ticket as it then stood, its Spec or the repo's standards, each such point named), and whether it amends the Ticket. A review asking only for a rebase, a squash or a retitle is no to both. Output without both answers breaks the run's contract. The Kit records them on the PR, under the run's push note or its note that it committed nothing, as a `<!-- fabrik:request-changes-answers {...} -->` marker naming the review and the lines "Review miss: yes, <point>" or "Review miss: no" and "Amends the Ticket: yes" or "no". The Implementer's output is their only source: there's no Operator override, and nothing re-judges them. The Weekly summary's Metrics table counts the week's Request changes, by when each was submitted, with a Review miss, amending the Ticket, and unanswered (a run held, failed, replaced by Send it back, or from before the answers), each against last week, and each repo's **Review misses this week** links each one's review, the comment holding the answer and the Review run whose pass it followed. Each Request changes in the Retro's evidence carries both answers, or null for each when unanswered. Every later Review and retry on the PR is given all the Operator's Request changes reviews on it but those deferred during a Retry (below), oldest first with their inline comments, as amendments to the Ticket, and the points of them set aside as Spin-offs, apart from the Operator's comments. A later review wins over an earlier one, either wins over the Ticket, and an amendment may widen scope. The Reviewer judges the PR against the Ticket as amended and gives a Design flaw from an amendment only when the amended Ticket contradicts itself or asks for what no run can meet, never for a change's size, and a retry never reverts a requested change. The Kit never rewrites the Ticket: the PR's reviews are the record. To send a PR back to Design instead, use Send it back. It isn't a retry, and a Broken run of it uses none either (#434): its failure notice names it a Broken run, and the run waits for you to re-add `agent:implement` on the Ticket. Its push carries a `<!-- fabrik:request-changes-run -->` note, so the Verdict Review gives it is marked as from a Request-changes run. The run itself uses no retry, but an Execution flaw on its push calls for the next one and counts like any other (#393), so after both retries are used it sends the Ticket back to design. On a PR that doesn't conflict with `main`, a run that commits nothing gets no Verdict and calls for no retry (#388); the empty-diff rule judges only its own commits. Its `<!-- fabrik:request-changes-run-empty -->` note ends it and settles the reviews it read, so no check starts another run for them. If the PR's head moved while it worked, as when you pushed the change yourself, the Kit adds `agent:review`, and that head's Verdict, marked as from a Request-changes run, decides what's next. Otherwise the note @-mentions you that your requested changes aren't built, and the Kit adds `ready-for-human` and takes the PR out of draft, never closing it, unless the run set aside every ask as a Spin-off and stated that no point was to be built, when the PR goes back to the Merge gate (see **A Spin-off from a Request changes** below). Unlike the conflicting case below, that note counts as no conflict attempt. On a pass the PR leaves draft and the Operator's review is requested again, the event's one notification. The Kit notes the run on the PR as it starts it (`<!-- fabrik:request-changes-run-started <reviews> -->`), naming the review and any earlier one of yours no run was started for, mentioning nobody: that note marks it in flight, so no other head gets a Verdict until it lands, and it ends once the run pushes, is given a Verdict or ends, once you take the PR out of draft, or once you dismiss every review it's for. A Request changes of yours on the draft while the run works counts too, though the run never read it, so neither check notes it: the run's push settles only the reviews it read, and an Execution flaw on that push gives way to the newer one. Anyone else's on the draft starts nothing. If you dismiss every review the run is for, the run is over and its work isn't pushed: a Request changes of yours no run has built, as one you submitted on the draft meanwhile, gets its run started instead, and otherwise the PR goes back to the Merge gate, saying so, even when an Execution flaw gave way to the review. That happens as the run lands, or, if no run is working, as after an Infrastructure failure, when `agent:implement` is re-added. If the PR's head moved since its last Verdict, as when you pushed, the Kit adds `agent:review` instead of handing it back, and that head's Verdict decides; a Verdict on a push after the dismissal ends the run too. If the note went up but the PR never went back to draft, as when what followed it failed, a check at least 10 minutes later starts the run. So does a check, at least 10 minutes after the note, on a draft with the run in flight and no Implement job under way anywhere in the repo, as when only a failed claim was re-run after its Implement job had already gone (#387). The Fabrik App can't read workflow runs, so each check reads them with its job's own read-only `GITHUB_TOKEN`, which is why the caller workflow's `tick` job grants `actions: read`. While every Subscription is used up, the note says the run is held until the weekly limit resets, or, held on a usage-credits or token-rotation issue, until a Subscription is free again. A conflict with `main` after another PR merged needs no review: the Kit resolves it itself (see **Conflicts with main** below), and hands the PR to you only when it can't. On a PR that conflicts with `main`, the run is told to merge `origin/main` in first, never rebasing, even if the review asks for a rebase, and its fix comment lists each conflicted file; the push job judges what it built against the `main` head it was told to merge, not `main` as it is by then. That head is the run's own word, so it counts only if it's `main` as the Kit job read it before the run or as it is at the push, and otherwise the run is judged against `main` as it is; a run whose word names no head is still judged, against `main` as it started or as it is at the push, if the PR's head, as the push job reads it, conflicts with that, and a merge that can't be made at all counts as a conflict. If what it built still conflicts with that head, or it committed nothing, or the trust-root guard refuses it, the Kit says why on the PR, @-mentioning you, adds `ready-for-human` and takes the PR out of draft, never closing it, and the Request changes still goes first once you take `ready-for-human` off and the PR is brought up to date (ADR-0036). On a PR that doesn't conflict, a review that asks for it still gets `main` brought in, merged or, if it asks for a rebase, rebased onto, and the push may then replace the branch, with a lease. GitHub starts no workflow for a review on a PR that conflicts with its base, so the push to `main` check and the hourly tick also look for one no run was started for: once one is more than 10 minutes old (on a PR that merges cleanly, older than the Implement job's timeout, since GitHub did start a run for it, which may still be working), they post one note naming and linking each such review (`<!-- fabrik:undelivered-request-changes <ids> -->`), put the PR back in draft and start its Request-changes run, for the latest review, using no retry; while one waits, they don't rebase the PR themselves. The two checks take turns, so neither notes a review the other has. If a Review is in flight when it's found, nothing starts until it lands: a pass settles the review, which the Reviewer read as part of the Ticket, and an Execution flaw gives way, calling for no Retry and using none, and starts the Request-changes run itself, which fixes its findings too. A Request changes of yours on the draft while a Retry is in flight, up to the Verdict on its push, is deferred (#427): the Kit says so on the PR, mentioning nobody, and neither that Review nor a Retry is given it. A pass or an Execution flaw on the Retry's push then gives way to it as though it had just arrived at the Merge gate: the PR stays in draft, its Request-changes run starts, and no retry is used; a Design flaw still sends the Ticket back to design. A Request changes of yours on a passed draft whose Merge gate has yet to open, as while its Digest is being written, is acted on at once as one at the Merge gate is, with the PR kept in draft (see [Digest](#digest), **The Operator's moves**). Otherwise, a review on a draft PR does nothing, and a Request changes from anyone else starts nothing: a person's gets one line on the agent PR, mentioning nobody, saying only the Operator's reviews start runs, and a bot's gets none. The caller workflow runs on `pull_request_review` (submitted) for this. GitHub has no `_target` form of that event, so the run uses the PR's copy of the caller workflow and Kit config, which an agent branch can never change (ADR-0005).
- **A Spin-off from a Request changes** (#884, ADR-0039): in a Request changes you can ask for a point to be its own issue, in words: "open this separately", "as its own issue", "in a different ticket", or any words that say so, in the review's own text or in a comment on the code in it. The Request-changes run leaves that point unbuilt and returns it in `spinOffs`, with a `title`, a `body` that stands alone and quotes your words, and `from`, the id of the review or comment that asked for it; its own review is headed by its id (`review-<id>`) for this, as each comment on the code is by its own (`inline-<id>`). It builds every other point. Only your words set a point aside: one without them is built, however large or unrelated (ADR-0010), where the run can't tell it builds, and an Operator comment asks for none (ADR-0007). Only a Request-changes run's `spinOffs` is read: on a first run, a Retry, a Touch-up or a conflict-only run the Kit never reads the field. A `from` that names anything but a Request changes of yours on the PR, or a comment of yours on the code in one, breaks the run's contract: the agent job checks it against the ids its prompt headed and asks the run once to put it right, and the push job checks it against its own read of the PR's reviews. The Kit opens each Spin-off in the plan that lands the run, on its push and on a run that committed nothing alike: an issue with `needs-triage` and no other label, whose body opens with `<!-- fabrik:spin-off {"from":"request-changes","pullRequest":<n>,"review":<id>,"ask":"<ask>"} -->`, where the ask is the `review-<id>` or `inline-<id>` that asked, and ends with a `From PR #<n>` line, with a blocked-by edge to the PR's Ticket, so Triage sorts it at once and Dispatch holds it until that Ticket closes as completed. Each opens once: a landing leaves out one the Fabrik App already opened from the PR for the same ask and under the same title, open or closed, naming it by its number all the same, and drops one an earlier note on the PR already records. The run's comment ends with each one's number, its title and a link to your words, and records each on a hidden line, `<!-- fabrik:spin-off-opened #<issue> {…} -->`, under the run's answers. Every later Implement run and Review on the PR, and the Digest writer, is given them under "The points set aside as Spin-offs", each with its issue and your words: a later run builds none and returns none again, and the Reviewer holds a point properly set aside to be no part of the Ticket as amended and never a finding for being unbuilt, while one your words did not ask to separate is an unbuilt requested change, an Execution flaw. A point set aside neither amends the Ticket nor is a Review miss. When the review asked only for Spin-offs, the run commits nothing and the PR goes back to the Merge gate at the same head, on the pass it had: out of draft, your review requested, with no Review, no Hand-back and no retry. That takes Kit code's check and the run's statement together, and neither alone. Kit code goes by asks, which are a review's own words when it has any and each of your comments on the code in it: the run committed nothing, the PR's head did not move, its latest Verdict is a pass on that head, and every ask of every review the run read is named by a Spin-off's `from`. And the run states, as `onlySpinOffs` in its output, that every point it was given was asked for as its own issue and it built nothing: one ask can hold a point to build and a point to set aside, which Kit code can't tell apart. Its note says what Kit code checked and what the run stated, and is still the run's outcome, so the reviews are settled and no check starts the run again. Anything short of that is handed back as above, or reviewed when the head moved, with its Spin-offs opened all the same. A run that commits nothing without stating it is handed back, as on an ask that holds a point it left unbuilt. A Request changes that came before the gate opened, as while the PR's Digest was being written, gets that Digest first, and the gate opens when it is posted. A run that ends without landing, as on a trust-root refusal, opens none. A Design session on such a Spin-off is told of the PR it was set aside from, and that a Roll-in onto it is not on offer.
- **Conflicts with main**: when a push to `main` leaves an agent PR out of draft conflicting with it, the Kit brings the PR up to date without you (ADR-0011). It first rebases the PR's branch onto `main` itself, with no agent, without a working tree: if that's clean, it puts the PR back in draft and pushes with a lease, and the push starts a full Review of the combined head, whose pass requests your review again. If the lease refuses the push, because the branch moved meanwhile, the PR comes back out of draft with a comment saying so and no attempt recorded, for the next check. If the rebase conflicts, it puts the PR back in draft and starts one conflict-only run: an Implementer run on the Step-up model, on the PR's branch, told to rebase onto `origin/main`, resolve the conflicts and change nothing else. Its fix comment lists each conflicted file and how it was resolved. Neither uses a retry itself. The run's push carries a `<!-- fabrik:conflict-run -->` note, so the Verdict Review gives it is marked as from a conflict-only run. The run itself uses no retry, but an Execution flaw on its push calls for the next one and counts like any other (#415), as for a Request-changes run, so no Retry number starts twice on one PR. While the run is in flight, no other head gets a Verdict. A PR that's only behind `main` is left alone, and so is a draft, a PR with a Retry or Request-changes run in flight, or one with a Request changes from you that no run has started for yet, whose Request-changes run brings `main` in instead. Each PR gets one attempt per `main` head, recorded by a `<!-- fabrik:conflict-attempt <sha> … -->` note on the PR. If the conflict-only run fails, a Broken run included, which uses no retry (#434), changes nothing, doesn't bring `main` in, its output breaks the contract, or the trust-root guard refuses it (the run's rebase rewrites the PR's commits, so they all count as its own: a conflict resolved inside a trust-root file, or any earlier Operator commit on the PR that touched one, is refused), the Kit says why on the PR, @-mentioning you, adds `ready-for-human`, and takes the PR out of draft again, never closing it. Bringing `main` in means the run's branch holds `main` as the Kit job read it before the run started or as it is at the push, so `main` moving during the run doesn't discard it (#861): its branch is pushed, and if that head still conflicts with the newer `main`, GitHub starts no Review of it and that `main` head gets its own attempt (ADR-0016), which starts from the pushed branch and its resolution. While a PR carries `ready-for-human`, whoever added it, the Kit leaves its branch alone (ADR-0036): no rebase, no conflict-only run and no check's fix brought in, however often `main` moves, though a Request changes from you still starts its run. Taking the label off gives it back, and a Verdict takes it off too: the next conflict check weighs it again, and tries it only at a `main` head it hasn't tried yet. The check runs on every push to the default branch and on the hourly tick, which catches a PR whose mergeable state GitHub hadn't worked out within the push's short poll. The checks take turns, and each judges the PRs against `main` as GitHub reads it when the check runs, which may be past the push that started it. The caller workflow's `push` trigger fires on any push to the default branch for this, not only a Kit config change: a Product repo set up before it must update its `.github/workflows/fabrik.yml` from `templates/fabrik.yml` (the Fabrik App has no `workflows` permission), and until then relies on the tick.
- **Send it back**: adding `needs-design` to an open agent PR takes the Design-flaw route: the PR closes unmerged, keeping its branch, and the Ticket swaps `ready-for-agent` for `needs-design`. The note's marker is `<!-- fabrik:back-to-design <pr> operator -->`, and round 1 says the Operator sent the Ticket back.

The way past the Merge gate is by hand, on github.com. In the default branch's protection settings, switch off "Do not allow bypassing the above settings", or take the check off the required list; merge; then run Setup, which puts enforcement back. That's how to merge past a Required check on purpose, and the only way out when a Required check can never report again, as after a CI job is renamed, where the PR that corrects `sandbox.checks` in the Kit config can't itself go green while the old name is still required. Setup adds Required checks and never takes one off, so a check that has gone for good is taken off the branch's required list by hand: switching enforcement off alone would leave it still required once Setup has put enforcement back, and no PR would merge.

## Audit

Once a week the scheduled tick starts an Auditor run in each Product repo. It reads what changed on the default branch since the last Audit and files at most 3 deepening opportunities as one `fabrik:audit` issue, the Audit. It changes nothing: no branch, no PR, no state label and no push. It's on from the release that ships it, with no setup step; `audit.day: null` in the Kit config turns it off.

- **When**: from 00:00 UTC on `audit.day` (Sunday by default), the hourly tick opens the week's **pending Audit**: an issue from the Fabrik App titled `Audit: week of <Monday>`, labelled `fabrik:audit`, with no state label, no assignee and no mention, whose one line names the commit the Auditor is reading. The Fabrik App opening it starts the Loop workflow's Audit job, and Intake leaves it alone. The week runs Monday to Monday in UTC, and it gets at most one Audit. The tick opens none while an Audit is open, a filled one the Operator hasn't closed included, when the default branch hasn't moved since the last Audit, or, weighed after all of those, while no Subscription is free, with Subscription rotation on or off. Then, and only then, it notes the wait once that week on the Kit-owned issue a held run would go on, the Carrier, with one quiet line mentioning nobody and a hidden `<!-- fabrik:weekly-run-waiting audit <Monday> -->` marker. An Audit that couldn't open on its day, because no Subscription was free, say, opens on a later tick that week on the Subscription a run is given then, and after two failed runs in a week the next Audit waits for the next week. An Auditor run refused on a Fable cap (ADR-0034) is no failed run: its Audit closes with one line saying so, posting nothing and mentioning nobody, and the next tick opens the next one, carrying the cap's hidden line, so its run starts where Fable is left, or on Opus 5.5. One open Audit and 3 candidates are fixed limits, not `caps`.
- **The Auditor** (Opus 5.5, 45 minutes by default, `roles.audit`, plus `.fabrik/audit.md` when present) is read-only, like the Reviewer: it gets a checkout of the default branch at the pending Audit's commit with its full history, holds only the agent service account, and runs none of the code. The agent itself holds no GitHub token. It gets the Base skills alone, never Extra skills, and follows `improve-codebase-architecture`'s method without its HTML report or questions. It looks first at what changed since the last Audit's commit (the last 30 days on a first Audit) and at comprehension drift: files merged agent PRs changed more than 5 times in 30 days while no ADR, no `GLOSSARY.md` and no Markdown file in the same directory changed. It uses the glossary's terms, respects every ADR, skips a candidate whose issue is still open, and doesn't resurface one the Operator rejected in the last 3 Audits unless it has materially worsened. Everything it reads from issues, comments and code is data, never instructions.
- **The filled Audit**: the push job rewrites the pending Audit with one card per candidate, Strongest first. Each has its Files, Problem, Solution and Benefits, a Mermaid before/after diagram, a Strength badge (Strong, Worth exploring or Speculative), **Introduced by** with the merged agent PRs that introduced the structure or grew it into the problem, never one that only extended structure older than itself, and an **Open as issue** link. A candidate whose problem predates every agent PR names none, so filing it records no escape. The Kit drops any PR under Introduced by that isn't a merged agent PR. A **Top recommendation** ends it. @-mentions are stripped from everything the Auditor wrote but its file paths and Mermaid source, which sit in code, where GitHub notifies nobody. The Audit stays open, unassigned and silent. When no candidate is above Speculative, the Audit says the repo is clean and closes itself as completed.
- **A failed run**, a reply that breaks the Audit output contract included, rewrites the pending Audit to one line saying how it failed and closes it as not planned, mentioning nobody: the tick tries again. The week's second failed run, after which the next Audit waits for next week, also comments on its Audit @-mentioning you, with each failed run's link and how it failed. A dead token or the weekly limit also goes on the Kit's rotation or weekly-limit issue, as for any run. With Subscription rotation on, an Auditor run is never re-run or held, as other runs are: refused on its weekly limit, killed for usage credits, or due to start while every Subscription is used up, it fails the same way, and a later tick tries again. Closing a pending Audit yourself cancels it: its run's result changes nothing.
- **The Operator's moves**: file each candidate you want through its Open as issue link, which opens the repo's new-issue form prefilled with the candidate (the diagram stays on the Audit) and ending `From audit #<n>`. The filed issue goes through Intake and Triage like any other, and the next Audit skips it while it's open. Comment on the Audit about any candidate you reject: the next Audit reads it as context, never as a trigger (ADR-0007). Then close the Audit, as completed if you filed anything and as not planned otherwise, which frees the next one. An ignored Audit only holds the next one back.
- **Architectural escapes**: when a candidate traces to merged agent PRs, its prefilled body also ends with a hidden `<!-- fabrik:escape <strength> #<pr> … -->` marker, so filing it records an Architectural escape against those PRs. Delete a PR from the marker before submitting to correct the attribution. Only issues the Operator opened count, and only for PRs that are merged agent PRs. A link too long for GitHub's URL limit cuts the candidate's text, never `From audit` or the marker, and a Design session that rewrites the filed issue keeps both lines.
- **In the Weekly summary**: the Metrics table's **Architectural escapes (90 days)** counts the escapes filed, each once however many PRs it traces to, with the Audits and merged agent PRs behind the count and the candidates still undecided, such as "3, from 4 Audits over 68 merged agent PRs, 2 candidates undecided", beside last week's and the change in the count. Each repo's window is the trailing 90 days, starting no earlier than 30 days before its first Audit, so a new repo's count grows into them; Audits count only once landed, filled or clean, and "no Audits yet" stands in for a week no repo had one. Undecided candidates are those on an open Audit whose card traces to a merged agent PR, less the issues filed from it with an escape marker: one rejected by comment stays undecided until the Audit closes, and a closed Audit's unfiled candidates count for nothing. Only this week's cell names them: an Audit's facts say whether it's open now, not when it closed, so last week's cell leaves them out rather than guess. A line under the table counts the 90 days' escapes by Strength. Each repo's **Architectural escapes this week** lists the escapes filed that week, each PR with the Ticket it built, its last passing Review run and whether the Operator pushed to it. An open Audit, filled or still pending, is in the repo's Waiting on you with its age, and an Audit that failed twice in a week, the second time that week, is under Held, linking both: the next Audit is held until the weekly gate's next week ("was held until this week" when that week has begun by the filing). A week whose Audit never opened because no Subscription was free gets its own line beside the repo's **Loop** line, under neither Held nor Stuck, such as "No Audit last week: no Subscription was free (#41, #43)", naming the Carriers that noted the wait, even once they're closed. Filed before the gate's week has ended in UTC, as it is east of UTC on a Monday morning, the line says "The week's Audit still waits for a free Subscription (#41)" instead, and only while none is free, since with one free the next tick opens it. A week skipped because the default branch didn't move, an Audit still open, two failed runs or `audit.day: null` gets no such line. An Auditor run leaves a Run record like any agent run, and counts in the week's total cost but never in cost per merged PR or per Spec.

## Retro

Once a week the scheduled tick starts a Retro run in each Product repo that has the `fabrik-runs` store. It reads the repo's Run records, transcripts and scores in the store, and the Operator's feedback on its agent PRs, since the last Retro, and files at most 3 proposals to change how the factory works in that repo as one `fabrik:retro` issue, the Retro. It changes nothing itself: no branch, no PR, no state label and no push. The Operator files what they want through each proposal's link. It's on from the release that ships it, with no setup step beyond the store; `retro.day: null` in the Kit config turns it off.

- **When**: from 00:00 UTC on `retro.day` (Saturday by default, a day before the Audit), the hourly tick opens the week's **pending Retro**: an issue from the Fabrik App titled `Retro: week of <Monday>`, labelled `fabrik:retro`, with no state label, no assignee and no mention, whose one line says when its window starts. The window runs from where the last Retro's ended (the 7 days before the tick on a first Retro) up to the tick that opened it, so nothing falls between two Retros, and a failed Retro is never the last one. The Fabrik App opening it starts the Loop workflow's Retro evidence job and then its Retro job, and Intake leaves it alone. The week runs Monday to Monday in UTC, and it gets at most one Retro. The tick opens none while a Retro is open, a filled one the Operator hasn't closed included, or when nothing is new since the last Retro: no agent PR merged or closed and no escape filed. It opens none, and says nothing about it, while the `fabrik-runs` store isn't ready: the Fabrik App isn't on it, or it isn't private. Weighed after all of those, it opens none while no Subscription is free, with Subscription rotation on or off, and notes the wait once that week on the Carrier, as the Audit does, with a `<!-- fabrik:weekly-run-waiting retro <Monday> -->` marker. A Retro that couldn't open on its day, because no Subscription was free, say, opens on a later tick that week, and after two failed runs in a week the next Retro waits for the next week. A Retro run refused on a Fable cap is no failed run either, and the next Retro falls back as the Audit's does. One open Retro and 3 proposals are fixed limits, not `caps`.
- **The evidence**: the Retro evidence job runs no agent and no Product code. Like the push job, it checks out only the Kit and loads the Fabrik App key through the push service account, then mints a token with Contents read on `fabrik-runs` alone and a read-only token on the Product repo (ADR-0009's addendum). It refuses a store that isn't private and reads only this repo's paths in it. It builds one bundle: the window's Architectural escapes, each with the last passing Review run that missed it; the Operator's feedback on agent PRs (Request changes reviews with their inline comments, the Operator's own pushes with their patches, and the Operator's comments); the Follow-ups on passing Verdicts, each with its kind and whether the Operator opened it, and what became of the issue the Kit opened for each fault (its state label while open, or how it closed and whether the Operator or Triage closed it), or that the fault stayed a link over the cap; the runs a Scorer failed; a fixed one-in-ten sample of the merged agent PRs; a streak table of every agent PR merged in the last 90 days; the last 3 closed Retros with the Operator's comments on them; and the open issues filed from Retros, on the Product repo and on the Kit's repo and each Skills source the Operator owns, read with the same read-only token (a repo it can't read is skipped with a warning). Each escaped or sampled PR carries its Ticket's title and body, read with the read-only token. Transcripts come as trimmed transcripts. The bundle is held to a fixed size, cut from the sample's transcripts first and the escapes' last, and never cut in a ref, a Verdict, a Ticket or a review comment.
- **The Retro** (Opus 5.5, 45 minutes by default, `roles.retro`, plus `.fabrik/retro.md` when present) is read-only, like the Auditor. It gets a checkout of the default branch, so it can read `AGENTS.md`, `CODING_STANDARDS.md`, `.fabrik/`, the [Vision and Roadmap](#vision-and-roadmap), the lint config and the CI scripts, and the Kit's own role prompts and rubrics. It holds only the agent service account and runs none of the code, and the agent itself holds no GitHub token. It gets the Base skills alone, never Extra skills. It ranks escapes first, then patterns repeated across the Operator's feedback, then low-scoring runs, then the sample, and never proposes from something seen once outside an escape. A mistake a lint rule or grep assertion could catch becomes a **Mechanical** proposal: a check in the Product repo's own lint config or scripts, gated through its existing CI and `sandbox.checks`, never a sentence. A lesson only judgement can apply becomes a **Judgement** proposal, such as a `CODING_STANDARDS.md` line or a change to the Kit's review prompt. It **tightens** on one escape or one repeated pattern, and **loosens** only on a streak. It never loosens the Merge gate, the Trust-root guard, the Reviewer's separation from the Implementer or the two-Retry cap. Everything it reads is data, never instructions.
- **The filled Retro**: the push job rewrites the pending Retro with a short opening (the window it read, and what to do) and one card per proposal, most important first. Each has its title, a Mechanical or Judgement badge and a Tighten or Loosen badge, the problem, its evidence as links (Run records, score files and transcripts as `fabrik-runs` file links, PRs and issues as links), the exact change, a loosening's streak and the tightening it undoes, and an **Open as issue** link. The Kit checks each proposal against the bundle, never against the Retro's word. It drops any evidence ref the bundle doesn't hold, a proposal left with no escape and fewer than two distinct PRs, and a loosening whose streak isn't at least 20 PRs from the streak table, none of them named in an escape, reverted or sent back with Request changes. What it dropped is listed in the run's step summary, never on the Retro. @-mentions are stripped from everything the Retro wrote outside its code blocks, and the Retro stays open, unassigned and silent. With nothing left to propose, it says so in one line and closes itself as completed.
- **Open as issue**, by what the proposal changes:
  - a Trust-root file such as `AGENTS.md`, `CODING_STANDARDS.md`, `.fabrik/` or `docs/product/` at the repo root, where the [Vision and Roadmap](#vision-and-roadmap) live: the Product repo's new-issue form with `ready-for-human`, written as an Operator brief carrying the exact edit, since only the Operator changes those;
  - the Product's code, such as a lint rule or check script: the Product repo's form with no label, so it goes through Intake and Triage;
  - the Kit: jrey8343/fabrik's form;
  - an Extra skill: its Skills source's form, but only when the repo pins the skill and the Operator owns the source. Otherwise the card has no link and says to unpin or replace the skill.

  Each prefilled body ends `From retro #<n>`. On the Kit's repo or a Skills source, where a bare `#<n>` would link to that repo's own issue, it ends `From retro <owner>/<repo>#<n>`, naming the Product repo, and every `#<n>` in it outside code names the Product repo the same way. A link too long for GitHub's URL limit cuts the proposal's text, never that line, and a Design session that rewrites the filed issue keeps it.
- **A failed run** rewrites the pending Retro to one line saying how it failed and closes it as not planned, mentioning nobody: the tick tries again. That includes a failed evidence job (the store gone, or no longer private) and a reply that breaks the Retro output contract. The week's second failed run, after which the next Retro waits for next week, also comments on its Retro @-mentioning you, with each failed run's link and how it failed. A dead token or the weekly limit also goes on the Kit's rotation or weekly-limit issue, as for any run. With Subscription rotation on, a Retro run is never re-run or held, as other runs are: refused on its weekly limit, killed for usage credits, or due to start while every Subscription is used up, it fails the same way, and a later tick tries again. Closing a pending Retro yourself cancels it: its run's result changes nothing.
- **The Operator's moves**: file each proposal you want through its Open as issue link; the next Retro skips one whose `From retro` issue is still open, wherever it was filed. Comment on the Retro about any proposal you reject: the next Retros read the comments on the last 3 closed Retros as context, never as a trigger (ADR-0007), and don't propose it again without new evidence. Then close the Retro, as completed if you filed anything and as not planned otherwise, which frees the next one. An ignored Retro only holds the next one back.
- **In the Weekly summary**: an open Retro, filled or still pending, is in the repo's Waiting on you with its age, and a Retro that failed twice in a week, the second time that week, is under Held, linking both, as an Audit's is. A week whose Retro never opened because no Subscription was free gets its own line beside the **Loop** line, such as "No Retro last week: no Subscription was free (#41)", as an Audit's skipped week does, and none for a week with nothing new or `retro.day: null`. A Retro run leaves a Run record like any agent run (the evidence job, which is no agent run, leaves none), and counts in the week's total cost but never in cost per merged PR or per Spec. Scores still never show in the summary: a low score reaches the Operator only through a Retro's proposals.

## Replay

A Replay tests one change to how the factory works before the Operator makes it. It re-runs recent merged Tickets from the commit each one's first Implement run started from, once as the Ticket was built then (the **baseline**) and once with one thing changed (the **variant**), and sets the two side by side. Nothing changes in the Product repo: no branch, no PR, and no label or comment except on the replay issue. It's on from the release that ships it, in every Product repo with the `fabrik-runs` store, and costs nothing until the Operator files a replay issue.

- **Filing one**: open an issue labelled `fabrik:replay` whose body holds one request block, below any text of your own:

  ````
  ```replay
  review.effort: high
  tickets: #41, #12
  ```
  ````

  The block names exactly one variable: `implement.model`, `implement.effort`, `review.model` or `review.effort`, set to a value, or `kit`, set to a full 40-character Fabrik commit sha whose prompts and Base skills the variant loads in place of the pinned release's, as a Retro proposal's would. Efforts are Kit config's: `low`, `medium`, `high`, `xhigh` or `max`. A model must be a full Claude model name such as `claude-opus-5-5`, so the record says exactly which model ran: CLI aliases like `opus` are refused, and so is `best`, for Kit config's reason, in every repo. Fable is held to the repo's `allow_fable`, as a role's model is (ADR-0034): in a repo that opted in, a variable may name it by its full id, such as `claude-fable-5-2`, never the bare `fable`; in one that hasn't, it's refused, with Kit config's reason. A `kit` sha changes only the role prompts and the Base skills lock, never the workflows, the Scorers' rubrics or the Kit's code, and it must be a commit in jrey8343/fabrik, on a branch or not, as a merged Retro proposal's still is once its branch is deleted: ADR-0003's addendum refines the pinned release for it. `tickets` is optional and lists up to 10 Ticket numbers. Only the Operator's replay issues count: one anyone else files gets no comment and runs nothing. Intake leaves a replay issue alone, and no agent ever files one.
- **"Replay this"**: a new-issue link with the `fabrik:replay` label and a prefilled request block (`replayThisUrl` in `src/kit/replayRequest.ts`), such as a Retro proposal's PR can carry, so testing a proposal takes one click.
- **Accepting it**: the next hourly tick reads the request. A request that doesn't read (no variable or two, an unknown role, a refused model or effort, a short sha or one that isn't a Fabrik commit, more than 10 Tickets), or picks no eligible Ticket, gets one comment saying why. Edit the body to fix it, and the next tick reads it again. A valid request is accepted once: the tick picks its Tickets then and lists them in the body, below your text, which the Kit never rewrites. Only merged, never-reverted Tickets built by Implement runs are eligible, whose first Implement run left a Run record with its `baseSha`, and whose merged PR changed no Trust-root file. The first Implement run is the one that cut the branch that merged: a first run that left an empty diff, which its record says, is passed over for the fresh run after it. A Ticket is also left out when its Kit config at `baseSha` doesn't resolve under this release, runs a role on Fable in a repo whose Kit config no longer opts in, or already runs the variable's value, as `review.effort: high` on a Ticket built with Review at `high` already, so its two arms would be the same. This is a deliberate refinement of the Spec, whose eligibility rules name neither case: a Ticket the arms can't compare would only spend a run. With no `tickets`, it picks 5: the most recent eligible ones, spread across thirds of their original cost. A listed Ticket left out is named with why. A picked Ticket keeps its flags: Human touches, a Ticket or Spec edited since its first run, or a merged PR with no test files ("no hidden tests").
- **How each Ticket runs**: both arms in one workflow run, on the pinned release, each one Implement run and one Review, with no Retry and no Step-up. A marked Ticket's baseline runs Implement on the Step-up model and effort, as it was built, unless the variable sets `implement.model` or `implement.effort`; no arm reads the `fabrik:step-up` label. Each arm checks out the Ticket's `baseSha`, so Kit config and Extra skills are the ones it was built with. A Ticket whose first run was a Kept-branch start can't be rebuilt from its `baseSha`, which holds a closed PR's work the Ticket doesn't describe, so the pick leaves it out, naming why, and no arm runs it. Its Implement and Review jobs fetch that one commit alone, with no branch or tag, so neither agent can read the merged result from the checkout; only the gates, which run no agent, fetch the history that holds the merged PR's tests. Each arm rebuilds a first Implement run's input from the Ticket and its Spec as GitHub holds them now. The baseline runs the models and efforts Kit config held at `baseSha`, Fable included in a repo that opted in; the variant differs only in the variable. Each arm's run holds its model to the repo's own `allow_fable` as it is now, never `baseSha`'s, so a variant can name Fable on a Ticket built before the repo opted in. The replay Implement job holds no write credential, as a live one doesn't (ADR-0002), passes its diff out as a patch rather than pushing it, and is never named `Implement`, so it never takes a Dispatch slot. Each arm's gates run `sandbox.setup`, `sandbox.build` and `sandbox.test` on its patch, then lay the merged PR's test files over the tree and run the tests again. Its Review judges the diff against the Ticket, with no PR, whether or not the gates passed. The three Scorers score every replay Implement run, never a sample, at the pinned release's rubrics, unless it left no transcript, ended in an Infrastructure failure or read near its weekly limit, as for any run.
- **Spare capacity only**: the tick starts at most one Ticket, both arms, per hour, and only while Dispatch has no ready, unblocked Ticket or research Decision to start, no Subscription has an open weekly-limit, usage-credits or token-rotation issue, and the last weekly-limit reading on the Subscription it would use is `allowed` and under 50% (no reading counts as spare). A reading whose limit has reset since counts as spare too, whatever it said, since the week it read is over. This is a deliberate refinement of the Spec, which counts only no reading as spare: in a quiet repo the newest reading can come from before the reset, and nothing runs to replace it, so without it a Replay could wait on a stale reading for good. A Replay whose arms run Fable (ADR-0034) weighs, in place of the first free Subscription, the first free one with Fable left, by the Fable cap readings in the store's Run records, and both arms run on it; while none has Fable left it starts nothing, since an arm never falls back, and a Fable cap costs the Replay time only. A Replay whose arms don't run Fable is unchanged. Only one replay Ticket runs at a time across every replay issue, the oldest issue first, and the claim checks it again as the run starts. Adding `agent:replay` to a replay issue by hand starts its next Ticket at once, as adding `agent:implement` by hand starts past Dispatch's cap: only a replay Ticket already in progress, on any of your replay issues, or a used-up Subscription stops it, never Dispatch's queue or the last reading. A replay run is never held or re-run on another Subscription: refused on a weekly limit, it opens the weekly-limit issue as any run does, and its Ticket waits for a later tick. Refused on a Fable cap, it opens nothing, as a live run doesn't, and never falls back to Opus, since another model would spoil the comparison: its Ticket waits, as for a weekly limit, and is tried again on a later tick with spare capacity, so a Fable cap costs the Replay time until it resets, never the Ticket. Any other Infrastructure failure is tried once more on a later tick, then shown as failed. A `kit` variant whose candidate sha the Kit job can't lay, as one GitHub has no commit for, runs neither arm and fails its Ticket at once, with no retry, its row naming `kit-sha-unavailable` and why.
- **What you read**: the body grows a results table as Tickets finish, your request kept at the top: a row per arm with its gates, Verdict, hidden tests, the three scores, cost, turns, duration, a link to its patch in `fabrik-runs` and its flags. Below it come the totals per arm beside the original runs, each mean score with how many of the Tickets done it was scored over, as `0.95 (2/5)`, the baseline's gap from the original, which shows how much results vary by chance, and a headline the Kit computes from the totals, such as `variant: hidden tests 4/5 vs 5/5; cost −38%`. A Ticket whose first run had no Review, its checks red, is left out of the original's totals and the gap, which say so. No model judges the results or recommends anything. When the last Ticket is in, one comment mentions you, and the issue stays under Waiting on you in the Weekly summary until you close it. Act on it yourself, by changing a Kit config default or merging the Retro PR, then close it.
- **Cancelling**: close the replay issue. The tick ignores a closed one, and a run already going finishes and keeps its records in the store but doesn't rewrite the body. Anyone who can edit the issue can edit its body, so keep replay issues to repos whose collaborators you trust with your Subscriptions.
- **A run that never lands**: the replay-record job lands each run whatever its arms came to, a cancelled one included. If its landing fails once the Kit config has loaded, whether GitHub failed a call or the Loop refused the run, the job releases the Ticket itself, as an Infrastructure failure when both arms ran, so the next tick runs it again. If it can't do even that, as when 1Password is down, the Ticket's progress marker still says when its claim started it, and the tick releases it once it's been in progress longer than a run can last: every replay job's timeout end to end at your Kit config's, plus an hour to queue (210 minutes at the defaults). The replay step goes by that time, not by workflow runs. A released Ticket counts as an Infrastructure failure: it runs once more on a later tick, then shows as failed, so no Ticket holds every Replay back for good.
- **In the store**: every replay run gets a Run record, at schema 6, whose `replay` field names the replay issue, the arm and the Ticket, plus a `kit` variant's candidate sha. Records, transcripts, score files, each arm's patch, at `replays/<owner>/<repo>/<replay-issue>/<ticket>-<arm>-<run>.patch`, and its gates beside it, at `<ticket>-<arm>-<run>.gates.json`, are written create-only by the replay-record job, the Replay's own push job (ADR-0009's addendum). The Weekly summary and the Retro leave replay records and score files out of every figure. The week's total gains a **Replay spend** line, judge runs included, in a week that had any. A Replay costs about twice the original Tickets' first Implement runs and their Reviews: two Implement runs, two Reviews and two judge runs per Ticket, all under the 50% line.

- **Held work is silent.** Work a full cap holds (see `max_in_flight` and `caps` in the [Kit config](#kit-config)) waits with no comment, label or notification. It pushes when its slot opens, as a Design session's round 1 does, and the Weekly summary's **Held** section shows, per Product repo and by that repo's own Kit config, how many `needs-design` issues wait for a slot and how long the oldest has waited, how many Sentry error groups wait for a Monitor issue slot, which open Maps fill the Map cap, each `ready-for-agent` Ticket and research Decision Dispatch would release but `max_in_flight` holds, with how long since it got its `ready-for-agent` or `wayfinder:research` label and what's in flight ("waiting for a slot: `max_in_flight` is 2 and #11, #12 are in flight · #14 (3 days)"), or that Dispatch is paused, each Ticket `caps.merge_gate` holds, with the PRs at the gate and the Tickets on their way ("waiting for the Merge gate: `caps.merge_gate` is 3 and #21, #22 are at it, #23 on its way · #14 (3 days)") and any check's fix that goes first or is under way ("…, #23 on its way; #50 fixes a red check and goes first · #14 (3 days)"), a Ticket both caps hold listed here alone and the PRs at the gate staying under Waiting on you, and, with Subscription rotation on, each Held run with its role and the weekly-limit issue holding it, beside each open weekly-limit issue and its reset, and each Audit or Retro that failed twice in the week, whose next run the weekly gate holds until its next week. A Held run is never listed under Stuck, its failed run and its draft PR included: the Kit resumes it itself. A Ticket with a slot free isn't Held, as the next hourly tick's Dispatch check releases it, and nor is one Dispatch wouldn't release anyway (assigned, blocked, its last run failed). Until the Operator accepts the Fabrik App's Actions: read, the runs in progress can't be read, so the `max_in_flight` line counts what it can and says "(runs in progress unread)". A repo whose Kit config is invalid on its default branch shows no Held: its Waiting on you leads with the config's first error, as the Loop does nothing there.
- **A red push or claim job says why, and Re-run failed jobs recovers it.** Setup turns Actions notifications off, so when the push job or the claim job fails, whether GitHub refused or failed a call (the Kit's GitHub client already tries a failed read, and a write GitHub never took, twice more first) or the Loop wouldn't land the run, the job's step summary and one comment on the run's issue or PR say what it was landing, what failed, which of its plan's actions landed and which didn't. An agent's finished work waits in the run's `fabrik-agent-result` artifact, which Actions keeps for 7 days: open the run and choose **Re-run jobs → Re-run failed jobs** before then, and the push job lands it. A bundle that doesn't verify fails the same way on every re-run, so its comment gives git's reason and says to run the work again from the start instead. A failed landing of a Ticket's first Implement run, or of a Research run, holds its Ticket or Decision back from Dispatch as a failed run does, until the Operator re-adds its trigger label. A push to `main` has no issue to comment on, so only its step summary says. The run's Run record keeps how the landing failed in `landing` (#487): GitHub's refusal, GitHub's own failure, a missing file or the Kit's own failure, with the action, the request, its status and GitHub's request id. The Weekly summary's Metrics table counts the week's **Landings failed** against last week, apart from the runs whose agent failed.
- **There is no push budget.** Every push but the Weekly summary is the Operator's move, and the Weekly summary is one a week, so the Kit never holds one back: it caps the sources, never the pushes.

## Kit config

A Product repo's Kit config lives in `.fabrik/`. Every file is optional and every field has a default, so a release never needs a config edit. An invalid config, or an unknown field, fails the run with a message naming the field.

What Setup and the Visual evidence writer write in `.fabrik/config.json` is printed as Prettier prints JSON with its default options, 80 columns wide. A Product whose own Prettier settings set another width (`printWidth` in `.prettierrc` or in `package.json`'s `prettier` key, or `max_line_length` in `.editorconfig`) can fail `prettier --check` on the setup PR's `subscriptions` line or on the Visual evidence PR. Then run the Product's own `prettier --write .fabrik/config.json` and commit it in that PR.

- Leave a field out to take its default. `null` is accepted only where the default is `null` (the Sandbox commands, `monitor.errors`, `operator`, `ui`, `ui.before_url`, `preview`, `preview.url`, `production`, `production.environment`, `production.workflow`, `staging` and `time_zone`), and in `audit.day` and `retro.day`, where it turns the Audit or the Retro off. Every role's `effort` defaults to `medium`, except the Review's and Design's, which default to `high` ([#759](https://github.com/jrey8343/fabrik/issues/759), [#767](https://github.com/jrey8343/fabrik/issues/767); a prototype turn runs at Design's), each named outright so each Run record says the level it ran at and a Claude Code upgrade can't change it unseen; set it to `low`, `medium`, `high`, `xhigh` or `max`. A `null` effort, as the starter Kit config once wrote for every role, names no level, so it reads as its default like a field left out (for `roles.digest`, as the repo's own `roles.review` effort, or `medium` when that names none).
- The Sandbox commands, each skipped when `null`:
  - `sandbox.setup` readies the runner: tools, services and stubs (daemonise any it starts). It runs before the agent starts in every run that runs the Product's code: an Implement run (first, Retry, Step-up and Request-changes alike), a Replay arm's Implement run, Triage, and every turn of an async Design session, a prototype turn included. Replay's gates run it too.
  - `sandbox.build` installs the Product's dependencies and builds it. It runs after `sandbox.setup`, before the agent starts, in every run that builds a branch: an Implement run, a Replay arm's Implement run and a prototype turn. Their prompts give it to the agent to run again after changing the dependencies. Replay's gates run it after `sandbox.setup`, and UI evidence and Prototype capture run it before `ui.serve`.
  - `sandbox.test` runs the tests. The Kit never runs it before an agent: the Implementer's prompt gives it to the agent to run, and Replay's gates run it after `sandbox.build`.
  - In a run that readies the Sandbox, each command runs only if the one before it passed, and a failing one fails the run before the agent takes a turn. The Reviewer, the Auditor, the Retro, the Researcher, the Digest writer and a Replay arm's Reviewer read the code and run neither `setup` nor `build`, and nor does the Scorers' judge.
- `sandbox.env` holds non-secret values. `sandbox.secrets` maps an env var name to an `op://` reference; a literal secret is refused.
- `allow_fable` (default `false`) opts this repo in to Fable for its AFK roles (ADR-0034). Without it, a role naming Fable is refused, because Fable can bill metered usage, and the error says to set `allow_fable` to `true` to opt in. With it, a role may name Fable only by its full id, such as `claude-fable-5-2`, so a Claude Code upgrade or `ANTHROPIC_DEFAULT_FABLE_MODEL` can't change which Fable runs unseen: the bare `fable` alias is refused. `best` is refused either way, since the CLI can resolve it to any model. Anything but `true` or `false` is a Kit config error. Set it only with usage credits off on every listed Subscription, which the Kit can't read: every Fable run stops on its first overage message, rotation or not, and opens its Subscription's usage-credits issue, which keeps every run off that Subscription until you close it: with rotation off, runs due are held until then. With it, the Kit job reads the Fable cap readings in `fabrik-runs`' Run records, read-only, so a run due while no listed Subscription has Fable left starts on Opus 5.5 at the role's effort with no refusal first, until the cap resets. A store it can't read counts every Subscription as having Fable left, and its step summary says so (ADR-0009's addendum). Setup and the starter Kit config never write it, and `true` with no role naming Fable changes nothing. A Replay follows it too: its variable may name Fable on the same terms, and its arms run Fable only while the repo opts in (see Replay). To revert, remove `allow_fable` and name non-Fable models.
- `max_in_flight` caps how many Tickets and research Decisions are in flight at once: open agent draft PRs, Implement and Research runs in progress, and Tickets and research Decisions dispatched but not yet started. An agent PR out of draft, at the Merge gate, no longer counts here: it falls under `caps.merge_gate`. Set it to `0` to pause Dispatch: the Kit adds `agent:implement` to no new Ticket and `agent:research` to no research Decision, while Intake, Triage, Design, Review, the Merge gate, retries and Request-changes runs carry on. While it's paused, the Weekly summary's Held says so, naming each Ticket and research Decision that waits ("Dispatch is paused (`max_in_flight` is 0): #14 (3 days) waits"). Set it back above `0` and Dispatch resumes straight away: a push to the default branch that changes `.fabrik/config.json` runs a Dispatch check. A Product repo set up before the caller workflow had a `push` trigger gets it by running Setup again; until then Dispatch resumes at the next Dispatch check, on the hourly tick at the latest.
- `caps` holds the attention budget: per-repo caps on what the Kit opens in front of the Operator. A cap can only be lowered: a value above its Kit default is a Kit config error that names the field and the default.
  - `caps.design_sessions` (default 2) caps how many Design sessions are open in the repo at once; set it to `1`, or to `0` to pause new Design sessions while those already open carry on. Raising it back starts waiting issues straight away, as the config push runs a Design queue check. See [Design session (async)](#design-session-async).
  - `caps.monitor_issues` (default 5) caps how many error issues the Monitor keeps open in the repo at once. Past it, new error groups are held, `fatal` ones first and then the most users affected, and filed on later ticks as slots free up; the newest open error issue's stats block says how many are held. Set it to `0` to pause new error filings. The red-main issue never counts toward it, and still files and closes at `0`.
  - `caps.maps` (default 1) caps how many Maps are open in the repo at once, counting every open `wayfinder:map` issue, whoever made it. Set it to `0` to stop new Maps; Maps already open carry on. See [Maps](#maps).
  - `caps.follow_up_issues` (default 5) caps how many issues the Kit has open that it opened for a Follow-up that is a fault (#885, ADR-0039). It counts the open issues the Fabrik App opened whose first line is the `<!-- fabrik:follow-up … -->` marker, whichever pull request each came from. When an agent PR merges, the Kit opens its faults only up to the room under the cap, and each fault over it stays an Open as issue link in the Kit's comment on the merged PR. Closing such an issue, or its fix merging, frees its slot for the next merge. Set it to `0` to open none, so every fault stays a link. See **Faults open as issues** under [Merge gate](#merge-gate).
  - `caps.merge_gate` (default 3) caps how many agent PRs wait on you at the [Merge gate](#merge-gate), counting the Ticket work on its way there (ADR-0023): Dispatch releases a Ticket only if its PR could fit, so the open agent PRs out of draft plus the open agent draft PRs, Implement runs for a Ticket with no PR yet and Tickets dispatched or held never pass it. A Retry or Request-changes run counts once, by its draft. Research runs and research Decisions never reach the gate, so they count for neither and still release while it holds Tickets; retries, Request-changes runs, Reviews and Digests carry on. A Request changes frees nothing, as its PR moves from the gate back to work on its way; a merge or a close frees a slot and runs a Dispatch check. Set it to `0` to release no Ticket while any agent PR is at or on its way to the gate: unlike the other caps, `0` is no pause, as a Ticket still goes when nothing is at or on its way, one at a time, so it holds Dispatch as `1` does. While it holds, Dispatch's step summary names the cap, the PRs at the gate and the work on its way ("caps.merge_gate is 3 and #21, #22 are at the Merge gate and #23 is on its way, so #14 and #15 wait"), naming `max_in_flight` too when both hold. A check's fix, a `ready-for-agent` Ticket carrying `fabrik:flaky-check` and so a Check's issue Triage routed or a Ticket of the Spec a Design session wrote from one (ADR-0037), passes the cap at any value, `0` included, and goes ahead of every other Ticket and research Decision (ADR-0035): the agent PRs its red check holds are what fill the gate, and only the fix can clear them. `max_in_flight` and every other test still hold it, and once released its work counts toward the Gate load, which can then stand over the cap until the Tickets behind it fit. A Ticket the gate holds names each fix Dispatch would release now ("#50 fixes a red check and goes first") and each already under way, dispatched, running, held or with an open PR ("#50 fixes a red check and is under way"), in Dispatch's step summary, its Standing and the Weekly summary. A fix that is going nowhere yet, as one a Blocker holds or whose last run failed, isn't named, nor is the Spec written from a Check's issue, which carries the label but has sub-issues, so it is never released.
- `monitor` says what the Monitor watches. It files issues with the `fabrik:monitor` label and no state label, so Intake gives them `needs-triage`, except its Sentry token issue, which is `ready-for-human`. It never reopens them, and its only comments are the notes it closes its red-main issue, each Main check's issue and its Sentry token issue with. An invalid `monitor` block is a Kit config error like any other. Each source it can't read yet, for a setup step not done, is a quiet note in the hourly tick's step summary, never a failed run.
  - `monitor.errors` is where it reads production errors. `null`, the default, leaves them off. To turn them on, set it to `{ "provider": "sentry", "org": "<org slug>", "project": "<project slug>" }`, then run Setup again: while 1Password lacks the Sentry token, it walks the wizard's Sentry stage to store it. `provider` takes only `sentry`, and `org` and `project` are the slugs in the project's Sentry URL. Once the Monitor has filed an issue for a Sentry group, a token Sentry rejects (with a `::warning`) or a `Sentry token` item that goes missing gets one "Rotate the Sentry token" issue, `ready-for-human` and assigned to the Operator, which the Monitor closes itself on the first tick that reads Sentry again. `url` (default `https://sentry.io`) points it at another Sentry region or a Sentry-compatible host such as GlitchTip, and must be `https://`, since the token is sent there. `min_events` (default 3) is how many events in 24 hours an unresolved `error` group needs before it's filed; a `fatal` group needs none. Each qualifying group gets one issue, whose stats block the Monitor rewrites in place while it's open. A group that comes back after its issue was closed as completed gets a new issue, "Regressed from #n"; one closed as not planned or as a duplicate, or labelled `wontfix`, is never filed again. The issue quotes only Sentry's title, culprit, counts, release and in-app frames (file, line and function), never request data, breadcrumbs, user context, tags or variables.
  - `monitor.red_main` (default `true`) has the Monitor file one issue while the default branch's newest decided commit is red, and close it itself, with a "green at" note, once the newest decided commit is green. Set it to `false` to turn it off. It needs the Fabrik App's Checks: read, and at least one of the checks it reads running on pushes to the default branch: the Required checks `sandbox.checks` lists when it lists any, else every check but those of Fabrik's own `loop` and `tick` jobs. A commit is decided once the checks it reads have all finished and one failed or timed out (red), or none did and one passed (green); cancelled, skipped and neutral results decide nothing. This is the Monitor's own question, whether the default branch is healthy, not the Review's: a pull request's skipped or neutral Required check has passed. A red-main issue the Operator closes stays closed until the default branch is seen green.
  - `monitor.main_checks` (default `[]`) names the Main checks: checks the Monitor reads on the default branch that aren't Required checks, such as a deploy and the smoke check after it, `["deploy", "smoke-check"]`. No pull request runs one, so none can be in `sandbox.checks`: a name in both is a Kit config error, and a name listed twice counts once. Each Main check is red or green by itself, at the newest commit where its newest run finished with a failure or a time-out (red) or a success (green), whatever any other check did there, and gets an issue of its own, "Red main: `deploy` is failing on the default branch", which the Monitor keeps current while it's red and closes itself, with a "green at" note, once it passes. The red-main issue never reads a Main check: when `sandbox.checks` lists none, red main reads every check but Fabrik's own and the Main checks. A Main check's issue closed as completed by anyone but the Monitor, as when its fix merges, stays closed until the check fails on a newer commit than the one it named, and the new issue says "Still failing after #n", since no pull request can test the fix; one closed as not planned or as a duplicate stays closed until the check is seen green. A Main check no commit read decides is a quiet line in the step summary. `monitor.red_main: false` turns Main checks off too, and a Main check's issue never counts toward `caps.monitor_issues`. See ADR-0025.
- `audit.day` is the UTC day of the week the Audit is due, `"monday"` to `"sunday"` (default `"sunday"`, so it's open by Monday's Weekly summary), or `null` to turn the Audit off in this repo. `roles.audit` sets the Auditor's model, effort and timeout like any role: by default the Reviewer's frontier model, Opus 5.5, at `medium` effort and 45 minutes. See [Audit](#audit).
- `retro.day` is the UTC day of the week the Retro is due, `"monday"` to `"sunday"` (default `"saturday"`, a day before the Audit's default, so the two frontier runs never share an hour and both are open by Monday's Weekly summary), or `null` to turn the Retro off in this repo. `retro` takes no other field. `roles.retro` sets the Retro's model, effort and timeout like any role: by default the Reviewer's frontier model, Opus 5.5, at `medium` effort and 45 minutes, within which its evidence job runs too. See [Retro](#retro).
- `roles.research` sets the Researcher's model, effort and timeout like any role: by default Opus 5.5, at `medium` effort and 30 minutes. See [Maps](#maps).
- `roles.digest` sets the Digest writer's model, effort and time limit. Left out, its model is the repo's own `roles.review`, whatever that is set to, its effort is the effort the repo's own `roles.review` sets, or `medium` when it sets none (never the Review's `high` default), and its time limit is 10 minutes, so the block above names only its effort and time limit. `digest.enabled` (default `true`) is the Digest's switch: set it to `false` and a pass opens the Merge gate itself, with no Digest, and `agent:digest` is declined, with one line saying so. See [Digest](#digest).
- `subscriptions` lists the Subscriptions the Kit runs agents on, each the name of an item in the `Fabrik` 1Password vault that holds that Claude account's token, as `claude setup-token` gives it. The default is the one V1 item, `Claude token`. List one and rotation is off: every run uses it, as before. List two or more, such as `["Claude token", "Claude token 2"]`, and Subscription rotation is on. Setup lists the second one itself: when the Operator says yes to a second Subscription, in the run that installs the Kit or any later one, Setup walks the wizard's "A second Subscription" stage, which creates the `Claude token 2` item, and then lists it after the first, in the setup PR. Setup never adds to a list of two or more: it doesn't ask about a second Subscription then, `--second-subscription` has no effect but to say so, and the wizard's stage says to list a `Claude token 2` it stores there by hand. A list that names `Claude token 2` already, alone or not, has nothing for Setup to list, so it doesn't ask then either. With rotation on:
  - **The order is the Operator's, and the Kit fails over, never balances.** Every run starts on the first listed Subscription with no open weekly-limit, usage-credits or token-rotation issue, so the second is used only while the first is used up. Each run's Kit job step summary names the Subscription it gave the run, and its Run record names it too. A Kit job whose plan does nothing, as for an event the Loop declines, says why in its step summary instead.
  - A run refused on its Subscription's weekly limit opens that Subscription's own weekly-limit issue quietly and is re-run on the next free one, with no comment on its Ticket. Once every Subscription is used up, the issue that sees it @-mentions the Operator once, naming the first reset. Until then each run due is held, not started: its trigger label comes off, the weekly-limit issue names it, and its own issue or PR gets one quiet held line, mentioning nobody, that says what it's held on and until when. That line is edited, never deleted, when the run resumes or is dropped, and nothing reads it: deleting it changes nothing. An Auditor or Retro run, which has no trigger label, is never held: its Audit or Retro fails, and a later tick opens the next one. At the reset the scheduled tick closes that Subscription's issue and resumes the held runs itself, in the order they were held, under `max_in_flight` and `caps.design_sessions` as usual; one whose issue or PR has closed or moved on is dropped. There is nothing to re-add. A Subscription freed any other way resumes them too, ahead of any newer Ticket: closing its usage-credits or token-rotation issue resumes them straight away, as does listing another Subscription, and the next hourly tick catches anything else. Closing a weekly-limit issue yourself says its Subscription works again, so the runs held on it resume straight away too. Should that fail partway, the hourly tick, which reads the issues closed in the last week as well, deals with whatever it left, each run once. When the Kit doesn't know when a limit resets, the issue says so and asks you to close it once agent runs work again.
  - **Every Subscription used up, whatever the mix, holds runs.** With every Subscription blocked by any mix of weekly-limit, usage-credits and token-rotation issues, each run due is held, not started, so nothing is spent, and a run killed for usage credits or refused on a dead token is held too. Its held marker goes on the weekly-limit issue when one is open; otherwise, quietly, on the usage-credits or token-rotation issue already naming held runs, else the most recently opened, in its body when the held run's own failure opened it. Such an issue has no reset: the held runs resume once you close an issue that frees a Subscription. A run held there stays there if a weekly-limit issue opens later, and runs still resume in the order they were held. The issue a held run would go on, the Carrier, also notes the week's Audit or Retro, once, while it waits on a free Subscription, with rotation on or off: one quiet line and a hidden waiting marker, which the Weekly summary reads.
  - **Usage credits must be off on every listed Subscription.** With rotation on, a run whose stream shows usage credits being spent is killed, and that Subscription gets a "Turn off usage credits" issue, labelled `fabrik:usage-credits` and assigned to the Operator. The killed run is re-run on the next free Subscription, or held while none is free, and the Kit skips that one until the Operator closes the issue.
  - **A dead token makes its Subscription used up too.** A run whose token is refused (`authentication_failed`), as when a `claude setup-token` token expires, opens that Subscription's own "Rotate the Claude token of the `<name>` Subscription" issue, labelled `fabrik:token-rotation` and assigned to the Operator, and is re-run on the next free Subscription with no comment on its Ticket. The Kit skips that Subscription until the Operator stores a new token and closes the issue. With no other Subscription free, the run is held, as above. A rotation issue that names no Subscription, as one opened before this did, is read as the first listed one's.
  - The Weekly summary reports usage per Subscription: one line each, with its cost and its last weekly-limit reading. With a repo opted in to Fable (`allow_fable`, ADR-0034), a Subscription's line, or the one line with one Subscription, also says when its Fable cap resets while a Run record shows it reached, and the Metrics table counts the week's Fable fallbacks against last week's, apart from Infrastructure failures: every Run record with `fallback` `fable-cap`, one that ended in an Infrastructure failure included. The Fable cap's own refusals ran on Fable, so they are never fallbacks.
  - The list must be non-empty, and each name a non-empty string listed once; anything else is a Kit config error naming the field.
  - The wizard stores only `Claude token` and `Claude token 2`. A Subscription listed under any other name, such as a third, or one listed alone in place of `Claude token`, is the Operator's to store by hand: its account's `claude setup-token`, as an API Credential of that name, with its expiry date, in the `Fabrik` vault. Setup's plan names each one the vault lacks.
- `ui` turns on **Visual evidence**: screenshots of a UI pull request's pages, for the Operator and the Reviewer. It also lets a Design session offer a [Prototype](#prototypes), which a prototype turn builds with `sandbox.build`, serves with `ui.serve` and captures under `ui.url`. `null`, the default, leaves both off: nothing is captured, no Design session offers a Prototype, and each Implement run's Kit job step summary says so in one quiet line. To turn it on, or change its answers, the Operator runs `/fabrik-visual-evidence` in a Claude session in the repo. It first asks where pull requests' UI evidence comes from, captured routes or [Evidence shots](#evidence-shots), suggesting Evidence shots when the repo has Journeys run by one of `sandbox.checks`. For Evidence shots it asks which of `sandbox.checks` runs the Journeys and the artifact's name, offering the default, and tells the Operator that the Product repo's side must exist first: the helper, shots in its Journeys, and an upload step that runs whether the Journeys passed or failed, a workflow change that is the Operator's own to make. It suggests each answer from the repo for the Operator to confirm or correct, then writes them with the Kit's writer program, from the release the repo pins, and opens a PR with the change for the Operator to merge. The writer checks the answers against these rules first, and writes nothing when any would be refused, naming each problem. It writes only the `ui` and `preview` blocks, printed as Prettier prints JSON with its default 80 columns (a Product with another Prettier width runs its own `prettier --write .fabrik/config.json` in the PR, as above), and keeps every other byte of `.fabrik/config.json`. A field the answers leave out keeps its value, and a field is taken out only once the Operator confirms it, named in the answers' `remove`: `default_routes`, `before_url` and `resolve_route` when UI evidence moves to Evidence shots, each named before it goes, and `shots` when it goes back to captured routes. Running it again with the same answers writes nothing. The block:
  - `paths` (required, at least one): globs of the files whose change makes a pull request UI, such as `src/pages/**`, read as Node's path globs. Whether a PR is UI is the push job's call, never an agent's: from the run's changes against these globs, or, on a retry, from the evidence marker the Fabrik App already wrote in the PR's body. A PR that isn't UI gets no evidence section, and its Reviewer no screenshots or extra text.
  - `serve` (required): the command run in the background, after `sandbox.build`, to serve the branch, such as `npm run preview`. `url` (required): the local `http://` or `https://` base URL it serves on, such as `http://localhost:4321`, which capture waits up to 3 minutes to answer, and captures routes under. Something already answering on its port, such as a server the agent left running, is stopped first, so a stale server is never captured.
  - `before_url` (default `null`): the production site's base URL, which Before screenshots of the same routes are taken from. Without it Before is skipped.
  - `default_routes` (default `[]`): the routes captured when neither the Ticket nor the Implementer names one, each a path starting with one `/`.
  - **Pages behind a sign-in** (ADR-0012): three fields, all absent by default, which come together; a `ui` block that sets none captures as above. `sign_in` maps each Capture identity, a named kind of fake user such as `owner`, to the command that signs it in, such as `{ "owner": "pnpm sign-in owner" }`: at least one, each name letters, digits, `-` and `_`, and no command blank. `sign_in_path` is the route the app sends a signed-out visitor to, such as `/sign-in`. `signed_in_routes` is an ordered, non-empty list of rules such as `{ "route": "/console/**", "as": "operator" }`, saying which Capture identity views a route: the first rule whose `route` matches the route's path wins, its query left out, so a Prototype's `?variant=a` changes nothing; `as: null`, or no rule matching, views it signed out. In a rule's `route`, `*` matches within one path segment and `**` across segments, and `/**` matches `/` too. Every `as` must be `null` or one of `sign_in`'s identities, and Kit config is refused when `sign_in_path` or `signed_in_routes` is set without `sign_in`, or `sign_in` is set and `url`'s host isn't loopback (`localhost`, a name under `.localhost`, `127.0.0.1` or `[::1]`): a sign-in only ever reaches the Sandbox's own server, with fake users. Once `ui.serve` answers, and before any screenshot, capture runs the sign-in command of each Capture identity its routes need, once each, and none for a capture of public routes alone, Implement and prototype capture alike. Each runs in the Product directory with the env `ui.serve` gets, never `sandbox.secrets`, plus `FABRIK_STORAGE_STATE`: a temp file, outside the evidence folder so it's never uploaded, to write a Playwright storage state to, a JSON object with `cookies` and `origins` lists, which a Product can write by hand without Playwright. Each signed-in route's screenshots, and a prototype turn's takes, load that identity's state at both viewports; every public shot, and every Before, loads none. So a signed-in route has no Before: `before_url` is a deployed site, which these sessions can't reach and must not. The evidence section, both Evidence pages and the Reviewer's prompt name the Capture identity on each signed-in shot. A command that fails, runs past 3 minutes, or leaves no state that reads stops capture as `sign-in-failed` before any screenshot; so does a signed-in shot whose page ends on `sign_in_path`, whose image is thrown away, the shots before it kept. A public shot is never checked, so a public route can show the sign-in page. An app that shows its sign-in form without redirecting to `sign_in_path`, or keeps its session in sessionStorage or memory, isn't caught.
  - **Routes with a dynamic segment** (ADR-0024): a route with a segment such as `[patientId]`, `<patientId>` or `:patientId` stands for a record no page answers as written, so capture never visits it as written. `resolve_route` (default unset) is one command that turns such a route into a concrete path, such as `pnpm resolve-route`, and Kit config refuses it when it's blank or `url`'s host isn't loopback, as with `sign_in`. Once `ui.serve` answers and the capture's sign-ins are done, capture runs it once for each named route with a dynamic segment, never per viewport, for up to 2 minutes within capture's budget. It runs in the Product directory with the env `ui.serve` gets, never `sandbox.secrets`, plus `FABRIK_ROUTE`, the route as named, and, when `signed_in_routes` views the route as a Capture identity, that identity's storage state in `FABRIK_STORAGE_STATE`. It prints the path to capture on stdout, and capture reads the last line it prints, so a package manager's banner above it is no matter. The Capture identity is still the route's, by its pattern. Each capture of it records both the route and the `resolved` path it was captured at, and the evidence section, the Evidence page and the Reviewer's prompt show the route beside that path. A resolved route has no Before, even viewed signed out: the record it found is on the Sandbox's server, not on `before_url`'s site. A route with a dynamic segment that isn't resolved is never visited: with no `resolve_route`, or when its command exits non-zero, runs past its 2 minutes, prints no path, or prints one that still has a dynamic segment, each of its After shots is missed as `unresolved-route`, and its route's line says why.
  - **UI evidence from [Evidence shots](#evidence-shots)**: `shots` (default unset) says a UI pull request's UI evidence comes from the Evidence shots a Required check uploads, not from captured routes, such as `{ "check": "e2e", "artifact": "fabrik-evidence-shots" }`. `check` (required in the block) names the check, and must be one of `sandbox.checks` and a job of a GitHub Actions workflow, named as the check is: the Kit finds the check's run and its artifact through Actions alone, so a check another app reports has no artifact the Kit can find, and reads as `no-artifact`. `artifact` (default `fabrik-evidence-shots`) names the artifact its run uploads them in. Each is non-empty text on one line, and a field the block doesn't have is a Kit config error naming it. With `shots` set, the Implement job captures no routes: no browser is installed and nothing is built or served for capture, and each Implement run's Kit job step summary says in one quiet line which check UI evidence comes from. `default_routes`, `before_url` and `resolve_route` are only route capture's, so Kit config refuses each beside `shots`, naming it, even set to `null` or `[]`. `paths` still says which pull requests are UI, and `serve`, `url` and the sign-in fields stay, because a prototype turn still captures its variants with them. A `ui` block with no `shots` captures routes as above.
  - **Capture**: once the Implementer's agent has ended well, on first, retry and Request-changes runs alike, the Implement job diffs the branch against the default branch, and when it touches a file matching `ui.paths` in that commit's Kit config, never the branch's own, it installs Chromium, runs `sandbox.build`, starts `ui.serve`, and screenshots each route, a PNG one screen high from the top of the page, at mobile (390 by 844) then desktop (1440 by 900): After from the branch, then Before. Build and server get `sandbox.env`, but never `sandbox.secrets`, the Claude token or a GitHub token. No model turn is used. Capture has its own 20-minute timeout, and the Implement job's timeout is the Implement role's plus those 20 plus 10 minutes, while the agent still stops at the role's own, so capture never cancels the job.
  - **The routes**: every route the Ticket names, as the path alone in backticks such as `` `/book` `` (outside a fenced code block), then the ones the Implementer names in its output, or `default_routes` when neither names one. Each is captured once, and the list stops at 4, though every route the Ticket names is captured even past that.
  - **The evidence section**: a UI PR's body gets one, between the summary and `Closes #n`, ending in a hidden `<!-- fabrik:ui-evidence {"run":…,"artifact":…,"failure":…,"routes":[…],"preview":{"is":…,"url":…},"missed":[…],"resolved":[…]} -->` marker, which records the Implement run that holds its screenshots and why its capture failed (`null` when it captured); `routes`, the routes the section lists under "Captured routes" in its order (the Ticket's, then the Implementer's, then the defaults, a route missed outright among them; empty when capture had none); and `preview`, what came of the preview deployment: `none` when Kit config declares no `preview.url`, `pending` until the preview step has polled it, then `linked` or `never-answered` with the `url` it polled, which the step writes in the edit that rewrites the preview's line. `linked` says the branch's address answered within the poll, not that the PR's head is what answers; and `missed`, each shot capture meant to take and missed while going on to the rest, by its `route`, `viewport` and `side` alone (why it missed, the address tried and the browser's error stay in the artifact), empty when it missed none, and left out when the push job had no capture result to read; and `resolved`, each route with a dynamic segment `resolve_route` resolved, as its `route` and the `path` it was captured at, left out when none was. So a reader can still build a link to each route, and name each missed shot, once GitHub has deleted the screenshots. The marker's JSON spells `<`, `>` and `@` as escapes, so a route can neither end the comment nor mention anyone; a marker from an earlier release has no `routes`, `preview`, `missed` or `resolved`, and reads as it did, with them unknown. It links the Evidence page, one self-contained HTML page of every screenshot, Before and After side by side, kept as an unzipped Actions artifact so it opens in one click; it and the zipped screenshots are kept 30 days. It lists each captured route with why it was chosen, flags any that answered with a server error, links the preview deployment or says why there's none, and, when capture failed, says why: `build-failed`, `server-did-not-start`, `timeout`, `no-routes`, `sign-in-failed`, `unreachable` when no page it went to would load, `error`, or `no-result` when the push job got no capture result it could read. A failed capture keeps the screenshots it took first. A page that won't load, as when production is down or refuses the headless browser, is one screenshot missed, not capture's end: capture goes on to the rest, and the route's line says what of it was captured and what wasn't and why, such as `Before: unreachable, ERR_CONNECTION_REFUSED, at mobile and desktop`. An After whose page answers 4xx or 5xx is missed the same way, with its status and no screenshot kept, such as `After: answered 404, at mobile and desktop`, while a Before's error page is kept, since a route the PR adds is expected to 404 on production. A capture whose every shot was missed, for any of these reasons, fails as `unreachable`. Route capture never blocks the PR, uses a retry or counts as an Infrastructure failure. An Evidence miss on a Product repo that uses [Evidence shots](#evidence-shots) does send the PR back and use a Retry (ADR-0033), and still counts as no Infrastructure failure. Every retry and Request-changes run captures again and replaces the section, so it matches the PR's head.
  - **The Reviewer** gets at most 8 of the screenshots in its working directory: After before Before, mobile before desktop, then the Ticket's routes, the Implementer's and the defaults, so with 4 routes all 8 are After. Its prompt names each one's route, viewport and side, and asks whether they show what the Ticket asked for, whether there's plain breakage, and whether a part the Ticket didn't touch regressed against Before. Taste stays the Operator's, and a visual failure is an Execution flaw naming the route and the screenshot. When the PR's head has moved on since capture, as after the Operator's own push or a Retry's rebase, the prompt says the screenshots were captured at that earlier commit, so later commits may change what they show. When capture failed, the prompt says why, from the marker when there are no screenshots to read, and the Reviewer reviews the code as usual. When a side's page wouldn't load for some routes, the prompt says that side is missing for those routes, and why, rather than that capture failed.
  - To ask for a visual change, use Request changes and cite a screenshot: no reaction is a trigger (ADR-0007).
- `preview.url` (default `null`) is where a UI PR's preview deployment appears, as a template that may use only `{pr}`, the PR's number, `{sha}`, its full head commit as the push left it, and `{branch_slug}`, its branch in lower case with each run of characters other than `a` to `z` and `0` to `9` made one `-`, and no `-` at either end (so `fabrik/ticket-12` is `fabrik-ticket-12`; the Kit never shortens it, though a host may). It must fill in to an `http://` or `https://` URL. Once it has pushed a UI PR, the push job polls that URL for 4 minutes at most, in a step with its own timeout that never fails the job, and links it in the evidence section once it answers with a 2xx page, redirects followed, or says it never answered. For a prototype round it fills the template in for `prototype/<issue>` and the head it pushed, polls the approved route's page on it the same way, and once it answers links it beside each variant with `?variant=` and the variant's letter, or says in the round it never answered. A template that uses `{pr}` has nothing to fill in for a Prototype, so its round says there's no preview for prototypes. The Kit never calls a hosting provider's API and needs no new secret. `null`, or a `preview` block of `null`, links no preview.
- `time_zone` (default `null`) is the Operator's time zone, an IANA zone such as `"Australia/Sydney"`, which every time the Kit shows the Operator is written in (ADR-0023): the weekly-limit issues and their notes, held lines and the Kit job's held-run summary, a failure comment's reset time, the Audit's and the Retro's due times, the Retro's window, the skills bump's summary, the Monitor's First seen and Last seen, and the Tick's note closing a Dead-tick issue. `null`, or leaving it out, writes them in UTC. Setup writes it from its time zone question, the same zone it writes into the `fabrik-runs` store's caller, which the Weekly summary and the daily Tick check read instead; a repo set up before it has none until Setup runs there again. Only the times shown change: `audit.day` and `retro.day` stay UTC days, due from 00:00 UTC, and the skills bump tick stays Monday's 04:00 UTC hour. A value that isn't an IANA zone the runtime knows fails nothing: the Kit writes its times in UTC, and each Loop run's step summary says so in one line naming the value.
- `production` (default `null`) says where the repo's production is, so that nothing ever guesses it (ADR-0021), such as `{ "url": "https://shop.example", "environment": "production" }`. `null`, or leaving it out, declares nothing. It changes nothing in the Loop, which still ends at the merge: no Loop rule, job or prompt reads it, and only a reader of the Kit, such as the Console through the [read library](#reading-the-kit-from-another-program), acts on it. Kit config is a Trust-root file, so no agent can change where a live link points. The block:
  - `url` (required): the production site's base address, an `http://` or `https://` URL, which live links are built from. It stays separate from `ui.before_url`: a repo with no `ui` block can declare production, and one can set `ui.before_url` to `null` while production stays declared. `preview.url` is untouched, and stays the only way a preview reaches the Kit.
  - `environment` (default `null`): the name the repo's production deploys carry in GitHub's Deployments, as non-empty text on one line. `null` is for a repo whose host reports none.
  - `workflow` (default `null`): the file name of the workflow the Operator dispatches to deploy production, such as `"deploy.yml"`: one file's name ending in `.yml` or `.yaml`, never a path. It is read only to build the address of that workflow's page under the repo's Actions, which the Promote list carries as its dispatch page in a repo that declares `staging`. Nothing in the Kit dispatches the workflow, and nothing checks that the repo has it.
  - A block with no `url`, a `url` that isn't `http://` or `https://`, a blank or many-line `environment`, a `workflow` that is blank, many lines, a path or not a `.yml` or `.yaml` file's name, or a field the block doesn't have, is a Kit config error naming the field. The Visual evidence writer never writes `production`, and keeps the block byte for byte.
  - **What each declaration gets**, from a reader of the Kit:

    | Declared | A reader of the Kit gets |
    |---|---|
    | No `production` | Nothing past the merge, even when `ui.before_url` is set. |
    | `production.url`, no `environment` | The merged pull request for 24 hours as merged, with links into production marked not tracked and no claim that a change is live. |
    | `production.url` and `environment` | A merged agent pull request followed to production for 24 hours after its merge, through GitHub's Deployments in that environment: Deploying while a deploy at the merge commit or later runs, Live once one succeeds, Deploy failed with its log, and No deploy seen when nothing started within an hour. A repo that also declares `staging` is followed there first, and what it gets at Production is in `staging`'s table, below. |

  - **Which hosts report Deployments by themselves:** Vercel does. Netlify, Cloudflare Workers Builds and Cloudflare Pages do not: they post check runs, commit statuses or a pull request comment instead. A repo on one that doesn't is tracked once it deploys from an Actions job that names an environment, since GitHub then creates the Deployment itself, whatever the host.
- `staging` (default `null`) says where the repo's staging environment is: the site every merge deploys to, where the Operator tries a merged change by hand before they deploy it to production, which is a Staging trial (ADR-0038), such as `{ "url": "https://staging.shop.example", "environment": "staging" }`. `null`, or leaving it out, declares none, and the repo reads exactly as it does without the block. Like `production`, it changes nothing in the Loop: no Loop rule, job or prompt reads it, nothing waits on staging, and only a reader of the Kit acts on it. Kit config is a Trust-root file, so no agent can change where a staging link points. The block:
  - `url` (required): the staging site's base address, an `http://` or `https://` URL, which staging links are built from.
  - `environment` (required): the name the repo's staging deploys carry in GitHub's Deployments, as non-empty text on one line. Unlike `production.environment` it can't be `null` or left out, since a staging link that can't say whether anything is deployed is no use. It can't be the environment `production.environment` names either: the Kit couldn't tell a deploy to staging from a deploy to production.
  - A block with no `url` or no `environment`, a `url` that isn't `http://` or `https://`, a blank or many-line `environment`, one that `production.environment` names too, or a field the block doesn't have, is a Kit config error naming the field.
  - **What each declaration gets**, from a reader of the Kit (see [Reading the Kit from another program](#reading-the-kit-from-another-program)):

    | Declared | A reader of the Kit gets |
    |---|---|
    | No `staging` | What `production` gets by itself, in its table above, and nothing of Staging. |
    | `staging`, and no `production.environment` | A merged agent pull request at Staging from its merge, through GitHub's Deployments in `staging.environment`: Merged, Deploying, Deploy failed or No deploy seen, then On staging once a deploy that contains it has succeeded and every Main check `monitor.main_checks` names is green on the deployed commit, with links to the staging site and what to try. One that needs a Staging trial is the Operator's move until they label it, then reads Accepted or Problem found for 24 hours; one that changes no screen stands for 24 hours from its merge. Nothing moves it to Production. The Promote list starts at the first successful staging Deployment. |
    | `staging` and `production.environment` | The same at Staging, until a production deployment that contains the pull request has started. It is then at Production, with production's names, for 24 hours from that Deployment, not from its merge. One that still needs a Staging trial and has no result stays longer, while that deployment runs and after it failed, until a production deployment that contains it has succeeded: production has not taken it until then. Merged and No deploy seen are only ever said at Staging. The Promote list starts at the newest successful production Deployment, or at the first successful staging one while production has none. |
    | `production.workflow` too | The Promote list's dispatch page: GitHub's page for dispatching that workflow. Nothing dispatches it, and without the field the list has no page. |

  - Setup asks for the block beside production's, and creates the two labels a Staging trial ends in, `fabrik:trial-accepted` and `fabrik:trial-problem`, which the Operator puts on the merged pull request they tried. A repo set up before them gets both by running Setup again.
- `operator` is the Operator's GitHub login: the one person whose comments drive a Design session, whom its rounds and failure notices @-mention, and to whom `ready-for-human` work is assigned. `null` means the repo's owner; set it for a repo an organization owns.
- Per-phase instructions are optional Markdown files: `.fabrik/triage.md`, `.fabrik/design.md`, `.fabrik/implement.md` and `.fabrik/review.md`, the Auditor's `.fabrik/audit.md`, the Retro's `.fabrik/retro.md`, the Researcher's `.fabrik/research.md` and the Digest writer's `.fabrik/digest.md`.
- `CODING_STANDARDS.md` at the repo root is optional too, though it isn't Kit config: it holds the repo's coding standards. The Reviewer judges every PR against it when it's there (see [Review](#review)), every Implement run is given it inline, and the Retro proposes Judgement lessons as lines for it. It's a Trust-root file, so only the Operator changes it, and the Kit ships no template for it.
- `roles.triage`, `roles.design`, `roles.implement` and `roles.review` each take an optional `skills` list of Extra skills (see [Extra skills](#extra-skills)). `roles.dispatch`, `roles.step_up`, `roles.audit`, `roles.retro`, `roles.research` and `roles.digest` don't: a Step-up run is an Implement run and gets implement's, and the Auditor, the Retro, the Researcher and the Digest writer get the Base skills alone (ADR-0008).

### Evidence shots

UI evidence can come from Evidence shots instead of captured routes (ADR-0032): a Journey, one of the Product repo's end-to-end tests, takes an Evidence shot at a moment it names, and the Required check that runs the Journeys uploads the shots with a manifest as an artifact. This is the contract a Product repo builds to. The helper, the shots and the upload step are the Product repo's own code: the Kit documents them here, and nothing the Kit versions runs inside a Product's tests.

- **The artifact** is named `fabrik-evidence-shots` by default (Kit config's `ui.shots.artifact` can name another), and holds `manifest.json` and the images at its root:

  ```
  fabrik-evidence-shots
    manifest.json
    composer-draft-ready.mobile.png
    composer-draft-ready.desktop.png
  ```

- **The manifest**, one entry per shot:

  ```json
  {
    "version": 1,
    "shots": [
      {
        "name": "composer: draft ready",
        "journey": "write-a-clinical-note",
        "path": "/patients/6f1b2c3d/notes/new",
        "images": {
          "mobile": "composer-draft-ready.mobile.png",
          "desktop": "composer-draft-ready.desktop.png"
        }
      }
    ]
  }
  ```

  `version` is `1`. `name` and `images` are required, with at least one of `mobile` and `desktop`. `journey` (the Journey's own name for itself) and `path` (where the page was at that moment) are optional and only shown. The name alone says which shot it is: free text as the Journey wrote it, one line, unique in the run, and always compared exactly, with no trimming and no folding of case.
- **The two sizes** are the Kit's: `mobile` is 390 by 844 and `desktop` is 1440 by 900, each image one screen high. The Kit takes the manifest's word for which size an image is and does not measure it. A shot with only one of its images still counts, with the other size listed as missing.
- **The upload step runs whether the Journeys passed or failed**, and keeps the artifact 30 days, as the Kit keeps a pull request's captures. A green check that uploaded no artifact is a failure of the wiring, the Operator's to fix. For example, after the step that runs the Journeys:

  ```yaml
  - name: Upload Evidence shots for Fabrik
    if: ${{ !cancelled() }}
    uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
    with:
      name: fabrik-evidence-shots
      path: evidence-shots/
      retention-days: 30
  ```

- **The artifact is untrusted**, since the pull request's own code writes it. The Kit reads `manifest.json` and the images the manifest lists, and nothing else in the artifact, and runs none of it. An entry that breaks one of these rules is dropped, with its reason kept, and the other shots are read:
  - An image's file name is flat: letters, digits, `.`, `_` and `-`, starting with a letter or digit, with no folder and no `..`, and ending `.png`. The file starts as a PNG does. An image is at most 1 MB (1,048,576 bytes). A listed image that isn't in the artifact is that size missing; an entry none of whose images is there is dropped.
  - A name is at most 80 characters on one line, of letters A to Z, digits, spaces and `: - _ / . ,` only. `journey` is held to the same rule, and `path` to the rule a route is held to: a path starting with one `/`.
  - At most 100 shots. Past that the manifest's first 100 are kept, and the rest are counted as dropped.
  - Two entries with one name make that name ambiguous: neither is shown under it. Other shots are unaffected.
  - A manifest that is missing, isn't JSON, has another `version` or has no `shots` list can't be read at all, and no shot of it is.
- **No Before.** A shot is of the pull request's head only.
- **A reference helper for Playwright**, to copy into the Product repo and change as it likes. It takes a page and a name, takes the shot at both sizes one screen high, puts the page's size back as it was, and adds the entry to the manifest. It reads and rewrites `manifest.json`, so run the Journeys that call it in one worker, or give each worker its own folder and join their manifests before the upload step. The Kit ships and runs none of it.

  ```ts
  // e2e/evidenceShot.ts: this Product's own helper, copied from the Fabrik README.
  import { mkdir, readFile, writeFile } from "node:fs/promises";
  import { join } from "node:path";
  import type { Page } from "@playwright/test";

  const FOLDER = "evidence-shots";
  const SIZES = { mobile: { width: 390, height: 844 }, desktop: { width: 1440, height: 900 } };

  /** Takes the Evidence shot `name` of `page` at both of Fabrik's sizes, and adds it to the manifest. */
  export async function evidenceShot(page: Page, name: string, options: { journey?: string } = {}): Promise<void> {
    await mkdir(FOLDER, { recursive: true });
    const manifestFile = join(FOLDER, "manifest.json");
    const manifest = await readFile(manifestFile, "utf8").then(JSON.parse, () => ({ version: 1, shots: [] }));
    const slug = name.toLowerCase().replace(/[^a-z0-9]+/g, "-").replace(/^-|-$/g, "");
    const stem = `${String(manifest.shots.length + 1).padStart(3, "0")}-${slug}`;
    const was = page.viewportSize();
    const images: Record<string, string> = {};
    try {
      for (const [size, viewport] of Object.entries(SIZES)) {
        await page.setViewportSize(viewport);
        images[size] = `${stem}.${size}.png`;
        await page.screenshot({ path: join(FOLDER, images[size]) });
      }
    } finally {
      if (was !== null) await page.setViewportSize(was);
    }
    const { pathname, search } = new URL(page.url());
    const path = pathname.startsWith("/") ? { path: `${pathname}${search}` } : {};
    manifest.shots.push({ name, ...options, ...path, images });
    await writeFile(manifestFile, `${JSON.stringify(manifest, null, 2)}\n`);
  }
  ```

  A Journey then marks its moment in one line, such as `await evidenceShot(page, "composer: draft ready", { journey: "write-a-clinical-note" });`.

- **The Implementer names the shots** that show its change (#819). On a Product repo with `ui.shots`, its prompt gains an "Evidence shots" part, and its output two optional fields: `shots`, a list of names, and `nothingVisible`, one sentence saying why nothing a person sees changes. It finds names by reading the Journeys, never names a shot that isn't in a Journey's code, adds a shot to the Journey that reaches a state with none (extending a Journey when none does), and runs that Journey when the Sandbox's test command includes it. A malformed field reads as not given, and with both given the names win. At most four names count, in the order given, each held to the name rule above: a fifth, and a name that breaks the rule, is dropped, and the section says so in one line. `routes`, and routes a Ticket names in backticks, are ignored. On a Product repo without `shots`, the prompt and the output contract are as they were.
- **The pull request keeps its names.** The latest Implementer run that says anything wins: names replace the PR's, `nothingVisible` clears them and keeps the sentence, and a run that gives neither keeps what the PR had. It holds for a first run, a Retry, a Touch-up, a Request-changes run and a conflict-only run alike. The names live in the evidence section's marker, read back only from a body the Fabrik App wrote: `<!-- fabrik:ui-evidence {"source":"shots","head":…,"run":…,"artifact":…,"failure":…,"routes":[],"named":[{"name":…,"journey":…,"path":…}],"nothingVisible":…,"dropped":{"pastFour":…,"broken":…},"miss":"nothing-named","missed":[…],"preview":{…},"implementRun":…,"pushed":…,"red":true,"pastLimit":…} -->`. A marker without `source` is a route marker and reads as before; `routes` is always empty, so a reader from an earlier release sees no captured route. `head`, `run` and `artifact` are `null` while the section waits for the named check, `implementRun` is the Implement run whose push job wrote the names and links the preview, `pushed` the head that run pushed, and the marker's JSON spells `<`, `>` and `@` as escapes, so the sentence can neither end the comment nor mention anyone. The section lists the names, or gives the sentence in the Implementer's words, quoted on one line, and says it is waiting for the named check.
- **Naming neither is an Evidence miss** (ADR-0033). When an Implementer run pushes a UI pull request left with no names and no sentence, and the Ticket has a Retry left, the push job gives the Kit's own Execution flaw at the head it pushed (`"source":"evidence-miss"`), in the same step in which it opens or updates the PR: its comment says the PR changes the UI and shows nothing of the change, and what to do. It calls for a Retry, never a Touch-up, and counts in the Ticket's one pool (see [Execution-flaw retries](#execution-flaw-retries)), and the Reviewer never judges that head. With no Retry left nothing is sent back: the section says plainly that nothing was named, the marker records `"miss":"nothing-named"`, and Review goes ahead. A body-only Touch-up pushes no head, so a miss on it is shown and never sent back. A PR that isn't UI gets no section and no miss, whatever its output says.
- **The Review's jobs collect the head's shots** (#820). Once the Required checks have been waited for, the review job finds the newest attempt of the check `ui.shots.check` names at the PR's current head, whatever commit the check checked out, and downloads the artifact `ui.shots.artifact` names from that attempt, through GitHub Actions with the token it already holds: no job gains a permission. It reads the artifact by the rules above against the PR's names, builds an Evidence page of every shot of the run at both sizes, the named ones first, each under its name with its Journey and path, and uploads it to the Review's own run, unzipped and kept 30 days. The Reviewer gets the named shots the run produced, at most 8 images, mobile before desktop, in the Implementer's order: its prompt names each image's shot and size, gives the `nothingVisible` sentence to check against the diff (a diff that plainly changes what a person sees is an Execution flaw), says each miss and failure in the Kit's own sentence, that the shots are from a run that failed when the check is red, and to review the code as usual when there are no pictures. Unnamed shots are the Evidence page's alone. A download of the artifact the check uploaded that fails is not `no-artifact`: the Reviewer doesn't run, as after a wait that gives up, and the section keeps waiting.
- **A named shot the check didn't produce is an Evidence miss** when the named check finished green, the head is one an Implementer run pushed (the marker's `pushed`), and the Ticket has a Retry left: a name the manifest lacks (`not-produced`), one two entries share (`ambiguous-name`), or one whose entry broke the artifact's rules (`refused`). Then the Reviewer doesn't run, and the push job gives the Kit's own Execution flaw at that head (`"source":"evidence-miss"`): its comment names each missed name with why and lists the names the run did produce. It calls for a Retry, never a Touch-up, and counts in the pool. Nothing is sent back, and the Review goes ahead with the section saying what was missed, when no Retry is left, at a head the Operator pushed or the Kit's plain rebase made, when the named check is still red after the Kit's re-run (the shots the artifact holds are shown, from a run that failed, and the Reviewer's judgment of the check decides the Retry), for a shot with one of its two images (`size-missing`, shown with the missing size listed), and for a failure of the whole collection, the Product's wiring, the Operator's to fix: `no-artifact`, when the check's newest attempt uploaded no artifact of that name, and `bad-manifest`. A PR whose Implementer said nothing visible changes has no miss. Nor does the Kit start a Reviewer at a head its Implement run's push sent back for naming nothing.
- **The section once read**: the push job writes the section and the marker either way, from what the Review's jobs read: the head the check ran at, the Review run and the Evidence page's artifact, each named shot with its Journey and path, `missed`, `failure`, `red`, and `pastLimit`, the shots dropped past the first 100. The section says which head the shots are from, by its commit, and links the Evidence page, lists each named shot or why it was missed, and says each failure and miss and what came of it at that commit, so it stays true when the Operator pushes at the Merge gate, where the Kit writes nothing. Until the Review's jobs have read the shots it keeps waiting: a wait that gives up, or a conflict, leaves it so, and a new head an Implementer run pushes, or the Kit's plain rebase, puts it back to waiting with the names kept.

### Extra skills

Every run gets the Base skills, which Fabrik's own `skills.lock.json` pins and which move only with a Kit release, plus Fabrik's own skills. A Product repo that needs more pins its own public **Skills sources** in `.fabrik/skills.lock.json` and gives **Extra skills** from them to roles in `.fabrik/config.json` (ADR-0008). A repo with neither runs exactly as before and pays nothing.

`.fabrik/skills.lock.json` is a list of pins, each a repository and a full 40-character lowercase commit SHA:

```json
[{ "repository": "jrey8343/skills", "sha": "0123456789abcdef0123456789abcdef01234567" }]
```

Each role's picks name the source, then the skill by the name it installs as under `.claude/skills/` (the last segment of its folder in the source's `.claude-plugin/plugin.json`):

```json
{
  "roles": {
    "design": { "skills": ["jrey8343/skills/event-storming"] },
    "review": { "skills": ["jrey8343/skills/event-storming"] },
    "implement": { "skills": ["jrey8343/skills/deciders"] }
  }
}
```

- Write a source's first pin and the picks by hand; Setup writes neither. After that, the Kit's scheduled tick checks each source's default branch on the Monday tick in the 04:00 UTC hour and opens, or refreshes, one PR per source on `fabrik/skills-bump/<owner>-<name>`, pushed with the Fabrik App token. It changes only that source's SHA, shows the upstream diff under the picked skills' folders, lists the other changes in one line, and flags a picked skill removed upstream as breaking. A week in which no picked skill changed opens nothing. The Loop ignores these PRs; only the Operator merges them.
- Each AFK run installs the Base skills plus only its own role's Extra skills, before any secret loads, and its prompt gets one Kit line naming them. A local, Pairing or live Design session's `SessionStart` hook installs every pick, and warns, still installing the Base and Kit skills, when a pick is wrong.
- Say when to use an Extra skill in that phase's instructions, `.fabrik/<phase>.md`, not in the Kit config. The Kit's line only says the skills are there and that this repo's instructions say when to use them.
- These are Kit config errors, which stop the Loop before any agent starts: a malformed lockfile or pick; the same repository pinned twice; a pick naming an unpinned source, or a skill its source's manifest doesn't list at the pin; a pinned source no role picks from; a source with no readable manifest; and a pick named like a Base skill, a Kit skill (one of Fabrik's own) or a pick from another source. The Kit job reads each source's manifest from public GitHub at its pin, only when the repo pins a source.
